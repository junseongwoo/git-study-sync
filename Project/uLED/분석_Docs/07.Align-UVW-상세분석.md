# Align 및 UVW 보정 상세 분석

## 1. 문서 목적

이 문서는 카메라와 설비 사이의 일반적인 Align 원리부터 현재 uLED Console에 구현된 자동 Align과 UVW 보정까지 연결해서 설명한다.

주요 목표는 다음과 같다.

- 통상적인 카메라 Align이 무엇을 측정하는지 이해한다.
- Align Mark 한 개로 알 수 있는 것과 알 수 없는 것을 구분한다.
- 이미지 Pixel 편차가 설비의 µm 편차로 변환되는 과정을 이해한다.
- uLED가 좌·우 두 Align Mark로 X/Y/Theta를 계산하는 원리를 이해한다.
- X/Y/Theta 보정값이 U/V/W 축 이동량으로 바뀌는 과정을 이해한다.
- 프로그램이 Align 성공과 실패를 어떤 조건으로 판단하는지 이해한다.
- Config, GlassSizeModel, Recipe가 각각 어떤 Align 값을 소유하는지 이해한다.
- 장비 개발자가 어떤 순서로 문서와 코드를 읽어야 하는지 파악한다.

분석 기준은 다음과 같다.

- 현재 저장소의 Docs와 실제 코드를 함께 확인한다.
- 문서와 코드가 다르면 현재 실행 코드를 우선한다.
- 실제 장비 설정과 현재 선택 Recipe를 두 번째 검증 자료로 사용한다.
- 확인되지 않은 장비 동작은 추론으로 단정하지 않는다.

> NOTE
>
> 이 문서에서 말하는 자동 Align은 검사 알고리즘 IP가 아니라 Console과 Control이 수행하는 설비 위치 보정이다.  
> Dot 검출, DenseMap, 표준맵 정합과는 목적과 좌표계가 다르다.

### 핵심 요약

- Align은 카메라로 제품 위치 오차를 측정하고 설비 축으로 보정하는 기능이다.
- uLED는 좌·우 두 마크를 사용해 X/Y/Theta를 구하고 UVW로 보정한다.
- 이 문서는 일반 원리와 현재 uLED 구현을 분리해서 설명한다.

## 2. 먼저 보는 전체 결론

uLED의 자동 Align은 다음 순서로 동작한다.

```text
검사 Run에서 Use Align 선택
        ↓
Recipe의 Align 기준 자세로 이동
        ↓
Left/Right Align Camera 동시 촬영
        ↓
각 카메라에서 기준 Template과 현재 Mark를 매칭
        ↓
Image Pixel 편차 계산
        ↓
카메라 보정값으로 Stage X/Y µm 편차로 변환
        ↓
GlassSizeModel의 좌·우 Mark 좌표로 Theta 계산
        ↓
Theta를 UVW 상대 이동으로 먼저 보정
        ↓
재촬영
        ↓
공통 X/Y 이동 오차 계산
        ↓
X/Y를 UVW 상대 이동으로 보정
        ↓
재촬영
        ↓
X/Y/Theta 잔차가 모두 허용 오차 이내인지 확인
        ↓
합격이면 Align 성공
불합격이면 MaxIteration까지 반복
```

핵심은 다음 세 문장으로 정리할 수 있다.

1. 한 개 Align Mark의 중심 이동으로는 기본적으로 X/Y만 알 수 있다.
2. uLED는 좌·우 두 Mark의 이동 차이로 Theta를 계산한다.
3. 계산 결과는 X/Y/Theta이지만 실제 설비에는 U/V/W 축 이동 명령을 보낸다.

> NOTE
>
> 현재 uLED Template Matching은 마크 중심 위치만 반환한다.  
> 마크 자체의 회전각을 직접 측정하지 않기 때문에 한 개 Mark만으로 X/Y/Theta 세 자유도를 모두 계산하지 않는다.

### 핵심 요약

- 측정 좌표는 Pixel이지만 최종 보정 좌표는 X/Y/Theta이다.
- 실제 구동 축은 StageU/StageV/StageW이다.
- Theta 보정 후 X/Y를 보정하는 `ThetaThenXY` 방식이다.

## 3. Align을 이해하기 위한 좌표계

### 3.1 이미지 좌표

카메라가 촬영한 영상의 Pixel 좌표이다.

```text
ImagePx = (px, py)
```

일반적으로 이미지 왼쪽 위가 원점이며 다음 방향을 사용한다.

```text
+px : 화면 오른쪽
+py : 화면 아래쪽
```

하지만 이미지 좌표 방향과 Stage 축 방향은 같다고 볼 수 없다.

- 카메라가 90도 회전 장착될 수 있다.
- 카메라 또는 렌즈 구성에 따라 좌우·상하가 반전될 수 있다.
- Stage +X 이동이 이미지에서는 -Y 이동으로 보일 수 있다.
- 좌·우 카메라가 서로 다른 방향으로 장착될 수 있다.

### 3.2 Stage 좌표

설비가 사용하는 물리 축 좌표이다.

uLED Align과 관련된 축은 크게 두 그룹이다.

```text
Align 기준 위치 이동:
StageX
InspectionUnit2Y
InspectionUnit1Y

Glass 보정:
StageU
StageV
StageW
```

### 3.3 Glass 좌표

Glass 중심을 기준으로 정의한 제품 좌표이다.

```text
Glass Position = (GlassXUm, GlassYUm)
```

GlassSizeModel에는 다음 값이 포함된다.

- Glass 폭과 높이
- PanelAngleDeg
- Left Align Mark Glass 좌표
- Right Align Mark Glass 좌표

### 3.4 X/Y/Theta 보정 좌표

카메라 측정 결과를 사람이 이해하기 쉬운 Glass 중심 기준의 세 자유도로 표현한 것이다.

```text
XytDelta = (XUm, YUm, ThetaDeg)
```

- XUm: Glass 중심의 X 병진 오차
- YUm: Glass 중심의 Y 병진 오차
- ThetaDeg: Glass 평면 회전 오차

### 3.5 UVW 축 좌표

실제 Glass를 보정하는 세 액추에이터의 이동량이다.

```text
UvwDelta = (U, V, W)
```

X/Y/Theta는 논리적인 Glass 움직임이고 U/V/W는 이를 만들기 위한 실제 축 움직임이다.

### 핵심 요약

- Pixel 좌표와 Stage 좌표는 방향이 같다고 가정하면 안 된다.
- Glass 좌표는 제품 기준, Stage 좌표는 설비 기준이다.
- X/Y/Theta는 원하는 Glass 움직임이고 U/V/W는 실제 Motor 명령이다.

## 4. 통상적인 카메라-설비 Align 구현

### 4.1 기준 상태를 먼저 만든다

Align은 현재 위치만 보고 판단하지 않는다. 정상 위치의 기준 상태가 먼저 필요하다.

통상적인 Teach 과정은 다음과 같다.

```text
Glass를 정상 위치에 배치
        ↓
Align Camera를 기준 위치로 이동
        ↓
Align Mark가 정상 위치에 보이도록 조정
        ↓
기준 이미지 저장
        ↓
기준 Mark 중심 또는 기준 Template 저장
```

이 기준 이미지가 이후 현재 이미지와 비교되는 기준이 된다.

### 4.2 카메라와 Stage 관계를 Calibration한다

이미지에서 Mark가 오른쪽으로 이동했다는 사실만으로 Stage를 어느 방향으로 움직여야 할지 결정할 수 없다.

따라서 다음과 같은 카메라-Stage 보정이 필요하다.

```text
Stage를 +X로 알려진 거리만큼 이동
        ↓
이미지에서 Mark가 이동한 방향과 Pixel 수 측정
        ↓
Stage +X의 Image 방향 벡터 계산

Stage를 +Y로 알려진 거리만큼 이동
        ↓
이미지에서 Mark가 이동한 방향과 Pixel 수 측정
        ↓
Stage +Y의 Image 방향 벡터 계산
```

이를 행렬로 표현하면 다음과 같다.

```text
[Stage ΔX]   [c11 c12] [Image Δpx]
[Stage ΔY] = [c21 c22] [Image Δpy]
```

이 행렬에는 다음 정보가 포함된다.

- 카메라 장착 회전
- 카메라 좌우·상하 반전
- X/Y 방향 배율
- Pixel당 실제 µm

### 4.3 운전 중 오차를 측정한다

기준 중심과 현재 중심의 차이를 구한다.

```text
ReferenceCenter = (rx, ry)
CurrentCenter   = (cx, cy)

ImageDelta:
Δpx = cx - rx
Δpy = cy - ry
```

그 후 카메라 Calibration을 적용해 Stage 좌표의 물리 이동량으로 바꾼다.

### 4.4 보정 후 다시 확인한다

Align은 계산한 값을 한 번 이동시키는 것으로 끝내지 않는다.

```text
오차 측정
    ↓
보정 이동
    ↓
재촬영
    ↓
잔차 측정
    ↓
허용 오차 이내인지 판정
```

이를 Closed-loop Align이라고 볼 수 있다.

### 핵심 요약

- Align은 기준 이미지와 현재 이미지를 비교한다.
- Pixel 이동을 Stage 이동으로 바꾸려면 카메라-Stage Calibration이 필수다.
- 보정 후 반드시 재촬영하여 남은 오차를 확인해야 한다.

## 5. 하나의 Align Mark로 알 수 있는 것

### 5.1 하나의 Mark 중심은 두 개의 값을 제공한다

한 개 Mark 중심에서 얻는 측정값은 다음 두 개이다.

```text
MarkCenter = (X, Y)
```

하지만 평면 위 Glass의 위치 오차는 세 개이다.

```text
X 이동
Y 이동
Theta 회전
```

따라서 Mark 중심 하나만으로는 일반적으로 세 값을 모두 독립적으로 계산할 수 없다.

### 5.2 한 개 Mark로 X/Y를 계산하는 조건

다음 조건 중 하나가 필요하다.

- Theta가 0이라고 가정한다.
- Theta가 다른 센서나 기구에서 이미 결정됐다.
- Mark 모양의 방향을 별도 알고리즘으로 직접 측정한다.

uLED의 현재 Template Matching 결과는 다음 값만 가진다.

- 기준 중심
- 현재 중심
- Match Score
- Match Rect

마크 자체의 회전각은 반환하지 않는다.

### 5.3 왜 두 개 Mark가 필요한가

두 Mark가 단순히 같은 X/Y 방향으로 이동하면 Glass가 병진한 것으로 볼 수 있다.

```text
Left  Mark: (+10, +5)
Right Mark: (+10, +5)

→ 두 Mark가 거의 동일하게 이동
→ 공통 X/Y 이동 가능성이 큼
```

반면 Glass가 회전하면 두 Mark는 기준 위치에 따라 서로 다른 방향으로 움직인다.

```text
Left  Mark: (-8, +2)
Right Mark: (+8, +2)

→ 좌·우 차이가 존재
→ 회전 성분 포함
```

uLED는 이 상대 이동 차이를 이용해 Theta를 계산한다.

### 핵심 요약

- 한 점의 중심은 X/Y 두 개 측정값만 제공한다.
- uLED는 Mark 방향을 직접 측정하지 않는다.
- 따라서 자동 Align의 Theta 계산에는 좌·우 두 Mark가 필요하다.

## 6. uLED Align 설정의 책임 분리

### 6.1 Config가 소유하는 값

Config는 장비 고정값을 소유한다.

```text
Config
├─ AlignY1CameraName
├─ AlignY2CameraName
├─ AlignCameras
│  ├─ PixelSizeXUm
│  ├─ PixelSizeYUm
│  ├─ StagePlusXImageUnitX/Y
│  └─ StagePlusY1ImageUnitX/Y
└─ UvwCoordinateSystem
   ├─ PositiveThetaDirection
   ├─ GlassPlacement
   ├─ UvwGeometry
   └─ UseAutoCalculation
```

현재 장비 설정에서 카메라 연결은 다음과 같다.

| 논리 위치 | Camera | 장비 모듈 |
|---|---|---|
| Left Align | CAM2 | Y2 |
| Right Align | CAM1 | Y1 |

현재 카메라 Calibration 값은 대략 다음과 같다.

| Camera | PixelSizeX | PixelSizeY |
|---|---:|---:|
| CAM1 | 5.3244 µm/px | 5.3229 µm/px |
| CAM2 | 5.3307 µm/px | 5.3449 µm/px |

> NOTE
>
> 이 값은 일반적인 예시값이 아니라 분석 시점의 로컬 `config.yaml`에서 확인한 값이다.

### 6.2 GlassSizeModel이 소유하는 값

GlassSizeModel은 제품 기하를 소유한다.

```text
GlassSizeModel
├─ GlassWidthUm
├─ GlassHeightUm
├─ PanelAngleDeg
└─ AlignMarks
   ├─ LeftAlignUm
   └─ RightAlignUm
```

현재 선택 모델의 값은 다음과 같다.

```text
GlassSizeId   = 370x470_1.33_Model
GlassWidth    = 370000 µm
GlassHeight   = 470000 µm
PanelAngleDeg = 270°

Left Mark  = ( 170000, -220000) µm
Right Mark = (-170000, -220000) µm
```

마크의 Glass 좌표는 GlassSizeModel이 정본이다.

### 6.3 Recipe가 소유하는 값

Recipe는 운전 조건과 기준 이미지를 소유한다.

```text
ConsoleRecipeDocument
├─ AlignPlan
│  ├─ Enabled
│  ├─ CorrectionMode
│  ├─ MaxIteration
│  ├─ ToleranceXUm
│  ├─ ToleranceYUm
│  ├─ ToleranceThetaDeg
│  ├─ Left/RightMatchThreshold
│  ├─ Left/RightTemplateRect
│  └─ Left/RightSearchAreaRect
└─ ControlPlan
   ├─ AlignReferenceStageX
   ├─ AlignReferenceLeftUnitY
   ├─ AlignReferenceRightUnitY
   ├─ AlignReferenceStageU
   ├─ AlignReferenceStageV
   └─ AlignReferenceStageW
```

기준 이미지는 Recipe 폴더의 다음 고정 파일명을 사용한다.

```text
align_left.png
align_right.png
```

`AlignPlan.LeftImageFileName`, `RightImageFileName` 필드는 존재하지만 현재 실제 로딩 코드는 고정 파일명만 사용한다.

### 6.4 Test Runner와 검사 Run

Test Runner 또는 검사 Run에서 `Use Align`이 선택되면 검사 시작 전에 자동 Align을 실행한다.

```text
Test Runner UseAlign
        ↓
GlassInspectionRunOptions.UseAlign
        ↓
MainWindowViewModel
        ↓
RunAlignBeforeInspectionOnUiThreadAsync
        ↓
AlignWindow
        ↓
RunThetaThenXyAlignForInspectionAsync
```

Recipe의 `AlignPlan.Enabled`는 기본 Run 옵션을 만드는 데 사용되지만, 실제 실행 여부는 최종 `UseAlign` 옵션으로 결정된다.

### 핵심 요약

- Config는 카메라와 UVW 장비 기하를 소유한다.
- GlassSizeModel은 Glass 크기, 각도, Align Mark 좌표를 소유한다.
- Recipe는 기준 이미지, 검색 영역, 허용치, 기준 자세를 소유한다.
- 실제 검사 전 Align 실행 여부는 Run의 `UseAlign` 옵션이 결정한다.

## 7. uLED의 Align Mark 검출

### 7.1 기준 이미지와 Template

좌·우 카메라마다 별도 기준 이미지를 사용한다.

```text
Left  Camera → align_left.png
Right Camera → align_right.png
```

각 기준 이미지에는 두 개 사각형이 존재한다.

- TemplateRect: 기준 마크 모양을 잘라내는 영역
- SearchAreaRect: 현재 영상에서 마크를 찾는 범위

### 7.2 실제 Template Matching 순서

```text
현재 이미지 확인
        ↓
기준 이미지 확인
        ↓
두 이미지를 Gray로 변환
        ↓
기준 이미지의 TemplateRect를 Template으로 생성
        ↓
기준 이미지의 SearchArea에서 기준 중심 계산
        ↓
현재 이미지의 SearchArea에서 현재 중심 계산
        ↓
TM_CCOEFF_NORMED Score 계산
        ↓
최대 Score 위치 선택
        ↓
포물선 보간으로 Sub-pixel 위치 계산
        ↓
Score와 MatchThreshold 비교
```

OpenCV 호출은 다음 방식이다.

```text
MatchTemplate Mode = CCoeffNormed
Result              = 가장 높은 Score 위치
Sub-pixel           = 최대점 주변 3개 값을 포물선 보간
```

### 7.3 현재 Recipe의 검색 범위

| 항목 | Left | Right |
|---|---|---|
| Match Threshold | 0.8 | 0.8 |
| Template Rect | `(560,448,160,128)` | `(553,465,175,124)` |
| Search Area | `(145,92,987,858)` | `(88,48,962,840)` |

마크가 SearchArea 밖으로 이동하면 찾을 수 없다.

또한 Template가 SearchArea보다 크면 즉시 실패한다.

### 7.4 현재 Matching의 전제

현재 구현은 다음을 전제로 한다.

- 기준과 현재 마크 크기가 거의 같다.
- 마크 회전이 Template Matching을 무너뜨릴 정도로 크지 않다.
- 조명과 초점 변화가 Score 0.8 아래로 떨어질 정도로 크지 않다.
- 동일한 모양의 다른 물체가 SearchArea 안에서 더 높은 Score를 만들지 않는다.

현재 구현에서 명시적으로 하지 않는 것은 다음과 같다.

- Multi-scale Template Matching
- 회전 Template 탐색
- Feature 기반 회전각 측정
- Lens Distortion 보정
- Homography 보정

### 핵심 요약

- 마크는 지정된 SearchArea 안에서만 찾는다.
- 검출 결과는 중심과 Score이며 마크 각도는 아니다.
- Score가 Threshold 미만이면 Align 계산으로 넘어가지 않고 실패한다.

## 8. Image Pixel 편차를 Stage µm 편차로 변환

### 8.1 카메라 Geometry Calibration

uLED는 Align Camera Geometry 설정 시 UVW Stage에 다음 논리 이동을 준다.

```text
Original
+X 1000 µm
-X 1000 µm
+Y 1000 µm
-Y 1000 µm
+Theta 0.1°
-Theta 0.1°
```

각 위치에서 좌·우 카메라 이미지를 촬영하고 Template 중심을 기록한다.

X 방향은 다음 두 이미지 중심의 차이로 계산한다.

```text
ImageDeltaX
  = Center(+X1000) - Center(-X1000)

CommandedDistance
  = 2000 µm
```

Y 방향도 동일하다.

```text
ImageDeltaY
  = Center(+Y1000) - Center(-Y1000)
```

방향 벡터와 Pixel 크기는 다음처럼 계산한다.

```text
LengthPx = sqrt(DeltaPxX² + DeltaPxY²)

ImageUnitVector
  = (DeltaPxX / LengthPx, DeltaPxY / LengthPx)

PixelSizeUm
  = CommandedDistanceUm / LengthPx
```

> NOTE
>
> `+Theta/-Theta` 이미지도 저장하고 Match Score를 확인하지만 현재 `CalculateAlignCameraGeometry()`는 X/Y 촬영값만 사용해 Config 값을 만든다.

### 8.2 운전 중 Pixel 편차

현재 중심과 기준 중심의 차이는 다음과 같다.

```text
DeltaPixelX = CurrentCenterX - ReferenceCenterX
DeltaPixelY = CurrentCenterY - ReferenceCenterY
```

이를 Stage +X 이미지 방향에 투영한다.

```text
StageXProjectionPx
  = DeltaPixelX × StagePlusXImageUnitX
  + DeltaPixelY × StagePlusXImageUnitY
```

Stage +Y 방향에도 투영한다.

```text
StageYProjectionPx
  = DeltaPixelX × StagePlusYImageUnitX
  + DeltaPixelY × StagePlusYImageUnitY
```

현재 구현은 X/Y PixelSize의 평균을 사용한다.

```text
PixelSizeUm
  = (PixelSizeXUm + PixelSizeYUm) / 2

StageDeltaX
  = StageXProjectionPx × PixelSizeUm

StageDeltaY
  = StageYProjectionPx × PixelSizeUm
```

### 8.3 현재 장비에서 이미지 방향의 의미

현재 CAM1/CAM2 설정은 모두 다음에 가깝다.

```text
Stage +X → Image -Y 방향
Stage +Y → Image -X 방향
```

따라서 이미지에서 마크가 오른쪽으로 이동했다고 Stage +X 오차로 단정하면 안 된다.

Config의 방향 벡터를 통과한 후에야 Stage X/Y 오차의 부호가 결정된다.

### 핵심 요약

- µm/px만으로는 부족하고 Stage 축의 이미지 방향도 필요하다.
- uLED는 ±1000 µm 이동으로 방향 벡터와 Pixel 크기를 구한다.
- 현재 운전 계산은 PixelSizeX/Y 평균값을 사용한다.

## 9. 좌·우 Mark로 X/Y/Theta 계산

### 9.1 Glass Mark 좌표를 Stage 방향으로 회전

GlassSizeModel의 Mark 좌표는 Glass 좌표이다.

uLED는 `PanelAngleDeg`를 사용해 이를 Stage 방향 좌표로 회전한다.

```text
rad = PanelAngleDeg × PI / 180

StageMarkX = GlassX × cos(rad) - GlassY × sin(rad)
StageMarkY = GlassX × sin(rad) + GlassY × cos(rad)
```

### 9.2 두 Mark 사이 기준 벡터

```text
LeftStageMark  = L
RightStageMark = R

Vector = R - L

vx = RightX - LeftX
vy = RightY - LeftY
```

두 Mark가 같은 위치이면 Theta를 계산할 수 없으므로 즉시 실패한다.

### 9.3 좌·우 측정 이동량

카메라에서 얻은 Pixel 편차를 Stage µm로 바꾼 값을 다음처럼 둔다.

```text
LeftDelta  = (Ldx, Ldy)
RightDelta = (Rdx, Rdy)
```

두 결과의 차이는 다음과 같다.

```text
DeltaDiffX = Rdx - Ldx
DeltaDiffY = Rdy - Ldy
```

공통 X/Y 병진은 좌·우 차이에서 대부분 제거되고 회전 성분이 남는다.

### 9.4 Theta 계산

현재 구현은 작은 각도 근사를 사용한다.

```text
ThetaRad
  = (vx × DeltaDiffY - vy × DeltaDiffX)
    / (vx² + vy²)

ThetaDeg
  = ThetaRad × 180 / PI
```

이 식은 두 Mark 사이 거리가 길수록 동일한 Pixel 측정 노이즈가 Theta에 미치는 영향을 줄여준다.

### 9.5 회전 성분 제거

현재 코드의 회전 성분 계산은 다음과 같다.

```text
RotationX = -ThetaRad × MarkStageY
RotationY = -ThetaRad × MarkStageX
```

각 Mark 측정값에서 이를 제거한다.

```text
LeftTranslate
  = LeftDelta - LeftRotation

RightTranslate
  = RightDelta - RightRotation
```

최종 병진값은 평균이다.

```text
TranslateX
  = (LeftTranslateX + RightTranslateX) / 2

TranslateY
  = (LeftTranslateY + RightTranslateY) / 2
```

### 9.6 좌·우 결과 일관성 검사

좌·우에서 구한 병진 결과가 너무 다르면 잘못된 마크를 찾았거나 Calibration이 맞지 않는 상태일 수 있다.

```text
PairDiffX
  = RightTranslateX - LeftTranslateX

PairDiffY
  = RightTranslateY - LeftTranslateY
```

허용 범위는 다음과 같다.

```text
PairToleranceUm
  = max(
      30 µm,
      3 × max(ToleranceXUm, ToleranceYUm)
    )
```

현재 Recipe는 X/Y Tolerance가 3 µm이므로 Pair 허용치는 30 µm이다.

```text
max(30, 3 × 3) = 30 µm
```

X 또는 Y 차이가 30 µm를 초과하면 Align을 실패시킨다.

### 핵심 요약

- 공통 이동은 X/Y, 좌·우 이동 차이는 Theta 계산에 사용한다.
- Theta는 두 Mark 기준 벡터와 측정 차이의 외적 형태로 계산한다.
- 좌·우 Translation이 서로 맞지 않으면 잘못된 측정으로 보고 실패한다.

## 10. 현재 370×470 Recipe를 적용한 계산 해석

### 10.1 현재 Mark 좌표

```text
PanelAngle = 270°

Left Glass Mark
  = (170000, -220000) µm

Right Glass Mark
  = (-170000, -220000) µm
```

270도 회전 후 Stage 방향의 Mark는 다음 관계가 된다.

```text
Left Stage Mark
  ≈ (-220000, -170000) µm

Right Stage Mark
  ≈ (-220000, 170000) µm
```

따라서 기준 벡터는 다음과 같다.

```text
Vector
  = Right - Left
  ≈ (0, 340000) µm
```

두 Mark 간 거리는 약 340 mm이다.

### 10.2 Pixel과 X/Y 허용치

현재 카메라 배율은 대략 5.33 µm/px이다.

```text
1 pixel
  ≈ 5.33 µm

X/Y 허용치 3 µm
  ≈ 3 / 5.33
  ≈ 0.56 pixel
```

따라서 X/Y 합격을 위해서는 1 pixel보다 작은 위치 차이를 안정적으로 측정해야 한다.

현재 구현에 Sub-pixel 보간이 포함된 이유와도 연결된다.

### 10.3 Pixel과 Theta 허용치

두 Mark 사이가 약 340000 µm이므로 좌·우 상대 이동 1 pixel은 대략 다음 회전각에 해당한다.

```text
ThetaRad
  ≈ 5.33 / 340000

ThetaDeg
  ≈ (5.33 / 340000) × 180 / PI
  ≈ 0.00090°
```

현재 Theta 허용치는 0.001°이다.

```text
Theta 허용치 0.001°
  ≈ 좌·우 상대 이동 약 1.1 pixel
```

### 10.4 해석

현재 조건은 다음 특성을 가진다.

- X/Y 허용치는 약 0.56 pixel 수준이다.
- Theta 허용치는 좌·우 차이 약 1.1 pixel 수준이다.
- X/Y 판정이 특히 Sub-pixel 안정성에 민감하다.
- 조명, 초점, 진동, Mark 형상 변화가 중심점에 영향을 주면 3 µm 판정에 직접 영향을 줄 수 있다.

### 핵심 요약

- 현재 Mark 간 기준 거리는 약 340 mm이다.
- X/Y 3 µm는 약 0.56 pixel이다.
- Theta 0.001°는 좌·우 상대 차이 약 1.1 pixel이다.

## 11. UVW 보정의 개념

### 11.1 UVW 기구가 필요한 이유

Glass를 평면에서 움직이려면 다음 세 자유도가 필요하다.

```text
X 병진
Y 병진
Theta 회전
```

UVW 기구는 서로 다른 위치에 설치된 세 개 액추에이터의 이동을 조합해 이 세 자유도를 만든다.

하나의 축만 움직이면 단순한 X 또는 Y 이동만 발생하는 것이 아니라, 축 작용선과 Glass 중심의 관계에 따라 회전도 발생할 수 있다.

### 11.2 uLED의 일반 UVW 변환식

각 UVW 축은 X, Y, Theta에 대한 세 개 계수를 가진다.

```text
AxisDelta
  = PerX × XUm
  + PerY × YUm
  + RotationPerThetaRad × ThetaRad
```

U/V/W 전체는 다음과 같다.

```text
U
  = U.PerX × X
  + U.PerY × Y
  + U.RotationPerThetaRad × ThetaRad

V
  = V.PerX × X
  + V.PerY × Y
  + V.RotationPerThetaRad × ThetaRad

W
  = W.PerX × X
  + W.PerY × Y
  + W.RotationPerThetaRad × ThetaRad
```

행렬로 보면 다음과 같다.

```text
[U]   [U.PerX U.PerY U.RotationPerThetaRad] [X       ]
[V] = [V.PerX V.PerY V.RotationPerThetaRad] [Y       ]
[W]   [W.PerX W.PerY W.RotationPerThetaRad] [ThetaRad]
```

### 11.3 회전 계수의 의미

`RotationPerThetaRad`의 단위는 `µm/rad`이다.

의미는 다음과 같다.

```text
Glass가 1 rad 회전할 때
해당 UVW 축이 이동해야 하는 거리
```

이 값은 Glass 중심과 축 작용선 사이의 수직 거리에서 유도할 수 있다.

축이 중심에서 멀수록 같은 회전각을 만들기 위해 더 많은 이동량이 필요하다.

### 핵심 요약

- UVW는 X/Y/Theta를 실제 세 축 이동으로 바꾸는 기구이다.
- 각 축은 병진과 회전 기여도를 동시에 가질 수 있다.
- 회전 계수는 Glass 중심과 축 작용선의 상대 위치에서 계산된다.

## 12. 현재 uLED의 UVW 자동 계산

### 12.1 Config 상태

현재 Config는 다음 상태이다.

```text
UvwCoordinateSystem.UseAutoCalculation = true
PositiveThetaDirection                 = CW
```

따라서 구형 `AlignUvw` 고정 계수보다 `UvwCoordinateSystem`의 장비 기하를 기준으로 유효 파라미터를 계산한다.

### 12.2 Glass 중심 계산

현재 구현은 PanelAngle이 90도 또는 270도이면 Stage X 방향 Glass 길이로 Height를 사용한다.

```text
PanelAngle 0/180:
StageSpanX = GlassWidth

PanelAngle 90/270:
StageSpanX = GlassHeight
```

현재 모델은 270도이므로 다음과 같다.

```text
StageSpanX
  = GlassHeight
  = 470000 µm

GlassMinusXEdgeStageX
  = -460000 µm

CurrentCenterX
  = -460000 + 470000 / 2
  = -225000 µm

CurrentCenterY
  = 0 µm
```

### 12.3 현재 UVW 기하

현재 Config의 축 방향과 작용선은 다음과 같다.

```text
U Axis:
TranslationAxis = PlusY
AxisLineStageX  = -380000 µm

V Axis:
TranslationAxis = PlusY
AxisLineStageX  = 380000 µm

W Axis:
TranslationAxis = MinusX
AxisLineStageY  = -280000 µm
```

### 12.4 현재 모델의 유효 변환식

현재 370×470, PanelAngle 270도 모델에 대해 계산되는 식은 다음과 같다.

```text
U =  Y + 155000 × ThetaRad
V =  Y - 605000 × ThetaRad
W = -X + 280000 × ThetaRad
```

의미는 다음과 같다.

#### 순수 +X 이동

```text
X = +10 µm
Y = 0
Theta = 0

U = 0
V = 0
W = -10
```

#### 순수 +Y 이동

```text
X = 0
Y = +10 µm
Theta = 0

U = +10
V = +10
W = 0
```

#### 순수 회전

```text
X = 0
Y = 0
Theta ≠ 0

U/V/W가 서로 다른 거리와 방향으로 이동
```

### 12.5 Positive Theta 부호

Config에서 Positive Theta는 CW로 정의돼 있다.

현재 자동 Align 코드는 측정한 `ThetaDeg`를 그대로 UVW 변환기에 전달한다.

```text
Theta correction command
  = +MeasuredTheta
```

코드 이력에는 `-MeasuredTheta`를 보낼 경우 오차가 다음처럼 커졌다는 실측 기록이 있다.

```text
0.088°
→ 0.176°
→ 0.352°
```

따라서 현재 구현은 `+MeasuredTheta`를 보정 방향으로 사용한다.

### 핵심 요약

- 현재는 Config 기하와 Glass 크기로 UVW 계수를 자동 계산한다.
- 현재 모델의 유효식은 `U=Y+155000T`, `V=Y-605000T`, `W=-X+280000T`이다.
- Theta 입력은 rad로 변환한 뒤 회전 계수에 곱한다.

## 13. 자동 Align의 정확한 실행 순서

### 13.1 검사 전 호출

검사 Run에서 `UseAlign=true`이면 검사 셀 처리 전에 Align을 실행한다.

```text
MainWindowViewModel
└─ Run align before inspection
   └─ MainWindow.RunAlignBeforeInspectionOnUiThreadAsync
      └─ AlignWindow
         └─ AlignViewModel.RunThetaThenXyAlignForInspectionAsync
            └─ RunThetaThenXyAlignCoreAsync
```

### 13.2 사전 조건 검사

다음 조건을 확인한다.

- 자동 Align이 이미 실행 중이지 않은가
- CorrectionMode가 `ThetaThenXY`인가
- ControlRuntime이 존재하는가
- GlassSizeModel을 정상 로드할 수 있는가
- 기준 이미지 두 장이 존재하는가
- Left/Right 카메라가 모두 연결됐는가

### 13.3 Align 기준 자세 이동

Recipe `ControlPlan`의 다음 값을 이용해 이동한다.

```text
StageX
InspectionUnit2Y
InspectionUnit1Y
StageU
StageV
StageW
```

이 값은 마크를 카메라 시야에 넣는 Teach 기준 자세이다.

### 13.4 반복 1회의 순서

```text
[1] 좌·우 촬영
        ↓
[2] Left/Right Template Matching
        ↓
[3] Pixel → Stage µm 변환
        ↓
[4] X/Y/Theta Snapshot 계산
        ↓
[5] 이미 모든 허용치 이내인가?
        ├─ Yes → 즉시 성공
        └─ No
             ↓
[6] Theta가 허용치 밖인가?
        ├─ Yes → Theta UVW 상대 이동
        └─ No
             ↓
[7] 좌·우 재촬영
        ↓
[8] X/Y Snapshot 재계산
        ↓
[9] X/Y가 허용치 밖인가?
        ├─ Yes → -X/-Y UVW 상대 이동
        └─ No
             ↓
[10] 좌·우 재촬영
        ↓
[11] 최종 X/Y/Theta 잔차 계산
        ↓
[12] 모두 허용치 이내인가?
        ├─ Yes → 성공
        └─ No → 다음 Iteration
```

### 13.5 Theta 보정

```text
ThetaMove
  = ToUvw(
      X = 0,
      Y = 0,
      Theta = MeasuredTheta
    )
```

### 13.6 X/Y 보정

```text
XyMove
  = ToUvw(
      X = -MeasuredTranslateX,
      Y = -MeasuredTranslateY,
      Theta = 0
    )
```

Theta와 X/Y의 명령 부호가 서로 다르다는 점에 주의해야 한다.

```text
Theta correction = +MeasuredTheta
XY correction    = -MeasuredXY
```

### 13.7 실제 Control 명령

변환된 U/V/W는 하나의 상대 이동 요청으로 보낸다.

```text
AxisMove StageU, Mode=Relative, Value=U
AxisMove StageV, Mode=Relative, Value=V
AxisMove StageW, Mode=Relative, Value=W
```

Control 응답이 없거나 `Ok=false`이면 해당 Align은 실패한다.

### 핵심 요약

- 기준 자세 이동 후 좌·우 카메라를 촬영한다.
- 한 Iteration 안에서 Theta와 X/Y 사이에 재촬영이 존재한다.
- 최종 재촬영 결과가 합격해야 성공한다.

## 14. 왜 Theta를 먼저 보정하는가

회전 오차는 Mark 위치에 따라 서로 다른 X/Y 이동으로 나타난다.

Glass 중심에서 멀리 있는 Mark일수록 같은 Theta에서 더 큰 선형 이동이 발생한다.

```text
회전 이동 거리
  ≈ 중심으로부터 거리 × ThetaRad
```

Theta가 남아 있는 상태에서 두 Mark의 이동량을 단순 평균하면 회전 성분이 X/Y 병진으로 섞일 수 있다.

따라서 현재 구조는 다음 순서를 사용한다.

```text
좌·우 차이
→ Theta 계산
→ Theta 먼저 보정
→ 재촬영
→ 남은 공통 이동으로 X/Y 계산
→ X/Y 보정
```

> 장비 개발자 관점의 해석
>
> 이는 회전과 병진을 한 번에 큰 이동으로 보정하는 것보다 각 단계의 원인과 결과를 로그로 확인하기 쉽고, 부호가 잘못됐을 때 어느 단계에서 발산했는지 추적하기 쉬운 구조이다.

### 핵심 요약

- 회전이 남아 있으면 Mark 위치별 X/Y 오차가 달라진다.
- Theta를 먼저 제거하면 남은 공통 이동을 X/Y로 해석하기 쉬워진다.
- 단계별 재촬영으로 수렴 여부와 부호 오류를 확인할 수 있다.

## 15. Align 성공 판정

### 15.1 최종 잔차 조건

최종 성공 조건은 세 값이 모두 허용치 이내인 것이다.

```text
abs(TranslateXUm)
  <= ToleranceXUm

abs(TranslateYUm)
  <= ToleranceYUm

abs(ThetaDeg)
  <= ToleranceThetaDeg
```

현재 Recipe 기준은 다음과 같다.

```text
ToleranceX     = 3 µm
ToleranceY     = 3 µm
ToleranceTheta = 0.001°
MaxIteration   = 5
```

### 15.2 Matching 조건

각 Snapshot을 만들 때 양쪽 카메라가 모두 Match Threshold를 통과해야 한다.

```text
LeftScore  >= 0.8
RightScore >= 0.8
```

한쪽이라도 미달이면 X/Y/Theta를 계산하지 않고 실패한다.

### 15.3 Pair 일관성 조건

좌·우에서 계산한 병진 결과의 차이가 현재 기준 30 µm 이하여야 한다.

```text
abs(PairDiffX) <= 30 µm
abs(PairDiffY) <= 30 µm
```

### 15.4 반복 조건

최대 5회 안에 수렴해야 한다.

```text
Iteration 1
Iteration 2
...
Iteration 5

5회 후에도 잔차가 남음
→ Align 실패
```

### 15.5 성공의 정확한 의미

Align 성공은 다음을 뜻한다.

- 마지막 촬영에서 양쪽 마크를 정상 검출했다.
- Match Score가 Threshold 이상이다.
- 두 Mark로 계산한 결과가 서로 일관된다.
- 최종 X/Y/Theta가 모두 Recipe 허용치 이내다.

다음은 Align 성공을 의미하지 않는다.

- UVW 이동 명령이 성공적으로 전송된 것
- Stage가 이동 완료한 것
- 검사 Run이 계속 진행된 것
- 한쪽 마크만 정상 검출된 것

반드시 최종 재촬영 잔차가 허용치 이내여야 한다.

### 핵심 요약

- 최종 X/Y/Theta가 모두 합격해야 한다.
- Match Score와 Pair 일관성도 필수 조건이다.
- 이동 명령 성공과 Align 성공은 다른 의미이다.

## 16. Align 실패와 검사 Run의 관계

### 16.1 결과 저장

성공과 실패 모두 다음 파일에 저장한다.

```text
C:\elp\uLedAoi\Data\Runtime\align_result.json
```

저장 항목은 다음과 같다.

- Timestamp
- Success
- FailureReason
- Iterations
- FinalDxUm
- FinalDyUm
- FinalDtDeg
- Tolerance X/Y/Theta
- Left/Right Score
- 누적 AppliedU/V/W
- RecipeName

검사 세션이 만들어지면 최신 Align 결과를 세션 폴더에도 복사할 수 있다.

### 16.2 Align Alarm

검사 Run에서 Align이 실패하면 다음 Alarm을 발생시킨다.

```text
ConAlignFail
```

Alarm 심각도에 따라 동작이 달라진다.

```text
Heavy
→ 검사 Run 중단

Light
→ 경고 기록
→ Align 실패를 무시하고 검사 계속
```

따라서 검사 결과가 생성됐다는 사실만으로 Align 성공을 판단해서는 안 된다.

### 16.3 현재 저장된 최신 결과

분석 시점의 최신 `align_result.json`은 다음 상태였다.

```text
Timestamp = 2026-07-15
Success   = false
Reason    = Left/Right camera가 모두 연결되어야 함
```

이 기록은 알고리즘 수렴 실패가 아니라 자동 Align 실행에 필요한 카메라 연결 조건을 만족하지 못한 실패이다.

현재 장비에서 실제 Align 성공과 수렴을 확인하려면 연결된 실카메라와 실축으로 별도 운전 검증이 필요하다.

### 핵심 요약

- Align 결과는 성공과 실패 모두 JSON으로 저장된다.
- Alarm이 Light이면 Align 실패 후에도 검사가 진행될 수 있다.
- 검사 진행 여부가 아니라 `Success`와 최종 잔차를 확인해야 한다.

## 17. 장비 개발자 관점에서 본 설계 의도

이 절은 코드에서 확인되는 구조와 그에 대한 공학적 해석을 구분한다.

### 17.1 장비 고정값과 제품별 값을 분리

코드에서 확인되는 구조:

- 카메라 Geometry와 UVW Geometry는 Config
- Glass 크기와 Mark 좌표는 GlassSizeModel
- Template, 검색 범위, 허용치는 Recipe

**설계 의도 해석**

- 카메라 설치 방향은 제품이 바뀌어도 장비에 고정된다.
- Align Mark 위치는 Glass 모델에 따라 달라질 수 있다.
- 허용치와 Template은 제품 및 Recipe 운전 조건에 따라 달라질 수 있다.

따라서 서로 다른 수명주기의 값을 분리한 구조로 볼 수 있다.

### 17.2 Pixel 좌표를 바로 Motor 명령으로 사용하지 않음

코드에서 확인되는 구조:

```text
Pixel
→ Stage X/Y µm
→ Glass X/Y/Theta
→ UVW
```

**설계 의도 해석**

- 카메라 교체나 설치 방향 변경은 Camera Geometry에서 흡수한다.
- Glass 크기 변경은 UVW 유효 계수 계산에서 흡수한다.
- Align 알고리즘은 장비 축 배치 세부사항보다 X/Y/Theta에 집중할 수 있다.

### 17.3 두 Mark와 Pair 검증

코드에서 확인되는 구조:

- 좌·우 두 Mark로 Theta 계산
- 회전 제거 후 좌·우 Translation 차이 검사
- 차이가 크면 즉시 실패

**설계 의도 해석**

- 한쪽 오검출이 Glass 전체를 잘못 움직이는 것을 방지한다.
- 단순 평균 전에 좌·우 측정이 하나의 강체 움직임으로 설명되는지 확인한다.

### 17.4 Theta와 X/Y 단계 분리

코드에서 확인되는 구조:

```text
Theta 보정
→ 재촬영
→ X/Y 보정
→ 재촬영
```

**설계 의도 해석**

- 회전과 병진이 서로 섞이는 것을 줄인다.
- 단계별 로그와 재촬영으로 발산 원인을 추적하기 쉽다.
- 한 번의 큰 보정보다 수렴 상태를 관찰하기 쉽다.

### 17.5 결과를 검사와 별도로 보존

코드에서 확인되는 구조:

- `align_result.json` 저장
- GEM Data Variable 갱신
- 검사 세션 폴더에 결과 복사
- Alarm 정책과 연계

**설계 의도 해석**

- 검사 불량과 위치 보정 실패를 구분해 추적한다.
- Align이 Light Alarm으로 무시된 검사도 사후 판별할 수 있게 한다.

### 핵심 요약

- 장비값, 제품값, Recipe값의 수명주기를 분리했다.
- Pixel부터 Motor까지 좌표 변환 책임을 단계별로 분리했다.
- 오보정을 막기 위해 두 Mark 일관성 검사와 재촬영을 사용한다.

## 18. Docs와 현재 코드가 다른 부분

### 18.1 AlignUvw 고정값과 UvwCoordinateSystem 자동 계산

`docs/uvw-kinematics-converter.md`는 `ULedConfig.AlignUvw` 고정 파라미터 사용을 중심으로 설명한다.

현재 코드는 다음 조건을 사용한다.

```text
UvwCoordinateSystem.UseAutoCalculation == true
→ UvwCoordinateSystem + GlassSizeModel로 자동 계산

UseAutoCalculation != true
→ AlignUvw를 fallback 파라미터로 사용
```

현재 실제 Config는 자동 계산이 활성화돼 있다.

### 18.2 ReferencePoseStandard 명칭

일부 문서는 `ReferencePoseStandard`를 사용하지만 현재 모델은 다음 구조로 분리돼 있다.

```text
GlassSizeModel
├─ AlignStageSharedPose
└─ AlignBridgeReferencePose

Runtime Recipe
└─ ControlPlan AlignReference...
```

실제 Align 기준 위치 이동은 Recipe `ControlPlan` 값을 정본으로 사용한다.

### 18.3 Left 3점, Right 1점 Affine 문서

`docs/glass-axis-affine-transform-design.md`는 UVW Align 완료 후 Glass 좌표를 설비 축 좌표로 변환하기 위한 Affine 설계 문서이다.

이 문서는 다음 자동 Align 계산과 직접 같은 기능이 아니다.

```text
Template Matching
→ Pixel Delta
→ X/Y/Theta
→ UVW 보정
```

Affine 문서는 Align 후 검사 카메라를 특정 Glass 좌표로 이동시키는 좌표 변환 관점에서 읽어야 한다.

### 18.4 LoadingAligner 또는 UVW

`docs/전체 flow.md`에는 LoadingAligner 축 또는 UVW 보정 가능성이 함께 표현돼 있다.

현재 자동 Align 실행 코드는 다음 축만 사용한다.

```text
StageU
StageV
StageW
```

### 18.5 Theta 방향

일부 좌표 문서는 +Theta 방향의 최종 현장 검증이 필요하다고 적고 있다.

현재 상태는 다음과 같다.

- Config: PositiveThetaDirection = CW
- 현재 코드: +MeasuredTheta를 보정 명령으로 전송
- Git 이력: 반대 부호 사용 시 오차가 두 배씩 커진 실측 기록 존재

다만 기구 교체, 축 방향 변경, Config 변경 후에는 ±Theta Jog 검증을 다시 수행해야 한다.

### 핵심 요약

- 현재 운전은 `UvwCoordinateSystem` 자동 계산이 기준이다.
- Align 기준 자세는 Runtime Recipe의 `ControlPlan`이 기준이다.
- Affine 문서와 자동 Align 보정 알고리즘은 별도 기능이다.

## 19. WinForms 개발자 관점의 WPF 호출 흐름

### 19.1 버튼에서 자동 Align까지

WinForms에서는 Button Click 이벤트에서 직접 함수를 호출하는 형태가 익숙할 수 있다.

현재 WPF 구조는 다음과 같다.

```text
AlignWindow.xaml
└─ Button Command Binding
   └─ AlignViewModel.RunThetaThenXyAlignCommand
      └─ AsyncRelayCommand
         └─ RunThetaThenXyAlignAsync
            └─ RunThetaThenXyAlignCoreAsync
```

WinForms와 비교하면 다음과 같다.

| WinForms | WPF/MVVM |
|---|---|
| Button.Click | Button.Command |
| Form 필드 | ViewModel Property |
| Click Event Handler | RelayCommand 실행 메서드 |
| Form에서 UI 상태 직접 변경 | Observable Property 변경 |
| Form에서 장비 직접 호출 | ViewModel → Runtime/Service |

### 19.2 카메라 Pane 구조

좌·우 카메라는 각각 `AlignCameraPaneViewModel` 인스턴스를 가진다.

```text
AlignViewModel
├─ LeftCamera : AlignCameraPaneViewModel
└─ RightCamera: AlignCameraPaneViewModel
```

각 Pane가 담당하는 것은 다음과 같다.

- 카메라 연결
- Grab과 Live
- 현재 이미지 관리
- 기준 이미지 관리
- Template/Search Rect
- Template Matching
- Match 결과 표시

상위 `AlignViewModel`이 담당하는 것은 다음과 같다.

- 좌·우 동시 촬영
- 두 결과를 결합한 X/Y/Theta 계산
- UVW 보정
- 반복과 성공/실패 판정
- Align 결과 저장

### 핵심 요약

- 개별 카메라 처리와 두 카메라 결합 계산이 ViewModel 계층에서 분리돼 있다.
- Button은 Command를 통해 ViewModel 메서드를 실행한다.
- WinForms의 Click Handler를 찾듯 XAML의 Command부터 추적하면 된다.


확인 결과:

- 현재 Recipe 허용치는 X/Y 3 µm, Theta 0.001°이다.
- Match Threshold는 좌·우 모두 0.8이다.
- 현재 카메라 해상도는 약 5.32~5.34 µm/px이다.
- 현재 모델에 대한 유효 UVW 식을 코드와 Config로 재계산했다.
- 최신 저장 결과는 카메라 미연결 실패였다.
- Solution 빌드는 오류 0개로 성공했다.
- 기존 경고 49개가 있었지만 Align 코드 컴파일 오류는 없었다.

### 21.3 검증 범위의 한계

이번 검증에서 실제 장비 축을 움직이지 않았다.

따라서 다음은 확인하지 않았다.

- 현재 실카메라의 실제 Match Score
- 실제 Stage 응답과 위치 정착
- 실 Glass에서 5회 이내 수렴 여부
- 실장치에서 X/Y/Theta 최종 반복 정밀도
- 현재 기구의 backlash, 진동, 조명 변동 영향

즉 다음 두 가지를 구분해야 한다.

```text
확인 완료:
Docs, 코드, Config, Recipe, 결과 저장 구조의 연결

별도 실장비 검증 필요:
실제 Align 수렴과 반복 정밀도
```

### 핵심 요약

- 1차 검증은 문서에서 실제 실행 코드까지 순방향으로 확인했다.
- 2차 검증은 결과와 실제 설정에서 계산 코드로 역추적했다.
- 실장비 이동과 수렴 시험은 이번 문서 검증에 포함하지 않았다.

## 23. 최종 정리

uLED Align의 본질은 다음 변환 체인이다.

```text
기준 Mark와 현재 Mark 비교
        ↓
Image Pixel 편차
        ↓
Camera Geometry
        ↓
Stage X/Y µm 편차
        ↓
좌·우 Mark 기하
        ↓
Glass X/Y/Theta 오차
        ↓
UVW Center-Pivot 변환
        ↓
StageU/V/W 상대 이동
        ↓
재촬영 잔차
        ↓
Align 성공/실패
```

가장 중요한 사실은 다음과 같다.

- uLED는 한 개 Mark로 Theta를 직접 측정하지 않는다.
- Left/Right 두 Mark의 상대 이동으로 Theta를 계산한다.
- 각 카메라의 Pixel 이동은 Config의 방향 벡터와 µm/px로 Stage 이동량이 된다.
- GlassSizeModel의 Mark 좌표와 PanelAngle이 Theta 계산 기준을 만든다.
- Recipe의 Threshold, SearchArea, 허용치, 반복 횟수가 운전 판정을 결정한다.
- UVW는 Glass 중심 기준 X/Y/Theta를 실제 세 축 움직임으로 변환한다.
- Theta 보정 후 재촬영하고, X/Y 보정 후 다시 재촬영한다.
- 마지막 X/Y/Theta가 모두 허용치 이내여야 Align 성공이다.
- Alarm이 Light이면 Align 실패 후에도 검사가 진행될 수 있다.
- 실제 성공 여부는 `align_result.json`과 최종 잔차로 확인해야 한다.

### 최종 핵심 요약

```text
한 Mark
→ 위치 X/Y 측정

두 Mark
→ 위치 X/Y + 회전 Theta 계산

X/Y/Theta
→ UVW 이동량으로 변환

보정 후 재촬영
→ 잔차가 모두 허용치 이내일 때만 Align 성공
```
