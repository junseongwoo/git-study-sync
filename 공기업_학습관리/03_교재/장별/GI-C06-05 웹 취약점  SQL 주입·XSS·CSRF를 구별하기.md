# 06-05 웹 취약점: SQL 주입·XSS·CSRF를 구별하기

[[GI-교재06 정보보안|과목 목차]] · [[GI-문제06 정보보안|문제]] · [[GI-해설06 정보보안|해설]]

### SQL 주입
SQL 주입은 신뢰할 수 없는 입력이 SQL의 데이터 자리를 넘어 명령 구조에 영향을 주는 취약점이다. 핵심 예방은 파라미터 바인딩·준비된 문장 등으로 명령과 값을 분리하고, DB 계정에 최소권한을 적용하는 것이다. 입력의 따옴표를 제거하는 임시 처리만으로 모든 문법·인코딩·맥락 문제를 해결할 수 없다.

값 자리의 파라미터 바인딩이 테이블명·열명·정렬 방향 같은 SQL 구조를 자동으로 보호하는 것은 아니다. 그런 구조는 허용 목록에서 선택한다. 저장 프로시저도 내부에서 안전하지 않은 동적 SQL을 만들면 자동으로 안전하지 않다.

### XSS
XSS는 신뢰할 수 없는 데이터가 웹 문서의 실행 가능한 문맥으로 들어가 공격자가 의도한 스크립트가 실행되는 문제다. 저장형은 악성 값이 서버 등에 저장됐다가 표시되고, 반사형은 요청 입력이 응답에 돌아오며, DOM 기반은 클라이언트 코드의 처리 흐름에서 문제가 생긴다. 분류가 실제 사건에서 겹칠 수 있다.

예방은 출력 위치에 맞는 인코딩, 안전한 DOM API, 필요하면 검증된 HTML 정화 도구, 보조적인 CSP 등으로 구성한다. HTML 본문·속성·JavaScript·URL은 문맥이 다르다. 모든 위치에 같은 인코딩 함수를 적용하면 안 된다. HttpOnly는 JavaScript가 쿠키를 직접 읽지 못하도록 돕지만 XSS가 사용자를 대신해 요청을 보내는 모든 행동을 막는 것은 아니다.

### CSRF
CSRF는 인증된 사용자의 브라우저가 자동으로 보내는 인증 정보를 이용해 사용자가 원하지 않는 상태 변경 요청을 수행하게 하는 공격이다. 쿠키 기반 인증에서 특히 중요한 맥락이다. 서버는 CSRF 토큰 검증, 적절한 SameSite 정책, 요청 출처 확인, 중요 작업의 재확인 등을 설계할 수 있다. 토큰을 생성만 하고 서버에서 검사하지 않으면 방어가 아니다.

CSRF와 XSS는 다르다. CSRF는 대상 사이트의 스크립트 주입을 반드시 필요로 하지 않는다. XSS가 존재하면 일부 CSRF 방어를 우회할 수 있으므로 하나만 해결해 전체 웹 보안이 끝났다고 보지 않는다. GET을 상태 변경에 쓰지 않는다는 규칙도 잘못된 인증·인가를 대신하지는 않는다.

### 세 가지 사례를 비교
첫째, 계정 조회 SQL에 입력 문자열을 붙여 쿼리 구조가 달라졌다면 SQL 주입이다. 둘째, 게시판에 저장한 문자열이 화면에서 스크립트로 실행됐다면 저장형 XSS다. 셋째, 다른 사이트가 로그인된 브라우저를 통해 이체 요청을 보내도록 만들었다면 CSRF 시나리오다. 어느 사건인지 먼저 판단한 뒤 방어를 연결한다.

### 방어 설계 예제
신청서 검색 기능에서 검색어는 SQL 파라미터로 전달한다. 정렬 열은 allowedSort={name,date}라는 허용 목록에서 고른다. 결과 화면의 고객 이름은 텍스트 문맥으로 안전하게 출력한다. 승인 POST 요청은 권한 검사와 CSRF 검증을 한다. SQL 파라미터를 적용했다고 출력 화면의 XSS가 해결되지는 않는다. 방어가 적용되는 경계가 각각 다르다.

### 숫자·자가 연습
100개 입력 중 5개를 금지 문자열 목록으로 막았다는 사실만으로 나머지 95개가 안전하다고 증명할 수 없다. 블랙리스트 탐지율을 시스템의 완전한 안전성과 동일시하지 않는다. 강한 핵심 통제와 의미 있는 테스트를 함께 적용한다.

자가 연습: 검색 결과에 사용자 입력을 보여주는 페이지에서 SQL은 파라미터를 사용한다. XSS 검토도 필요할까? 필요하다. DB 명령 구조 보호와 브라우저 실행 문맥 보호는 별개의 문제다.

### 완료 기준
공격마다 입력이 어느 경계를 넘어 실행 의미를 얻는지 설명하고 SQL 주입→파라미터화, XSS→문맥에 맞는 출력 처리, CSRF→요청 진위 검증을 연결할 수 있어야 한다.

### 응용 문제: CORS와 CSRF의 차이
CORS는 브라우저에서 다른 출처의 응답을 읽는 것 등에 관한 통제다. 단순히 CORS를 설정했다고 모든 원치 않는 요청이 보내지지 않는 것은 아니다. CSRF는 인증 정보가 자동 첨부되는 상태 변경 요청의 진위 문제다. 허용 출처와 인증 방식·토큰 검증·쿠키 속성의 관계를 함께 확인한다.

파라미터 바인딩은 입력 문자열을 SQL 값으로 취급하지만 저장된 값이 나중에 HTML에서 실행되면 XSS는 여전히 생길 수 있다. 입력 검증·SQL 파라미터화·출력 인코딩·CSRF·인가 검사는 모두 다른 경계를 보호한다. 한 방어를 적용했으니 다른 검토는 필요 없다는 선택지를 경계하자.

### 강화 입력·출력 경계: 값과 SQL 구조는 다르다
가상 검색 API는 검색어 값을 매개변수로 보내고 정렬 항목은 외부 값 date/name을 내부 고정 열 created_at/customer_name에 대응시킨다. 미등록 정렬 항목은 거절한다.
1. 검색어는 자료 값이므로 SQL 문자열과 분리해 바인딩한다.
2. 열 이름·ASC/DESC 같은 SQL 구조는 일반 값 바인딩으로 대신할 수 없으므로 허용된 고정 선택으로 구성한다.
3. 실행 계정 권한과 객체 접근 조건을 별도로 확인한다.
검색어 매개변수화가 있어도 정렬 문자열을 그대로 이어 붙이는 반례는 구조 경계를 남긴다.
게시 내용은 출력되는 HTML 본문·속성·스크립트 문맥에 맞는 방어가 필요하다. 문자열에 'script'가 없다는 검사는 충분하지 않다. 일반 텍스트 표시 목적이면 텍스트용 안전한 출력 경로를 사용하고 HTML 허용이 필요하면 검증된 정제 정책을 적용한다. CSRF 방어는 상태 변경 요청의 요청 출처·토큰 등을 검증하는 별도 문제이며 XSS가 있으면 일부 방어를 우회할 수 있다. POST라는 메서드 이름만으로 안전성을 확정하지 않는다.
