# 03-06 트랜잭션·격리 수준·직렬 가능성: 동시에 실행해도 맞는 결과

[[GI-교재03 DB_SQL|과목 목차]] · [[GI-문제03 DB_SQL|문제]] · [[GI-해설03 DB_SQL|해설]]

## 학습 목표
ACID를 네 단어로 외우는 것을 넘어 이 체·동시 갱신의 실패 상황을 설명한다. SQL 표준의 격리 수준 설명과 특정 제품 구현의 차이를 구분한다. 거래를 여러 문장으로 나눌 때 발생할 수 있는 현상을 실행 순서로 추적한다.

## 1. ACID와 이체
원자성은 거래의 여러 변경이 전부 반영되거나 전부 취소되도록하는 성질이다. 일관성은 거래가 정의된 무결성 규칙을 지키는 상태 변화를 만드는 성질이다. DBMS가 잘못된 업무 로직까지 알아서 고쳐 준다는 뜻은 아니다. 격리성은 동시 거래의 간섭을 제어한다. 지속성은 성공한 커밋 결과가 약속된 장애 범위와 설정 아래 보존되는 성질이다.

잔액 A =1000,B =200에서 A로부터 B로 100을 이체하면 최종 A =900,B =300이어야한다. A만 차감하고 오류가 발생했을 때 B 증가가 취소되지 않은 상태로 남으면 안 된다. 애플리케이션은 예외 때 ROLLBACK하고 필요하면 재시도해야 한다. 커밋 응답 직전에 연결이 끊기면 실제 커밋 여부가 불확실할 수 있어 거래 ID 같은 멱등성 설계가 필요하다. 무조건 같은 이 체를 다시 실행하면 중복 처리될 수 있다.

```sql
BEGIN;
UPDATE account SET balance=balance-100 WHERE account_id=1;
UPDATE account SET balance=balance+100 WHERE account_id=2;
COMMIT;
```

실습에서는 영향 받은 행 수, 잔액 부족 검사, 금액 유효성도 확인한다. BEGIN 문법과 자동 커밋은 제품에 따라 다르다. Oracle의 트랜잭션 시작은 첫 DML 등으로 발생하므로 위 BEGIN을 Oracle에 그대로 복사하지 않는다.

## 2. 동시성 이상을 구분하기
### 손풀이 예제 12: 갱신 분실
초기 x =100이다. T1은 100을 읽어 +10 계산, T2도 100을 읽어 -20 계산, T1 이 110 을 저장, T2 가 80을 저장하면 최종 80이다. 두 연산을 모두 반영한 90이 아니다. 값을 애플리케이션에서 읽고 나중에 덮어 쓴 것이 문제다. `UPDATE SET x=x+10`과 `x=x-20` 같은 원자적 갱신 또는 적절한 잠금·버 전 검사로 제어한다. 모든 DBMS·격리 수준에서 동일 문장이 반드시 같은 갱신 분실을 만든다고 단정하지 않는다.

더티 리드는 아직 커밋 하지 않은 다른 거래의 값을 읽는 현상이다. 비반복 읽기는 동일 행을 다시 읽을 때 커밋된 변경 때문에 값이 달라지는 현상이다. 팬텀은 조건 검색을 반복할 때 조건에 맞는 행 집합이 삽입·삭제 등으로 달라지는 현상이다. '값 변경'과 '조건에 맞는 행 집합 변경'을 먼저 구분한다.

### 손풀이 예제 13: 비반복 읽기와 팬텀
T1이 고객 1 잔액 100을 읽고, T2가 150으로 변경·커밋 하고, T1이 같은 고객 1을 다시 읽어 150을 보면 비반복 읽기다. T1이 잔액 100 이상 계좌 수를 2로 읽고, T2가 새 계좌를 삽입·커밋해 T1의 같은 조건 결과가 3이 되면 팬텀이다. T2가 롤 백 할 값을 T1이 중간에 읽었다면 더티 리드다.

## 3. 표준 격리 수준의 최소 보장
| 격리 수준 | 더티 리드 | 비반복 읽기 | 팬텀 |
| --- | --- | --- | --- |
| READ UNCOMMITTED | 허용될 수 있음 | 허용될 수 있음 | 허용될 수 있음 |
| READ COMMITTED | 금지 | 허용될 수 있음 | 허용될 수 있음 |
| REPEATABLE READ | 금지 | 금지 | 표준상 허용될 수 있음 |
| SERIALIZABLE | 금지 | 금지 | 금지 |

이는 표준의 대표 읽기 현상 표다. 같은 수준 이름이라도 DBMS가 더 강한 보장을 제공할 수 있고 실제 동작은 일관 읽기·잠금 읽기·문장 형태에 따라 다르다. PostgreSQL의 REPEATABLE READ는 팬텀도 방지하지 만 직렬화 이상을 모두 배제하지는 않는다. MySQL InnoDB 기본 수준은 REPEATABLE READ, PostgreSQL 기본은 일반적으로 READ COMMITTED다. 설정 변경 가능성을 전제한다. Oracle의 지원 수준과 일관 읽기 구현 역시 별도로 본다.

### 예제: 쓰기 편향
당직자 A,B가 모두 근무 중이고 반드시 한 명 이상 근무해야 한다. T1과 T2가 같은 스냅샷에서 둘 다 근무 중이라고 읽고 각각 자기 행을 휴무로 바꾸면 서로 다른 행을 갱신했는데도 최종 둘 다 휴무가 될 수 있다. 이것이 쓰기 편향 사례다. 단순히 '같은 행 충돌만 막았으므로 모든 일관성이 보장'이라고 결론 내릴 수 없다. 직렬화 수준, 업무 제약을 표현하는 잠금, 재시도 전략을 검토한다.

## 4. 충돌 직렬 가능성과 선행 그래프
서로 다른 거래의 연산이 같은 데이터에 접근하고 하나 이상이 쓰기면 충돌한다. 읽기-읽기는 충돌이 아니다. 스케줄에서 앞선 충돌 연산의 거래에서 뒤 거래로 방향 간선을 그린다. 사이클이 없으면 충돌 직렬 가능하고 위상 순서가 동등한 직렬 실행 순서다. 사이클이 있으면 충돌 직렬 가능하지 않다. 이는 뷰 직렬 가능성과 동일 개념이 아니다.

### 손풀이 예제 14: 사이클
순서가 r1(A), r2(B), w1(B), w2(A)다. A에서 r1(A)가 w2(A)보다 먼저라 T1->T2가 생긴다. B에서 r2(B)가 w1(B)보다 먼저라 T2->T1이 생긴다. 사이클이므로 충돌 직렬 가능하지 않다. 단순히 최종 값 두 개가 존재한다고 안전한 실행이라고 판단하지 않는다.

## 5. 잠금·2 단계 잠금·MVCC
공유 잠금은 읽기, 배타 잠금은 쓰기를 제어하는 대표 모델이다. 잠금 호환성을 보고 다른 거래가 기다려야하는지 판단한다. 2PL은 잠금을 얻는 확장 단계와 해제하는 축소 단계를 구분하며 한 번 해제한 뒤 새 잠금을 획득하지 않는 규칙이다. 2PL은 충돌 직렬 가능성을 보장하지만 교착 상태는 발생할 수 있다. 엄격 2PL은 대표적으로 배타 잠금을 종료까지 유지해 연쇄 롤 백을 방지하는 데 도움을 준다. 모든 잠금을 끝까지 유지하는 형태와 교재 정의를 구분한다.

MVCC는 여러 버전으로 읽기 일관성을 제공한다. 읽는 거래가 특정 스냅 샷을 보는 동안 다른 거래의 새 버전이 존재할 수 있다. 'MVCC니까 잠금이 전혀 없다'는 틀리다. 쓰기 충돌, 스키마 변경, 특정 잠금 읽기 등에서는 잠금이 필요하다. 직렬화 실패·교착 상태로 거래가 취소되면 통상 전체 거래를 올바르게 재시도한다.

### 직접 풀기와 확인
r1(A),w1(A),r2(A),w2(B)에서 충돌 간선은 T1->T2이며 반대 간선은 없다. 따라서 T1 다음 T2의 직렬 순서와 충돌 동등하다. r1과 r2가 같은 값을 읽었다는 뜻은 아니다. 데이터 값과 충돌 순서 분석을 분리한다.

완료: 이상 현상을 실행 순서로 그리고, 읽기 격리 표와 제품 구현을 따로 설명한다. 참고: [PostgreSQL 격리](https://www.postgresql.org/docs/current/transaction-iso.html), [MySQL InnoDB 격리](https://dev.mysql.com/doc/refman/8.0/en/innodb-transaction-isolation-levels.html). 금액·스케줄·당직 사례는 자체 제작이다.

## 강화 조건 비교: 결과가 같음과 중복 처리가 안전함은 다르다
거래 X가 계좌 잔액을 100 증가시키고 COMMIT했지만 응답 전에 통신이 끊겼다고 가정한다. 클라이언트가 동일 UPDATE를 다시 보내면 200 증가할 수 있다. 격리 수준을 높여도 클라이언트 재시도 자체의 중복을 자동으로 해결하지는 않는다.

업무 거래 ID를 고유하게 저장하고 잔액 변경과 같은 트랜잭션 안에서 처리하는 설계를 생각한다. 같은 ID가 이미 처리되었다면 이전 결과를 조회하고, 새로운 ID일 때만 변경한다. 중복 판정과 변경 사이의 경쟁을 DB 고유 제약 등으로 제어해야 한다. 'SELECT로 없음을 확인했으니 안전'만으로는 두 요청이 동시에 통과할 수 있다.

**선행 그래프 손풀이:** r1(A),w2(A),r2(B),w1(B)에서 A는 T1→T2, B는 T2→T1이다. 사이클이므로 충돌 직렬 가능하지 않다. 두 거래를 잠금으로 막는 과정에서 교착 상태가 발생하는 것과 이미 관찰한 스케줄의 직렬 가능성은 다른 질문이다.

완료 기준: 격리 수준, 커밋 불확실성, 재시도 중복, 교착 취소를 각각 한 문장으로 설명하고 애플리케이션의 재시도 경계를 전체 거래 단위로 정한다.
