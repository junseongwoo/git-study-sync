# 07-04 라우팅·IP 단편화·ICMP·DHCP·NAT: 다른 망으로 이동하기

[[GI-교재07 네트워크|과목 목차]] · [[GI-문제07 네트워크|문제]] · [[GI-해설07 네트워크|해설]]

## 학습 목표
라우팅 테이블에서 최장 프리픽스로 다음 홉을 고른다. IPv4 단편화의 offset 단위를 계산한다. ICMP·DHCP·NAT가 TCP의 신뢰성과 다른 문제를 해결함을 이해한다.

## 1. 라우팅과 포워딩
라우팅은 경로 정보를 만드는 과정이고 포 워딩은 도착한 패킷을 테이블에 따라 다음 인터페이스로 보내는 동작이다. 정적 경로와 동적 라우팅 프로토콜로 테이블을 구성할 수 있다. 라우터는 목적지 IP에 맞는 가장 긴 프리픽스 경로를 우선 선택한다. 같은 프리픽스에 여러 후보가 있는 경우의 우선순위·비용 규칙은 그 다음이다.

### 손풀이 예제 10: 최장 일치
| 목적 프리픽스 | 다음 홉 |
| --- | --- |
| 0.0.0.0/0 | G0 |
| 10.0.0.0/8 | G1 |
| 10.2.0.0/16 | G2 |
| 10.2.3.0/24 | G3 |
| 10.2.3.128/25 | G4 |

목적지10.2.3.200은/8,/16,/24,/25 모두와 일치하므로 G4다. 10.2.4.7은 G2,10.5.1.1은 G1,203.0.113.2는 G0다. /0은 다른 구체적 일치가 없을 때의 기본 경로다. G0의 metric이 작다는 이유로 더 긴 일치 경로를 무시하지 않는다.

## 2. TTL과 ICMP
IPv4TTL은 라우터에서 감소하고 0이 되면 패킷을 버려 무한 순환을 제한하는 홉 기반 성질로 이해한다. 최초 TTL이 반드시 모든 운영 체제에서 같은 값인 것은 아니다. ICMP는 오류·진단 정보 전달에 사용되며 TCP·UDP 포트 통신과 동일한 계층 서비스가 아니다.

ping은 보통 ICMP Echo를 사용한다. ping이 실패해도 ICMP 정책만 차단되었을 수 있어 HTTP 서비스가 반드시 죽었다고 결론 내리지 않는다. traceroute는 TTL 등을 단계적으로 바꾸고 중간 오류 응답을 이용하여 경로를 추정하는 도구다. 구현에 따라 UDP·ICMP·TCP를 사용할 수 있다. 라우터가 항상 진단 응답을 주는 것은 아니다.

## 3. IPv4 단편화
링크 MTU보다 큰 IPv4 패킷은 DF 등 조건에 따라 단편화될 수 있다. 각 조각의 offset은 원래 IPpayload에서의 시작 위치를 8바이트 단위로 표현한다. 마지막이 아닌 조각 payload는 8의 배수가 되어야한다. 각 조각에 IP 헤더가 붙는다. TCP 세그먼트 분할과 IP 단편화는 다른 계층이다.

### 손풀이 예제 11: payload4000·MTU1500
IPv4 헤더 20바이트, 옵션 없음, 단편화 허용이다. 최대 조각 payload1480은 8의 배수다. payload를 1480,1480,1040으로 나누고 각 조각 전체 길이는 1500,1500,1060이다. offset은 0,1480/8=185,2960/8=370이다. MF는 1,1,0이다. 합계 payload4000 을 검산한다. offset을 바이트 값 1480이라고 그대로 쓰면 틀린다.

IPv6 라우터는 일반적으로 전달 중 단편화하지 않는다. 출발지에서 PathMTU 등 정보에 따라 크기를 조정하고 필요하면 출발지가 fragmentheader로 분할한다. IPv4 동작을 IPv6에 그대로 적용하지 않는다.

## 4. DHCP
DHCP는 IP 주소, 마스크, 게이트웨이,DNS 등 설정 정보를 임대하여 제공하는 대표 프로토콜이다. IPv4의 기본 신규 할당 흐름은 Discover,Offer,Request,Ack로 정리한다. 항상 모든 상황에서 네 단계가 그대로 일어나는 것은 아니다. 기존 임대 갱신은 다른 흐름이 가능하다. DHCP 주소는 영원히 고정된다는 뜻이 아니다.

DHCP는 IPv4UDP 서버 67·클라이언트 68을 기본 식별로 쓴다. 아직 주소가 없는 초기 흐름에서 브로드캐스트를 이용할 수 있다. 다른 서브넷 DHCP 서버와 연결하려면 relay 등 설계가 필요할 수 있다. DHCP가 DNS 이름을 모두 직접 해결하는 서비스라는 설명은 틀리다.

## 5. NAT와 포트 변환
NAT는 주소를 변환하고 NAPT/PAT는 포트 정보도 함께 이용하여 여러 내부 연결을 공유 공인 주소에 매핑할 수 있다. 사설 IP와 공인 IP는 서로 다른 범위에서 사용된다. 같은 외부 서버에 여러 내부 클라이언트가 접속하면 변환 포트 등으로 연결을 구별한다.

### 손풀이 예제 12: 두 연결
내부10.0.0.2:50000과10.0.0.3:50000 이 같은 외부203.0.113.20:443으로 TCP 접속한다. NAT의 공인 측 주소가198.51.100.10이고 각각 공인 포트 40001,40002 로 매핑하면 반환 패킷의 목적지 포트로 내부 대상을 구분할 수 있다. 같은 내부 포트를 사용해도 전체 연결 끝점이 달라 별개다.

NAT가 있다는 사실만으로 모든 악성 트래픽을 자동 차단하는 것은 아니다. 상태 추적·방화벽 정책·외부 접속 허용 설정은 함께 검토한다. end-to-end 주소 모델 변경, 직접 외부 접속, 일부 프로토콜의 내부 주소 포함 등에 영향이 생길 수 있다. 방화벽과 NAT는 역할이 연관되어도 같은 정의가 아니다.

### 직접 풀기와 확인
목적지10.2.3.100은10.2.3.128/25에 포함되지 않으므로 G3다. 100과 200이 모두10.2.3.x라는 이유로 G4를 고르면/25 호스트 범위를 놓친 것이다.

완료: 최장 일치·단편 payload/offset·DHCP 흐름·NAT 연결 매 핑을 독립 작성한다. 참고: [IPv4 RFC791](https://www.rfc-editor.org/rfc/rfc791.html), [IPv6 RFC8200](https://www.rfc-editor.org/rfc/rfc8200.html), [DHCP RFC2131](https://www.rfc-editor.org/rfc/rfc2131.html), [NAT RFC3022](https://www.rfc-editor.org/rfc/rfc3022.html). 경로와 연결 수치는 자체 예제다.

## 강화 손풀이: IPv4 단편의 8바이트 단위를 확인한다
IPv4 데이터1300바이트,각 단편 헤더20바이트,다음 링크 MTU600바이트,옵션 없음,DF=0이다. 마지막이 아닌 단편 데이터는8의 배수여야 하므로 floor((600-20)/8)×8=576바이트다.

| 단편 | 데이터 | 전체 길이 | Offset(8바이트 단위) | MF |
| --- | ---: | ---: | ---: | ---: |
| 1 | 576 | 596 | 0 | 1 |
| 2 | 576 | 596 | 72 | 1 |
| 3 | 148 | 168 | 144 | 0 |

데이터 합576+576+148=1300으로 검산한다. 헤더를 단편마다 새로 붙이며 마지막148은8의 배수일 필요가 없다. Offset을 바이트576·1152로 그대로 적으면 틀린다.

**IPv6 비교:** IPv6 라우터는 전달 도중 같은 방식으로 단편화하지 않는다. 송신 측은 경로 MTU와 오류 정보를 고려한다. IP 계층 보장,ICMP 오류 전달,방화벽 정책을 각각 점검한다. 'IPv4에서 가능한 동작이 모든 IP 버전에서 같다'는 일반화는 피한다.
