# 04-05 교착상태·기아·Banker: 자원 대기를 표로 분석하기

[[GI-교재04 운영체제|과목 목차]] · [[GI-문제04 운영체제|문제]] · [[GI-해설04 운영체제|해설]]

## 학습 목표
교착 상태와 기아를 구분하고 네 필요 조건을 사례에 대응시킨다. 안전 상태와 현재 교착 상태를 같은 뜻으로 취급하지 않는다. Banker 계산은 자원 개 수의 벡터 비교로 수행한다.

## 1. 교착 상태 네 필요 조건
상호 배제는 한 자원을 동시에 여러 흐름이 사용할 수 없는 조건이다. 점유·대기는 가진 자원을 유지하면서 추가 자원을 기다린다. 비선점은 사용 중 자원을 임의로 빼앗을 수 없다. 순환 대기는 대기 관계가 원을 이루는 조건이다. 네 조건이 모두 성립해야 교착 상태가 가능하다. 하나를 막으면 해당 모델에서 교착 상태를 예방할 수 있다.

### 손풀이 예제 13: 잠금 두 개
T1이 L1을 획득하고 L2를 기다린다. T2는 L2를 획득하고 L1을 기다린다. 잠금은 한 흐름만 보유하고, 보유 중 다른 잠금을 기다리며, 강제로 해제하지 않고, T1->T2->T1 순환이 생겼다. 모든 흐름이 L1 다음 L2 순으로 획득하도록 정하면 이 두 잠금의 역순 순환을 막을 수 있다. 같은 순서만 정하면 모든 종류의 시스템 교착을 자동 해결한다는 뜻은 아니다. 다른 자원과 예외 경로도 포함해야 한다.

## 2. 자원 할당 그래프
프로세스->자원 간선은 요청, 자원->프로세스는 할당으로 표현한다. 각 자원이 단일 인스턴스이면 순환은 교착 상태 판단의 필요 충분 조건이 된다. 여러 인스턴스가 있으면 순환만으로 교착이라고 단정할 수 없다. 추가 사용 가능 인스턴스나 완료 가능한 프로세스가 순환을 해소할 수 있기 때문이다.

기아는 어떤 작업이 계속 선택에서 밀려 오래 진행하지 못하는 상태다. 다른 작업은 진행할 수 있다. 교착 상태는 관련 흐름들이 서로의 자원 해제를 기다려 진행하지 못한다. 무한 반복 연산으로 CPU를 쓰며 상태만 바꾸는 라이브 락도 별도 개념이다. '오래 기다린다' 한 문장만으로 원인을 확정하지 않는다.

## 3. 예방·회피·탐지·복구
예방은 필요 조건 하나를 구조적으로 제한한다. 자원을 전부 한 번에 요청하면 점유·대기를 줄일 수 있지만 활용률과 기아 문제가 생길 수 있다. 자원 순서를 고정하면 순환 대기를 막을 수 있다. 회피는 요청을 허용한 뒤에도 안전하게 완료할 순서가 있는지 확인한다. 탐지는 이미 발생한 대기 상태를 분석한다. 복구는 거래·프로세스 취소, 롤백, 일부 자원 회수 등을 검토한다.

이미지를 출력하는 프린터처럼 자원을 강제로 빼앗기 어려운 상황이 있어 비선점 조건 제거가 항상 쉬운 것은 아니다. 데이터가 중간 상태인 프로세스를 종료하면 복구 비용도 생긴다. 정책의 이름만 외우지 말고 적용 가능성을 본다.

## 4. Banker의 벡터
Available은 현재 사용 가능한 개수, Allocation은 각 프로세스에 할당한 개수, Max는 미리 선언한 최대 요구, Need =Max-Allocation이다. Work를 Available로 두고 Need<=Work인 아직 미완료 프로세스를 골라 완료 가능하다고 가정한다. 완료 후 Work에 해당 Allocation을 돌려 더 한다. 모든 프로세스를 선택할 수 있으면 안전 상태다. 실제로 지금 실행하거나 반드시 그 순서로 스케줄링한다는 뜻은 아니다.

### 손풀이 예제 14: 안전 순서
자원 A,B 두 종류이며 Available =(1,1)이다.

| 프로세스 | Allocation(A,B) | Max(A,B) | Need(A,B) |
| --- | --- | --- | --- |
| P0 | (1,0) | (2,1) | (1,1) |
| P1 | (0,1) | (1,2) | (1,1) |
| P2 | (1,1) | (3,2) | (2,1) |

Work =(1,1)에서 P0 완료 가능 -> Work =(2,1). P1 완료 가능 -> Work =(2,2). P2 완료 가능 -> Work =(3,3). 따라서 P0,P1,P2가 한 안전 순서다. P1부터 시작하는 다른 안전 순서도 가능하다. 안전 순서가 반드시 하나일 필요는 없다.

### 손풀이 예제 15: 개수가 남아 있어도 위험한 요청
P2가 (1,0)을 추가 요청한다. Request<=Need이고 Request<=Available이라 단순 개수 검사는 통과한다. 임시 할당하면 Available =(0,1), P2 Allocation =(2,1), Need =(1,1)이다. P0·P1·P2 모두 A 하나가 더 필요하지만 Work의 A가 0이므로 완료 후보가 없다. 따라서 unsafe라 요청을 즉시 허용하지 않는다.

반면 P0가 (1,0)을 요청하면 Available =(0,1), P0 Need =(0,1)이 되어 P0를 완료할 수 있다. 완료 후 P0 Allocation =(2,0)을 반환하여 Work =(2,1)이 된다. 이후 P1,P2도 완료 가능하므로 안전하다. 두 요청이 같은 벡터라도 누가 받는지에 따라 안전성이 다르다.

## 5. 안전하지 않음과 현재 교착은 다르다
Unsafe는 선언된 최대 요구까지 고려할 때 모두 완료할 안전 순서를 보장하지 못한다는 뜻이다. 프로세스가 실제로 최대까지 요청하지 않고 일찍 끝나면 교착이 안 생길 수도 있다. 교착 상태는 현재 요청과 대기 때문에 실제 진행이 막힌 상태다. 'unsafe -> 이미 교착'이라는 오답을 피한다.

Banker는 최대 요구를 미리 알 수 있어야하고 자원 개수·프로세스 상태를 관리해야 한다. 일반 운영 체제에서 모든 자원에 이 알고리즘을 그대로 적용한다고 가정하지 않는다. 시험 계산 모델과 실제 운영 정책은 구분한다.

### 직접 풀기와 확인
위 초기 표에서 P2를 가장 먼저 완료할 수 있는가? Need(2,1)가 Work(1,1)보다 A에서 커서 불가능하다. B가 충분하다는 이유만으로 두 벡터 합계 2와 3만 비교하면 틀린다. 자원 종류별 성분을 각각 비교한다.

완료: 네 조건을 사례에 표시하고 Need 표·Work 갱신을 독립 계산한다. 참고: [OSTEP 동시성 오류](https://pages.cs.wisc.edu/~remzi/OSTEP/threads-bugs.pdf). Banker 자원 표는 자체 제작이며 안전성 계산의 가정을 본문에 명시했다.

## 강화 손풀이: 안전하지 않음은 지금 교착이라는 뜻이 아니다
단일 자원 종류의 총량은 10이다. P1 할당 3·최대 9,P2 할당 3·최대 6이면 가용 4,Need는 6,3이다. P2를 완료한다고 가정하면 Work=4+3=7이 되고 P1의 Need 6도 만족하여 안전 순서 P2→P1이 있다.

P1이 2를 추가 요청해 잠정 할당하면 가용 2,할당 5·3,Need 4·3이다. 어떤 프로세스의 Need도 Work 2 이하가 아니므로 안전 순서를 찾지 못한다. 요청이 가용 이하라는 조건만으로 승인하면 안 된다.

**반례:** 위 상태가 안전하지 않다는 이유만으로 지금 두 프로세스가 실제 필요한 요청을 내고 서로 기다리는 교착 상태라고 단정할 수는 없다. Banker의 최대 수요 모델 아래 미래 요청 전체를 만족시킬 완료 순서를 보장하지 못한다는 뜻이다. 실제 요청이 최대보다 작거나 자원을 먼저 반납하면 진행 가능할 수 있다.

락 순서를 통일하면 순환 대기 예방에 도움이 되지만,스케줄링 불공정으로 특정 작업이 오래 기다리는 기아까지 자동 제거하는 것은 아니다. 어떤 자원 모델과 진행 가정을 쓰는지 명시한다.
