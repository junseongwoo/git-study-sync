# 05-03 설계·아키텍처: 응집도와 결합도로 변경 비용 줄이기

[[GI-교재05 소프트웨어공학|과목 목차]] · [[GI-문제05 소프트웨어공학|문제]] · [[GI-해설05 소프트웨어공학|해설]]

### 설계가 해결하는 문제
요구사항이 무엇을 해야 하는지를 정했다면 설계는 책임을 어느 구성요소에 배치하고 어떻게 연결할지를 정한다. 모든 코드를 한 클래스에 넣으면 처음에는 쉽지만, 화면 변경이 데이터 저장과 장비 통신에 영향을 주기 시작한다. 아키텍처는 큰 구성요소와 관계, 중요한 품질 제약을 다룬다. 상세 설계는 클래스·함수·자료구조와 같은 내부 구조를 구체화한다.

### 응집도
응집도는 한 모듈 내부 요소가 같은 목적을 위해 얼마나 관련되어 있는가다. 일반적인 기초 교재에서는 우연적·논리적·시간적·절차적·통신적·순차적·기능적 응집도를 구별한다. 기능적 응집은 하나의 명확한 기능을 수행하는 요소들이 모인 경우다. 순차적 응집에서는 앞 단계의 출력이 다음 단계의 입력이 된다. 통신적 응집은 같은 데이터에 접근하는 처리들이 묶인 경우다. 시간적 응집은 초기화나 종료처럼 비슷한 시점에 실행된다는 이유로 묶인 경우다.

분류는 구체적인 구성에 따라 달라지므로 "Initialize"라는 이름만 보고 시간적 응집이라고 확정할 수 없다. 함수가 오직 한 장비의 연결 초기화만 책임진다면 기능적 응집으로 설명할 여지도 있다. 시험에서는 제시된 내부 책임을 본다.

### 결합도
결합도는 모듈 사이의 의존 정도다. 내용 결합은 다른 모듈의 내부 구현에 직접 의존하는 경우다. 공통 결합은 전역 데이터 공유와 관련된다. 제어 결합은 제어 플래그를 전달해 상대의 처리 방향을 결정하게 하는 경우다. 스탬프 결합은 필요 이상의 복합 자료구조를 통째로 전달하는 경우다. 자료 결합은 필요한 단순 데이터만 주고받는 경우를 설명한다.

고전적인 시험에서는 일반적으로 낮은 결합도와 높은 응집도를 바람직한 방향으로 본다. 다만 "모든 의존성이 0이어야 한다"는 뜻은 아니다. 시스템은 협력해야 하므로 공개 인터페이스를 통해 꼭 필요한 관계를 유지한다. 언어·프레임워크의 상세한 결합 분류에는 다른 체계도 있다.

### 계층·MVC·의존성 역전
계층 구조는 역할에 따라 표현·업무·데이터 접근 등을 나눈다. MVC는 Model·View·Controller의 책임을 나누는 패턴이다. Model은 단순히 DB 테이블과 같은 뜻이 아니라 업무 데이터와 동작을 포함할 수 있다. View는 표시, Controller는 입력을 받아 흐름을 조정한다.

단일 책임 원칙은 클래스가 변경될 이유를 좁히라는 관점이다. 개방·폐쇄 원칙은 안정된 부분을 직접 계속 수정하기보다 확장 지점을 통해 새 동작을 넣도록 설계하는 관점이다. 의존성 역전은 상위 정책과 하위 세부 구현을 적절한 추상화에 의존하게 한다. 의존성 주입은 객체가 필요한 의존 대상을 외부에서 받는 구현 기법이다. 두 용어는 관련되지만 같은 정의는 아니다.

### 단계별 예제: 한 화면에 묶인 검사 시스템
ReviewWindow가 이미지 표시·판정 규칙·SQL 저장·장비 연결을 모두 수행한다. 새 DB를 도입할 때 화면 클래스를 고쳐야 하고, 테스트에는 실제 장비 연결이 필요하다. 먼저 ImageRepository라는 인터페이스로 조회·저장을 표현한다. ReviewService는 업무 흐름을 담당하고, 화면은 표시와 사용자 입력만 다룬다. 장비 연결은 별도 Adapter로 감싼다.

이제 업무 테스트에서는 메모리 저장소를 넣어 판정 흐름을 확인할 수 있다. 구현 파일 수가 늘었다고 자동으로 좋은 설계가 되는 것은 아니다. 경계가 실제 변경 원인과 맞고 테스트·교체를 돕는지 확인해야 한다. 지나친 추상화도 읽기와 운영 비용을 만든다.

### 자가 연습과 풀이
함수 Process(Customer customer)는 고객 이름만 화면에 출력한다. 이름만 인자로 받도록 바꾸면 어떤 결합을 낮추는가? 필요한 정보보다 큰 구조를 전달하던 스탬프 결합을 줄이고 자료 결합 방향으로 개선한다. 반대로 "mode=1이면 저장, mode=2이면 삭제" 플래그가 상대의 동작을 결정한다면 제어 결합의 전형적인 사례다.

### 완료 기준
높은 응집도·낮은 결합도를 정의하고, 전역 변수 공유·제어 플래그·복합 구조 전달을 서로 구분할 수 있어야 한다. C# 클래스 하나를 골라 책임을 나눌 이유와 나누지 않을 이유를 각각 설명해보자.

### 응용 문제: 결합도를 낮췄는데도 변경이 어려운 이유
인터페이스를 만들었지만 Save(object data,int mode) 하나로 모든 작업을 처리하면 호출자는 자료 타입과 mode 규칙을 여전히 알아야 한다. 추상화의 이름만으로 책임과 계약이 명확해지지는 않는다. SaveApplication과 DeleteApplication처럼 목적이 다른 동작을 적절하게 드러내고 필요한 자료만 전달하는 선택을 검토한다.

고전적 기초 시험에서는 내용·공통·제어·스탬프·자료 결합의 강한/약한 방향을 묻는 경우가 있다. 본 교재가 설명한 체계에서는 내부 침범·전역 공유를 강한 의존으로, 필요한 자료만 전달하는 것을 더 약한 의존으로 본다. 외부 결합·메시지 결합 등 다른 항목이 추가된 문제에서는 해당 교재의 정의를 확인한다. 모든 목록의 순서를 혼합해 하나의 절대 순위로 만들지 않는다.

### 강화 설계 추적: 경계를 나눠도 공유 상태는 남는다
ReviewService가 저장소 인터페이스를 받고 두 테스트가 같은 메모리 저장소 객체를 공유한다고 하자. 테스트 1은 신청 X를 저장하고 테스트 2는 '처음에는 비어 있음'을 검사한다. 실행 순서에 따라 테스트 2가 실패한다면 인터페이스를 썼다는 사실만으로 테스트 격리가 완성된 것이 아니다.
1. 업무 규칙·저장 방식·화면 표시의 변경 이유를 분리한다.
2. 저장소의 계약을 입력·결과·실패·동시성으로 적는다.
3. 테스트마다 새 상태를 만들거나 합의한 초기화 절차를 적용한다.
4. 실제 저장소에서 트랜잭션·제약 위반·경쟁 조건도 별도로 확인한다.
가상 계약은 '같은 요청 키를 두 번 저장해도 거래는 하나, 다른 내용의 같은 키는 오류'다. 단순 메모리 대역으로 성공 경로를 검증한 결과는 실제 DB의 동시 처리까지 증명하지 않는다. 실패 뒤 재시도하는 정책은 업무 서비스에, 특정 DB의 오류 코드 해석은 어댑터에 배치할 수 있다. 모든 예외를 성공으로 바꾸는 반례는 의존성이 적어 보여도 계약을 깨뜨린다.
