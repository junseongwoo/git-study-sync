# 06-06 세션·API·안전한 개발: 인증 뒤의 공격면 점검

[[GI-교재06 정보보안|과목 목차]] · [[GI-문제06 정보보안|문제]] · [[GI-해설06 정보보안|해설]]

### 세션 식별자와 수명
세션은 여러 요청 사이에서 인증 상태 등을 이어가는 방식이다. 서버 측 세션에서는 추측하기 어려운 식별자가 서버 상태를 가리킨다. 로그인·권한 상승 뒤 식별자를 갱신하는 것은 세션 고정 공격의 위험을 줄인다. 로그아웃은 사용자 화면만 바꾸는 것이 아니라 필요한 서버 측 무효화도 수행해야 한다.

Secure는 쿠키를 안전한 전송 조건에서 보내도록 하는 속성, HttpOnly는 스크립트가 쿠키를 직접 읽지 못하게 하는 속성, SameSite는 사이트 간 전송을 제한하는 속성이다. 속성의 정확한 작동과 브라우저 정책은 최신 문서를 확인한다. 쿠키 속성은 애플리케이션의 인가 검사를 대신하지 않는다.

JWT는 형식과 서명·클레임 검증의 체계이며 "내용이 항상 암호화된 토큰"이 아니다. 서명된 일반 JWT의 payload는 읽을 수 있다. 검증 시 허용 알고리즘·서명·발급자·대상·만료 등 해당 서비스에 필요한 조건을 확인한다. 토큰을 디코딩한 것과 검증한 것은 다르다. 만료 시간을 매우 길게 하면 탈취된 토큰의 영향도 커질 수 있다.

### 객체 권한과 API
API에서 사용자 ID나 신청서 번호를 받아 처리할 때 요청자가 해당 객체에 접근할 수 있는지 검사한다. 경로가 /applications/902이고 버튼이 숨겨져 있어도 서버 측 검사가 빠지면 접근통제 문제가 남는다. 대량 요청에는 적절한 요청 제한·자원 제한·모니터링을 설계한다. 잘못된 오류 메시지로 계정 존재 여부나 내부 쿼리가 드러날 수 있다.

### 역직렬화·업로드·SSRF
신뢰할 수 없는 직렬화 입력을 임의 객체로 복원하면 예상치 못한 타입과 동작이 실행될 위험이 있다. 단순 데이터 형식, 허용 타입, 구조·크기 검증, 안전한 라이브러리를 사용하고 신뢰 경계를 분명히 한다. 모든 역직렬화가 곧 코드 실행이라는 뜻은 아니며 언어·형식·구현에 따라 위험이 다르다.

파일 업로드에서는 확장자만 보지 않고 내용·크기·저장 위치·실행 권한·이름·접근 권한을 확인한다. 경로 입력에서 ../ 등이 다른 디렉터리 접근으로 이어지는 경로 탐색도 고려한다. SSRF는 서버가 사용자 지정 주소 등에 요청하도록 유도되어 내부 자원 등에 접근하는 문제다. URL의 허용 목적지·스킴·네트워크 경계·리다이렉트 처리 등 통제가 중요하다.

### 단계별 사례: 토큰 유출
브라우저 저장소에 장기 토큰을 넣고 사이트에 XSS가 생겼다고 하자. 페이지에서 실행되는 악성 스크립트가 읽을 수 있는 저장소는 토큰 유출 위험이 있다. HttpOnly 쿠키 사용 등 구조적 선택을 검토할 수 있지만 그러면 쿠키 자동 전송에 따른 CSRF 맥락도 함께 검토한다. 저장 위치 한 가지만 고르면 모든 문제가 사라진다고 단정하지 않는다.

토큰 payload에 고객 식별값과 비밀번호를 넣고 서명만 했다고 하자. 서명은 내용 숨김을 제공하지 않으므로 민감 값을 불필요하게 넣으면 안 된다. 전송 TLS, 토큰 내용 최소화, 수명, 갱신·폐기, 서버 권한 검사를 함께 설계한다.

### 입력 검증과 인코딩 구별
입력 검증은 데이터의 타입·범위·구조·업무 규칙을 확인한다. 출력 인코딩은 데이터가 특정 실행 문맥에서 명령으로 해석되지 않도록 표현한다. 둘은 목적과 위치가 다르다. 요청 크기 10MB 제한은 자원 소모를 줄일 수 있지만 저장된 텍스트의 XSS를 해결하지 않는다.

### 자가 연습과 풀이
관리 기능 URL을 복잡하게 만들고 메뉴에서 숨겼다. 충분한가? 아니다. 인가 검사를 서버에 적용하고 필요한 역할·대상·환경 조건을 확인한다. 모호한 URL은 추측을 어렵게 할 수 있으나 권한 통제 자체가 아니다.

### 완료 기준
쿠키 3속성·세션 고정·JWT 서명/암호화 차이를 설명하고, 객체 권한·역직렬화·업로드·SSRF의 신뢰 경계를 각각 한 문장으로 말할 수 있어야 한다.

### 응용 문제: 로그아웃·만료·폐기의 차이
토큰이 사용자 기기에서 삭제되었어도 이미 복사된 토큰이 서버에서 계속 유효할 수 있다. 로그아웃의 요구에 따라 서버 세션 무효화, 토큰 수명, 갱신 토큰 폐기, 별도 폐기 목록 등을 검토한다. 구체적인 방식은 상태를 어디에 관리하는지에 달려 있다.

세션 식별자를 로그인 전과 후에 그대로 유지하는 상황은 공격자가 미리 정한 식별자로 사용자를 유도하는 세션 고정 위험과 연결될 수 있다. 로그인 후 갱신과 이전 식별자 무효화를 적용한다. 세션 탈취는 이미 유효한 식별자를 빼앗는 상황으로 개념을 구분한다. 두 공격이 동시에 가능할 수도 있다.

### 강화 API 검증표: 서명·사용 목적·현재 권한
가상 API는 토큰의 서명·허용 알고리즘·발급자·대상 서비스·만료를 검증하고, 사용자 현재 권한과 대상 자료의 소속을 확인한다. 조건 중 하나라도 실패하면 거절한다. 이는 토큰 검증과 객체 인가를 따로 생각하기 위한 연습 규약이다.
손풀이: 서명이 유효해도 대상 서비스가 다르거나 만료됐다면 거절이다. 토큰의 역할이 승인자로 적혀 있어도 서버 정책의 현재 승인 권한이 철회됐다면 승인할 수 없다. 일반 서명 JWT의 payload는 암호화된 비밀 저장소가 아니므로 비밀값을 넣고 숨겨졌다고 생각하지 않는다.
SSRF 가상 규칙은 승인된 외부 호스트만 요청하고 내부 주소·다른 호스트로의 리다이렉트는 거절한다. 처음 URL이 허용 호스트라도 응답이 내부 주소로 이동시킨다면 자동 따라가기는 이 규칙을 깨뜨린다. 리다이렉트를 비활성화하거나 매 단계의 최종 대상도 규칙대로 검증해야 한다. 이름 검사·DNS 결과·네트워크 경계는 서로 다른 확인 단계다. 화면 검증·첫 URL 검사·토큰 서명 중 하나만 맞는 사례를 전체 통과로 확대하지 않는다.
