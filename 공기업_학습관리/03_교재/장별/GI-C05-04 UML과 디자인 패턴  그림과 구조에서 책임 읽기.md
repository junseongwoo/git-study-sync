# 05-04 UML과 디자인 패턴: 그림과 구조에서 책임 읽기

[[GI-교재05 소프트웨어공학|과목 목차]] · [[GI-문제05 소프트웨어공학|문제]] · [[GI-해설05 소프트웨어공학|해설]]

### UML 그림별 질문
UML은 시스템을 설명하는 모델링 표기다. 유스케이스 다이어그램은 외부 행위자와 시스템이 제공하는 목표 중심 기능을 보여준다. 클래스 다이어그램은 클래스의 속성·연산과 관계를 보여준다. 시퀀스 다이어그램은 시간 흐름에 따른 객체 간 메시지를 보여준다. 상태 다이어그램은 한 대상의 상태와 사건에 따른 전이를 다룬다. 활동 다이어그램은 작업 흐름·분기·병렬 활동을 표현한다.

유스케이스의 include는 여러 유스케이스가 공통 동작을 재사용하는 관계를 나타낸다. extend는 정해진 확장 조건과 지점에서 기본 유스케이스에 선택적인 동작을 추가하는 관계다. 둘을 무조건 "필수/선택" 두 단어만으로 외우기보다 화살표 방향과 기본 동작의 성립 여부도 함께 본다.

### 클래스 관계와 다중성
일반화는 부모·자식 관계이며 자식이 부모의 특성을 물려받는다. 실체화는 인터페이스의 계약을 구현하는 관계를 표현할 때 쓰인다. 연관은 객체들이 관계를 맺는 것이고, 의존은 한 요소가 다른 요소의 변경에 영향을 받을 수 있음을 나타낸다. 집합은 전체·부분의 관계를 약하게 표현하며, 합성은 부분의 소유와 생명주기 결합이 더 강한 형태다.

합성에서 부분은 한 번에 하나의 합성 소유자에 포함된다는 의미가 중요하다. "DB에서 부모 행을 지우면 항상 물리적으로 자식 행을 즉시 삭제한다" 같은 특정 구현 규칙과 동일시하지 않는다. 다중성 0..1은 없거나 하나, 1은 정확히 하나, 0..*는 0개 이상, 1..*는 1개 이상이다.

### 패턴이 풀어주는 문제
Strategy는 같은 목적의 알고리즘을 교체 가능하게 분리한다. Observer는 상태 변화 알림을 구독 객체들에 전달하는 구조다. Adapter는 기존 인터페이스를 사용자가 기대하는 형태로 변환한다. Factory 계열은 객체 생성 결정을 분리한다. Decorator는 객체를 감싸 인터페이스를 유지하면서 책임을 덧붙인다. Facade는 복잡한 하위 시스템에 단순한 진입점을 제공한다.

Singleton은 인스턴스를 제한하는 문제와 관련되지만 전역 상태·동시성·테스트 격리 문제를 만들 수 있다. 따라서 "항상 가장 좋은 패턴"이라는 표현은 피한다. 패턴 문제는 이름을 맞히는 것보다 요구하는 변화가 알고리즘 교체인지, 인터페이스 변환인지, 알림 전파인지부터 판단하면 풀기 쉽다.

### 단계별 예제: 판정 알고리즘의 교체
검사 프로그램에 기본 판정, 고객사 A 판정, 고객사 B 판정이 있다. if문을 화면 곳곳에 추가하면 수정 지점을 빠뜨리기 쉽다. JudgeStrategy의 Evaluate를 정의하고 각 판정 규칙을 별도 구현한다. ReviewService는 선택된 전략을 호출한다. 이것은 Strategy다. 판정 결과가 바뀌었을 때 화면·기록 모듈에 알리는 것은 Observer의 문제다. 장비 회사의 낡은 API 이름을 프로그램 내부의 통일된 인터페이스로 감싸는 것은 Adapter의 문제다. 같은 프로젝트에서 여러 패턴이 다른 목적에 사용될 수 있다.

### 숫자·상태 예제
Application 한 개에는 Attachment가 0..* 연결되고, 각 Attachment는 정확히 하나의 Application에 속한다. 신청서 3개에 첨부가 각각 0, 2, 4개 있다면 총 첨부는 6개이며 "모든 신청서에 최소 1개가 필요하다"는 제약은 없다. 다중성 기호가 1..*였다면 첨부 0개인 첫 신청서는 제약 위반이다.

상태가 작성중→제출완료→심사중→완료이고 취소는 작성중·제출완료에서만 가능하다고 하자. 심사중에서 취소 버튼이 표시되지 않는지 확인하는 것은 상태 기반 테스트와 연결된다. 가능한 상태 이름만 외우지 말고 어떤 사건이 어느 전이를 허용하는지 그려보자.

### 자가 연습과 풀이
압축 방식만 교체하려면 Strategy, 구형 통신 라이브러리의 인터페이스를 바꾸지 않고 연결하려면 Adapter가 우선적인 후보다. 두 경우 모두 클래스를 사용한다는 공통점만으로 같은 패턴이라고 볼 수 없다.

### 완료 기준
다이어그램 5종의 목적을 구별하고 다중성 4개를 읽으며, Strategy·Observer·Adapter를 자신의 장비 프로그램 예로 설명할 수 있으면 된다.

### 응용 문제: 생성과 기능 추가의 구분
객체의 생성 방식을 하위 타입에 맡기는 Factory Method와 관련 객체군을 함께 생성하는 Abstract Factory는 모두 생성 문제를 다룬다. 기존 객체에 로깅·압축 같은 책임을 감싸서 추가하는 Decorator는 생성만의 문제가 아니다. Adapter는 상대가 기대하는 인터페이스로 변환하는 목적이다.

이미지 저장기에 압축 책임을 덧붙이면서 저장 인터페이스를 유지하면 Decorator가 후보이며, 구형 SaveToDisk를 내부의 Store 인터페이스로 맞추면 Adapter가 후보가 된다. 결과적으로 감싸는 코드가 있다는 점만으로 같은 패턴이라고 단정하지 않는다. 디자인 패턴 문제의 정답은 요구하는 변화와 책임 배치에서 찾는다.

### 강화 손풀이: 상태 전이의 허용·거절을 따로 확인
가상 상태는 작성 D, 제출 S, 심사 R, 취소 C, 완료 F다. 허용 전이는 D→S, D→C, S→R, S→C, R→S, R→F의 6개뿐이며 C·F는 종료 상태다. 허용 목록에 없는 전이는 거절하고 상태를 유지한다.
시험 경로 D→S→R→S→C는 허용 전이 4개를 방문한다. R→S를 거친 뒤 S→C는 허용되지만 R에서 바로 C로 가는 것은 금지다. 허용 전이 방문률은 4/6이다. 별도로 D→C와 D→S→R→F를 추가하면 허용 전이 6개를 모두 방문한다.
전이 커버리지 100%여도 금지 요청 R→C·F→S를 실제로 거절하는지 확인하지 않았다면 결함이 남을 수 있다. UML 상태 모델은 무엇이 허용되는지의 계약이고 구현 시험은 그 계약의 준수 여부다. 모델에 없는 동작을 화면에서 숨기는 것만으로 서버가 거절한다고 결론내리지 않는다. 관찰 가능한 상태 유지·오류 결과도 확인한다.
