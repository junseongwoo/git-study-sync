# 07-06 DNS·이름 해석·캐시: 도메인이 IP가 되는 흐름

[[GI-교재07 네트워크|과목 목차]] · [[GI-문제07 네트워크|문제]] · [[GI-해설07 네트워크|해설]]

## 학습 목표
DNS질의 흐름과 캐시·TTL을 이해한다. DNS에서 이름을 찾는 단계와 해당 IP의 서비스에 실제 접속하는 단계를 구분한다. DNS가 UDP만 쓴다는 오답을 교정한다.

## 1. 이름과 레코드
DNS는 이름 공간을 분산하여 관리하는 시스템이다. A 레코드는 IPv4 주소,AAAA는 IPv6 주소,CNAME은 별명 대상 이름,MX는 메일 관련 교환 서버,NS는 권한 네임 서버,PTR은 역 방향 이름 매핑에 쓰이는 대표 유형이다. TXT는 문자열 정보로 다양한 정책에 사용된다. CNAME이 IP 주소 자체라는 설명은 틀리다.

도메인의 점 구조는 계층을 표현한다. example.com과 api.example.com이 언제나 같은 IP라는 규칙은 없다. 하나의 이름에 여러 주소가 있거나 부하분산·지리·시간에 따라 답이 달라질 수 있다. DNS 답을 받았다는 사실만으로 응용 서비스가 정상이라는 뜻도 아니다.

## 2. 재귀와 반복 질의
단말의 stub resolver는 보통 설정된 재귀 resolver에 최종 답을 요청한다. 재귀 resolver는 캐시를 사용하거나 root,TLD, 권한 서버 등에 필요한 질의를 하여 답을 구한다. 반복 질의에서는 서버가 최종 답 또는 다음 참조 정보를 줄 수 있다. 모든 조회가 반드시 root부터 시작하는 것은 아니다. 캐시가 있으면 단계를 줄인다.

### 손풀이 예제 17: 캐시가 없는 기본 흐름
사용자가 api.example.com을 조회한다. 단말->재귀 resolver, resolver->root에서 com 참조, resolver->com 서버에서 example.com 권한 서버 참조, resolver->권한 서버에서 A 답을 얻어 단말에 전달하는 간단 흐름이다. 별명·추가 참조·DNSSEC·캐시가 있으면 흐름이 더 복잡하거나 짧아진다. 서버의 역할과 질의 종류를 따로 표시한다.

## 3. TTL과 음성 캐시
TTL은 캐시가 답을 사용할 수 있는 시간의 제한을 나타내는 대표 필드다. 권한 서버 주소를 바꿨다고 전 세계 캐시가 즉시 동일한 새 답으로 바뀌는 것은 아니다. 음성 캐시는 이름 없음 등의 응답도 일정 기간 저장하는 개념이다. 잘못된 설정을 고친 뒤에도 잠시 이전 실패가 보일 수 있다.

### 손풀이 예제 18: 남은 TTL
t =0에 TTL300 초인답을캐시에 저장하고 시간 경과만 고려한다. t =120에 남은 시간 180초다. t =200 에권한서버IP가 변해도 캐시된 답은 원래 유효 범위 안에서 계속 사용할 수 있다. 설정·재검증 정책에 따라 실제 동작은 다를 수 있지만'권한 수정 =모든 캐시 즉시 갱신'은 틀리다. TTL이 최초 저장 시점과 질의마다 무조건 다시 300으로 리셋된다고 가정하지 않는다.

## 4. UDP·TCP·암호화 DNS
기본 DNS는 UDP와 TCP의 53 포트를 사용한다. 큰 응답·잘림·zone transfer 등 조건에 따라 TCP가 필요할 수 있다. EDNS 확장도 있다. 'UDP53만 열면 어떤 DNS도 문제 없다'는 일반 명제는 틀리다.

DoT는 TLS 위 DNS,DoH는 HTTPS 위 DNS다. 이들은 질의 경로의 암호화를 제공하지만 resolver가 받는 정보와 신뢰 관계는 남는다. DNSSEC는 DNS 데이터의 검증과 관련되며 질의 내용 자체를 암호화하는 프로토콜과 같지 않다. 프라이버시·무결성·이름 관리자 신뢰를 구분한다.

## 5. 이름 해석 장애와 서비스 장애
도메인 질의가 실패하면 DNS 설정·서버 응답·이름·권한 레코드·캐시를 본다. IP 접속은 되는데 이름만 실패하면 이름 해석 경로의 가설이 강해진다. 그러나 HTTPS는 IP만 직접 접속하면 인증서 호스트 명·SNI·가상 호스트 조건이 달라질 수 있어 동일한 서비스 시험이라고 단정하지 않는다.

DNS가 정상인 뒤 TCP 연결 거절·TLS 오류·HTTP 오류가 발생하면 다음 계층을 조사한다. 모호한'네트워크 안 됨'을 단계별 관찰로 좁힌다. 요청 시간·사용한 resolver·반환주소·TTL·연결 끝점 등을 기록하면 캐시 및 다중경로 문제를 추적하기 쉽다.

### 직접 풀기와 확인
CNAME api.example.com->service.example.net,A service.example.net->203.0.113.20이라면 CNAME 답 값은 service.example.net이라는 이름이다. 최종 IP를 얻으려면 해당 이름의 주소 정보가 필요하다. 별명 답과 주소 답을 한 형식으로 외우지 않는다.

완료: DNS4 역할과 대표 레코드,TTL,UDP/TCP, 암호화와 검증을 설명한다. 참고: [DNS RFC1035](https://www.rfc-editor.org/rfc/rfc1035.html), [DNS TCP RFC7766](https://www.rfc-editor.org/rfc/rfc7766.html), [DoH RFC8484](https://www.rfc-editor.org/rfc/rfc8484.html), [DNS 음성캐시 RFC2308](https://www.rfc-editor.org/rfc/rfc2308.html). example.com·example.net과 문서용 주소는 예제다.

## 강화 시간 추적: DNS 캐시 TTL은 조회할 때마다 원래 값으로 재설정하지 않는다
한 재귀 캐시가 t=0에 TTL60초의 레코드를 저장했다. 별도 재검증·갱신·prefetch가 없고 로컬 시계가 정상이라고 가정한다. t=20의 캐시 응답은 남은 TTL40초이며 t=59에는1초다. 캐시를 읽었다는 이유로 만료가 t=80으로 연장되지는 않는다. 실제 캐시의 최소/최대 TTL 정책은 별도 계약이다.

**오류 비교:** 이름 자체가 없음을 뜻하는 NXDOMAIN과 이름은 존재하나 질의한 레코드 종류에 답이 없는 NODATA는 다르다. 둘 모두 무조건 네트워크 연결 실패나 대상 서버 장애를 뜻하지 않는다. 음성 캐시의 근거·기간은 SOA 등 DNS 규칙을 따른다.

권한 서버에 새 주소가 설정되어도 기존 캐시에 남은 과거 응답이 즉시 전부 사라지는 것은 아니다. 따라서 서비스 이전은 TTL·권한 설정·캐시 상태·애플리케이션의 별도 캐시를 함께 확인한다. DNS 성공은 그 IP로 TCP 연결·TLS 인증·HTTP 업무 처리가 성공했다는 보장이 아니다.
