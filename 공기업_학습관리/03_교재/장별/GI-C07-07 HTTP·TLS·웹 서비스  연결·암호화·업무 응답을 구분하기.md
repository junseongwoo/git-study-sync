# 07-07 HTTP·TLS·웹 서비스: 연결·암호화·업무 응답을 구분하기

[[GI-교재07 네트워크|과목 목차]] · [[GI-문제07 네트워크|문제]] · [[GI-해설07 네트워크|해설]]

## 학습 목표
URL을 분해하고 HTTP 메서드·상태·쿠키를 이해한다. TLS 인증서가 무엇을 검증하며 무엇까지 보장하지 않는지 설명한다. HTTP 버전별 전송과 멀티플렉싱을 기초 수준에서 구분한다.

## 1. URL과 요청
`https://api.example.com:8443/v1/items?limit=10`에 서 scheme은 https,host는 api.example.com,port는 8443,path는/v1/items,query는 limit =10이다. https 기본 포트는 443이지만 명 시 포트 8443도 가능하다. URL fragment는 일반적으로 클라이언트 측 참조에 사용하며 HTTP 요청 대상에 그대로 보내는 경로 부분과 구분한다.

HTTP 요청은 메서드, 대상, 헤더, 선택적 본문 등으로 의미를 표현한다. HTTPS는 HTTP를 TLS 보안 채널 위에서 사용하는 방식이다. 포트 443으로 TCP 연결됐다는 사실만으로 TLS가 완료되거나 로그인이 성공했다는 뜻은 아니다.

## 2. 메서드의 안전성과 멱등성
안전한 메서드는 요청의 의도상 서버 상태 변경을 요구하지 않는다. 로그 기록 등 부수 효과가 절대 없다는 뜻은 아니다. 멱등은 같은 요청을 여러 번 적용한 의도된 서버 효과가 한 번과 같다는 성질이다. 매번 응답 코드가 완전히 같아야한다는 뜻은 아니다.

GET은 대표적으로 안전·멱등,PUT·DELETE는 멱등 의미로 정의되지만 상태를 바꿀 수 있어 안전한 메서드는 아니다. POST는 일반적으로 멱등을 보장하지 않는다. 애플리케이션에서 거래 ID·멱등키를 설계하면 일부 요청의 재시도를 안전하게 만들 수 있다. HTTP 동작을 의미에 맞지 않게 구현한 서버도 존재하므로 규격과 실제 구현을 분리한다.

### 손풀이 예제 19: DELETE 재시도
첫 DELETE로 객체가 제거되어 204, 같은 DELETE 재시도로 404를 받았다고 하자. 두 번 후에도 객체가 없다는 의도된 효과는 한 번 후와 같다. 응답 코드 차이만으로 멱등이 아니라고 판정하지 않는다. 반면 POST 송금 요청을 그대로 두 번 적용하면 업무가 두 번 일어날 수 있어 별도의 중복 방지가 필요하다.

## 3. 상태 코드와 인증
2xx는 성공,3xx 는리디렉션 관련,4xx는 클라이언트 요청 관련,5xx는 서버 측 처리 관련 분류다. 401은 인증 관련 도전,403은 접근 거부,404는 자원 없음,405 는 메서드 불허를 대표 기초로 본다. 502는 게이트웨이가 잘못된 상위 응답을 받은 경우,503은 일시적 서비스 불가,504는 게이트웨이 타임 아웃이다. 단순 숫자 암기보다 어느 처리 단계가 답을 냈는지 파악한다.

HTTP는 기본적으로 상태 없는 요청/ 응답 의미를 갖지만 쿠키·서버 세션·토큰 등으로 사용자 상태를 관리할 수 있다. stateless가 어떤 서버 상태도 저장할 수 없다는 뜻은 아니다. 쿠키는 자동 전송 조건·Secure·HttpOnly·SameSite 등 설정이 보안에 영향을 준다. 쿠키 그 자체와 서버 세션 객체는 동일하지 않다.

## 4. TLS가 하는 일
TLS는 도청·변조·위조에 대응하도록 보안 채널을 설계한다. 대표적 서버 인증에서는 인증서 체인·신뢰 기반·유효 기간·호스트명 등을 검사한다. 키합의·인증 단계와 실제 데이터의 대칭 AEAD 암호화를 구분한다. 단순 해시만 사용한다고 데이터가 암호화되는 것은 아니다.

### 손풀이 예제 20: 인증서 호스트명
요청 host 가 api.example.com인데 인증서가 only-other.example.net만 포함하면 정상 신뢰 서명과 기간이 있어도 호스트명 검증에서 문제가 된다. 검증을 끄면 접속이 될 수 있다는 이유로 올바른 해결이라고 하지 않는다. 신뢰된 인증서는 접속 상대의 이름·키 관계를 검증하는 데 쓰며 해당 사이트의 모든 상품·콘텐츠가 안전하거나 정직함을 보장하지 않는다.

TLS가 적용되어도 통신 IP·타이밍·패킷크기 같은 일부 메타 데이터와 끝점 자체 침해 위험은 별도로 남을 수 있다. DNS·SNI가 어떤 설계로 보호되는지도 각기 다르다. 'HTTPS면 모든 정보가 어디서도 보이지 않는다'는 절대 명제는 틀리다.

2026 기준 RFC Editor는 TLS1.3 기존 RFC8446을 대체하는 RFC9846을 안내한다. 이 책은 TLS1.3의 기초 원리를 설명하며 세부 암호 모음·규격 최신 목록은 공식 정보 페이지에서 확인한다. 오래된 TLS1.2 핸드셰이크 그림을 TLS1.3의 모든 단계로 그대로 옮기지 않는다.

## 5. HTTP 버전과 HOL
HTTP/1.1 은 지속 연결을 사용할 수 있다. HTTP/2 는 한 연결에 여러 스트림을 멀티플렉싱하는 프레임 구조를 사용한다. 다만 TCP 기반 바이트 순서 대기는 패킷 손실 시 다른 스트림 전달에도 영향을 줄 수 있다. HTTP/3는 QUIC 기반이며 UDP 위에 신뢰성·보안·다중 스트림 설계를 제공한다.

HTTP/3가 UDP를 쓴다고 전송 신뢰성·암호화를 포기한 것이 아니다. QUIC는 그 보장을 상위 프로토콜로 제공한다. 스트림 간 전송 계층 HOL을 줄이는 성질과 네트워크 혼잡·전체 연결 제한이 완전히 사라진다는 것은 다르다. 모든 HOL·지연 문제가 제로가 된다고 표현하지 않는다.

### 직접 풀기와 확인
서버로그에는 HTTP503이 남았다. DNS 조회와 TCP/TLS가 전혀 성립하지 않은 상황인가? HTTP 응답을 실제로 받았다면 그 응답 경로에서 상위 처리가 진행되었다는 증거다. 프록시·게이트웨이가 답을 냈을 수 있으므로 원본 앱 상태는 추가 관찰한다.

완료: 요청 경로·멱등·상태코드·인증서·버전 차이를 연결한다. 참고: [HTTP의미 RFC9110](https://www.rfc-editor.org/rfc/rfc9110.html), [TLS1.3 RFC9846정보](https://www.rfc-editor.org/info/rfc9846/), [HTTP/2 RFC9113](https://www.rfc-editor.org/rfc/rfc9113.html), [HTTP/3 RFC9114](https://www.rfc-editor.org/rfc/rfc9114.html). 거래·인증서 사례는 자체 예제다.

## 강화 계약 비교: HTTP 응답 유실·멱등성·업무 거래를 구분한다
클라이언트가 결제 요청을 보냈고 서버가 처리한 직후 응답을 잃었다. TCP 연결 오류나 HTTP 응답 부재만으로 결제 미처리를 확정할 수 없다. 업무 거래 ID를 이용한 조회·중복 제어 계약이 필요하다. 어떤 HTTP 메서드를 썼는지와 같은 업무 요청을 재실행해도 중복 효과가 없는지는 별도로 설계한다.

HTTP에서 멱등성은 동일 요청의 의도한 서버 효과를 반복해도 같다는 뜻이지 모든 응답 코드·시간·로그까지 동일하다는 뜻은 아니다. PUT·DELETE의 의미와 GET의 안전성,POST의 일반적 의미를 구분한다. 앱은 비멱등 업무에 재시도 정책을 명시한다.

**TLS 경계:** TLS는 통신 경로에서 인증·암호화 계약을 제공하지만 정상 인증서를 가진 애플리케이션의 업무 로직 오류나 접근권한 누락까지 고치지는 않는다. HTTPS로503을 받으면 이 경로에서 HTTP 응답이 진행된 증거지만 응답을 만든 주체가 원본 앱인지 프록시인지 추가 증거가 필요하다. 2xx도 업무 요청의 명세에 따라 결과를 확인한다.
