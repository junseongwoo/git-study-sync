# 04-04 경쟁 조건·뮤텍스·세마포어·조건 변수: 실행 순서를 설계하기

[[GI-교재04 운영체제|과목 목차]] · [[GI-문제04 운영체제|문제]] · [[GI-해설04 운영체제|해설]]

## 학습 목표
같은 변수를 동시에 수정할 때 발생하는 오류를 명령 단위로 보인다. 잠금과 대기 조건의 역할을 구분한다. 용어 암기보다 공유 상태·임계 구역·대기 조건을 찾는다.

## 1. 경쟁 조건과 임계 구역
경쟁 조건은 여러 실행 흐름의 순서에 따라 올바르지 않은 결과가 나오는 상황이다. `counter++`는 개념적으로 읽기->더하기->쓰기 여러 단계일 수 있다. 고수준 한 줄이라고 자동으로 원자적이지 않다. 언어별 원자적 연산과 메모리 모델의 보장을 확인한다.

### 손풀이 예제 10: 갱신 분실
counter =0. T1 읽기 0,T2 읽기 0,T1 계산 1,T2 계산 1,T1 쓰기 1,T2 쓰기 1이면 두 번 증가했지만 최종 1이다. T1 전체 증가 후 T2 증가면 2다. 임계 구역은 이 읽기-수정-쓰기를 함께 보호해야하는 범위다. 쓰기 문장만 잠그고 읽기는 밖에 두면 같은 옛 값을 기반으로 쓰기 때문에 여전히 틀릴 수 있다.

임계 구역 조건은 상호 배제, 진행, 한정 대기 등으로 설명한다. 상호 배제는 한 번에 한 실행 흐름만 접근한다. 진행은 아무 도 구역에 없을 때 진입 선택이 불필요하게 무한 지연되지 않도록하는 조건이다. 한정대기는 요청 뒤 무제한 추월로 기아가 발생하지 않도록하는 조건이다. 단순뮤텍스 인터페이스가 모든 공정성 성질을 항상 보장한다고 가정하지 않는다.

## 2. 뮤텍스·스핀락
뮤텍스는 소유권을 기반으로 상호 배제를 제공하는 대표 수단이다. 얻지 못하면 잠들 수 있는 구현이 있다. 스핀 락은 계속 상태를 검사하여 짧은 대기를 할 수 있지만 CPU를 사용한다. 단일 코어·긴임계구 역·선점 조건에서는 낭비가 커질 수 있다. 잠금 보유 시간과 실행 환경을 보고 선택한다.

원자적 test-and-set·compare-and-swap 등은 잠금이나 lock-free 구조를 구현하는 기초다. 원자적 한 연산으로 복잡한 전체 자료 구조 불변 식이 자동 보장되지는 않는다. volatile은 언어별 가시성·순서 규칙과 관련되지만 C#counter++를 상호배제로 만드는 키워드가 아니다.

## 3. 세마포어
세마포어는 허용 개수와 대기를 관리하는 카운터 기반 수단이다. wait/P는 사용 가능한 허가를 획득하며 없으면 대기하고,signal/V는 반납·통지를 한다. 구현에 따라 내부 카운터에 음 수를 사용하는 설명이 있어 값 표현의 모델을 문제에서 확인한다. 본 장은 허가 수 0 이하일 때 블로킹하는 추상 모델을 사용한다.

카운팅 세마포어는 동시에 최대N개 작업을 허용하는 데 적합하다. 이진세마포어는0/1허가 상황에서 사용할 수 있지만 뮤텍스와 소유권·해제 규칙이 동일하다고 단정하지 않는다. 생산자가 full을 signal하고 소비자가 wait하는 식으로 서로 다른 흐름 간 순서를 만들 수 있다.

### 손풀이 예제 11: 용량 3 생산자·소비자
버퍼 3 칸,empty =3,full =0,mutex =1로 시작한다. 생산자는 빈 칸 획득->버퍼잠금->삽입->잠금 해제->완료 항목 증가. 소비자는 완료 항목 획득->버퍼잠금->제거->잠금 해제->빈칸 증가다.

```text
producer: P(empty); P(mutex); insert;
          V(mutex); V(full);
consumer: P(full); P(mutex); remove;
          V(mutex); V(empty);
```

생산 3 회후소비가 없으면 empty0,full3이다. 네 번째 생산은 empty 를 기다리며 버퍼 뮤텍스를 아직 획득하지 않는다. 먼저 mutex를 잡은 채 empty를 기다리면 버퍼가 가득한 경우 소비자가 mutex를 얻지 못해 빈 칸을 만들 수 없는 교착 관계가 될 수 있다. 잠금 순서와 자원 대기를 함께 본다.

## 4. 조건 변수
조건 변수는'버퍼가 비어 있지 않다'같은 공유 상태 조건을 기다리는 수단이다. 조건 자체는 공유 변수이고, 조건 변수의 wait는 관련 뮤텍스를 원자적으로 해제하고 잠들며 재개할 때 다시 획득하는 인터페이스를 제공한다. signal은 대기자가 있으면 깨울 수 있지만 원하는 조건을 영구 저장하는 허가 카운터와 같지 않다.

```text
lock(m);
while (queue_is_empty()) wait(not_empty,m);
item = remove();
unlock(m);
```

while로 조건을 재검사하는 이유는 허위 깨움 가능성과 깨어난 뒤 다른 스레드가 먼저 상태를 바꿀 수 있기 때문이다. 깨어났다는 사실만으로 조건이 참이라고 가정하지 않는다. 일반 Mesa 방식에서 signal 직후즉시뮤텍스 소유권이 대기자에게 이전되는 것으로 그리지 않는다.

### 손풀이 예제 12: if가 위험한 이유
소비자 C1,C2가 대기한다. 생산자가 항목 하나를 넣고 깨우며,C1이 항목을 가져간 뒤 C2도 재개했다고 하자. C2가 if 검사 이후 곧바로 remove 하면 빈 큐를 잘못 꺼낼 수 있다. while로 다시 검사하면 C2는 다시 대기한다. 이 사례의 깨움 정책·스케줄은 명시한 가정이다.

## 5. C# 연결과 주의
`lock`은 짧은 공유 상태 수정 구역에 사용하고 C#lock본문에서await를사용할수없다. 비동기 기다림이 필요할 때 SemaphoreSlim.WaitAsync 등을 적절히 쓸 수 있지만 획득-해제 짝을 예외 경로에서도 맞추고 공유 불변 식을 확인해야 한다. Interlocked.Increment는 해당 증가를 원자적으로 하지만 여러 필드의 복합 규칙을 한 번에 보호하는 것은 아니다.

### 직접 풀기와 확인
버퍼가 비어 있는 데 소비자가 먼저 mutex를 획득한 상태로 P(full)에서 대기한다. 생산자는 삽입에 mutex가 필요하다. 서로 진행할 수 있는가? 없다. 소비자는 항목, 생산자는 mutex를 기다린다. 먼저 P(full)후 P(mutex)순으로 자원 대기를 구분한다.

완료: counter 실행 순서, 버퍼세마포어 순서, 조건 변수 while을 설명한다. 참고: [OSTEP 조건변수](https://pages.cs.wisc.edu/~remzi/OSTEP/threads-cv.pdf), [동시성오류](https://pages.cs.wisc.edu/~remzi/OSTEP/threads-bugs.pdf). 자체 추적 예제이며 구현 환경에 따라 API 세부는 다르다.

## 강화 실행 추적: 조건 변수의 알림은 데이터 개수 그 자체가 아니다
공유 큐를 보호하는 뮤텍스 m과 조건 변수 cv를 가정한다. 소비자는 m을 잡고 while(queue.empty()) cv.wait(m)을 실행한다. wait는 조건을 기다리는 동안 잠금을 풀고,반환 전에 다시 획득하는 계약을 사용한다. 생산자는 같은 잠금으로 큐를 바꾼 뒤 알림한다.

**반례 순서:** 소비자 C1,C2가 모두 기다리는 중 생산자가 한 항목을 추가했다. 둘이 깨어나도 한 소비자가 먼저 항목을 꺼내면 다른 소비자가 잠금을 얻을 때 큐는 다시 비어 있다. if로 한 번만 검사하면 빈 큐에서 꺼낼 수 있다. while로 조건을 재검사해야 한다. 허위 깨어남을 허용하는 API 계약에서도 같은 이유가 적용된다.

**세마포어 비교:** items 세마포어의 카운트는 큐에 준비된 항목 수와 일치하도록 설계할 수 있다. 일반적인 잠금 기반 공유 큐에서는 데이터 접근의 상호배제도 별도로 필요하다. lock-free 구현 등 다른 방식이라면 그 동기화 계약을 확인한다. '항목 하나를 예약했다'와 '공유 컨테이너를 동시에 수정해도 된다'는 다른 보장이다.

완료 기준: 보호 데이터,잠금,대기 조건,알림,조건 재검사를 각각 식별한다. 모든 공유 접근이 같은 규칙을 따르는지도 확인한다.
