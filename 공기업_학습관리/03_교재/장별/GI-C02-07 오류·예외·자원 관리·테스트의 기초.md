# 02-07 오류·예외·자원 관리·테스트의 기초

[[GI-교재02 프로그래밍_Cpp_Python|과목 목차]] · [[GI-문제02 프로그래밍_Cpp_Python|문제]] · [[GI-해설02 프로그래밍_Cpp_Python|해설]]

## 오류 종류를 먼저 분류한다
문법 오류, 타입·링크 오류, 실행 중 오류, 논리 오류를 구별한다. 실행된다는 사실이 요구대로 계산한다는 뜻은 아니다. 예외 처리는 오류를 없애는 장식이 아니라 오류를 알리고 복구·정리의 흐름을 명시하는 구조다.

### 1. 예외의 흐름
try에서 예외가 발생하면 일치하는 except/catch로 제어가 이동하고 try의 남은 문장을 그대로 계속 실행하지 않는다. finally는 정리 흐름을 나타내며 일반적인 예외 처리·return 상황에서 실행되지만 프로세스 강제 종료 등의 모든 외부 상황까지 보장하는 만능 규칙은 아니다. 예외를 잡은 후 무시할지 다시 던질지는 함수 계약에 맞춰 판단한다.

예제 A:
```python
out = []
try:
    out.append("A")
    int("x")
    out.append("B")
except ValueError:
    out.append("C")
finally:
    out.append("D")
print("".join(out))
```

int("x")에서 ValueError가 발생해 B는 실행하지 않는다. C를 추가하고 finally에서D를 추가하므로 ACD를 출력한다. try가 끝난 뒤의 출력도 실행된다. 다른 예외 타입을 잡도록 바꾸면 잡히지 않을 수 있으나 finally 정리 흐름을 별도로 생각한다.

### 2. 자원 관리와 RAII
파일·소켓·락·DB연결은 사용을 끝내면 해제해야 하는 자원이다. 메모리 GC가 있다고 그 해제 시점까지 자동으로 원하는 대로 정해지는 것은 아니다. Python with는 context manager의 진입·종료를 통해 사용 범위를 표현하고, C# using은 Dispose 기반 정리를, C++ RAII는 소멸자를 통한 범위 기반 정리를 제공한다.

예제 B: 파일을 열고 중간에 숫자 변환 실패가 생겨도 파일 닫기가 필요하다. `with open(path, encoding="utf-8") as f:` 안에서 읽으면 일반적인 예외 흐름에서도 context 종료 처리로 닫힌다. open 직후 수동 close를 맨 마지막에만 쓰면 중간 예외에서 close에 도달하지 못할 수 있다. 단, 모든 사용자 context manager가 반드시 파일 닫기 의미를 갖는 것은 아니다.

C++에서는 std::vector·std::string·unique_ptr 같은 소유 구조를 사용하여 new/delete 직접 관리 부담을 줄인다. unique_ptr는 단일 소유를 표현하고 shared_ptr는 공유 소유를 표현한다. shared_ptr를 사용했다고 순환 참조 등 모든 수명 문제가 자동으로 사라지지는 않는다. 모든 객체를 shared_ptr로 바꾸는 것은 설계 원칙이 아니다.

### 3. 예외를 결과 값으로 바꾸는 계약
읽기 실패에서0을 반환하면 정말 값0을 읽은 경우와 구별하지 못할 수 있다. 성공 여부와 값의 쌍, optional, 예외 등 선택지가 있다. 입력이 항상 올바른 공식 시험 문제에서는 과한 외부 입력 복구가 핵심이 아닐 수 있으나 빈 입력·배열 범위 같은 알고리즘 경계는 꼭 확인한다.

금융 IT 맥락에서는 실패를 삼켜서 성공처럼 보이게 하는 코드는 특히 위험하다. 여기서는 면접 준비가 아니라 프로그래밍 이론의 오류 전파를 이해하는 예시로 사용한다. 변환 실패를0으로 바꾸는 정책을 쓴다면 그렇게 해도 되는 요구가 명확해야 한다.

### 4. 테스트: 정상·경계·반례
새 알고리즘에는 손으로 답을 구할 수 있는 작은 입력, 빈/최소 입력, 동률·중복, 큰 합, 답이 없는 경우를 만든다. 테스트를 많이 돌렸다는 사실만으로 일반적 정확성이 입증되지는 않지만 실패를 발견하고 추적할 근거가 된다. 작은 범위의 완전 탐색 정답과 효율적 풀이를 비교하는 방식도 유용하다.

예제 C: 최대 찾기의 요구가 비어 있지 않은 배열이면 [5]→5,[-3,-8]→-3,[2,2]→2를 확인한다. max_value=0으로 초기화하면 음수만 있는 입력에서0을 반환해 실패한다. 첫 원소로 초기화하는 이유를 불변식으로 설명한다. 빈 배열을 허용한다면 반환 정책을 먼저 정해야 한다.

예제 D: 두 수 합에서 [3,3],target6을 만들면 서로 다른 인덱스를 쓰는 조건을 검증한다. [3],target6은 같은 원소를 두 번 쓸 수 없으면 실패해야 한다. 문제의 “서로 다른 원소/인덱스” 문장을 코드에 반영한다.

### 5. 디버깅의 순서
기대 결과를 먼저 적고 실제와 처음 달라지는 시점을 찾는다. 입력 파싱→초깃값→조건 경계→업데이트 순서→출력 형식 순으로 분리한다. 디버그 출력은 제출 전에 제거하고 C++ sanitizers 같은 보조 도구가 탐지할 수 있는 메모리 오류와 언어의 보장을 구별한다. 본 교재는 실제 시험에서 해당 도구 사용이 가능하다고 가정하지 않는다.

### 완료 기준
예제 A의 ACD가 나오는 제어 흐름을 설명한다. 오류를 잡고도 정리를 해야 하는 자원을 하나 적는다. 자신의 함수 하나에 최소 입력·음수·동률·큰 합을 적용하고 기대 답을 손으로 계산한다. “예외가 안 났으니 맞다”라는 판단에서 벗어나면 완료한다.

### 보강 검증: 실패 입력을 설계하기
정렬 배열의 lower_bound 반환값이 n인 사례를 만든다. [2,4]에서 target9이면 위치2다. 값을 읽기 전에 위치<len(a)인지 확인해야 한다. 배열 접근 오류가 없더라도 다른 target을 잘못 반환할 수 있으므로 a[pos]==target 조건도 필요하다.

정수 합 문제에[2000000000,2000000000]을 넣으면 수학적 합4000000000이다. C++ int 범위를 넘는지를 확인하고 초기 accumulator의 타입을 적는다. Python에서 int가 자동 확장된다는 사실이 입력 파싱과 조건 오류까지 막아 주지는 않는다.

테스트 기록은 입력→기대 답→실제 답→처음 다른 상태 순서로 적는다. 통과한 예제 수 대신 “왜 이 입력이 흔한 버그를 드러내는가”를 설명하면 오답 복습이 학습이 된다. 정답·시간·메모리·출력 계약을 별도 점검한다.

### 강화 응용: 조건을 바꾸어 다시 증명하기
정상 종료·예외 종료 모두에서 자원을 정리해야 한다. C++ 지역 RAII 객체는 스코프를 벗어나며 소멸자로 자원을 정리하고, Python with는 컨텍스트 관리자의 종료 처리를 호출한다. 그러나 Python에서 파일 객체에 대한 참조를 사라지게 하면 모든 구현에서 즉시 닫힌다고 일반화하지 않는다. 명시적 with가 자원 수명 의도를 표현한다.

finally에서 새 return이나 예외를 발생시키면 이전의 return/예외를 덮을 수 있다. Python 함수가 try에서 ValueError를 발생시키지만 finally에서 return 7을 하면 호출자는 7을 받고 그 ValueError는 밖으로 전달되지 않는다. 정리 코드가 오류를 숨기지 않도록 finally에는 자원 정리에 집중하고 반환을 피한다. close 자체가 실패할 가능성도 원래 오류와 함께 설계한다.

테스트는 구현의 내부 식을 같은 코드로 복사해 비교하는 것보다 독립 기준을 둔다. 정렬 테스트는 결과 값뿐 아니라 길이·중복 원소 개수 보존·순서 조건을 확인하고, 작은 입력에서 완전 탐색 기준과 비교할 수 있다. 정의되지 않은 동작의 출력을 관찰해 특정 값이 나왔다는 결과는 언어 표준 안전성의 근거로 쓰지 않는다. 잘못된 코드를 실행해도 우연히 원하는 값이 나올 수 있다.
