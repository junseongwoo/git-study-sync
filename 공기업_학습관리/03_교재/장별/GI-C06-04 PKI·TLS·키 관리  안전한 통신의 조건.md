# 06-04 PKI·TLS·키 관리: 안전한 통신의 조건

[[GI-교재06 정보보안|과목 목차]] · [[GI-문제06 정보보안|문제]] · [[GI-해설06 정보보안|해설]]

### 인증서와 신뢰
인증서는 공개키와 주체 정보를 서명으로 연결하는 문서다. CA의 서명 확인만 해서는 충분하지 않을 수 있다. 신뢰할 수 있는 경로, 유효기간, 호스트 이름, 사용 목적, 필요한 폐기·상태 확인 정책 등을 검증한다. 화면에 자물쇠 표시가 있다는 사실만으로 서비스의 사업 내용이나 모든 프로그램 코드가 안전하다고 보장하지는 않는다.

인증서 체인은 서버 인증서에서 중간 CA를 거쳐 신뢰 저장소의 루트까지 연결된다. 루트의 신뢰는 해당 기기·운영 환경의 신뢰 저장소 정책과 관련된다. 자기서명 인증서라는 이유만으로 모든 내부 활용이 불가능한 것은 아니지만 외부 사용자에게 자동 신뢰되는 것은 아니다.

### TLS의 큰 흐름
TLS는 통신 상대 인증과 안전한 키 협상, 전송 데이터 보호를 제공한다. 일반적인 웹 연결에서는 서버를 인증하고, 클라이언트 인증서를 사용하는 상호 TLS는 별도 구성을 한다. TLS 1.3은 암호 스위트와 핸드셰이크가 과거 버전과 다르므로 RSA 키로 모든 세션키를 직접 암호화해 전송한다는 설명을 최신 TLS 전체에 적용하지 않는다.

개념적으로 클라이언트와 서버가 지원 값을 협상하고, 키 공유와 서버의 인증 정보를 검증하며, 합의한 비밀로 트래픽 키를 유도한다. 실제 데이터 보호에는 AEAD 계열처럼 암호화와 무결성 검증을 결합한 방식이 사용된다. 디지털 인증서·서명은 신뢰 확인, 대칭키 보호는 효율적인 데이터 전송에 기여한다.

전방향 안전성은 장기 개인키가 나중에 노출되어도 과거 세션의 비밀이 자동으로 복구되지 않도록 하는 특성과 관련된다. 임시 키 교환과 안전한 키 삭제 같은 조건이 중요하다. "서버 개인키가 유출되어도 미래 공격도 모두 불가능하다"는 뜻은 아니다.

### 키의 생명주기
키 생성에는 암호학적으로 안전한 난수가 필요하다. 저장·사용·분배·회전·폐기·복구 정책을 함께 관리한다. 소스 코드에 키를 그대로 넣거나 같은 nonce를 반복 사용하는 것은 알고리즘이 강해도 전체 시스템을 취약하게 만들 수 있다. 인증서 만료 갱신, 키 유출 시 교체, 접근 기록과 최소권한도 키 관리에 들어간다.

암호 모드와 IV/nonce의 조건은 알고리즘별로 다르다. "IV는 항상 비밀이어야 한다"처럼 일반화하지 않는다. 특히 일부 AEAD 방식의 nonce 재사용은 심각한 위험을 만들 수 있으므로 도구의 계약을 지켜야 한다.

### 단계별 상황 예제
내부 개발자는 HTTPS 오류를 피하려고 인증서 검증을 껐다. 암호화된 연결은 만들어질 수 있지만 상대가 진짜 서버인지 확인하지 못하면 중간자 공격 위험이 커진다. 올바른 해결은 개발 환경의 신뢰 경로·호스트 이름·유효기간을 맞추는 것이다. 오류 무시 코드를 운영에 남기면 보안 목표를 훼손한다.

인증서가 10월 10일 만료이고 갱신 후 재시작이 필요한 가상 서비스에서 10월 9일 마지막 점검만 하면 갱신 실패와 롤백 시간이 부족할 수 있다. 만료 전에 갱신·배포·실제 연결 시험을 계획하고 경보를 걸어야 한다. 날짜는 학습용 예시이며 기관 정책을 뜻하지 않는다.

### 자가 연습과 풀이
TLS가 적용되었는데 서버 로그에 비밀번호를 평문으로 남겼다. 전송 구간의 보호는 서버 저장 데이터의 안전을 자동으로 보장하지 않는다. 전송 중·저장 중·사용 중의 경계를 각각 확인해야 한다.

### 완료 기준
공개키 인증서와 대칭키 데이터 보호의 역할을 구분하고 인증서 검증을 껐을 때 어떤 목표가 훼손되는지 설명한다. TLS는 모든 응용 프로그램 취약점의 해결책이 아니라는 점도 사례로 말할 수 있어야 한다.

### 응용 문제: 인증서와 키를 함께 점검하기
유효한 인증서를 제시했지만 접속 호스트 이름이 인증서의 허용 이름과 맞지 않으면 정상 검증을 통과하지 못할 수 있다. 반대로 이름만 맞아도 신뢰 경로·기간·사용 목적 조건이 빠지면 충분하지 않다. 자기서명 여부 하나만으로 모든 검증을 대체하지 않는다.

장기 키 유출 시에는 해당 키를 교체하고 인증서·토큰·관련 접근을 정책에 따라 재검토한다. 키 회전은 단순히 새 키를 만드는 작업만이 아니라 새 키 적용·기존 자료 처리·옛 키 사용 종료·복구 가능성 확인을 포함한다. 오래된 암호문을 복호화해야 하는 요구와 노출 키의 사용 중단을 함께 설계해야 한다.

### 강화 통신·키 관리: 세 검사를 하나로 뭉치지 않기
가상 서비스는 서버 인증서의 신뢰 경로·요청 서버 이름·유효 조건을 확인한 뒤 통신한다. 신뢰된 발급자가 서명했어도 요청한 호스트와 이름이 다르면 그 서버의 신원 검증을 통과한 것이 아니다. TLS 사용만으로 애플리케이션의 객체 권한과 로그 보호가 해결되지 않는다.
봉투 암호화 예제에서는 자료를 DEK로 암호화하고, DEK를 KEK로 보호한다. KEK를 교체할 때 DEK 자체를 바꾸지 않고 새 KEK로 재포장하는 방식과 자료까지 새 DEK로 재암호화하는 방식을 구분한다. 재포장만 했다면 DEK 사용 기간·사용량 제한이 새로 시작된다고 단정하지 않는다. 이전 복호 경로는 이행 검증·백업 복구 조건을 확인한 뒤 정책에 따라 정리한다.
손풀이 반례: 프로세스별 nonce 카운터를 0부터 시작하고 같은 키로 두 프로세스를 실행하면 둘 다 첫 nonce 0을 쓸 수 있다. 재시작·다중 서버까지 포함해 유일성을 설계한다. 암호키를 코드 저장소와 암호문 옆 파일에 같은 권한으로 저장하면 저장소 침해로 둘 다 노출될 수 있다. 키 식별자·권한·변경 기록·복구 경로를 함께 관리한다.
