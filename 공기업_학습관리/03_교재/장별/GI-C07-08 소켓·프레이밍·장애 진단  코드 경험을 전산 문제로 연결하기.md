## 학습 목표
TCP 응용 메시지를 정확하게 수신하는 흐름을 설계한다. 연결 안 됨을 DNS·경로·전송·TLS·응용으로 분리하여 증거를 찾는다. C# 장비 개발 경험을 재사용하되 어느 언어에서도 성립하는 통신 원리를 우선한다.

## 1. TCP 서버/클라이언트 흐름
전형적 서버는 socket 생성->bind->listen->accept로 연결을 받고, 클라이언트는 socket 생성->connect를 수행한다. accept가 반환한 연결 소켓과 listen 중인 서버 소켓은 역할이 다르다. 각 연결의 입출력을 관리하고 종료·예외·취소를 처리한다. 플랫폼 API명과 비동기 구현은 달라도 역할 구분은 유효하다.

블로킹은 결과가 준비될 때까지 호출 흐름이 기다리는 성질, 논블로킹은 즉시 완료 가능 여부를 반환하는 인터페이스 성질, 비동기는 완료를 나중에 통지받는 모델로 설명한다. 세 개념을 언제나 같은 뜻으로 쓰지 않는다. 단일 스레드 이벤트 루프도 I/O 다중화로 여러 연결을 진행시킬 수 있고 CPU 연산을 오래 하면 그 루프를 막을 수 있다.

## 2. 길이 헤더 프로토콜
메시지 한 개를 4바이트 unsigned big-endian 길이 헤더와 그 길이의 payload로 정한다. 최대 payload 4MiB이며 길이 0은 빈 메시지로 허용한다. 읽기는 헤더 4바이트를 정확히 모으고 길이를 해석하고 상한을 검사한 다음 본문을 정확히 모은다. 헤더와 본문이 여러 번 recv로 나뉘는 상황도 처리한다.

```python
import struct

def recv_exact(sock, n):
    data = bytearray()
    while len(data) < n:
        block = sock.recv(n - len(data))
        if not block:
            raise EOFError('message was incomplete')
        data.extend(block)
    return bytes(data)

def recv_message(sock):
    header = recv_exact(sock, 4)
    n = struct.unpack('!I', header)[0]
    if n > 4 * 1024 * 1024:
        raise ValueError('message too large')
    return recv_exact(sock, n)

def send_message(sock, payload):
    if len(payload) > 4 * 1024 * 1024:
        raise ValueError('message too large')
    sock.sendall(struct.pack('!I', len(payload)) + payload)
```

이 예는 동기 TCP 소켓교육용이다. 별도 timeout·취소·인증·메모리 정책은 운영 설계에서 추가한다. 입력이 네트워크에서 온다는 이유로 무조건 신뢰하지 않고 길이 상한을 검사한다. UTF-8 문자 수와 바이트 수를 같다고 생각하지 않는다. '가'는 UTF-8에서 3바이트이며 헤더는 전송 바이트 길이를 담는다.

### 손풀이 예제 21: 부분 수신
payload =b'ABCDE'면 길이 5 이고헤더는 00 00 00 05다. 전체 9바이트가 2,3,4바이트로 나뉘어 수신될 수 있다. recv_exact(4)는 첫 2바이트와 다음 블록 일부를 모으고 나머지 payload를 이어서 읽는다. 실제 recv(n)는 요청한 n보다 많이 반환하지 않으므로'일부'와 다음 읽기의 수신 상태를 구분한다. socket 버퍼에나머지가 남는다.

TCPrecv가 빈 바이트를 반환하는 대표 상황은 상대의 정상 송신 종료다. 메시지 중간에서 빈 결과이면 본문이 불완전한 상태다. timeout 예외와 정상 EOF를 같은 종류의 빈 메시지로 처리하지 않는다. recv_exact의 n =0 은소켓 읽기 없이 빈 payload를 반환한다.

## 3. C++와 C# 연결
C++표준 라이브러리는 플랫폼 중립 TCP 소켓 API 자체를 일반 표준으로 제공하지 않으므로 WindowsWinsock·POSIX·별도 라이브러리의 규칙을 따른다. 한 번 send가 전체 버퍼를 항상 보냈다고 가정하지 않고 실제 전송량에 따라 반복하는 원리를 배운다. Python의 sendall은 이 반복을 돕는 API다. C#Stream·SocketAPI의 계약도 각각 문서로 확인한다.

C++에서 네트워크 헤더를 읽을 때 endianness와 부호·폭을 명시한다. little-endian 메모리의 int를 그대로 상대에게 보내면 big-endian 프로토콜과 맞지 않을 수 있다. 구조체를 그대로 전송하면 패딩·자료형 크기·ABI 문제도 생긴다. 직렬화 규칙을 명시한다.

## 4. 장애를 단계별로 좁히기
| 관찰 | 먼저 확인할 가설 | 단정하면 안 되는 것 |
| --- | --- | --- |
| 이름 질의 실패 | resolver·레코드·캐시·정책 | 서버 앱이 반드시 죽음 |
| TCP 연결 거절 | 해당 끝점 수신자·RST·정책 | 모든 망이 단절됨 |
| 연결 timeout | 경로·드롭·서버 무응답 | 무조건 방화벽 한 원인 |
| TLS 검증 실패 | 이름·체인·시간·정책 | 검증을 꺼도 안전함 |
| HTTP 5xx | 앱·프록시·상위 의존성 | DNS가 반드시 실패함 |

같은 시각·같은 끝점에서 한 가지만 바꿔 관찰한다. 호스트 IP·포트·프로토콜·호스트명·응답 코드·시간을 기록한다. 연결 거절과 timeout은 다른 증상이지만 패킷 정책·중간 장비 때문에 한 증상만으로 원인을 확정할 수 없다.

## 5. 종합 연결 시나리오
패드에서 학습 웹 api.example.com을 접속한다고 하자. 먼저 DNS로 주소를 찾고, 라우팅으로 다음 홉을 정하고, 같은 링크의 ARP 등으로 전달하고,TCP 또는 QUIC 연결을 진행하고,TLS 보안 채널을 확인하고,HTTP 요청으로 학습 기록을 교환한다. 계정·진행 기록 저장은 응용 DB 문제다. 오프라인 HTMLlocalStorage 기록이 저절로 서버에 동기화되는 것은 아니다. 주소·전송·인증·데이터 저장은 다른 요건이다.

### 직접 풀기와 확인
수신헤더 길이가 4,294,967,295인데 상한 검사 없이 그만큼 메모리를 할당하면 문제가 된다. 최대 4MiB 조건을 먼저 검사하면 본문 수신 전에 거부할 수 있다. 길이 필드 4바이트라는 사실은 안전한 메시지 크기를 자동 정해 주지 않는다.

## 강화 손풀이: 길이 접두 프로토콜의 부분 수신을 상태로 관리한다
각 메시지는4바이트 unsigned big-endian 길이 접두와 해당 길이의 본문이다. 접두00 00 00 05,본문HELLO를 보내도 recv가 첫2바이트만 반환하고 다음에7바이트를 반환할 수 있다. 먼저 접두4바이트가 모일 때까지 누적해 길이5를 파싱하고 본문5바이트를 모은 뒤 하나의 메시지로 전달한다.

한 recv에 메시지 두 개가 붙어 오면 첫 프레임만 파싱하고 나머지를 버리지 않는다. 버퍼에 남겨 다음 프레임을 반복 파싱한다. 0바이트 수신을 상대의 정상 송신 종료로 해석하는 API에서는 미완료 프레임이 남았는지 확인해 프로토콜 종료/절단을 구분한다.

**방어 계약:** 최대 본문4096바이트라는 자체 규칙이면 접두를 읽자마자4097 이상은 거부하고 거대한 메모리를 먼저 할당하지 않는다. 접두·본문 각각의 시간 제한과 버퍼 상한을 정한다. TCP가 바이트 순서를 보장해도 메시지 경계와 악의적 길이 검사는 애플리케이션의 책임이다.
