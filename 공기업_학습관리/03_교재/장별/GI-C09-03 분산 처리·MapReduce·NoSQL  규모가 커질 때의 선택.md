# 09-03 분산 처리·MapReduce·NoSQL: 규모가 커질 때의 선택

[[GI-교재09 빅데이터_AI기초|과목 목차]] · [[GI-문제09 빅데이터_AI기초|문제]] · [[GI-해설09 빅데이터_AI기초|해설]]

### 수평 확장과 분산의 비용
수직 확장은 한 시스템의 자원을 늘리고, 수평 확장은 여러 노드를 함께 사용하는 방식이다. 분산은 처리량과 저장량을 늘리고 장애 영향을 줄이는 데 도움을 줄 수 있지만 네트워크·조정·재시도·일관성 비용을 추가한다. 데이터가 작고 단일 시스템이 충분하다면 복잡한 분산 구조가 오히려 부담일 수 있다.

파티셔닝은 데이터를 여러 부분으로 나눠 저장·처리한다. 복제는 같은 자료의 사본을 여러 곳에 둔다. 둘은 다르며 함께 사용할 수 있다. 해시 파티셔닝은 키의 해시를 기준으로 나누고, 범위 파티셔닝은 값 범위를 기준으로 나눈다. 인기 키에 자료가 몰리면 데이터 편향으로 일부 노드가 느려질 수 있다.

### MapReduce의 흐름
Map은 입력을 중간 키·값으로 변환한다. Shuffle/Group은 같은 키의 값을 모아 Reduce로 보내며, Reduce는 키별로 결과를 계산한다. Combiner는 허용되는 경우 지역 중간 집계를 줄여 전송량을 낮출 수 있지만 모든 연산에 안전하거나 실행이 보장되는 단계로 가정하면 안 된다. 재결합해도 결과가 유지되는 성질을 검토한다.

### 단계별 예제: 지점별 신청 건수
원천 행은 부산·부산·수원·부산·수원이라고 하자. Map은 (부산,1),(부산,1),(수원,1),(부산,1),(수원,1)을 만든다. Group은 부산:[1,1,1],수원:[1,1]로 모은다. Reduce에서 합계를 내면 부산 3,수원 2다. 같은 입력에 재시도가 생길 수 있으므로 처리 프레임워크와 출력 저장 방식의 계약을 이해해야 한다.

평균을 Combiner에서 단순 평균값 하나로만 합치면 틀릴 수 있다. 파티션 A의 값 10·20은 평균 15, B의 값 100은 평균 100이다. 두 평균의 평균 57.5는 전체 평균 130/3 약 43.33과 다르다. 지역 합계·개수를 함께 전달하면 (30+100)/(2+1)로 올바르게 재결합할 수 있다.

### NoSQL의 종류
키-값 저장소는 키로 값을 찾는 접근, 문서 저장소는 구조 있는 문서 단위의 저장, 넓은 열 계열 저장소는 큰 분산 테이블과 열 계열 구조, 그래프 저장소는 관계와 탐색을 중심으로 설명한다. 제품마다 쿼리·트랜잭션·일관성·인덱스 기능이 다르다. "NoSQL은 SQL을 전혀 지원하지 않는다", "트랜잭션이 무조건 없다"는 일반화는 틀릴 수 있다.

어떤 DB를 선택할지는 데이터 형태만 아니라 접근 패턴, 거래 정확성, 지연, 운영·복구 비용에 달려 있다. 계좌 이체처럼 원자성과 명확한 일관성이 필요한 거래와 대규모 로그 검색의 요구는 같지 않다.

### CAP의 조건
CAP의 설명에서 네트워크 분할이 발생한 상황에 모든 요청의 가용성과 강한 일관성을 동시에 보장하기 어렵다는 제한을 이해한다. 여기서 C는 모든 노드가 임의 순간 완전히 같은 파일을 가진다는 모호한 말이 아니라 일관성 모델의 의미와 연결된다. A도 단순 연간 가동률과 다른 엄밀한 정의를 가진다. "언제나 셋 중 둘을 아무 조건 없이 고른다"는 암기보다 분할이 생겼을 때 어떤 요청을 거부하거나 어떤 읽기를 허용하는지를 생각한다.

### 자가 연습과 풀이
지점 키로 나눴더니 부산 데이터가 90%이고 나머지가 10%다. 노드가 10대라는 이유만으로 각 노드가 10%씩 처리한다고 볼 수 없다. 키 분포와 파티션 배치를 확인해야 한다. 복제를 늘려 저장 사본이 많아져도 쓰기 조정 비용과 복구 조건이 함께 생긴다.

### 완료 기준
파티셔닝·복제, Map·Group·Reduce, 합계·개수 기반 평균을 구분하고 NoSQL과 CAP의 과도한 일반화를 고칠 수 있어야 한다.

### 응용 문제: 장애 재시도와 한 번 처리
분산 작업에서 실패한 작업을 다시 실행할 수 있다. 처리 코드가 외부 시스템에 '금액을더한다'라는 부작용을 만들면 재시도 때 중복 반영될 수 있다. 프레임워크가 내부 계산 결과를 관리한다고 외부 거래도 항상 한 번만 실행되는 것은 아니다. 이벤트 식별자와 멱등 처리·트랜잭션 경계를 확인한다.

같은 요청을 여러 번 적용해도 의도한 상태가 같으면 멱등성의 관점으로 설명할 수 있다. '잔액을10증가'와 '이벤트E를미반영이면한번적용'은 조건이 다르다. 로그 분석과 실제 금전 거래의 실패 처리 요구를 똑같이 취급하지 않는다.

### 강화 손풀이: 분산 평균은 평균끼리 평균 내지 않는다

같은 키에 속하는 정확한 정수 자료를 두 파티션으로 나눴다. P1=[2, 4], P2=[10, 10, 10, 10]이다. 이 예시에서는 오버플로와 부동소수점 반올림을 무시한다.

**1단계 - 잘못된 방법을 먼저 계산한다.** P1 평균은 3, P2 평균은 10이다. 평균의 평균은 (3+10)/2=6.5다. 이 계산은 두 파티션의 건수가 같을 때의 가중치만 사용하므로 여기서는 전체 평균이 아니다.

**2단계 - 합과 건수를 함께 보낸다.** P1은 (6, 2), P2는 (40, 4)를 보낸다. 결합 규칙은 `(s1+s2, n1+n2)`다. 최종 값은 (46, 6), 평균은 46/6=23/3  약  7.67이다. 빈 파티션은 (0, 0)으로 결합하고, 최종 건수가 0이면 평균을 정의하지 않는 정책을 둔다.

**3단계 - 중간 결합 후에도 같은 의미를 유지한다.** 합과 건수의 쌍은 어느 순서로 묶어도 정확한 정수 계산에서는 같은 결과를 낸다. 중간 집계의 유무나 여러 번의 재집계에도 원자료의 평균과 같은 결과를 얻도록 설계한다. Hadoop 문서는 combiner를 선택적인 지역 집계로 설명한다. 응용에서는 combiner가 한 번 실행될 것을 전제로 정답을 만들면 안 된다.

**병목 반례.** 가상 병렬 작업 세 개가 동시에 시작하고 필요한 작업자가 충분하며 공유 자원 경합과 통신 비용이 없다고 하자. 시간은 2초, 2초, 8초다. 전체 완료 시간은 합 12초가 아니라 최댓값 8초다. 작업자 수만 늘려도 이미 시작된 8초 작업이 저절로 빨라지지는 않는다. 키 편중, 파티션 분할 가능성, 집계 의미 보존을 확인한다. 실제 시스템에서는 스케줄링·셔플·재시도 비용도 있어 이 단순 최댓값 모형을 그대로 성능 보장으로 쓰면 안 된다.
