# 04-02 프로세스·스레드·IPC·비동기: 독립성과 공유를 구분하기

[[GI-교재04 운영체제|과목 목차]] · [[GI-문제04 운영체제|문제]] · [[GI-해설04 운영체제|해설]]

## 학습 목표
프로그램·프로세스·스레드의 관계와 ready/blocked 차이를 설명한다. C#에서 Task·async를 사용한 경험을 OS 스레드 개념과 연결하되 같다고 취급하지 않는다.

## 1. 프로그램과 프로세스
프로그램은 실행 가능한 코드와 데이터의 정적인 표현이고 프로세스는 실행 중인 프로그램의 자원·상태를 포함한 개체다. 같은 실행 파일을 두 번 켜면 서로 다른 프로세스가 될 수 있다. 프로세스에는 주소 공간, 열린 파일 관련 자원, 권한, 실행 상태 등이 있다. PCB는 프로세스를 관리하기 위한 정보 구조의 추상 개념이다. 실제 구현에서는 프로세스·스레드 정보가 여러 구조로 나뉠 수 있다.

주소 공간의 전형적 구획은 코드, 정적 데이터, 힙, 스택이다. 힙은 동적 할당에 쓰이고 스택은 호출 프레임·지역 상태에 쓰인다. 언어 런타임·최적화 때문에 특정 C# 값이 반드시 특정 구획에 존재한다는 절대 판정은 피한다. 시험에서 주는 전통적 C 메모리 모델과 관리 런타임 세부는 구분한다.

## 2. 상태 변화
new->ready->running은 생성·실행 준비·CPU 배정을 나타낸다. running 중 I/O를 기다리면 blocked, 타임 슬라이스가 끝나 선점되면 ready, 작업이 끝나면 terminated로 간다. blocked는 기다리는 사건이 충족되지 않아 CPU를 줘도 현재 작업 진행이 불가능한 상태다. ready는 자원이 준비되었지만 CPU 차례를 기다린다.

### 손풀이 예제 3: 상태 추적
A가 실행 중이고 파일 읽기 요청을 한다. A:running->blocked. B가 ready에서 running으로 선택된다. 파일 완료 인터럽트가 오면 A:blocked->ready다. A가 반드시 즉시 running이 되는 것은 아니다. 우선순위·선점 규칙이 허용할 때 B를 대신할 수 있다. 'I/O 완료 =자동 즉시 실행'오답을 이 흐름으로 반박한다.

문맥 교환에서는 레지스터·PC·스택 관련 실행 상태 등을 저장·복원한다. 프로세스가 바뀌면 주소 공간 설정과 관련된 추가 비용이 생길 수 있다. 캐시·TLB의 영향도 중요하지만 모든 전환이 캐시 전체를 항상 비운다고 단정하지 않는다.

## 3. 스레드의 공유와 독립
한 프로세스의 스레드들은 보통 주소 공간·코드·힙·열린 파일 관련 자원을 공유한다. 각 스레드는 자신의 실행 PC·레지스터·스택을 가진다. 공유 덕분에 통신이 빠르지만 오류가 다른 스레드의 상태를 손상시킬 수 있다. 별도 프로세스는 보통 주소 공간을 분리하므로 직접 같은 일반 변수를 공유하지 않으며 IPC나 공유 메모리 설정이 필요하다.

| 대상 | 프로세스 단위 공유 예 | 스레드별 상태 예 |
| --- | --- | --- |
| 메모리 | 코드·전역변수·힙 | 호출 스택·레지스터 |
| 실행 | 프로세스 자원·권한 | PC·스케줄링 상태 |
| 파일 | 열린 파일 관련 자원 | API 호출 중 진행 상태 |

단일 코어에서도 여러 스레드가 번갈아 진행하는 동시성이 가능하다. 병렬성은 실제 같은 시점에 여러 연산을 수행하는 것으로 여러코어·장치 등이 필요하다. CPU 연산이 직접 병렬 실행되려면 실행 자원이 필요하지만, I/O 장치는 CPU와 독립적으로 작업할 수 있다.

## 4. IPC 선택
공유 메모리는 같은 영역을 매 핑하여 데이터를 교환하고 동기화를 별도로 관리한다. 메시지 전달은 파이프·메시지큐·소켓처럼 데이터를 전달하는 인터페이스다. 소켓은 같은 기계의 프로세스 또는 네트워크 원격 사이 통신에 사용할 수 있다. 공유 메모리에는 복사 량 감소 장점이 있지만 잠금·권한·수명·구조 일관성 관리가 필요하다. 메시지 전달은 경계가 명확하지만 복사·직렬화 비용이 들 수 있다.

## 5. C# Task·async·await를 정확히 연결
Task는 작업의 완료를 표현하는 추상화이며 그 자체가 새 OS 스레드라는 뜻은 아니다. async 메서드는 컴파일러에 의해 상태 기계 등으로 변환될 수 있고,await는 미완료 작업을 기다리는 동안 현재 실행을 반환하고 이후 계속할 수 있게한다. async/await 키워드 자체가 새 스레드를 만들지는 않는다.

### 손풀이 예제 4: 이미지 분석과 파일 읽기
파일 읽기 완료를 기다리는 I/O 중심 작업은 실제 비동기 API를 await 하면 스레드를 빈 대기로 묶지 않을 수 있다. 반면 500msCPU 연산을 async 메서드 안에서 그대로 실행하면 자동으로 다른 코어로 옮겨 가지 않는다. 필요하면 Task.Run 등으로 스 레드 풀에 작업을 넘길 수 있지만 처리량·UI 응답·메모리 복사 비용을 측정해야 한다. 동시 태스크 수 100이 실제 CPU 스레드 100이라는 뜻도 아니다.

UI 컨 텍스트에서 동기적으로 Result·Wait로 막으면 연속 작업이 같은 컨 텍스트를 기다리는 교착 상태가 생길 수 있다. 이것은 일반적인 모든 Task.Wait가 언제나 교착이라는 뜻이 아니라 대기 관계와 컨 텍스트 조건을 분석해야 한다는 뜻이다.

## 6. 병렬화의 상한: Amdahl 법칙
프로그램 중 비율 s가 직렬이고 나머지를 N 배 병렬화하는 단순 모델에서 속도 향상은 1/(s +(1-s)/N)이다. 통신·스케줄링 오버헤드는 무시한다고 명시한다.

### 손풀이 예제 5
직렬 비율 20 %,N =4이면 시간 비율 0.2 +0.8/4 =0.4, 속도 향상 2.5 배다. 코어가 무한히 늘어도 상한1/0.2 =5 배다. '4 코어이므로 무조건 4 배'가 아니다. 실제 오버헤드가 있으면 상한보다 더 작을 수 있다. CPU가 아닌 디스크 병 목을 CPU 코어 증가만으로 해결할 수도 없다.

### 직접 풀기와 확인
두 스레드가 한 프로세스의 힙 객체 counter를 함께 수정한다. 스택이 다르므로 객체까지 자동 분리되는가? 아니다. 각 스레드의 스택에서 참조하는 대상 힙 객체는 공유될 수 있다. 공유 변경을 원자적 연산·잠금 등으로 보호해야 한다.

완료: ready/blocked를 상태 도로 그리고 Task·스레드·프로세스 각각을 구분한다. 참고: [OSTEP 프로세스](https://pages.cs.wisc.edu/~remzi/OSTEP/cpu-intro.pdf), [스레드 소개](https://pages.cs.wisc.edu/~remzi/OSTEP/threads-intro.pdf), [Microsoft async/await](https://learn.microsoft.com/dotnet/csharp/asynchronous-programming/task-asynchronous-programming-model). 수치·장비 사례는 자체 제작이다.

## 강화 손풀이: 비동기 실행에서도 데이터 소유권을 먼저 정한다
한 프로세스의 스레드 A,B는 같은 힙 객체를 참조할 수 있지만 각 스레드는 통상 별도 스택과 실행 문맥을 가진다. 스레드 수가 늘었다고 주소 공간이 분리되지는 않는다. 프로세스를 분리해도 공유 메모리·파일·소켓 같은 IPC를 명시적으로 사용하면 통신할 수 있다.

**반례:** C#의 await 뒤 연속 실행이 재개될 때 같은 OS 스레드에서만 실행된다고 보장하지 않는다. 동기화 문맥·스케줄러·호출 환경에 따라 다르다. await 자체가 새 OS 스레드를 매번 생성하거나 CPU 계산을 자동 병렬화하는 것도 아니다. I/O 완료를 기다리는 상태와 CPU를 사용해 계산하는 상태를 구분한다.

**소유권 예제:** 이미지 버퍼를 생산 스레드가 채운 뒤 큐에 넣고 다시 덮어 쓰면 소비자는 동일 객체의 바뀐 내용에 접근할 수 있다. 복사·불변 데이터·소유권 이전·재사용 완료 신호 중 계약을 정해야 한다. 큐 자체가 스레드 안전해도 큐 안의 가변 객체를 임의로 동시에 수정해도 안전하다는 뜻은 아니다.
