# 05-06 품질·유지보수·신뢰성: 출시 후의 소프트웨어 이해하기

[[GI-교재05 소프트웨어공학|과목 목차]] · [[GI-문제05 소프트웨어공학|문제]] · [[GI-해설05 소프트웨어공학|해설]]

### 품질 활동의 역할
품질보증은 적절한 절차와 기준을 통해 품질을 확보하는 활동을 포함한다. 품질관리는 산출물과 측정 결과를 확인하는 활동을 포함한다. 두 용어의 조직별 역할이 겹칠 수 있으므로 단순히 "문서 담당/테스트 담당"으로 고정하지 않는다. 리뷰·정적 분석·테스트·운영 지표는 서로 보완한다.

검증(verification)은 산출물이 명세와 기준에 맞게 만들어졌는지 확인하는 관점이다. 타당성 확인(validation)은 결과가 실제 사용자 필요와 의도한 사용에 적합한지 확인하는 관점이다. 번역이 교재마다 다르기 때문에 영문과 설명을 함께 기억하자. 요구사항 자체가 잘못되면 구현이 명세에 맞더라도 사용 목적에는 맞지 않을 수 있다.

정적 분석은 프로그램을 실행하지 않고 코드·모델 등을 분석한다. 동적 시험은 실행 결과를 확인한다. 정적 분석이 모든 논리 오류를 증명하거나 동적 시험이 모든 실행을 완전히 탐색하는 것은 아니다. 코드 리뷰는 사람의 이해와 문맥 판단을 활용하며 자동 분석과 동일한 활동은 아니다.

### 유지보수 분류
수정 유지보수는 발견된 결함을 고친다. 적응 유지보수는 운영체제·법규·외부 시스템 같은 환경 변화에 맞춘다. 완전 유지보수는 기능·성능·유지보수성 등을 개선한다. 예방 유지보수는 미래의 잠재 결함과 유지보수 문제를 줄이기 위해 수행한다. 현실의 한 작업에는 여러 목적이 섞일 수 있지만 시험은 주된 동기를 묻는다.

장비 고객사 프로토콜이 바뀌어 연결 코드를 변경하면 적응 유지보수 사례다. 틀린 이미지 좌표 계산을 바로잡으면 수정 유지보수다. 조회 속도를 높이는 기능 개선은 완전 유지보수의 사례이고, 중복 로직을 정리해 향후 오류 발생 가능성을 낮추면 예방 관점으로 볼 수 있다.

### 신뢰성과 가용성
신뢰성은 정해진 조건·시간 동안 기능을 실패 없이 수행할 가능성과 관련된다. 가용성은 필요할 때 사용할 수 있는 정도다. 빠르게 복구하는 시스템은 실패가 자주 발생해도 일정한 가용성을 유지할 수 있지만, 그것이 곧 높은 신뢰성을 의미하지는 않는다.

가용성 계산에는 가정이 중요하다. 안정 상태의 단순 모델에서 평균 정상 운영 시간을 MTBF, 평균 복구 시간을 MTTR로 두면 가용성은 MTBF/(MTBF+MTTR)로 근사한다. MTBF를 고장 사이의 시간으로 정의하는 방식이나 계획 중단 포함 여부가 다르면 계산 기준을 다시 확인한다. 시험에서는 제시된 정의를 우선한다.

### 단계별 숫자 예제
가상 서비스의 평균 정상 운영 시간이 99시간, 평균 복구 시간이 1시간이라면 가용성은 99/(99+1)=0.99, 즉 99%다. 복구 시간을 0.5시간으로 줄이면 99/99.5 약 99.497%다. 운영 시간을 늘리거나 복구 시간을 줄이는 것이 가용성 개선에 기여한다. 30일을 720시간으로 보고 99.9%가 보장되는 단순 조건이면 허용 중단 시간은 720×0.001=0.72시간, 즉 43.2분이다. 실제 SLA에는 제외 조건과 측정 방식이 있으므로 이 계산을 실제 계약에 그대로 적용하지 않는다.

### 기술부채와 리팩터링
기술부채는 빠른 선택이 나중의 변경 비용과 위험을 늘릴 수 있다는 비유다. 코드가 오래됐다는 이유만으로 모두 기술부채는 아니다. 리팩터링은 외부 관찰 가능한 동작을 유지하면서 내부 구조를 개선하는 활동이다. 새 기능 추가나 버그 수정과 함께 진행할 수 있지만 개념상 목적을 구분한다. 회귀시험과 작은 변경 단위가 안전한 리팩터링을 돕는다.

### 자가 연습과 풀이
인터넷 API 버전 폐지에 맞춰 연계 코드를 바꾸는 작업은 적응 유지보수가 중심이다. 처리 결과는 같게 유지하면서 긴 함수만 분리하는 작업은 리팩터링의 전형적인 예다. 성능 개선을 목표로 알고리즘의 외부 응답 특성을 바꾼다면 그 변경은 단순 리팩터링과 구별해 기록한다.

### 완료 기준
유지보수 4종을 사례로 구분하고, 가용성 계산에서 운영 시간·복구 시간·측정 기간의 단위를 맞출 수 있어야 한다.

### 응용 문제: 장애 지표의 정의를 확인하기
관찰 기간 총 100시간 중 중단이 2시간이면 단순 관측 가용성은 98/100=98%다. 이것은 평균 정상 운영 시간과 평균 복구 시간을 사용하는 안정 상태 모형과 입력 의미가 다르다. "MTBF 100시간"이라는 말이 정상 운영 시간인지 실패 시작 사이의 전체 경과 시간인지 불분명하다면 식에 넣기 전에 정의를 확인한다.

신뢰성 향상은 오류가 덜 발생하도록 원인을 줄이는 활동과 연결되고, 유지보수성 향상은 원인 분석과 수리가 쉽도록 만드는 활동과 연결된다. 복구 절차 자동화로 MTTR이 줄어 가용성이 개선되어도 고장 원인이 그대로라면 고장 빈도는 줄지 않을 수 있다. 지표 하나를 전체 품질의 증거로 확대하지 않는다.

### 강화 손풀이: 복구 개선과 고장 빈도를 구분
가상 반복 모형에서 평균 정상 운전은 48시간, 평균 복구는 2시간이다. 가용성은 48/(48+2)=96%다. 정상 운전은 그대로이고 복구만 1시간으로 줄이면 48/49 약 97.959%다. 고장 빈도가 줄었다는 관측 없이 신뢰성까지 개선됐다고 단정하지 않는다.
관측 10일=240시간 중 장애 3시간·계획 중단 1시간이고 모든 중단을 포함한다는 가상 보고 규약이면 가용 시간은 236시간, 관측 가용성은 236/240 약 98.333%다. SLA가 계획 중단을 제외한다면 분모와 분자의 규약을 다시 정의해야 하며 여기 수치를 계약에 그대로 옮기지 않는다.
유지보수 동기를 따로 적어보자. 외부 API 변경에 맞추는 것은 적응, 잘못된 합계 수정은 수정, 조회 성능 개선은 완전, 잠재 오류 예방은 예방 관점이다. '변경 줄 수가 적다'는 분류 근거가 아니다. 리팩터링이라면 보존하려는 외부 동작과 회귀 검증을 명시한다.
