# 03-01 데이터 모델·키·무결성: 표를 만들기 전에 결정할 것

[[GI-교재03 DB_SQL|과목 목차]] · [[GI-문제03 DB_SQL|문제]] · [[GI-해설03 DB_SQL|해설]]

## 학습 목표와 전공 연결
검사 프로그램의 객체 목록을 테이블에 저장한다고 생각하자. 프로그램 안에서 같은 장비 객체가 두 번 생기면 참조를 비교할 수 있지만, DB에는 여러 프로그램이 동시에 접근한다. 따라서 중복·참조 오류를 프로그램의 선의에 맡기지 않고 데이터 규칙으로 표현해야 한다. 이 장을 끝내면 개체와 관계, 키의 최소성, 참조 무결성을 구분한다.

## 1. 데이터베이스가 파일 저장과 다른 이유
DBMS는 데이터 정의, 질의, 동시 접근, 복구, 권한을 관리한다. 데이터베이스는 관리 대상 데이터이고 DBMS는 이를 관리하는 소프트웨어다. 스키마는 테이블 이름·열·자료형·제약과 같은 구조이며 인스턴스는 특정 시점의 실제 행들이다. 행이 추가되어도 스키마가 반드시 바뀌는 것은 아니다.

외부 스키마는 사용자 관점, 개념 스키마는 조직의 논리 구조, 내부 스키마는 저장 방법을 나타낸다. 물리적 데이터 독립성은 파일 배치나 인덱스 변경이 논리 구조에 미치는 영향을 줄이는 성질이다. 논리적 데이터 독립성은 논리 구조 변화가 사용자 뷰에 미치는 영향을 줄이는 성질이다. 완전히 아무 변경도 필요 없다는 절대 명제가 아니라 층 사이 의존을 줄인다는 의미로 이해한다.

관계 모델의 릴레이션은 속성과 튜플로 표현된다. 수학적 관계는 집합이므로 같은 튜플의 중복을 허용하지 않으며 순서가 본질적이지 않다. SQL 조회 결과는 기본적으로 중복을 유지할 수 있다. `ORDER BY`가 없으면 출력 순서를 시험 답안의 근거로 사용하지 않는다.

## 2. 개체와 관계를 테이블로 변환하기
개체는 독립적으로 구분할 대상이다. 고객, 계좌, 거래가 예다. 속성은 고객 이름, 계좌 잔액처럼 대상의 성질이다. 관계의 차수는 참여하는 개체 유형 수이고 카디널리티는 각 유형 사이 대응 수를 말한다. 두 용어를 혼동하지 않는다.

고객 한 명이 여러 계좌를 보유하고 한 계좌의 소유자는 한 명이라는 업무 규칙이면 고객: 계좌는 1:N이다. 이때 N 쪽 계좌에 고객 ID를 외래키로 둔다. 공동 계좌를 허용하면 규칙 자체가 달라진다. 두 명 이상 고객과 여러 계좌의 연결은 M:N이고 고객 계좌 연결 테이블이 필요하다. 업무 규칙을 먼저 확정하고 도식에 맞춰 추론한다.

| 상황 | 구현 예 | 함께 검토할 규칙 |
| --- | --- | --- |
| 1:N 고객-계좌 | 계좌에 고객 ID 외래키 | 계좌에 소유자가 반드시 필요한가 |
| M:N 학생-강좌 | 수강(학생 ID, 강좌 ID) | 같은 강좌를 재수강하는 학기를 키에 포함하는가 |
| 1:1 직원-사물함 | 외래키 + UNIQUE | 미배정 직원과 미사용 사물함 허용 여부 |
| 약한 개체 주문 항목 | 주문 ID + 항목 번호 복합 키 | 항목 번호가 주문 안에서만 유일한가 |

## 3. 키는 유일성과 최소성을 함께 본다
슈퍼키는 모든 행을 유일하게 식별하는 속성 집합이다. 후보키는 최소 슈퍼키다. 여기서 최소는 속성 하나라도 빼면 유일 식별을 보장할 수 없다는 뜻이지, 여러 후보키 중 열 수가 가장 적다는 뜻이 아니다. 후보키 중 기본 키로 선택하지 않은 것을 대체키라고 한다. 복합 키는 두 개 이상 속성으로 구성된 키다.

기본 키는 유일하고 NULL을 허용하지 않는다. 외래키는 다른 테이블의 후보키 등에 대한 참조 규칙을 구현한다. 외래키 자체가 항상 유일하거나 항상 NOT NULL인 것은 아니다. 외래키를 NOT NULL로 지정하면 관계 참여를 강제하는 데 도움을 준다. 실제 제품이 외래키 참조 대상으로 허용하는 UNIQUE·키 규칙은 제품 문서를 확인한다.

### 손풀이 예제 1: 후보키와 복합 슈퍼키
직원(직원 번호, 주민 식별 코드, 이름, 부서)에서 직원 번호와 주민 식별 코드는 각각 전 직원에 대해 유일하고 NULL이 아니라고 업무 규칙으로 주어졌다. 이름은 중복 가능하다. 후보키는 {직원 번호}, {주민 식별 코드}다. {직원 번호, 이름}은 슈퍼키지만 후보키가 아니다. 이름을 빼도 직원 번호만으로 식별하기 때문이다. {이름, 부서}는 현재 행이 우연히 구별되어도 규칙상 유일성을 보장하지 못하므로 키라고 결론 내리지 않는다.

### 손풀이 예제 2: 수강 이력
수강(학생 ID, 강좌 ID, 학기, 성적)에서 한 학생은 같은 학기에 같은 강좌를 한 번만 수강하고 다른 학기에는 재수강 가능하다. 키는 (학생 ID, 강좌 ID, 학기)다. (학생 ID, 강좌 ID)만 키로 두면 정상적인 재수강 행을 삽입할 수 없다. 기본 키 선택은 자료 구조보다 업무 규칙이 먼저다.

## 4. 제약을 SQL로 표현하기
다음은 공통 학습용 구조다. 실제 운영 금액에는 업무 범위에 적합한 DECIMAL 정밀도와 반올림 규칙을 별도로 정한다.

```sql
CREATE TABLE customer (
  customer_id INTEGER PRIMARY KEY,
  name VARCHAR(30) NOT NULL
);
CREATE TABLE account (
  account_id INTEGER PRIMARY KEY,
  customer_id INTEGER NOT NULL,
  balance DECIMAL(12,2) NOT NULL CHECK (balance >= 0),
  FOREIGN KEY (customer_id) REFERENCES customer(customer_id)
);
```

개체 무결성은 기본 키의 유일성과 비NULL, 참조 무결성은 참조 대상의 존재, 도메인 무결성은 자료형·값 범위 같은 속성 규칙이다. `CHECK (balance >= 0)`만으로 NULL이 배제된다고 생각하지 않는다. SQL에서 CHECK 조건의 UNKNOWN 처리 때문에 NOT NULL과 별도로 검토해야 한다. DBMS별 CHECK 지원 버전·제약 평가 규칙도 확인한다.

### 직접 풀기
고객 1,2가 있고 계좌의 customer_id를 NOT NULL 외래키로 둔다. ① 고객 ID 3을 가진 계좌 추가 ② 고객 ID NULL인 계좌 추가 ③ 고객 1의 계좌 두 개 추가 중 가능한 것은 무엇인가?

### 확인해설
③은 1:N 규칙과 맞아 가능하다. ①은 참조 대상 부재, ②는 NOT NULL 위반이다. 외래키가 있으므로 고객별 계좌가 한 개뿐이라는 해석은 틀리다. UNIQUE를 추가한 경우에만 별도 제약이 된다.

## 오해 교정과 완료 기준
- 현재 샘플에서 유일한 열과 업무 규칙상 후보키는 다르다.
- 기본 키는 DB가 고른 행 번호라는 뜻이 아니다. 자연 키·대리키 모두 선택 가능하다.
- ID를 추가해도 이름·코드의 업무상 중복 금지 규칙은 사라지지 않는다.
- 완료: 새로운 사례에서 후보키를 쓰고, 불필요한 속성을 하나씩 빼 최소성을 설명한다.

참고: [PostgreSQL 제약](https://www.postgresql.org/docs/current/ddl-constraints.html). 예제의 업무 규칙과 데이터는 자체 제작이다.

## 강화 손풀이: 키 제약과 업무 중복은 따로 확인한다
가입(member_id,email,team_id)에서 member_id가 기본 키이고 email은 필수가 아니며, 입력된 이메일은 중복 금지라는 업무 규칙을 가정한다. member_id만 추가한다고 이메일 중복 규칙이 표현되지는 않는다. email에 UNIQUE가 필요한지 별도로 판단한다. NULL의 중복 처리와 문자열 대소문자·공백 동등성은 제품·정렬 규칙에 따라 확인해야 한다.

더 안전한 사고 순서는 ① 업무상 같은 대상을 무엇으로 판단하는가 ② 값이 없는 상태를 허용하는가 ③ 어느 열 조합에서 중복을 금지하는가 ④ 참조 대상이 삭제되면 어떻게 할 것인가다. 기본 키, NOT NULL, UNIQUE, FOREIGN KEY가 각각 다른 질문에 답한다.

**반례:** order_id를 대리 기본 키로 둔 수강 이력에서 (student_id,course_id,term)에 UNIQUE를 두지 않으면 같은 학기의 동일 수강이 서로 다른 order_id로 두 번 들어갈 수 있다. 대리키가 참조를 단순하게 해 주어도 업무 유일성 검사는 남는다.

**손으로 판정:** 한 고객의 두 계좌는 customer_id 외래키만으로 허용된다. customer_id에 UNIQUE를 추가하면 고객당 최대 한 계좌가 되며, NOT NULL까지 추가해도 고객이 반드시 계좌를 가진다는 역방향 참여까지 강제하지는 않는다.
