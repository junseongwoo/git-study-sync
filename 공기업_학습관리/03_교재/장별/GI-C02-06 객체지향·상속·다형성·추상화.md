# 02-06 객체지향·상속·다형성·추상화

[[GI-교재02 프로그래밍_Cpp_Python|과목 목차]] · [[GI-문제02 프로그래밍_Cpp_Python|문제]] · [[GI-해설02 프로그래밍_Cpp_Python|해설]]

## 용어보다 호출 결과의 원리를 이해한다
클래스는 데이터와 동작의 구조를 정의하고 객체는 그 구조를 바탕으로 만들어진 실행 중 실체다. 캡슐화는 내부 표현을 바깥 사용과 분리하고 허용된 인터페이스로 불변 조건을 유지하는 것이다. private 필드를 썼다는 사실만으로 잘 설계된 캡슐화가 완성되는 것은 아니다.

### 1. 상속과 구성
상속은 기존 타입의 관계를 확장하고 구성은 객체가 다른 객체를 포함해 협력하도록 만든다. “자동차는 엔진이다”는 잘못된 is-a 관계이며 자동차가 엔진을 갖는 has-a 구성 관계다. 모든 코드 중복을 상속으로 해결하면 부적절한 대체 관계가 생길 수 있다. 금융 계좌 잔액은 음수가 가능한지 같은 규칙을 클래스가 보장해야 한다.

예제 A: 검사기의 공통 인터페이스 inspect()를 두고 점등 검사·이미지 검사가 구현하게 하는 것은 기존 장비 경력과 연결된다. 하지만 특정 고객사 연결 방식·파일 포맷을 깊은 상속 층으로 만드는 것이 항상 최선은 아니다. 변경 이유가 다른 기능을 구성하여 교체할 수도 있다. 객체지향의 목표는 “상속을 최대한 많이 사용”이 아니다.

### 2. 오버로딩과 오버라이딩
오버로딩은 같은 이름에 다른 매개변수 형태를 정의하는 것, 오버라이딩은 상위 타입의 동작을 하위 타입에서 재정의하는 것이다. 반환 타입만 다른 함수를 모두 오버로딩할 수 있다고 단정하지 않는다. 언어의 허용 규칙을 확인한다.

동적 디스패치는 실제 객체의 타입에 따라 적절한 재정의 동작을 선택한다. 정적 타입은 소스에서 변수에 부여된 타입, 동적 타입은 실행 중 객체의 타입이라고 학습한다. 모든 멤버가 자동으로 동적 호출되는 것은 아니다. C++은 virtual, C#은 virtual/override 등의 선언이 중요하다. Java의 일반 인스턴스 메서드 규칙과 static/필드 규칙도 구별한다.

예제 B: C++에서 Base의 virtual f가1, Derived의 override f가2를 반환한다고 하자. Derived 객체를 가리키는 Base&로 f를 호출하면2다. virtual이 없는 Base의 같은 이름 함수라면 선언된 타입을 기준으로 선택될 수 있다. C++에서 기반 클래스 포인터로 파생 객체를 삭제하는 다형적 사용에는 virtual 소멸자 같은 수명 설계도 중요하다.

### 3. 객체 슬라이싱과 다형성
C++에서 Derived 객체를 Base 값 변수에 복사하면 Base 부분만 담는 객체 슬라이싱이 생길 수 있다. Base 포인터·참조로 파생 객체를 다루는 것과 다르다. 단순히 “상속했으니 어느 변수에서든 파생 동작”이라고 답하지 않는다.

C#·Java의 참조 형 변수에 하위 클래스 객체를 대입하는 일은 C++ 기반 값 객체 복사와 동일한 슬라이싱 모델이 아니다. 값 형·참조 형, 실제 객체 생성·변수 대입·메서드 선언을 함께 본다. Python은 이름의 정적 클래스 타입 선언보다 객체가 제공하는 동작을 활용하는 duck typing을 자주 사용한다.

### 4. 추상 클래스와 인터페이스
추상 클래스는 직접 인스턴스화하지 못하도록 하고 공통 틀과 일부 구현을 제공할 수 있다. 인터페이스는 제공해야 할 동작의 계약을 표현한다. 특정 언어·버전에서 인터페이스가 기본 구현을 허용하는 등의 세부 기능이 달라져 “인터페이스는 언제나 어떤 구현도 못 가진다” 같은 절대 문장은 피한다.

예제 C: PaymentProcessor가 authorize(amount)를 제공한다는 계약이 있다면 사용자는 카드·계좌 처리 내부를 모르고 그 계약을 사용할 수 있다. 성공·실패·예외·중복 요청 처리의 의미도 계약에 포함되어야 한다. 이름과 매개변수만 같아도 의미가 다르면 올바른 대체가 아니다.

### 5. static과 인스턴스, 접근 제한
인스턴스 필드는 각 객체의 상태를 나타내고 static/class 멤버는 타입 차원의 공유 상태나 동작에 사용한다. “static은 모든 경우 메모리 한 번만 쓴다” 같은 표현보다 선언한 클래스·로드·생명주기 범위를 생각한다. static 메서드에는 특정 인스턴스를 자동 제공하는 this가 없으므로 인스턴스 상태를 쓰려면 대상이 필요하다.

손풀이 예제 D: 객체 a와 b의 개별 balance를 각각10,20으로 유지하며 class-level created_count가 두 번 생성 후2라면 balance는 객체마다 다르고 count는 공유 개념이다. Python 클래스 속성에 변경 가능한 목록을 두고 인스턴스에서 append하면 공유가 드러날 수 있어 객체별 목록은 생성자에서 만든다.

### 6. SOLID를 코드 결과와 연결
단일 책임은 클래스가 한 가지 변경 이유에 집중하는 원칙, 개방·폐쇄는 기존 사용의 변경을 줄이며 확장, 리스코프 대체는 하위 타입이 상위 계약을 깨뜨리지 않는 대체, 인터페이스 분리는 사용하지 않는 동작 의존을 줄임, 의존성 역전은 세부 구현보다 추상 계약에 의존하게 하는 것이다. 이 장은 프로그래밍 관점의 시작이며 자세한 설계·시험은 소프트웨어공학 교재와 연결한다.

### 완료 기준
상속·구성의 예 하나, 오버로딩·오버라이딩 차이, C++ virtual 호출과 값 복사의 차이를 말한다. 실제 장비 코드의 클래스 하나를 골라 무엇이 객체별 상태이고 무엇이 공유 상태인지 표시하면 이론이 경험과 연결된다.

### 보강 손풀이: 호출 종류를 먼저 분류하기
정적 타입 Base,실제 객체 Derived라는 조건만 적지 말고 호출 대상이 인스턴스 virtual 메서드인지,static 메서드인지,필드인지 먼저 표시한다. Java의 일반 인스턴스 오버라이딩과 C++ virtual 호출은 동적 동작을 설명할 수 있지만 필드 숨김까지 같은 규칙을 적용할 수는 없다.

C++에서 Base 값 변수에 Derived를 복사한 경우는 새 Base 객체가 만들어지는 슬라이싱 모델이다. Base&가 기존 Derived를 가리키는 경우와 그림이 다르다. 포인터·참조·값 중 무엇인지 표시하면 “부모 타입 변수에 자식이 있으니 무조건2”라는 단순 암기를 피한다.

클래스 계층 연습에서는 출력 숫자만 쓰지 말고 어떤 함수 정의가 선택되는지를 한 줄로 적는다. 인터페이스/추상 클래스를 사용해도 실제 객체를 만드는 과정과 오류 계약은 별도로 존재한다. 장비의 검사 전략을 한 가지 바꾸는 예로 상속과 구성을 각각 모델링해 보고 변경 영향이 어떤지 비교한다.

### 강화 응용: 조건을 바꾸어 다시 증명하기
C++ 다형성에서 호출 방식과 소멸 방식은 별도로 설계한다. Base::f가 virtual이면 실제 객체가 Derived일 때 Base*를 통한 f 호출은 재정의한 Derived::f로 연결될 수 있다. virtual이 아닌 동일 이름 함수는 정적 형의 Base::f를 선택한다. 기반 포인터로 파생 객체를 delete할 설계라면 기반 소멸자를 virtual로 두어야 한다. 그렇지 않은 삭제는 정의되지 않은 동작이므로 '기반 소멸자만 실행되어 조금 누수'라는 확정 결과로 축소하지 않는다.

상속 관계가 문법상 가능해도 대체 가능성이 필요한 인터페이스 계약을 깨뜨릴 수 있다. 기본 구현이 '음수 입력도 처리한다'고 약속했다면 파생 구현이 '양수만 허용한다'로 전제조건을 강화하면 기존 호출자가 깨진다. 반환 결과의 보장을 약화하는 것도 위험하다. 구현을 재사용하고 싶다는 이유만으로 상속을 택하지 않고 협력 객체를 보유하는 합성도 검토한다.

Python super()는 단순히 코드에 적힌 첫 부모를 호출하는 문법이라고 일반화하지 않는다. 실제 객체의 MRO에 따른 다음 구현을 찾는다. 다중 상속의 협력 호출에서는 같은 이름 메서드들이 일관된 인수와 super 호출 정책을 공유해야 한다. 기초 문제에서는 클래스 관계·메서드 정의·호출 대상을 모두 제시한 뒤 순서를 추적한다.
