# 03-07 인덱스·B+트리·실행계획: 빠르다는 말을 검증하기

[[GI-교재03 DB_SQL|과목 목차]] · [[GI-문제03 DB_SQL|문제]] · [[GI-해설03 DB_SQL|해설]]

## 학습 목표
인덱스가 항상 빠르다는 문장을 버리고 검색 조건·선택도·정렬·쓰기 비용을 함께 본다. B 트리 계열과 해시 인덱스의 적합 질의를 구분하고 실행 계획의 추정과 실제를 구분한다.

## 1. 페이지와 탐색 비용
DBMS는 보통 저장소를 페이지 또는 블록 단위로 읽는다. 큰 테이블에서 모든 행을 확인하는 전체 스캔은 많은 페이지를 읽을 수 있다. 인덱스는 키와 위치 정보를 조직하여 후보 행을 찾게한다. 후보가 거의 모든 행이면 인덱스를 훑고 테이블로 왕복하는 것이 전체 스캔보다 비쌀 수 있다. 메모리 캐시·행 크기·저장 배치·병렬 실행 등도 비용에 영향을 준다.

선택 도는 조건이 걸러 내는 정도를 설명할 때 쓰지만 자료마다 '선택되는 비율'과 '선별력' 용법이 혼용된다. 계산에서는 '100 만행 중 100 행 =0.01 % 선택'처럼 분모와 분자를 직접 적어 혼동을 피한다. 성별처럼 값이 적어도 데이터 분포가 치우치면 특정 값의 선택 비율은 작을 수 있다. 카디널리티만으로 인덱스 유용성을 단정하지 않는다.

## 2. B 트리와 B+트리
균형 탐색 트리는 리프 깊이를 맞춰 탐색 비용을 안정적으로 유지한다. B+트리의 전형적 설명에서 내부 노드는 탐색 키·자식 포인터, 리프는 키와 레코드 위치 또는 데이터 정보를 가진다. 리프가 순서대로 연결되어 범위 검색을 이어 가기 좋다. 제품 문서의 B-tree 명칭과 교재의 B +tree 구현 세부는 다를 수 있다.

### 손풀이 예제 15: 팬아웃과 높이
단순 모델에서 한 내부 페이지 4096바이트, 키 16바이트, 포인터 8바이트, 페이지헤더 0바이트라고 가정한다. 키k개면 포인터 k +1개여서 크기는 16k +8(k +1)=24k +8이다. 4096 이하 조건에서 k는 170, 포인터는 171개다. 171 ^2 =29241,171 ^3 =5000211이므로 분기 수가 큰 트리는 작은 높이로 많은 리프에 도달할 수 있다. 실제 페이지 헤더·노드 채움률·키 압축을 고려하면 숫자는 달라진다. 이 예는 높이 원리를 위한 계산이며 실 제품 높이를 보장하지 않는다.

B+트리 범위 검색은 시작 키를 찾아 리프를 순차 탐색한다. 해시 인덱스는 동등 검색에 적합하지만 일반적인 정렬 범위 검색을 직접 지원하는 구조로 설명하지 않는다. 해시 충돌과 버킷 넘침도 가능하다. B 트리 삽입·삭제는 분할·병합·재균형 비용과 페이지 변경을 수반하므로 인덱스 수가 늘면 쓰기 비용이 증가할 수 있다.

## 3. 복합 인덱스와 조건
인덱스가 (branch_id,txn_date) 순으로 정렬되면 같은 지점 안에서 날짜가 이어진다. branch_id =10 AND 날짜 범위는 좋은 시작점이 된다. 날짜만 조건이면 여러 지점의 해당 날짜가 흩어진다. 선두 열 조건이 없으면 항상 인덱스를 절대 사용할 수 없다는 명제는 과하다. 제품·버전의 skip scan 등 다른 경로가 가능하므로 기본 정렬 구조와 실제 실행 계획을 함께 본다.

```sql
CREATE INDEX ix_txn_branch_date ON txn2(branch_id,txn_date);
SELECT txn_id,amount FROM txn2
WHERE branch_id=10
  AND txn_date>='2026-01-01' AND txn_date<'2026-02-01';
```

DATE 열의 표현은 실습 제품의 DATE/ 문자열 정렬 규칙에 맞춰 정한다. 위 문자열 리터럴은 형식 이해 예이며 날짜형 변환은 명시적으로 확인한다. 열에 함수를 씌우는 `YEAR(txn_date)=2026` 같은 조건은 일반 인덱스 활용을 어렵게할 수 있다. 함수 기반·표현 식 인덱스가 있으면 다른 결과가 된다. 이를 '함수가 있으면 모든 인덱스 무조건 불가'로 외우지 않는다.

## 4. 커버링·클러스터·정렬
필요한 열이 인덱스에 모두 있으면 테이블 접근을 줄일 수 있다. 제품마다 index-only scan 조건과 가시성 확인이 달라 항상 0회 테이블 읽기라고 보장하지 않는다. 클러스터 링은 행의 물리 배치와 인덱스 순서를 관련시키는 개념이다. MySQL InnoDB와 다른 DBMS의 clustered 용어·구현을 동일하게 취급하지 않는다.

ORDER BY와 인덱스 키 순서가 맞으면 정렬 단계를 줄일 수 있지만 조건·방향·NULL 순서·추가 열·실행 계획에 달려 있다. 인덱스가 있다는 이유만으로 결과가 정렬되어 나온다고 의존하지 않는다. 요구되는 결과 순서는 항상 ORDER BY로 표현한다.

## 5. 실행계획 읽기
EXPLAIN은 계획과 비용 추정을 보여 준다. PostgreSQL EXPLAIN ANALYZE는 질의를 실제 실행하여 측정한다. 쓰기 질의에 실행 분석을 적용하면 데이터가 실제로 바뀔 수 있어 안전한 실습 DB나 롤백 가능한 거래 안에서 확인한다. 비용 숫자를 시간 밀리 초로 바로 읽지 않는다. 추정 행수, 실제 행수, 반복 횟수, 접근 방식, 정렬·조인 연산을 구분한다.

### 손풀이 예제 16: 추정 오류 찾기
스캔 노드가 예상 100 행, 실제 10000 행이면 조건 선택 비율 추정이 100 배 틀렸다. 다음 nested loop가 바깥 10000 행마다 안쪽 탐색을 하게 되면 계획의 의도와 실제 비용이 크게 달라질 수 있다. 통계가 오래 되었는지, 값이 치우쳤는지, 열 사이 상관관계가 있는지 확인한다. 무조건 인덱스 하나 추가하거나 힌트로 고정하는 것이 첫 해결책은 아니다.

조인 방식에서 nested loop는 작은 바깥 집합과 안쪽 인덱스 탐색 등에 유리할 수 있다. hash join은 동등 조인에서 해시 테이블을 이용하고, merge join은 정렬된 입력을 함께 훑는다. 메모리 부족·입력 크기·정렬 비용·조건 특성 때문에 어느 하나가 항상 최선이라는 명제는 틀리다.

## 6. 튜닝 학습의 순서
정답 결과 확인 -> 대표 데이터와 경계 데이터 구성 -> 계획의 추정/ 실제 비교 -> 병목 가설 -> 한 가지 변경 -> 결과 동일성·비용 재측정 순서로 한다. 쿼리의 NULL·중복 의미를 바꾸면서 빠르게 만든 것은 올바른 최적화가 아니다.

### 직접 풀기와 확인
100 만행 중 조건 A가 100 행, 조건 B가 80 만 행을 고른다. 두 조건이 같은 폭의 행을 반환하고 다른 비용 조건도 같다면 A가 인덱스 후보로 더 유리하다. 그러나 A의 열에 인덱스가 존재한다는 사실만으로 특정 DB에서 반드시 인덱스를 선택한다고 말하지 않는다. 통계·캐시·비용 추정이 필요하다.

완료: 인덱스 키 순서를 종이에 정렬해 그리고, 동등/ 범위/ 정렬 요구를 설명한다. 참고: [PostgreSQL 복합 인덱스](https://www.postgresql.org/docs/current/indexes-multicolumn.html), [EXPLAIN](https://www.postgresql.org/docs/current/using-explain.html). 비용·팬아웃 계산은 명시한 자체 모델이다.

## 강화 손풀이: 인덱스의 유리함을 선택도와 요청 열로 판단한다
100만 행 로그에서 status='완료'가 90만 행, trace_id='T7'가 한 행이라고 가정한다. 두 조건에 모두 인덱스가 있어도 어떤 계획이 빠른지는 같은 결론이 아니다. 넓은 범위를 인덱스로 따라가며 테이블을 반복 방문하면 순차 스캔보다 비쌀 수 있다. 통계, 물리 배치, 캐시, 요청 열, 제품의 비용 모델이 관여한다.

복합 B-tree 인덱스 (branch_id,created_at,id)를 생각하자. branch_id 동등 조건과 created_at 범위 조건은 정렬된 연속 범위를 찾는 데 유리한 대표 사례다. 세 번째 id의 조건이 붙었다고 항상 범위가 그만큼 줄어드는 것은 아니다. 제품의 최적화 방식과 실제 실행계획을 확인한다. 선두 열이 없는 검색도 모든 제품에서 무조건 인덱스를 못 쓴다고 단정하지 않는다.

**측정 반례:** 실제 실행계획의 예상 행 수 100,실제 행 수 10만이면 추정 오차가 크다. '인덱스를 사용했다'보다 추정-실제 차이, 반복 횟수, 필터 탈락, 읽은 블록을 확인해야 한다. 실제 실행 기능은 문장을 실행하므로 변경문에는 주의한다. 실습은 별도 DB에서 수행한다.
