# 07-05 TCP·UDP·신뢰성·흐름/혼잡 제어: 무엇을 보장하는가

[[GI-교재07 네트워크|과목 목차]] · [[GI-문제07 네트워크|문제]] · [[GI-해설07 네트워크|해설]]

## 학습 목표
TCP의 바이트 스트림과 UDP 데이터 그램을 비교하고, TCP가 응용 메시지 경계를 보장하지 않음을 이해한다. 수신자의 처리 능력과 네트워크 혼잡을 서로 다른 제어 문제로 본다.

## 1. TCP와 UDP
TCP는 연결 상태를 관리하고 순서·중복·손실을 제어하여 응용에 바이트 스트림을 제공한다. UDP는 개별 데이터 그램을 전달하는 간단한 전송 프로토콜로, 기본 UDP만으로 전달·순서·중복 방지를 보장하지 않는다. 그렇다고 UDP 위에서 신뢰성 있는 응용 프로토콜을 절대 만들 수 없다는 뜻은 아니다. QUIC 같은 상위 설계를 구분한다.

| 항목 | TCP | UDP |
| --- | --- | --- |
| 서비스 기본 단위 | 바이트 스트림 | 데이터 그램 |
| 연결 관리 | 연결 상태 관리 | 기본 UDP는 연결 설정 핸드셰이크 없음 |
| 기본 신뢰성 | 재전송·순서·중복 제어 | 전송 계층에서 동일한 보장 없음 |
| 응용 경계 | 직접 프레이밍 필요 | 데이터 그램 경계 유지 |
| 기본 헤더 | 최소 20바이트 | 8바이트 |

UDP도 포트를 사용하며 체크섬 등 기본 오류 검출이 있다. IPv4/IPv6에 따른 체크섬 필수 조건을 동일하게 외우지 않는다. 'UDP는 무조건 빠르고 TCP 는 무조건 느림'은 요구·손실·설계 비용을 무시한 명제다.

## 2. 연결 식별과 3-way handshake
TCP 연결은 출발 IP·출발 포트·목적 IP·목적포트 등의 끝점으로 구분된다. 서버의 443 포트 하나로 여러 클라이언트의 서로 다른 연결을 관리할 수 있다. 클라이언트가 같은 서버에 재접속할 때도 포트·상태·시간 조건을 고려한다.

### 손풀이 예제 13: SYN과 번호
클라이언트 최초 sequence =700, 서버 최초 =900이라고 가정한다. 클라이언트 SYN(seq700), 서버 SYN +ACK(seq900,ack701), 클라이언트 ACK(seq701,ack901)로 시작한다. SYN은 데이터가 없어도 순서 번호 공간에서 1을 소비한다. FIN도 1을 소비한다. ACK 플래그만 있는 세그먼트는 그 자체로 데이터 바이트를 소비하는 것은 아니다.

TCP 연결 성립이 로그인 인증이나 TLS 암호화 완료를 뜻하지 않는다. 응용 인증과 보안 채널은 다른 단계다. 종료는 양쪽 방향을 별도로 닫는 개념이므로 반쪽 종료가 가능하다. TIME_WAIT은 지연된 이 전 세그먼트와 종료 제어 등과 관련되며, 이를 '서버 장애 상태'로 단정하지 않는다.

## 3.바이트 번호와 누적 ACK
### 손풀이 예제 14
첫 데이터 바이트 sequence =1000이고 payload200바이트를 연속 수신하면 다음 기대바이트는 1200, 누적 ACK =1200이다. 1000~1199 를 받았다는 뜻이다. ACK를 마지막 수신 바이트 1199로 쓰면 1 차이가 난다. 순서가 어긋나 나중 데이터가 먼저 와도 연속 구간에 빈틈이 있으면 누적 ACK는 아직 필요한 앞 바이트를 가리킨다. SACK은 별도로 수신 구간 정보를 알려 줄 수 있다.

패킷 하나가 손실되어도 각 바이트의 의미가 응용 요청과 같지는 않다. TCP는 데이터 전송을 제어하지만 송금 요청이 서버에서 처리되었는지까지 확인하는 거래 의미는 응용 응답·거래ID·멱등성 설계가 필요하다. 연결이 끊겼다고 같은 요청을 무조건 다시 보내면 중복 업무가 생길 수 있다.

## 4. 흐름 제어와 혼잡 제어
수신 윈도 rwnd는 수신 측 버퍼·처리 능력에 관련된 흐름 제어다. 혼잡 윈도 cwnd는 네트워크 혼잡에 대응하는 송신 측 제한이다. 전송 가능한 미확인 데이터는 두 제한 등 조건을 함께 받는다. cwnd와 rwnd를 같다고 취급하지 않는다.

### 손풀이 예제 15: 윈도에 의한 처리량 상한
cwnd =64,000 바이트,rwnd =32,000 바이트,RTT20ms, 연속 송신·손실 없음 등 단순 모델이면 미확인 데이터 제한은 32,000바이트다. 상한 근사값 32,000/0.02 =1,600,000byte/s =12.8Mbit/s다. 물리 링크가 100Mbit/s 여도 윈도 조건 때문에 다 못 채울 수 있다. 실제 전송은 ACK 방식·혼잡 알고리즘·응용·버퍼에 따라 달라진다.

## 5. 혼잡 제어 기초 모델
고전적 Reno 계열의 원리를 배우는 단순 예에서 slow start는 ACK에 따라 윈도를 빠르게 늘리고 혼잡 회피는 더 완만하게 늘린다. 손실·타임 아웃 등에 반응하여 윈도를 조정한다. 실제 현대 시스템은 CUBIC·BBR 등 다양한 알고리즘을 사용할 수 있어 본 예를 모든 OS의 현재 구현이라고 말하지 않는다.

### 손풀이 예제 16: 단순 slow start
초기 cwnd =1MSS, 임계 값 8MSS,RTT당 두 배 증가, 손실 없음이라는 학습 모델을 명시한다. 시작 1,1RTT 후 2,2RTT 후 4,3RTT 후 8이다. 이후 혼잡 회피를 RTT당 1MSS 증가로 가정하면 다음 9다. 초기 윈도 1이 항상 현재 TCP 기본 값인 것은 아니다. ACK마다의 정교한 구현과 학습용 RTT 단위 모델을 구분한다.

## 6. 메시지 경계
응용이 send로 'ABC'와'DEF'를 두 번 보냈다고 상대 recv가 꼭 두 번에 3바이트씩 받는 것은 아니다. 6바이트를 한 번에 받거나 1 +5 바이트 등으로 나뉠 수 있다. 바이트 스트림 위에 고정 길이, 구분자, 길이 헤더 같은 메시지 경계 규칙을 만든다. 텍스트 구분자에는 escaping, 길이 헤더에는 최대 값과 부분 수신 검사가 필요하다.

### 직접 풀기와 확인
sequence5000에서 100바이트와 150바이트를 빠짐없이 연속 수신하면 다음 기대바이트는 5250이다. TCP 기본 헤더 길이는 ACK 번호 계산에 더하지 않는다. 순서 번호는 payload 바이트와 SYN·FIN 소비를 따로 본다.

완료: SYN 번호·누적 ACK·두윈도·프레이밍을 각각 독립 설명한다. 참고: [TCP RFC9293](https://www.rfc-editor.org/rfc/rfc9293.html), [UDP RFC768](https://www.rfc-editor.org/rfc/rfc768.html), [기초 혼잡제어 RFC5681](https://www.rfc-editor.org/rfc/rfc5681.html). 번호·윈도 예제는 자체 제작한 단순 모델이다.

## 강화 손풀이: TCP 바이트 번호와 속도 상한의 다른 단위를 연결한다
순서 번호1000부터 데이터120바이트를 연속 수신했다면 다음 기대 바이트는1120이어서 누적 ACK=1120이다. 이 예제는 순서 번호 랩어라운드·SYN·FIN을 제외한다. ACK는 받은 세그먼트 개수가 아니라 바이트 순서 공간의 위치를 나타낸다.

전송 가능 in-flight가 cwnd=20KiB,rwnd=12KiB이고 RTT40ms,손실·재전송·연결 준비 비용 없이 충분한 데이터가 있다고 하자. 두 윈도 중 작은12KiB=12288바이트가 제한이다. 단순 윈도 상한은12288×8/0.04=2457600bit/s=2.4576Mbps다. 링크 속도가10Mbps여도 이 모델에서는 윈도 상한이 더 작다. 실제 goodput은 헤더·혼잡 변화 등의 영향으로 더 낮을 수 있다.

**개념 비교:** rwnd는 수신 측 버퍼 여유와 관련한 흐름 제어,cwnd는 송신 측의 네트워크 혼잡 제어 상태다. UDP 사용은 연결 준비와 전송 계약이 다르다는 의미이며 자동으로 애플리케이션 신뢰성이 필요 없어지거나 언제나 TCP보다 빠르다는 보장은 아니다.
