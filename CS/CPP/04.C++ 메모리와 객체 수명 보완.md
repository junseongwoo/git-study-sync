## 3. 메모리를 한 층으로 보면 안 되는 이유

PDF들을 함께 보면 C++ 객체 하나의 메모리는 다음 계층을 거친다.

```text
C++ 객체와 객체 수명
        ↓
new/delete와 C++ 런타임
        ↓
사용자 수준 메모리 할당기와 힙 청크
        ↓
프로세스 가상 주소 공간
        ↓
TLB와 페이지 테이블을 통한 주소 변환
        ↓
물리 프레임 또는 보조 저장장치
```

각 계층의 질문은 서로 다르다.

| 계층 | 핵심 질문 |
|---|---|
| C++ 객체 | 해당 저장 공간에 지금 `T` 객체가 살아 있는가? |
| 소유권 | 누가 객체 또는 자원의 정리를 책임지는가? |
| 할당기 | 요청을 만족할 빈 청크가 있는가? 청크를 분할·병합해야 하는가? |
| 가상 메모리 | 가상 페이지가 유효하며 현재 물리 메모리에 존재하는가? |
| 하드웨어 변환 | TLB에 변환 정보가 있는가? 페이지 테이블을 읽어야 하는가? |

이 질문들은 서로 대체되지 않는다.

- 주소 변환이 성공해도 C++ 객체 수명이 끝났다면 그 객체를 사용하면 안 된다.
- 힙 전체의 빈 공간 합계가 충분해도 연속된 빈 청크가 부족하면 할당이 실패할 수 있다.
- 가상 주소가 유효해도 페이지가 현재 물리 메모리에 없다면 page fault가 발생할 수 있다.
- 스마트 포인터가 객체 수명을 관리해도 객체 내부 범위 검사까지 대신하지는 않는다.

## 4. 힙 할당기의 빈 공간 관리

### 4.1 `malloc`은 시스템 콜 자체가 아니다

OSTEP은 `malloc()`과 `free()`를 사용자 수준 라이브러리 함수로 설명한다. 할당 라이브러리는 프로세스 가상 주소 공간의 일부를 관리하고, 더 큰 영역이 필요할 때 운영체제의 지원을 받는다.

C++의 `new` 표현식도 단순히 “OS에서 페이지 하나를 받는다”는 뜻으로 해석하면 안 된다. 00번의 [[00.메모리·객체 수명·RAII#2.5 C++ 할당에서 물리 메모리까지|C++ 할당에서 물리 메모리까지]]와 연결해 다음처럼 기억한다.

```text
new 표현식
  = 저장 공간 획득 시도
  + 그 저장 공간에 객체 생성

delete 표현식
  = 객체 파괴
  + 저장 공간 반환
```

반환된 저장 공간은 먼저 할당기의 빈 공간으로 돌아갈 수 있다. 이 사실과 객체 수명 종료는 별개의 사건이다.

### 4.2 할당기의 header

`free(void* ptr)`는 크기를 별도 인자로 받지 않는다. OSTEP의 할당기 설명에서는 할당된 청크 앞의 header에 크기 같은 정보를 저장하여, 반환 시 해당 영역의 크기를 알아내는 방식을 보여 준다.

```text
[ allocator header ][ caller가 사용하는 payload ]
                    ↑
                  ptr
```

이 구조는 다음 오류가 왜 할당기 자체까지 손상시킬 수 있는지 이해하는 데 도움이 된다.

- 같은 포인터를 두 번 해제하는 double free
- 할당된 범위 앞이나 뒤를 덮어쓰는 buffer overflow
- 서로 다른 할당·해제 방식을 잘못 짝짓는 오류

구체적인 오류 분류와 C++ 예방책은 [[00.메모리·객체 수명·RAII#10. 메모리 오류 분류]]에서 다룬다.

### 4.3 Splitting

빈 청크가 요청 크기보다 크다면 할당기는 청크를 둘로 나눌 수 있다.

```text
할당 전: [             빈 청크 30             ]
요청 12: [ 사용 12 ][          빈 청크 18       ]
```

요청을 만족한 앞부분은 호출자에게 주고, 나머지는 빈 공간 자료 구조에 남긴다. 이것이 splitting이다.

### 4.4 Coalescing

서로 인접한 빈 청크를 그대로 따로 두면 큰 요청을 만족하지 못할 수 있다.

```text
병합 전: [ 빈 10 ][ 빈 10 ][ 빈 10 ]
병합 후: [             빈 30             ]
```

전체 빈 공간이 30이어도 10짜리 청크 세 개로만 인식하면 20짜리 연속 요청은 실패한다. 반환된 청크의 이웃이 비어 있을 때 하나로 합치는 것이 coalescing이다.

### 4.5 내부 단편화와 외부 단편화

| 구분 | PDF에서 확인되는 의미 |
|---|---|
| 내부 단편화 | 할당기가 요청보다 큰 청크를 제공해 **할당된 청크 내부**에 사용하지 않는 공간이 생김 |
| 외부 단편화 | 빈 공간 총량은 충분하지만 여러 작은 청크로 흩어져 **필요한 연속 청크**가 없음 |

따라서 다음 두 문장은 동시에 참일 수 있다.

- 프로세스의 힙에는 빈 공간이 남아 있다.
- 현재 크기의 새 할당 요청은 실패한다.

### 4.6 적합 정책의 비용

OSTEP과 OCS는 대표적인 연속 할당 정책을 비교한다.

| 정책 | 선택 | 확인되는 특성 |
|---|---|---|
| Best fit | 요청을 만족하는 가장 작은 빈 청크 | 공간 낭비를 줄이려 하지만 전체 검색 비용이 들 수 있음 |
| Worst fit | 가장 큰 빈 청크 | 큰 잔여 청크를 남기려 하지만 검색 비용과 단편화 문제가 있음 |
| First fit | 처음 발견한 충분한 청크 | 전체를 항상 검색하지 않아 빠를 수 있으나 앞부분에 작은 조각이 모일 수 있음 |
| Next fit | 마지막 탐색 위치부터 검색 | 탐색 시작점을 분산시키고 전체 검색을 피하려는 방식 |

핵심은 “Heap은 큰 연속 배열이고 `delete`가 빈칸을 하나 만든다” 정도로 끝나지 않는다는 점이다. 할당기는 청크의 크기와 위치를 추적하고, 분할·병합·탐색 정책을 수행한다.

## 5. 가상 주소 접근의 실제 경로

### 5.1 TLB hit

CPU가 가상 주소를 만들면 하드웨어는 가상 페이지 번호(VPN)에 해당하는 변환 정보가 TLB에 있는지 먼저 확인한다.

```text
가상 주소
  ↓ VPN 추출
TLB 조회 -- hit --> 물리 프레임 번호(PFN)
                         ↓
                     실제 메모리 접근
```

TLB hit이면 페이지 테이블을 추가로 읽지 않고 물리 주소를 얻을 수 있다. OCS는 이 적중률이 실질 메모리 접근 시간에 직접 영향을 준다는 계산 예를 제시한다.

### 5.2 TLB miss

TLB에 변환 정보가 없으면 페이지 테이블에서 PTE를 확인해야 한다.

```text
TLB miss
  ↓
페이지 테이블에서 PTE 조회
  ↓
PTE가 유효하고 페이지가 메모리에 존재
  ↓
PFN을 TLB에 적재
  ↓
명령 재실행
```

TLB miss는 곧바로 “잘못된 포인터”를 뜻하지 않는다. 필요한 주소 변환 정보가 TLB에 없어서 페이지 테이블을 추가로 확인해야 한다는 뜻이다.

### 5.3 Present bit와 page fault

PTE의 present bit는 해당 페이지가 현재 물리 메모리에 존재하는지를 표현한다.

- present bit가 설정되어 있으면 PTE에서 PFN을 얻어 접근을 계속할 수 있다.
- 페이지가 유효하지만 현재 물리 메모리에 없다면 운영체제의 page-fault handler가 필요한 처리를 한다.
- 요구 페이징에서는 필요한 페이지가 처음 접근될 때 메모리에 적재될 수 있다.

따라서 page fault는 언제나 C++ 버그를 뜻하지 않는다. 요구 페이징에서 아직 적재되지 않은 **유효한 페이지**를 처음 접근할 때도 발생할 수 있다.

반대로 C++의 dangling pointer나 out-of-bounds 접근이 항상 page fault로 발견되는 것도 아니다. 잘못된 접근 주소가 우연히 매핑된 페이지 안에 있으면 하드웨어 주소 변환은 성공할 수 있다. C++ 객체 수명과 범위 규칙은 OS의 페이지 존재 검사보다 더 세밀한 규칙이다.

### 5.4 서로 다른 세 가지 실패를 분리하기

| 현상 | 어느 계층의 문제인가? | 의미 |
|---|---|---|
| TLB miss | 하드웨어 주소 변환 cache | 변환 정보가 cache에 없어 페이지 테이블 조회 필요 |
| 유효한 페이지의 page fault | 가상 메모리와 물리 상주 상태 | 페이지를 메모리로 가져오는 OS 처리가 필요 |
| C++ lifetime/range 위반 | C++ 객체 모델 | 해당 객체 또는 배열 원소를 사용할 권리가 없음 |

이 셋을 구분해야 “실행됐으니 유효하다”, “segmentation fault가 없으니 안전하다” 같은 잘못된 판단을 피할 수 있다.

## 6. 네 포인터 유형의 차이: 전이 규칙으로 보기

기본 정의는 [[00.메모리·객체 수명·RAII#13. 스마트 포인터]]에 있다. 여기서는 **누가 수명을 늘리고, 어떤 연산이 소유권을 바꾸는가**만 비교한다.

| 타입 | 소유권 | 복사 | 이동 | 대상 수명에 미치는 영향 | 안전한 접근 조건 |
|---|---|---|---|---|---|
| `std::unique_ptr<T>` | 단독 소유 | 금지 | 소유권 이전 | 소유자가 사라지면 대상 파괴 | 포인터가 비어 있지 않아야 함 |
| `std::shared_ptr<T>` | 공동 소유 | 같은 control block 공유 | 소유 핸들 이전 | 마지막 강한 소유자가 사라지면 대상 파괴 | `shared_ptr`가 비어 있지 않아야 함 |
| `std::weak_ptr<T>` | 비소유 관찰 | 약한 관찰 복사 | 가능 | 강한 참조 수를 늘리지 않음 | `lock()`으로 얻은 `shared_ptr`가 비어 있지 않아야 함 |
| raw pointer `T*` | 타입 자체로는 표현 안 됨 | 주소값 복사 | 주소값 이동과 의미 차이 없음 | 수명을 늘리거나 파괴하지 않음 | 별도의 수명 계약과 null·범위 조건 필요 |

### 6.1 `unique_ptr`: `move`는 소유권 이전

PDF의 `unique_ptr` 설명은 복사를 금지하고 이동으로 유일한 소유권을 이전한다.

```cpp
#include <memory>
#include <utility>

struct Resource {
    int id;
};

void consume(std::unique_ptr<Resource> resource) {
    // resource가 이 범위에서 소유권을 가짐
}

int main() {
    auto owner = std::make_unique<Resource>(Resource{7});
    consume(std::move(owner));

    // owner는 더 이상 객체를 소유하지 않음
}
```

함수가 `unique_ptr<T>`를 값으로 받으면 호출자가 소유권을 넘긴다는 사실이 형식에 드러난다.

### 6.2 `unique_ptr::get()`: 소유권 없는 일시 접근

PDF는 `get()`을 통해 실제 객체 주소를 얻어 일반 포인터 인자에 전달하는 예를 보여 준다.

```cpp
#include <memory>

struct Resource {
    int id;
};

int inspect(const Resource* resource) {
    return resource == nullptr ? -1 : resource->id;
}

int main() {
    auto owner = std::make_unique<Resource>(Resource{7});
    const Resource* borrowed = owner.get();

    return inspect(borrowed) == 7 ? 0 : 1;
}
```

`borrowed`는 객체를 삭제하지 않으며 수명을 늘리지도 않는다. `owner`가 객체를 계속 소유하는 동안만 사용할 수 있다.

> [!warning] `get()`의 결과를 오래 보관하지 않는다
> `get()`은 소유권을 복제하지 않는다. 소유 `unique_ptr`가 파괴되거나 이동되면 이전에 얻은 raw pointer를 계속 사용할 수 없다.

### 6.3 `shared_ptr`: 객체가 아니라 control block을 함께 공유

`shared_ptr` 복사본은 같은 대상과 control block을 공유한다. control block의 강한 참조 수가 마지막 소유자를 판단한다.

```cpp
#include <memory>

struct Resource {
    int id;
};

int main() {
    auto first = std::make_shared<Resource>(Resource{7});
    auto second = first; // 같은 control block을 공유

    return first->id == second->id ? 0 : 1;
}
```

PDF는 `make_shared<T>`가 객체와 control block을 한 번의 동적 할당으로 함께 만드는 방식을 설명한다.

### 6.4 같은 raw pointer로 별도 `shared_ptr`를 만들면 안 되는 이유

다음 두 `shared_ptr`는 같은 주소를 받았지만 서로의 존재를 모르는 별도 control block을 만든다.

```cpp
Resource* raw = new Resource{7};

std::shared_ptr<Resource> first{raw};
// std::shared_ptr<Resource> second{raw}; // 별도 control block: 금지
```

각 control block은 자신이 마지막 소유자라고 판단할 수 있으므로 같은 객체를 두 번 삭제하는 문제가 발생한다. 최초 소유 `shared_ptr`를 만든 뒤에는 그 `shared_ptr`를 복사해야 한다.

```cpp
auto first = std::make_shared<Resource>(Resource{7});
auto second = first; // 올바른 control block 공유
```

### 6.5 `weak_ptr`: 확인과 사용을 `lock()` 한 번으로 묶기

`weak_ptr`는 강한 참조 수를 늘리지 않는다. 대상에 접근하려면 `lock()`으로 임시 `shared_ptr`를 얻는다.

```cpp
#include <memory>

struct Resource {
    int id;
};

int read_if_alive(const std::weak_ptr<Resource>& observer) {
    if (auto owner = observer.lock()) {
        return owner->id; // 이 블록 동안 owner가 수명을 유지
    }
    return -1;
}
```

`lock()`이 빈 `shared_ptr`를 반환하면 대상은 이미 소멸된 상태다. 성공했다면 반환된 `shared_ptr`가 사용 중 수명을 유지한다.

### 6.6 소유 그래프에서 `shared_ptr`와 `weak_ptr`

부모가 자식을 소유하고 자식은 부모를 관찰하는 트리는 다음처럼 표현할 수 있다.

```cpp
#include <memory>
#include <vector>

struct Node {
    std::vector<std::shared_ptr<Node>> children;
    std::weak_ptr<Node> parent;
};

int main() {
    auto parent = std::make_shared<Node>();
    auto child = std::make_shared<Node>();

    parent->children.push_back(child); // 부모가 자식을 공동 소유
    child->parent = parent;            // 자식은 부모를 관찰

    if (auto p = child->parent.lock()) {
        return p->children.size() == 1 ? 0 : 1;
    }
    return 1;
}
```

자식의 `parent`까지 `shared_ptr`로 만들면 부모와 자식이 서로 강하게 소유하는 순환이 될 수 있다. PDF는 이 순환에서 참조 수가 0이 되지 않아 객체가 소멸되지 않는 문제와 이를 `weak_ptr`로 끊는 방법을 설명한다.

## 7. API에서 소유권을 읽는 방법

PDF의 `unique_ptr` 이동·`get()` 및 `shared_ptr` 복사 규칙을 API 선언에 적용하면 다음처럼 구분할 수 있다.

| 함수 선언 | 호출자가 읽어야 할 의미 |
|---|---|
| `void consume(std::unique_ptr<T> value)` | 단독 소유권을 함수에 넘김 |
| `void share(std::shared_ptr<T> value)` | 함수가 공동 소유에 참여함 |
| `void observe(const T* value)` | 선택적인 비소유 접근; 수명을 늘리지 않음 |
| `void use(T& value)` | 반드시 존재하는 객체를 빌려 사용; 소유하지 않음 |
| `std::weak_ptr<T>`를 멤버로 저장 | 공동 소유 그래프를 늘리지 않는 관찰 관계 |

### 호출 목적별 선택

```text
함수가 객체를 파괴 시점까지 책임져야 하는가?
  ├─ 단독 책임을 넘긴다       → unique_ptr<T>
  ├─ 여러 주체가 수명을 공유  → shared_ptr<T>
  └─ 소유하지 않고 사용       → T&, const T&, T*

공동 소유 객체를 관찰하지만 수명을 늘리면 안 되는가?
  └─ weak_ptr<T> + lock()
```

raw pointer는 “나쁜 포인터”가 아니라 **소유권을 자체적으로 표현하지 않는 포인터**다. 문제는 raw pointer가 가리키는 대상의 소유자와 유효 기간을 API 계약에서 알 수 없을 때 생긴다.

## 8. 객체 수명과 OS 상태를 함께 추적하는 예

```cpp
#include <cassert>
#include <memory>
#include <utility>

struct Session {
    int id;
};

int read_id(const Session* borrowed) {
    assert(borrowed != nullptr);
    return borrowed->id;
}

int finish(std::unique_ptr<Session> owned) {
    return owned->id;
}

int main() {
    auto owner = std::make_unique<Session>(Session{42});

    Session* borrowed = owner.get();
    assert(read_id(borrowed) == 42);

    assert(finish(std::move(owner)) == 42);
    assert(owner == nullptr);

    // borrowed는 더 이상 사용하지 않는다.
}
```

이 코드의 상태 변화는 다음과 같다.

| 시점 | `owner` | `borrowed` | 객체 수명 |
|---|---|---|---|
| `make_unique` 직후 | 단독 소유 | 없음 | 살아 있음 |
| `get()` 직후 | 계속 단독 소유 | 비소유 관찰 | 살아 있음 |
| `std::move(owner)` 후 | 비어 있음 | 이전 주소값을 보유할 수 있음 | `finish` 인자가 소유 |
| `finish` 반환 후 | 비어 있음 | 사용 불가 | 파괴됨 |

마지막 상태에서 가상 주소의 페이지가 여전히 매핑되어 있거나 같은 바이트가 남아 있을 수 있다. 그러나 C++ 객체 수명은 끝났으므로 `borrowed`를 역참조할 수 없다. OS의 주소 변환 가능성과 C++ 객체 접근 가능성은 같은 조건이 아니다.

## 9. 보완된 오해 정리

### “힙의 남은 용량 합계가 요청 크기보다 크면 할당된다”

항상 그렇지 않다. 외부 단편화 때문에 필요한 연속 빈 청크가 없을 수 있다.

### “`delete`하면 그 페이지가 즉시 물리 메모리에서 사라진다”

`delete`는 C++ 객체 파괴와 저장 공간 반환의 의미를 가진다. 반환된 청크를 할당기가 다시 보유할 수 있고, OS의 페이지 상주 상태는 별도 계층에서 관리된다.

### “page fault는 잘못된 포인터의 증거다”

항상 그렇지 않다. 요구 페이징에서는 유효하지만 아직 물리 메모리에 없는 페이지를 접근해도 page fault가 발생한다.

### “segmentation fault가 없으면 포인터는 유효하다”

그렇지 않다. C++ 객체 수명이나 배열 범위를 위반해도 접근 주소가 매핑된 페이지 안이면 하드웨어 예외가 즉시 발생하지 않을 수 있다.

### “`weak_ptr`가 대상을 안전하게 계속 살려 둔다”

아니다. `weak_ptr`는 강한 참조 수를 늘리지 않는다. `lock()`이 성공해 반환한 `shared_ptr`만 해당 작업 동안 수명을 유지한다.

### “같은 raw pointer로 만든 `shared_ptr`들은 자동으로 서로를 안다”

아니다. 별도로 생성하면 서로 다른 control block을 가질 수 있다. 기존 `shared_ptr`를 복사해야 같은 소유권 그룹에 참여한다.

## 12. 최종 압축 정리

1. 요청된 기본 메모리·객체 수명 항목은 00번 문서에 이미 정리되어 있다.
2. 04번은 할당기, 주소 변환, 소유권 전이라는 세 연결 지점을 보완한다.
3. 할당기는 힙의 빈 청크를 분할·병합하고 적합 정책으로 검색한다.
4. 내부 단편화는 할당 청크 안의 낭비이고, 외부 단편화는 빈 공간이 흩어진 상태다.
5. 가상 주소는 TLB와 페이지 테이블을 통해 물리 주소로 변환된다.
6. TLB miss는 변환 cache miss이고, page fault와 같은 사건이 아니다.
7. 요구 페이징의 page fault는 유효한 페이지를 처음 적재하는 정상 처리일 수 있다.
8. OS가 주소를 변환할 수 있다는 사실은 C++ 객체가 살아 있다는 보장이 아니다.
9. `unique_ptr`는 이동으로 단독 소유권을 넘기고 `get()`은 소유권 없는 주소만 제공한다.
10. `shared_ptr` 복사본은 같은 control block을 공유해야 한다.
11. `weak_ptr`는 수명을 늘리지 않으며 `lock()`에 성공한 동안만 안전하게 접근한다.
12. raw pointer는 수명을 관리하지 않으므로 소유자와 유효 기간을 별도 계약으로 보장해야 한다.

> [!tip] 한 문장으로 기억하기
> **OS는 주소와 페이지를 관리하고, 할당기는 힙 청크를 관리하며, C++ 타입과 RAII는 객체 수명과 자원 소유권을 관리한다. 어느 한 계층의 성공도 다른 계층의 유효성을 대신 증명하지 않는다.**
