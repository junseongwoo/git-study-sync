# 비동기 작업 취소와 UI 정지 없는 이미지 처리

> [!summary] 한 문장 정리
> **UI thread는 event 처리와 화면 반영만 담당하고, 이미지 buffer를 소유한 작업을 worker에게 넘긴 뒤, 취소는 협력적으로 요청하며, 결과는 generation을 재검사해 UI thread에서만 반영한다.**

이 문서는 다음 네 주제를 하나의 이미지 처리 pipeline으로 연결한다.

1. 비동기 작업
2. 작업 취소
3. 스레드 안전성
4. UI 정지 없는 이미지 처리

- 이미지 buffer 소유권과 SDK 수명: [[05.파일·소켓·비동기 IO와 Buffer]]

이 문서는 기존 설명을 반복하기보다 다음 실무 문제에 집중한다.

- 왜 이미지 처리를 worker로 옮겼는데도 UI가 멈추는가?
- 취소 버튼을 누르면 queued 작업과 running 작업은 각각 어떻게 되는가?

## 1. UI가 멈추는 이유

### 1.1 UI는 event loop 위에서 동작한다

대부분의 desktop UI framework는 하나의 UI thread에서 다음 작업을 반복한다.

```text
event queue에서 event 꺼내기
  -> mouse/keyboard/window message 처리
  -> layout·paint·animation 처리
  -> 다음 event 처리
```

하나의 handler가 오래 반환하지 않으면 뒤의 event들이 처리되지 못한다.

```text
UI thread
[클릭 handler: 이미지 처리 2초 ------------------]
                                                  [paint][mouse][timer]

사용자 관찰: 창 이동·버튼·progress 표시가 2초 동안 멈춤
```

OSTEP의 event-driven server 설명에서 blocking system call 하나가 event loop 전체를 막는 것과 같은 구조다. UI event handler의 긴 CPU 계산, blocking I/O, `future.get()`, `thread.join()`도 같은 결과를 만든다.

### 1.2 UI handler에서 피해야 할 작업

- 큰 이미지 decode·resize·filter·검사
- 동기 파일·network·camera I/O
- worker 완료를 기다리는 `future.get()`
- thread 종료를 기다리는 `join()`
- 긴 mutex 대기
- queue가 찰 때까지 기다리는 blocking push
- 대량 결과를 한 번에 widget에 삽입

> [!important] worker를 만들었다고 자동으로 UI가 유동적이지는 않다
> UI thread가 worker를 시작한 직후 `get()` 또는 `join()`하면 결국 UI가 완료를 기다린다. 작업 시작과 결과 소비를 분리하고, 결과를 UI event queue에 다시 게시해야 한다.

## 2. 비동기 작업의 정확한 모델

### 2.1 비동기는 “나중에 완료를 받는 것”이다

```text
UI thread                      Worker
   │ submit(OwnedImage)           │
   ├─────────────────────────────>│
   │ 즉시 event loop로 복귀       │ process
   │                              │
   │<──────── post(Result) ───────┤
   │ UI queue에서 result 적용     │
```

호출 직후 UI thread가 다시 event loop로 돌아가야 한다. worker는 완료 결과나 오류를 callback, future, completion queue 중 하나로 전달한다.

### 2.2 한 작업이 가져야 하는 상태

```cpp
enum class JobState {
    queued,
    running,
    cancel_requested,
    completed,
    cancelled,
    failed
};
```

실제 구현이 enum 하나를 반드시 가져야 하는 것은 아니지만 다음 사실은 구분해야 한다.

- queue에만 있고 아직 시작하지 않은가?
- worker가 buffer를 읽고 있는가?
- 취소 요청을 worker가 관찰했는가?
- 성공·실패·취소 중 어떤 결과로 종결되었는가?
- 결과가 만들어졌지만 UI에 아직 반영되지 않았는가?

### 2.3 요청·실행·전달은 서로 다른 단계다

```text
Submit
  -> Queue
  -> Start
  -> Process
  -> Produce result
  -> Post to UI queue
  -> Validate generation
  -> Commit to UI
```

작업이 `completed`여도 UI에 적용되기 전일 수 있다. 이 사이에 더 최신 요청이 들어오면 완료된 예전 결과도 폐기해야 할 수 있다.

## 3. 작업 취소

### 3.1 취소는 강제 종료가 아니다

일반적인 C++ 작업 취소는 cooperative cancellation이다.

```text
취소 요청자: cancel_requested = true
작업 수행자: 안전한 중단 지점에서 flag 확인
작업 수행자: 임시 결과 폐기·자원 정리 후 cancelled로 종료
```

thread를 임의의 instruction에서 강제로 멈추면 다음 상태가 남을 수 있다.

- mutex를 획득한 채 종료
- container 불변식이 깨진 중간 갱신
- SDK frame 미반납
- 파일·transaction 부분 반영
- callback 대상이 불완전한 상태

따라서 취소는 작업 코드가 일관성을 유지할 수 있는 지점에서 관찰한다.

### 3.2 queued 취소와 running 취소

| 상태 | 취소 방식 | 비용 |
|---|---|---|
| queued | queue에서 제거하거나 cancelled 표시 | 거의 즉시 |
| running | 작업이 cancellation checkpoint에서 확인 | checkpoint 간격만큼 지연 |
| OS/SDK I/O 대기 | API의 cancel 요청 후 completion 확인 | API 계약에 의존 |
| UI queue에 결과 게시 완료 | callback에서 generation/alive 재검사 후 폐기 | callback 자체는 실행될 수 있음 |

`cancel()` 함수가 반환한 시점과 작업이 buffer 접근을 끝낸 시점은 같지 않을 수 있다. [[05.파일·소켓·비동기 IO와 Buffer]]에서 다룬 것처럼 OS/SDK 비동기 I/O는 취소 완료까지 확인해야 buffer를 해제할 수 있다.

### 3.3 cancellation checkpoint의 크기

```cpp
for (std::size_t row = 0; row < height; ++row) {
    if (cancel_requested.load(std::memory_order_relaxed)) {
        return Cancelled{};
    }
    process_one_row(row);
}
```

매 pixel마다 atomic을 읽으면 반응은 빠르지만 overhead가 늘 수 있다. 이미지 처리에서는 row, tile, 단계 사이를 checkpoint로 두는 것이 이해하기 쉽다.

```text
decode -> [check] -> normalize -> [check] -> inference -> [check] -> annotate
```

한 단계가 3초 동안 interruption을 허용하지 않으면 취소 응답 시간도 최대 약 3초다. 취소 latency 요구를 먼저 정하고 작업 단위를 나눈다.

### 3.4 취소 결과는 실패와 다르다

```cpp
enum class ResultKind {
    success,
    cancelled,
    failed
};
```

사용자가 새 이미지를 선택해 이전 작업을 취소한 것은 일반적으로 오류가 아니다. error log를 쌓거나 경고 dialog를 띄우기보다 정상적인 제어 흐름으로 처리한다.

### 3.5 취소 후 결과 경쟁

다음 순서가 가능하다.

```text
Worker: 계산 완료
UI:     취소 요청 또는 새 이미지 선택
Worker: 이전 결과를 UI queue에 post
UI:     이전 callback 실행
```

취소 flag만으로 이 경쟁을 완전히 막을 수 없다. UI callback이 실행되는 마지막 순간에 generation과 controller 생존 상태를 다시 확인해야 한다.

## 4. latest-wins와 모든 작업 보존

### 4.1 latest-wins가 적합한 경우

- slider를 움직일 때 preview 재계산
- 사용자가 파일을 연속 선택
- camera preview에서 최신 frame만 중요
- 검색어 입력에 따른 thumbnail 갱신

```text
Job 10 running
Job 11 arrives -> Job 10 cancel requested
Job 12 arrives -> queued Job 11 폐기, Job 12만 유지
```

queue가 무한히 늘지 않고 오래된 결과가 화면을 덮지 않는다.

### 4.2 모든 작업을 보존해야 하는 경우

- 검사 결과가 법적·품질 기록이 되는 생산 frame
- 업로드·저장처럼 각 요청의 완료가 필요
- batch 처리에서 모든 입력이 결과를 가져야 함

이 경우 latest-wins로 frame을 조용히 버리면 안 된다. bounded queue, backpressure, 명시적 reject, retry 정책이 필요하다.

| 요구 | 권장 정책 |
|---|---|
| 화면 preview | latest-only 또는 drop-oldest |
| 모든 검사 기록 | bounded FIFO + 입력 제어 |
| 사용자 단일 명령 | 이전 명령 취소 후 최신 유지 가능 |
| 파일 저장 | 작업별 성공·실패 결과 보존 |

## 5. 스레드 안전성

### 5.1 thread-safe의 범위를 말해야 한다

“이 클래스는 thread-safe다”만으로는 부족하다.

- 어떤 public 함수들을 동시에 호출할 수 있는가?
- callback은 어느 thread에서 오는가?
- 결과 객체는 immutable인가?
- `stop()`과 `submit()`이 경쟁하면 어떤 결과인가?
- UI 객체는 어느 thread에서만 접근할 수 있는가?

### 5.2 UI 객체는 UI thread에 가둔다

worker가 계산을 마쳤다고 widget을 직접 변경하면 안 된다. UI framework의 dispatcher/event queue에 결과 적용 함수를 게시한다.

```text
Worker thread
  -> immutable Result 생성
  -> ui_dispatcher.post(...)

UI thread
  -> generation 확인
  -> widget/model 변경
```

이 방식은 UI 상태에 mutex를 추가하는 것보다 ownership이 명확하다. UI 상태는 UI thread 하나가 소유하고, worker는 값 결과만 전달한다.

### 5.3 공유 상태를 최소화한다

공유하기 쉬운 데이터 구조보다 이동 가능한 값 객체를 우선한다.

```cpp
struct OwnedImage {
    std::uint64_t id{};
    std::size_t width{};
    std::size_t height{};
    std::vector<unsigned char> pixels;
};
```

UI가 `OwnedImage`를 worker queue로 이동하면 UI와 worker가 같은 pixel vector를 동시에 수정하지 않는다.

### 5.4 mutex와 atomic의 역할을 구분한다

- 여러 필드의 관계와 queue 불변식: mutex
- 독립적인 단일 flag·generation: atomic 후보
- 기다림: condition variable
- 소유권 이전: 값 이동 또는 `unique_ptr`

```cpp
{
    std::lock_guard lock(mutex_);
    pending_ = std::move(job);
    stopping_ = false;
}
ready_.notify_one();
```

atomic 여러 개를 조합해 복잡한 상태 머신을 만들면 일관된 snapshot을 얻기 어렵다. queue·running token·shutdown 상태처럼 함께 변해야 하는 값은 한 mutex 아래 둔다.

### 5.5 condition variable은 상태 predicate와 함께 사용한다

```cpp
ready_.wait(lock, [this] {
    return stopping_ || pending_.has_value();
});
```

notification은 상태 자체가 아니다. spurious wakeup이나 이미 소비된 event를 고려해 깨어난 뒤 predicate를 다시 검사한다.

### 5.6 오래 잡은 lock도 UI를 멈춘다

UI thread가 짧은 mutex를 획득하려고 했는데 worker가 그 lock을 잡고 이미지 처리 전체를 수행하면 UI는 멈춘다.

```cpp
// 나쁜 구조
std::lock_guard lock(mutex_);
result_ = process_large_image(image_); // lock을 너무 오래 보유
```

```cpp
// 좋은 구조
OwnedImage local;
{
    std::lock_guard lock(mutex_);
    local = std::move(pending_image_);
}
auto result = process_large_image(local); // 공유 상태 밖에서 계산
```

## 6. 이미지 buffer 수명

### 6.1 주소만 넘기는 것은 비동기 전달이 아니다

```cpp
void on_open_clicked() {
    std::vector<unsigned char> pixels = load();
    worker.post([&pixels] { process(pixels); });
} // pixels 소멸 가능
```

lambda가 reference로 capture한 지역 buffer는 worker 실행 전에 소멸할 수 있다.

```cpp
worker.post([pixels = std::move(pixels)]() mutable {
    process(pixels);
});
```

작업이 값을 소유하게 만들면 완료·취소까지 buffer 수명이 작업 수명과 같아진다.

### 6.2 camera SDK buffer

SDK callback pointer는 callback 이후 재사용될 수 있다. UI 이미지 작업으로 넘길 때는 다음 중 하나가 필요하다.

- callback 안에서 app-owned `OwnedImage`로 복사
- 공식 SDK retain/lock handle을 RAII lease로 보유
- app-owned buffer pool의 상태를 Filling/Ready/Processing으로 관리

pointer나 `std::span`만 queue에 넣어서는 수명이 연장되지 않는다.

### 6.3 결과 이미지도 소유권이 필요하다

UI callback이 실행될 때까지 결과 pixel memory가 살아 있어야 한다. 결과 값을 callback lambda로 이동 capture하면 dispatcher queue가 그 수명을 보유한다.

```cpp
ui.post([result = std::move(result)]() mutable {
    apply_to_ui(std::move(result));
});
```

## 7. UI 정지 없는 pipeline

### 7.1 권장 흐름

```text
UI event
  -> 입력 검증
  -> image ownership 확보
  -> generation 증가
  -> 이전 token cancel
  -> latest job 교체
  -> worker notify
  -> 즉시 return

Worker
  -> latest job 인수
  -> tile/row마다 cancel 확인
  -> result 생성
  -> UI dispatcher에 callback 게시

UI callback
  -> controller alive 확인
  -> generation == latest 확인
  -> widget/model 갱신
```

### 7.2 generation이 필요한 이유

```text
generation 1: 큰 이미지, 먼저 시작했지만 늦게 완료
generation 2: 작은 이미지, 나중에 시작했지만 먼저 완료
```

완료 순서만 믿으면 generation 1이 마지막에 화면을 덮는다. submit 시 증가한 generation을 결과에 넣고 UI commit 직전에 최신 값과 비교한다.

```cpp
if (result.generation != latest_generation.load()) {
    return; // stale result
}
```

### 7.3 progress update를 너무 자주 보내지 않는다

worker가 pixel마다 UI event를 post하면 UI queue가 progress event로 가득 찬다. 다음 중 하나를 사용한다.

- 50~100 ms에 한 번만 게시
- 마지막 게시보다 일정 비율 이상 변했을 때만 게시
- atomic progress 하나를 갱신하고 UI timer가 주기적으로 읽음
- queue에서 이전 progress event를 최신 값으로 병합

## 8. C++20 통합 예제: latest-only image controller

다음 예제는 특정 GUI framework 대신 thread-safe `IUiDispatcher` interface를 사용한다. 실제 Qt·Win32·wxWidgets adapter는 해당 framework의 UI queue 게시 API로 `post()`를 구현하면 된다.

```cpp
#include <atomic>
#include <cassert>
#include <chrono>
#include <condition_variable>
#include <cstddef>
#include <cstdint>
#include <deque>
#include <functional>
#include <memory>
#include <mutex>
#include <optional>
#include <stdexcept>
#include <thread>
#include <utility>
#include <vector>

struct OwnedImage {
    std::uint64_t id{};
    std::size_t width{};
    std::size_t height{};
    std::vector<unsigned char> pixels;
};

struct ProcessedImage {
    std::uint64_t generation{};
    std::uint64_t source_id{};
    std::vector<unsigned char> pixels;
};

class IUiDispatcher {
public:
    virtual ~IUiDispatcher() = default;
    virtual void post(std::function<void()> callback) = 0;
};

class IImageView {
public:
    virtual ~IImageView() = default;
    virtual void show(ProcessedImage image) = 0; // UI thread only
};

class ImageController {
private:
    struct CancelFlag {
        std::atomic_bool requested{false};
    };

    struct Job {
        std::uint64_t generation{};
        OwnedImage image;
        std::shared_ptr<CancelFlag> cancel;
    };

    struct DeliveryState {
        std::atomic_bool alive{true};
        std::atomic_uint64_t latest_generation{0};
        IImageView* view{}; // UI thread에서만 사용
    };

public:
    ImageController(IUiDispatcher& ui, IImageView& view)
        : ui_(ui),
          delivery_(std::make_shared<DeliveryState>()),
          worker_([this] { worker_loop(); }) {
        delivery_->view = &view;
    }

    ~ImageController() {
        stop();
    }

    ImageController(const ImageController&) = delete;
    ImageController& operator=(const ImageController&) = delete;

    // UI thread에서 빠르게 호출하고 반환한다.
    void submit(OwnedImage image) {
        if (image.width == 0 ||
            image.height == 0 ||
            image.pixels.size() % image.width != 0 ||
            image.pixels.size() / image.width != image.height) {
            throw std::invalid_argument("invalid image dimensions");
        }

        auto cancel = std::make_shared<CancelFlag>();
        std::uint64_t generation{};

        {
            std::lock_guard lock(mutex_);
            if (stopping_) {
                throw std::runtime_error("controller is stopping");
            }

            generation =
                delivery_->latest_generation.fetch_add(1) + 1;

            if (pending_) {
                pending_->cancel->requested.store(true);
            }
            if (running_cancel_) {
                running_cancel_->requested.store(true);
            }

            pending_ = Job{
                generation,
                std::move(image),
                std::move(cancel)
            };
        }
        ready_.notify_one();
    }

    // 요청 중인 결과를 화면에 반영하지 않는다.
    void cancel_current() noexcept {
        delivery_->latest_generation.fetch_add(1);
        {
            std::lock_guard lock(mutex_);
            if (pending_) {
                pending_->cancel->requested.store(true);
                pending_.reset();
            }
            if (running_cancel_) {
                running_cancel_->requested.store(true);
            }
        }
    }

    // 예제 계약: UI thread에서 한 번 호출하며 worker 종료까지 기다린다.
    void stop() noexcept {
        delivery_->alive.store(false);
        {
            std::lock_guard lock(mutex_);
            if (stopping_) {
                return;
            }
            stopping_ = true;
            if (pending_) {
                pending_->cancel->requested.store(true);
                pending_.reset();
            }
            if (running_cancel_) {
                running_cancel_->requested.store(true);
            }
        }

        ready_.notify_all();
        if (worker_.joinable()) {
            worker_.join();
        }
    }

private:
    static std::optional<ProcessedImage> process(const Job& job) {
        ProcessedImage output;
        output.generation = job.generation;
        output.source_id = job.image.id;
        output.pixels.resize(job.image.pixels.size());

        const std::size_t row_size = job.image.width;
        for (std::size_t row = 0; row < job.image.height; ++row) {
            if (job.cancel->requested.load(std::memory_order_relaxed)) {
                return std::nullopt;
            }

            const std::size_t begin = row * row_size;
            const std::size_t end = begin + row_size;
            for (std::size_t index = begin; index < end; ++index) {
                output.pixels[index] =
                    static_cast<unsigned char>(255 - job.image.pixels[index]);
            }
        }
        return output;
    }

    void worker_loop() noexcept {
        for (;;) {
            std::optional<Job> job;
            {
                std::unique_lock lock(mutex_);
                ready_.wait(lock, [this] {
                    return stopping_ || pending_.has_value();
                });

                if (stopping_) {
                    return;
                }

                job = std::move(pending_);
                pending_.reset();
                running_cancel_ = job->cancel;
            }

            auto result = process(*job); // lock 밖에서 계산

            {
                std::lock_guard lock(mutex_);
                if (running_cancel_ == job->cancel) {
                    running_cancel_.reset();
                }
            }

            if (!result || job->cancel->requested.load()) {
                continue;
            }

            auto delivery = delivery_;
            ui_.post([delivery, image = std::move(*result)]() mutable {
                // 이 callback은 UI thread에서 실행된다는 계약이다.
                if (!delivery->alive.load()) {
                    return;
                }
                if (image.generation != delivery->latest_generation.load()) {
                    return; // 늦게 도착한 stale result
                }
                delivery->view->show(std::move(image));
            });
        }
    }

    IUiDispatcher& ui_;
    std::shared_ptr<DeliveryState> delivery_;
    std::mutex mutex_;
    std::condition_variable ready_;
    std::optional<Job> pending_; // latest-only slot
    std::shared_ptr<CancelFlag> running_cancel_;
    bool stopping_ = false;
    std::thread worker_;
};

// 실제 GUI event queue를 대신하는 검증용 dispatcher다.
class TestUiDispatcher final : public IUiDispatcher {
public:
    void post(std::function<void()> callback) override {
        {
            std::lock_guard lock(mutex_);
            callbacks_.push_back(std::move(callback));
        }
        ready_.notify_one();
    }

    template <class Predicate>
    bool run_until(Predicate done, std::chrono::milliseconds timeout) {
        const auto deadline = std::chrono::steady_clock::now() + timeout;
        while (!done()) {
            std::function<void()> callback;
            {
                std::unique_lock lock(mutex_);
                if (!ready_.wait_until(lock, deadline, [this] {
                        return !callbacks_.empty();
                    })) {
                    return done();
                }
                callback = std::move(callbacks_.front());
                callbacks_.pop_front();
            }
            callback(); // 테스트를 실행한 main(UI) thread에서 수행
        }
        return true;
    }

    void drain() {
        for (;;) {
            std::function<void()> callback;
            {
                std::lock_guard lock(mutex_);
                if (callbacks_.empty()) {
                    return;
                }
                callback = std::move(callbacks_.front());
                callbacks_.pop_front();
            }
            callback();
        }
    }

private:
    std::mutex mutex_;
    std::condition_variable ready_;
    std::deque<std::function<void()>> callbacks_;
};

class RecordingView final : public IImageView {
public:
    RecordingView() : ui_thread_(std::this_thread::get_id()) {}

    void show(ProcessedImage image) override {
        assert(std::this_thread::get_id() == ui_thread_);
        shown_.push_back(std::move(image));
    }

    std::size_t count() const { return shown_.size(); }
    std::uint64_t last_source_id() const { return shown_.back().source_id; }

private:
    std::thread::id ui_thread_;
    std::vector<ProcessedImage> shown_;
};

OwnedImage make_image(
    std::uint64_t id,
    std::size_t width,
    std::size_t height,
    unsigned char value) {
    return OwnedImage{

int main() {
    using namespace std::chrono_literals;

    TestUiDispatcher ui;
    RecordingView view;
    ImageController controller{ui, view};

    // 첫 결과가 이미 UI queue에 들어왔더라도 generation 검사가 폐기한다.
    controller.submit(make_image(1, 1024, 1024, 10));
    controller.submit(make_image(2, 32, 32, 20));

    const bool completed = ui.run_until(
        [&view] { return view.count() == 1; },
        2s);

    assert(completed);
    assert(view.last_source_id() == 2); // 최신 요청만 화면에 표시

    controller.stop();
    ui.drain(); // 남은 callback은 alive 검사로 안전하게 폐기
}
```

### 8.1 예제의 thread 계약

| 함수·객체 | 호출 thread | 동시 호출 계약 |
|---|---|---|
| `submit()` | UI thread | 예제에서는 UI 직렬 호출을 기본으로 함 |
| `cancel_current()` | UI thread | running token에 atomic 취소 요청 |
| `worker_loop()` | 전용 worker | UI 객체 직접 접근 금지 |
| `IUiDispatcher::post()` | worker 가능 | 구현이 thread-safe해야 함 |
| `IImageView::show()` | UI thread만 | dispatcher가 thread affinity 보장 |
| `stop()` | UI thread, 종료 시 1회 | worker join까지 기다림 |

`submit()`과 `stop()`을 여러 외부 thread에서 동시에 호출해야 한다면 별도의 API 계약과 lifecycle 동기화가 추가로 필요하다. UI controller를 UI thread에 가두면 이 복잡성을 크게 줄일 수 있다.

### 8.2 `DeliveryState`가 필요한 이유

worker가 UI callback을 게시한 뒤 controller가 먼저 파괴될 수 있다. callback이 `this`를 capture하면 use-after-free가 된다.

예제는 callback이 독립된 `shared_ptr<DeliveryState>`만 보유하게 한다.

- controller 종료 시 `alive = false`
- 게시된 callback은 state 수명을 유지
- UI에서 callback 실행 시 `alive`가 false면 view 접근 없이 종료
- UI callback과 controller 파괴가 같은 UI thread에서 직렬화된다는 계약 사용

### 8.3 왜 요청 교체 때 `join()`하지 않는가?

새 이미지를 선택할 때 이전 worker를 join하면 UI thread가 취소 checkpoint까지 기다려 다시 멈춘다. 요청 교체는 flag만 설정하고 즉시 반환한다. `join()`은 controller 최종 종료에서만 수행한다.

## 10. 오류·완료·취소 전달

### 10.1 결과를 tagged state로 전달하기

```cpp
struct JobResult {
    enum class Kind { success, cancelled, failed } kind;
    std::uint64_t generation{};
    std::optional<ProcessedImage> image;
    std::string error;
};
```

다음 불변식을 정할 수 있다.

- success면 `image`가 존재하고 `error`는 비어 있음
- cancelled면 UI 오류 dialog를 띄우지 않음
- failed면 error가 존재하고 최신 generation일 때만 화면에 표시

### 10.2 worker 예외 경계

worker thread 함수 밖으로 예외가 빠져나가지 않게 한다.

```cpp
try {
    auto result = process(job);
    post_success(std::move(result));
} catch (const std::exception& error) {
    post_failure(job.generation, error.what());
} catch (...) {
    post_failure(job.generation, "unknown error");
}
```

C++ PDF의 `packaged_task`·future 설명처럼 비동기 결과는 값뿐 아니라 예외도 전달할 수 있다. UI application에서는 future를 UI thread에서 blocking `get()`하기보다 completion callback이 오류 결과를 UI queue에 게시하는 구조가 자연스럽다.

## 11. 종료 순서

### 11.1 window 닫기

```text
새 submit 차단
  -> delivery alive=false
  -> pending job 폐기
  -> running job cancel 요청
  -> worker 깨우기
  -> worker가 checkpoint에서 종료
  -> join
  -> UI dispatcher의 남은 callback은 alive 검사로 폐기
  -> view/window 파괴
```

view를 먼저 파괴하면 이미 게시된 callback이 dangling view에 접근할 수 있다.

### 11.2 종료 중 UI freeze

예제의 `stop()`은 `join()`하므로 running 단계가 취소 flag를 오래 확인하지 않으면 창 닫기가 늦어진다.

해결 방법:

- 긴 알고리즘을 tile·stage로 나누고 checkpoint를 추가
- 취소 가능한 SDK API 사용
- 종료 화면을 먼저 숨기고 별도 lifecycle coordinator가 완료를 기다림
- timeout 뒤 process 자체 종료가 허용되는지 제품 정책으로 결정

강제 thread 종료는 일반적인 해결책이 아니다.

## 12. 성능과 응답성

### 12.1 응답성 지표

- UI event 처리 지연
- submit 함수 실행 시간
- cancel 요청부터 worker 종료까지 시간
- queue 대기 시간
- 이미지 처리 시간
- result 생성부터 UI commit까지 시간
- stale result 폐기 수
- frame drop 수

평균만 보면 긴 꼬리 지연을 놓친다. p95/p99 latency도 관찰한다.

### 12.2 복사와 zero-copy

UI 정지를 막기 위해 무조건 zero-copy가 필요한 것은 아니다.

- callback에서 짧게 복사하고 빠르게 반환하면 SDK buffer를 빨리 돌려줄 수 있음
- 복사 없는 frame lease는 처리 중 SDK pool을 점유
- 큰 이미지는 buffer pool로 할당 비용을 줄일 수 있음
- UI 표시용 축소 image와 정밀 검사 원본을 분리할 수 있음

정확성과 lifetime이 먼저이며, 복사 비용은 측정 후 최적화한다.

### 12.3 worker 수

worker를 늘린다고 항상 빨라지지 않는다.

- memory bandwidth 경쟁
- cache miss와 false sharing
- 결과 reorder 증가
- UI callback 폭주
- 외부 library가 thread-safe하지 않을 수 있음

preview latest-wins는 worker 하나로도 충분한 경우가 많다. 모든 frame 처리 pipeline은 bounded pool과 순서 정책이 필요하다.

### 13.1 단위 테스트

- generation 1 결과가 generation 2 이후 도착하면 폐기되는가?
- pending job을 새 job이 교체하는가?
- running 취소 요청을 checkpoint가 관찰하는가?
- cancelled 결과가 오류로 표시되지 않는가?

- worker 예외가 UI failure 결과로 변환되는가?

### 13.2 동시성 component test

- submit과 worker 인수가 반복 경쟁해도 data race가 없는가?
- stop 시 condition variable에서 worker가 반드시 깨어나는가?
- 결과 callback이 UI thread에서만 실행되는가?
- 큰 이미지 취소 latency가 요구 범위 안인가?
- queue·buffer 사용량에 상한이 있는가?

### 13.3 timeout은 성공 조건이 아니라 안전장치다

예제의 2초 timeout은 “2초 기다리면 작업이 끝날 것”이라는 test 방식이 아니다. 실제 성공 조건은 `view.count() == 1`이고 timeout은 deadlock 시 test process가 영원히 멈추지 않게 하는 상한이다.

## 14. 흔한 실패 패턴

### 14.1 UI thread에서 `future.get()`

```cpp
auto future = std::async(std::launch::async, process, image);
auto result = future.get(); // UI thread block
show(result);
```

계산은 worker에서 해도 UI는 기다리므로 멈춘다.

### 14.2 detached thread가 UI 객체 capture

```cpp
std::thread([this] {
    auto result = process();
    widget_->setImage(result);
}).detach();
```

객체 수명, UI thread affinity, 종료 대기를 모두 잃는다.

### 14.3 취소 flag만 설정하고 buffer 해제

worker가 아직 buffer를 읽고 있을 수 있다. 취소 완료 또는 worker join 전까지 소유 buffer를 유지한다.

### 14.4 오래된 결과가 최신 화면을 덮음

취소 flag를 마지막에 한 번만 확인하거나 generation이 없으면 발생한다. UI commit 직전에 최신 generation을 재검사한다.

### 14.5 unbounded image queue

입력 속도가 처리 속도보다 빠르면 메모리와 지연이 계속 증가한다. preview는 latest-only, 기록 작업은 bounded queue와 backpressure를 사용한다.

### 14.6 worker가 mutex를 잡고 UI callback 호출

UI callback이 controller를 다시 호출하면 deadlock이 가능하다. 공유 상태를 정리하고 lock을 해제한 뒤 dispatcher에 게시한다.

## 16. 핵심 결론

1. UI 정지는 event loop의 handler가 오래 반환하지 않을 때 발생한다.
2. 비동기 처리는 worker 생성이 아니라 submit과 UI commit을 분리하는 구조다.
3. 작업 취소는 강제 종료가 아니라 안전한 checkpoint에서 관찰하는 협력적 protocol이다.
4. 취소 flag만으로 늦은 결과를 막을 수 없으므로 generation 검사가 필요하다.
5. UI 객체는 UI thread가 소유하고 worker는 값 결과만 dispatcher로 전달한다.
6. 이미지 buffer는 작업이 완료·취소 완료될 때까지 명시적으로 소유해야 한다.
7. preview는 latest-wins가 적합하지만 모든 검사 기록에는 bounded FIFO가 필요하다.
8. 요청 교체 때 join하지 않고 최종 종료에서 cancel·notify·join한다.

|---|---|---|
| event loop에서 blocking call을 실행하면 다른 event 처리가 멈춘다 | `ostep.pdf` 물리 398~400쪽 | 일치 |
| event/AIO 방식은 요청·buffer·완료 뒤 continuation 상태를 따로 보관한다 | `ostep.pdf` 물리 400~403쪽 | 일치 |
| thread는 주소 공간을 공유하고 각자 stack을 가진다 | `ostep.pdf` 물리 287쪽, `ocs.pdf` 스레드 장 | 일치 |
| thread 완료를 기다릴 때 join을 사용하며 stack 지역 주소를 결과로 반환하면 위험하다 | `ostep.pdf` 물리 304~306쪽 | 일치 |
| condition variable은 predicate를 while로 재검사해야 한다 | `ostep.pdf` 물리 309쪽, 348쪽 부근 | 일치 |
| 공유 상태에는 race가 발생할 수 있고 mutex로 임계 영역을 보호한다 | `cpp.pdf` 물리 744~759쪽, `ocs.pdf` 동기화 장 | 일치 |
| future의 `get()`은 결과 준비를 기다리므로 UI thread에서 호출하면 block될 수 있다 | `cpp.pdf` 물리 799~800쪽 | 일치 |
| `std::async`의 async/deferred 정책은 실행 시점을 다르게 한다 | `cpp.pdf` 물리 807~808쪽 | 일치 |
| 작업 queue는 mutex/CV로 보호하고 종료 시 stop·notify·join한다 | `cpp.pdf` 물리 812~817쪽 | 일치 |
| cooperative cancellation·generation·UI dispatcher의 구체 패턴 | 세 PDF에 직접 구현 없음 | PDF 원칙에서 도출한 설계 종합으로 명시 |

2차 대조 결과, 특정 GUI framework의 thread affinity와 callback 폐기 동작을 일반 PDF가 보장하는 것처럼 단정하지 않았다. framework adapter를 구현할 때 별도 문서에서 확인해야 할 계약으로 분리했다.

## 참고한 PDF

- `cpp.pdf`: C++ thread, race condition, mutex/CV, promise/future, async와 thread pool 종료
- `ostep.pdf`: thread 공유 메모리, condition variable, event loop의 blocking 문제, AIO 상태 관리
- `ocs.pdf`: thread와 병행성, 공유 데이터 동기화, mutex와 semaphore
