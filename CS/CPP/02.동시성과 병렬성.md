# 동시성과 병렬성

> [!summary] 한 문장 정리
> **동시성은 여러 작업을 함께 진전시키는 구조이고, 병렬성은 여러 작업을 같은 순간에 실제로 실행하는 방식이다.**

- mutex, atomic, 조건 변수, 세마포어, barrier, future의 사용 목적을 구분한다.

## 1. 동시성과 병렬성의 차이

### 1.1 동시성

동시성(concurrency)은 둘 이상의 작업이 같은 시간 구간 안에서 진행되는 성질이다. 작업들이 반드시 같은 순간에 실행될 필요는 없다.

단일 코어에서도 운영체제가 실행 대상을 빠르게 바꾸면 여러 작업이 함께 진행되는 것처럼 보인다.

```text
시간 ─────────────────────────────────────>
CPU  [작업 A][작업 B][작업 A][작업 C][작업 B]
```

이 경우 한 순간에는 하나의 작업만 실행되지만 A, B, C의 실행 기간은 서로 겹친다.

### 1.2 병렬성

병렬성(parallelism)은 둘 이상의 작업이 여러 실행 자원에서 같은 순간에 실제로 실행되는 성질이다.

```text
시간 ─────────────────────────────────────>
CPU 0 [──────────── 작업 A ───────────────]
CPU 1 [──────────── 작업 B ───────────────]
CPU 2 [──────────── 작업 C ───────────────]
```

병렬 실행에는 여러 CPU 코어, 여러 프로세서, GPU 실행 유닛 또는 분산된 컴퓨터가 필요하다.

### 1.3 관계

| 상황 | 동시성 | 병렬성 |
|---|---:|---:|
| 단일 코어에서 여러 스레드를 번갈아 실행 | O | X |
| 이벤트 루프가 여러 네트워크 요청을 처리 | O | 반드시 그렇지는 않음 |
| 여러 코어가 배열의 서로 다른 구간을 계산 | O | O |
| 한 스레드가 순차적으로 하나의 작업만 수행 | X | X |

넓은 의미에서는 병렬 실행도 여러 작업이 함께 진행되므로 동시성에 포함된다. 하지만 설계 관점에서는 다음처럼 목적이 다르다.

- 동시성의 중심 질문: 여러 작업의 상호작용과 대기를 어떻게 올바르게 다룰 것인가?
- 병렬성의 중심 질문: 하나의 일을 어떻게 나누어 동시에 더 빨리 끝낼 것인가?

### 1.4 비결정성과 interleaving

동시 작업의 실제 실행 순서는 스케줄러, 인터럽트, 코어 수와 시스템 부하에 따라 달라진다. 같은 입력으로 실행해도 명령어가 섞이는 순서(interleaving)가 달라질 수 있다.

올바른 동시성 프로그램은 특정 스레드가 먼저 실행될 것이라고 가정하지 않고, 동기화 규칙이 허용하는 모든 실행 순서에서 불변식을 지켜야 한다.

> [!important]
> 동시성은 프로그램 구조에 관한 성질이고, 병렬성은 실행 시점에 실제 자원을 사용하는 방식에 가깝다.

## 2. 비동기와 동시성

비동기(asynchronous)는 호출자가 작업 완료를 기다리지 않고 제어권을 돌려받는 인터페이스 또는 실행 방식이다.

```text
요청 시작 ──> 즉시 반환 ──> 다른 작업 수행 ──> 완료 통지
```

비동기는 동시성과 관련 있지만 같은 개념은 아니다.

- 단일 스레드 이벤트 루프도 비동기 I/O로 동시성을 제공할 수 있다.
- 비동기 API가 내부적으로 별도 스레드를 사용할 수도 있다.
- 비동기라고 해서 반드시 여러 코어에서 병렬 실행되는 것은 아니다.
- 여러 스레드를 사용해도 호출자가 즉시 결과를 기다리면 비동기성이 거의 드러나지 않을 수 있다.

```cpp
auto future = std::async(std::launch::async, calculate);

do_other_work();

auto result = future.get();
```

`get()`을 바로 호출하면 계산과 다른 작업을 겹칠 기회를 잃는다.

## 3. 동시성이 필요한 이유

### 3.1 응답성

오래 걸리는 작업과 사용자 입력 처리를 분리하면 작업이 진행되는 동안 UI가 멈추지 않는다.

### 3.2 지연 시간 숨기기

한 작업이 디스크, 네트워크 또는 외부 장치를 기다리는 동안 다른 작업을 실행한다.

```text
작업 A: [CPU][──── I/O 대기 ────][CPU]
작업 B:       [CPU][CPU][CPU]
```

### 3.3 처리량 향상

서로 독립적인 요청을 겹쳐 처리하면 단위 시간당 더 많은 요청을 완료할 수 있다.

### 3.4 멀티코어 활용

CPU 중심 작업을 독립적인 부분으로 나누어 여러 코어에 배치하면 완료 시간을 줄일 수 있다.

### 3.5 자연스러운 문제 구조 표현

웹 서버의 연결, 게임의 여러 시스템, GUI 이벤트, 생산자와 소비자처럼 본질적으로 독립적인 활동을 별도 작업으로 표현할 수 있다.

> [!warning]
> 동시성 자체가 자동으로 성능을 높이지는 않는다. 작업 생성, 문맥 교환, 동기화, 캐시 미스와 통신 비용이 실제 이득보다 클 수 있다.

## 4. 작업을 나누는 방법

### 4.1 작업 병렬성

서로 다른 종류의 작업을 동시에 실행한다.

```text
작업 1: 네트워크 요청 수신
작업 2: 데이터 파싱
작업 3: 로그 기록
```

각 작업의 처리 시간과 자원 요구가 다르므로 파이프라인이나 작업 큐와 함께 사용하는 경우가 많다.

### 4.2 데이터 병렬성

같은 연산을 서로 다른 데이터 구간에 적용한다.

```text
배열: [ 0 ... 249 ][250 ... 499][500 ... 749][750 ... 999]
코어:       0             1            2            3
```

이미지 처리, 벡터 연산, 통계 계산처럼 요소 간 의존성이 적은 작업에 적합하다.

### 4.3 파이프라인 병렬성

작업을 여러 단계로 나누고 각 단계가 서로 다른 입력을 동시에 처리한다.

```text
입력 → [읽기] → [파싱] → [계산] → [저장]
```

파이프라인 처리량은 가장 느린 단계에 의해 제한된다. 단계 사이에는 유한 큐를 두어 무제한 메모리 증가를 방지하고 역압력(backpressure)을 전달해야 한다.

### 4.4 fork-join

큰 작업을 여러 하위 작업으로 나누어 실행한 뒤 결과를 합친다.

```text
                 ┌─ 작업 A ─┐
큰 작업 ─ fork ──┼─ 작업 B ─┼─ join ─> 결과
                 └─ 작업 C ─┘
```

분할 정복, 병렬 합계, 병렬 정렬 등에 적합하다.

### 4.5 데이터 분해와 기능 분해

- 데이터 분해: 데이터 영역을 여러 작업에 나눈다.
- 기능 분해: 서로 다른 기능을 별도 작업으로 나눈다.

데이터 분해는 부하 균등화가 비교적 쉽지만 경계 데이터의 의존성이 문제가 될 수 있다. 기능 분해는 구조가 자연스럽지만 단계별 처리량 차이 때문에 병목이 생길 수 있다.

### 4.6 멀티코어 프로그래밍의 다섯 과제

1. **작업 식별**: 서로 독립적으로 실행할 수 있는 부분을 찾아야 한다.
2. **균형**: 각 작업의 실행량이 비슷해야 일부 코어만 오래 일하는 상황을 줄일 수 있다.
3. **데이터 분할**: 작업이 처리할 데이터를 충돌 없이 나누어야 한다.
4. **데이터 의존성**: 한 작업의 입력이 다른 작업의 출력에 의존하는지 확인해야 한다.
5. **테스트와 디버깅**: 가능한 실행 순서가 많고 재현이 어려우므로 순차 프로그램과 다른 검증 전략이 필요하다.

## 5. 동시성 실행 모델

### 5.1 프로세스 기반

각 작업을 독립된 프로세스로 실행한다.

- 주소 공간이 분리되어 장애 격리가 좋다.
- 통신에는 파이프, 소켓, 공유 메모리 같은 IPC가 필요하다.
- 프로세스 생성과 전환 비용이 상대적으로 크다.

### 5.2 스레드 기반

하나의 프로세스 안에서 여러 스레드가 주소 공간을 공유한다.

- 데이터 공유와 통신이 빠르다.
- 공유 상태 때문에 데이터 경쟁과 교착 상태 위험이 크다.
- 한 스레드의 메모리 오류가 프로세스 전체에 영향을 줄 수 있다.

### 5.3 작업 기반

프로그래머는 스레드보다 수행할 작업을 표현하고 런타임이 작업을 제한된 작업자에게 배치한다.

- 스레드 풀
- fork-join 프레임워크
- work stealing 스케줄러
- OpenMP와 작업 그래프

작업 기반 모델은 스레드의 생성·소멸을 반복하지 않고 실행 자원의 수를 통제하기 쉽다.

### 5.4 이벤트 기반

이벤트 루프가 준비된 사건을 하나씩 가져와 처리한다.

```text
while (running) {
    events = wait_for_events();
    for (event : events) {
        process(event);
    }
}
```

단일 이벤트 루프는 매 순간 하나의 처리기만 실행하므로 공유 상태의 락을 줄일 수 있다. 그러나 처리기에서 블로킹 호출이나 긴 CPU 계산을 실행하면 전체 이벤트 루프가 멈춘다.

### 5.5 코루틴

코루틴은 실행을 중단하고 나중에 재개할 수 있는 함수다. 비동기 흐름을 순차 코드처럼 표현하는 데 도움이 되지만 코루틴 자체가 스레드는 아니며 병렬 실행을 자동으로 제공하지 않는다.

> [!important]
> 실행 모델과 실행 자원을 구분해야 한다. 코루틴 수천 개가 하나의 스레드에서 동작할 수도 있고, 작업 런타임이 여러 스레드에 작업을 병렬 배치할 수도 있다.

## 6. 멀티코어 하드웨어에서 생기는 문제

### 6.1 코어와 하드웨어 스레드

물리 코어는 실제 실행 자원을 제공한다. SMT 또는 Hyper-Threading은 한 물리 코어가 여러 논리 CPU 문맥을 노출하게 한다.

논리 CPU가 두 배라고 CPU 계산 성능이 정확히 두 배가 되는 것은 아니다. 논리 CPU들은 실행 유닛과 캐시 같은 자원을 일부 공유한다.

### 6.2 캐시 계층

CPU는 메인 메모리보다 훨씬 빠른 캐시를 사용한다.

```text
레지스터 → L1 → L2 → L3 → 메인 메모리
 빠름                           느림
 작음                           큼
```

병렬 프로그램의 성능은 연산 수뿐 아니라 데이터가 어느 캐시에 존재하는지에 크게 영향을 받는다.

### 6.3 캐시 일관성

여러 코어가 같은 메모리를 캐시에 보관할 수 있으므로 하드웨어는 캐시 일관성 프로토콜로 동일한 메모리 위치의 변경을 전달한다.

캐시 일관성은 같은 메모리 위치의 값이 모순되지 않도록 돕지만 다음을 자동으로 해결하지는 않는다.

- 프로그램의 데이터 경쟁
- 여러 연산의 원자성
- 원하는 실행 순서
- 고수준 자료 구조의 불변식

### 6.4 캐시 일관성과 메모리 일관성

- cache coherence는 주로 **하나의 메모리 위치**에 대한 여러 코어의 읽기·쓰기 값이 어떻게 일치하는지를 다룬다.
- memory consistency는 **서로 다른 메모리 위치를 포함한 여러 연산의 관찰 순서**를 다룬다.

하드웨어의 캐시 일관성 프로토콜이 있어도 다른 스레드가 모든 쓰기를 소스 코드 순서대로 관찰한다고 보장되지는 않는다. C++ 메모리 모델의 mutex, atomic, acquire/release 같은 동기화가 필요한 이유다.

### 6.5 false sharing

서로 다른 스레드가 논리적으로 다른 변수만 변경하더라도 변수가 같은 캐시 라인에 있으면 캐시 라인이 코어 사이에서 계속 이동할 수 있다.

```cpp
#include <atomic>

struct alignas(64) PaddedCounter {
    std::atomic<long long> value{0};
};

PaddedCounter counters[8];
```

`64`는 흔한 캐시 라인 크기를 가정한 교육용 예시다. 실제 값과 효과는 하드웨어 및 데이터 배치에 따라 다르므로 반드시 측정해야 한다.

### 6.6 NUMA

NUMA 시스템에서는 CPU와 가까운 메모리와 멀리 있는 메모리의 접근 비용이 다르다. 작업을 다른 NUMA 노드로 이동시키면 데이터 접근 비용이 증가할 수 있다.

따라서 대규모 병렬 프로그램은 다음을 함께 고려해야 한다.

- 작업을 어느 CPU에 배치하는가?
- 데이터는 어느 NUMA 노드에 할당되어 있는가?
- 작업을 이동할 것인가, 데이터를 이동할 것인가?

---

## 7. 작업 배치와 스케줄링

### 7.1 단일 작업 큐

OSTEP은 이 구조를 SQMS(Single-Queue Multiprocessor Scheduling)라고 설명한다.

모든 작업자가 하나의 큐에서 작업을 가져온다.

장점:

- 구현이 단순하다.
- 전체 부하를 균등하게 나누기 쉽다.

단점:

- 큐의 락과 캐시 라인에 경합이 집중된다.
- 작업이 여러 CPU를 이동해 캐시 친화성이 낮아질 수 있다.

### 7.2 작업자별 큐

OSTEP은 CPU별로 큐를 두는 구조를 MQMS(Multi-Queue Multiprocessor Scheduling)라고 설명한다.

각 작업자가 자신의 큐를 사용한다.

장점:

- 공유 큐 경합이 줄어든다.
- 작업이 같은 CPU에서 실행되어 캐시를 재사용하기 쉽다.

단점:

- 작업 분배가 잘못되면 어떤 CPU는 놀고 다른 CPU는 바빠진다.

### 7.3 work stealing

할 일이 없는 작업자가 다른 작업자의 큐에서 작업을 가져온다.

```text
Worker 0: [A][B][C][D]
Worker 1: []  ── steal ──> [D]
```

도둑질 빈도가 너무 높으면 큐 검사와 동기화 비용이 증가하고, 너무 낮으면 부하 불균형이 오래 유지된다.

### 7.4 affinity와 migration

- affinity는 작업을 이전에 실행한 CPU에 유지하여 캐시 재사용을 높인다.
- migration은 작업을 다른 CPU로 옮겨 부하 불균형을 해소한다.
- 두 목표는 충돌할 수 있으므로 스케줄러가 캐시 친화성과 균형 사이에서 절충한다.

### 7.5 oversubscription

실행 가능한 CPU 중심 스레드가 논리 CPU보다 훨씬 많으면 문맥 교환과 캐시 손실이 늘어난다.

- CPU 중심 작업: 보통 사용 가능한 코어 수 근처에서 시작해 측정한다.
- I/O 중심 작업: 대기 시간이 길어 더 많은 동시 작업이 유리할 수 있다.
- 스레드 수는 하드웨어 수만이 아니라 작업의 CPU/I/O 비율과 외부 제한을 반영해야 한다.

## 8. 동시성 정확성의 세 문제

### 8.1 원자성

여러 연산이 다른 스레드가 끼어들 수 없는 하나의 단위처럼 실행되어야 하는 문제다.

```cpp
if (balance >= amount) {
    balance -= amount;
}
```

검사와 변경 사이에 다른 스레드가 끼어들면 잔액 불변식이 깨질 수 있다.

### 8.2 순서

A가 B보다 먼저 일어나야 하지만 그 순서가 강제되지 않은 문제다.

```text
생산자: 데이터 작성 → 준비 완료 표시
소비자: 준비 완료 확인 → 데이터 사용
```

준비 표시와 데이터 가시성 사이에 올바른 동기화가 필요하다.

### 8.3 가시성

한 코어의 스레드가 변경한 값을 다른 코어의 스레드가 언제 관찰할 수 있는가에 관한 문제다. 컴파일러 최적화, CPU의 메모리 순서, 캐시 때문에 소스 코드의 단순한 줄 순서만으로는 스레드 간 가시성이 보장되지 않는다.

### 8.4 데이터 경쟁

C++에서 다음 조건을 만족하면 데이터 경쟁(data race)이 발생한다.

- 서로 다른 스레드가 같은 메모리 위치에 접근한다.
- 접근 중 하나 이상이 쓰기다.
- 원자 연산이 아니며 happens-before로 정렬되지 않는다.

C++의 데이터 경쟁은 undefined behavior다.

> [!note] 실제 오류가 주는 교훈
> OSTEP이 소개한 실제 소프트웨어 연구에서는 조사된 비교착 상태 병행성 오류의 대부분이 원자성 위반 또는 순서 위반에 속했다. 교착 상태만 찾는 것으로는 동시성 오류를 충분히 예방할 수 없다.

## 9. C++ 메모리 모델

### 9.1 happens-before

happens-before는 한 스레드의 연산 결과가 다른 연산에 관찰 가능하도록 순서를 연결하는 관계다. 단순한 실제 시각의 선후 관계보다 강한 의미를 가진다.

대표적인 관계:

- 스레드 생성 전의 연산은 새 스레드 시작 이후보다 앞선다.
- 스레드 내부 연산은 성공한 `join()` 이후보다 앞선다.
- mutex의 `unlock()`은 같은 mutex를 이후에 획득한 `lock()`보다 앞선다.
- release 저장은 그 값을 관찰한 acquire 읽기보다 앞선다.
- barrier의 한 단계 도착 전 연산은 다음 단계 진행 이후에 관찰 가능하다.

### 9.2 release와 acquire

```cpp
#include <atomic>
#include <cassert>
#include <string>
#include <thread>

std::string payload;
std::atomic<bool> ready{false};

void producer() {
    payload = "complete";
    ready.store(true, std::memory_order_release);
}

void consumer() {
    while (!ready.load(std::memory_order_acquire)) {
        std::this_thread::yield();
    }

    assert(payload == "complete");
}
```

consumer가 release 저장을 acquire로 관찰하면 그보다 앞서 수행된 `payload` 기록도 관찰할 수 있다.

### 9.3 relaxed

`memory_order_relaxed`는 해당 원자 객체의 원자성만 보장한다. 다른 메모리 위치의 변경을 함께 공개하는 순서는 제공하지 않는다.

독립적인 통계 카운터처럼 다른 데이터와 순서 관계가 필요하지 않은 경우에 적합할 수 있다.

### 9.4 volatile

`volatile`은 멀티스레드 동기화 도구가 아니다. 메모리 맵 I/O나 구현이 정의한 특별한 접근에는 쓰일 수 있지만 C++ 스레드 사이의 원자성이나 happens-before를 만들지 않는다.

> [!tip]
> 약한 메모리 순서를 직접 사용하기 전에 mutex나 기본 순차 일관성 원자로 정확하게 구현하고 성능을 측정한다.

## 10. 동기화 도구 선택

| 도구 | 해결하려는 문제 | 대표 용도 |
|---|---|---|
| `std::mutex` | 복합 공유 상태의 상호 배제 | 컨테이너와 여러 필드의 불변식 보호 |
| `std::atomic` | 단일 값의 원자적 접근 | 카운터, 상태 플래그, 저수준 동기화 |
| `std::condition_variable` | 조건이 참이 될 때까지 대기 | 생산자-소비자, 작업 큐 |
| `std::counting_semaphore` | 사용 가능한 자원 수 관리 | 연결 수, 버퍼 슬롯 제한 |
| `std::latch` | 정해진 횟수의 완료를 한 번 기다림 | 시작 또는 완료 게이트 |
| `std::barrier` | 여러 스레드가 반복적으로 단계 동기화 | 반복 계산의 phase 경계 |
| `std::future`/`promise` | 결과 또는 예외를 전달 | 비동기 작업 결과 회수 |

### 10.1 mutex

복합 연산과 여러 필드로 이루어진 불변식을 보호할 때 사용한다.

```cpp
std::mutex mutex;

{
    std::lock_guard lock(mutex);
    update_shared_state();
}
```

### 10.2 atomic

단일 값의 독립적인 원자 변경에는 atomic이 더 단순할 수 있다.

```cpp
std::atomic<unsigned long long> completed{0};

void finish_one() {
    completed.fetch_add(1, std::memory_order_relaxed);
}
```

atomic 하나로 여러 필드 사이의 불변식을 자동으로 보호할 수는 없다.

### 10.3 조건 변수

조건 변수는 다른 스레드가 상태를 변경할 때까지 CPU를 점유하지 않고 기다리게 한다.

```cpp
std::unique_lock lock(mutex);
condition.wait(lock, [&] { return ready || stopped; });
```

조건은 반드시 predicate 또는 `while`로 다시 검사한다.

### 10.4 semaphore

동시에 접근할 수 있는 작업 수를 제한하거나 사건의 개수를 전달한다.

```cpp
std::counting_semaphore<8> slots{8};
```

### 10.5 latch와 barrier

- latch는 카운트가 0이 된 뒤 다시 사용할 수 없다.
- barrier는 여러 단계에 반복해서 사용할 수 있다.

### 10.6 blocking과 spinning

- blocking lock은 락을 얻을 수 없을 때 대기 스레드를 재우므로 CPU를 다른 작업에 사용할 수 있다.
- spin lock은 락을 반복 검사하므로 문맥 교환은 피할 수 있지만 기다리는 동안 CPU를 소비한다.

스핀은 임계 영역이 매우 짧고 락 소유자가 실제로 다른 코어에서 곧 실행을 마칠 때만 유리할 수 있다. 일반 C++ 응용 프로그램에서는 먼저 `std::mutex`를 사용하고 측정 결과가 있을 때만 다른 선택을 검토한다.

락의 정확성 외에도 공정성을 고려해야 한다. 특정 스레드가 계속 락을 얻지 못하면 기아가 발생할 수 있다. 반대로 강한 공정성 보장은 처리량이나 캐시 지역성을 낮출 수 있다.

## 11. C++ 병렬 합계 예제

다음 예제는 배열을 둘로 나누어 한쪽은 비동기 작업으로, 다른 쪽은 현재 스레드에서 계산한다.

```cpp
#include <future>
#include <numeric>
#include <span>

long long parallel_sum(std::span<const int> values) {
    constexpr std::size_t threshold = 50'000;

    if (values.size() <= threshold) {
        return std::accumulate(values.begin(), values.end(), 0LL);
    }

    const std::size_t middle = values.size() / 2;
    auto left_values = values.first(middle);
    auto right_values = values.subspan(middle);

    auto left = std::async(
        std::launch::async,
        [left_values] {
            return parallel_sum(left_values);
        }
    );

    long long right_result = parallel_sum(right_values);
    return left.get() + right_result;
}
```

핵심 사항:

- `std::launch::async`를 명시해 별도 비동기 실행을 요청한다.
- 작은 구간은 순차 실행해 작업 생성 비용을 제한한다.
- 서로 겹치지 않는 읽기 전용 구간을 사용하므로 데이터 경쟁이 없다.
- threshold가 너무 작으면 작업이 과도하게 생성될 수 있다.
- 실제 서비스에서는 스레드 수를 제어하는 작업 풀이나 검증된 병렬 런타임이 더 적합하다.

사용 예:

```cpp
#include <iostream>
#include <vector>

int main() {
    std::vector<int> values(1'000'000, 1);
    std::cout << parallel_sum(values) << '\n';
}
```

## 12. C++ 단계 병렬화 예제

`std::barrier`는 여러 스레드가 현재 단계를 모두 마친 뒤 다음 단계로 진행하게 한다.

```cpp
#include <barrier>
#include <cassert>
#include <thread>
#include <vector>

int main() {
    constexpr int worker_count = 4;
    std::vector<int> values(worker_count, 0);

    std::barrier phase(worker_count);
    std::vector<std::jthread> workers;

    for (int id = 0; id < worker_count; ++id) {
        workers.emplace_back([&, id] {
            values[id] = id + 1;       // 1단계
            phase.arrive_and_wait();

            values[id] *= 10;          // 2단계
            phase.arrive_and_wait();
        });
    }

    workers.clear(); // jthread를 join

    assert((values == std::vector<int>{10, 20, 30, 40}));
}
```

barrier는 단계 경계를 만들지만 각 단계 안에서 여러 스레드가 같은 요소를 변경하면 별도의 동기화가 필요하다.

## 13. 생산자-소비자와 역압력

생산자와 소비자의 속도가 다르면 중간 큐가 필요하다.

```text
생산자 ──> [유한 작업 큐] ──> 소비자
```

큐가 무한히 커질 수 있게 두면 소비자가 느릴 때 메모리가 계속 증가한다. 유한 큐는 가득 찼을 때 생산자를 대기시키거나 다음 정책 중 하나를 적용한다.

- 새 작업 거부
- 오래된 작업 제거
- 낮은 우선순위 작업 제거
- 호출자에게 부하를 되돌리는 역압력
- 디스크나 외부 저장소로 넘김

정책은 데이터 손실 가능성, 지연 시간, 처리량, 메모리 제한에 맞춰 선택해야 한다.

구현 시 필요한 두 조건:

- 소비자는 큐가 비어 있지 않을 때까지 기다린다.
- 생산자는 큐에 빈 슬롯이 생길 때까지 기다린다.

구체적인 C++ 유한 버퍼 구현은 [[01.프로세스와 스레드#15.1 생산자-소비자 유한 버퍼]]를 참고한다.

### 13.1 Readers-Writers

여러 reader는 동시에 공유 데이터를 읽을 수 있지만 writer는 독점 접근해야 한다. reader 선호 정책은 writer 기아를, writer 선호 정책은 reader 지연을 일으킬 수 있다. 읽기가 많다고 항상 `std::shared_mutex`가 더 빠른 것은 아니므로 임계 영역 길이와 경합을 측정해야 한다.

### 13.2 식사하는 철학자

각 작업이 자원 하나를 보유한 채 다음 자원을 기다리면 환형 대기가 만들어진다. 자원 획득 순서를 통일하거나 필요한 자원을 함께 획득하여 교착 상태를 예방할 수 있다.

## 14. 이벤트 기반 동시성

### 14.1 장점

- 단일 이벤트 루프에서는 처리기 사이의 공유 상태 동기화를 줄일 수 있다.
- 많은 연결마다 스레드를 하나씩 만들 필요가 없다.
- 프로그램이 어떤 사건을 언제 처리할지 비교적 직접 제어할 수 있다.

### 14.2 블로킹 호출 문제

하나의 처리기가 파일 I/O나 긴 계산으로 멈추면 전체 이벤트 루프가 진행하지 못한다.

해결 방법:

- non-blocking I/O
- asynchronous I/O
- readiness notification
- 블로킹 작업 전용 스레드 풀
- CPU 작업 전용 작업자 풀

명시적으로 호출한 I/O만 블로킹 원인이 되는 것은 아니다. 이벤트 처리 중 페이지 폴트가 발생하거나, 이전에는 non-blocking이던 라이브러리 함수가 구현 변경으로 블로킹 동작을 하게 되어도 이벤트 루프 전체가 지연될 수 있다.

### 14.3 상태 관리

스레드 기반 코드에서는 호출 스택과 지역 변수가 중단된 작업의 상태를 자연스럽게 보관한다. 이벤트 기반 코드에서는 완료 후 이어서 실행할 상태를 별도 객체나 continuation으로 보존해야 한다.

코루틴은 이러한 상태 기계를 컴파일러가 생성하도록 도와주지만, 공유 상태와 병렬 실행의 동기화 문제를 없애지는 않는다.

### 14.4 멀티코어 이벤트 루프

여러 코어를 사용하려고 이벤트 루프를 여러 개 실행하면 처리기들이 동시에 공유 상태에 접근할 수 있으므로 다시 동기화가 필요하다.

실제 서버는 다음과 같은 하이브리드 구조를 자주 사용한다.

```text
프로세스 여러 개
  └─ 프로세스별 이벤트 루프
       └─ 제한된 CPU/블로킹 작업자 풀
```

## 15. 확장성과 Amdahl의 법칙

프로그램의 일부만 병렬화할 수 있다면 코어 수를 늘려도 최대 성능 향상에는 한계가 있다.

병렬화 가능한 비율을 $P$, 실행 자원 수를 $N$이라고 하면 이상적인 최대 속도 향상은 다음과 같다.

$$
S(N) = \frac{1}{(1-P) + \frac{P}{N}}
$$

프로그램의 90%를 병렬화하고 8개 실행 자원을 사용한다면:

$$
S(8) = \frac{1}{0.1 + \frac{0.9}{8}} \approx 4.71
$$

코어는 8개지만 최대 속도 향상은 약 4.71배다. 실제로는 작업 생성, 통신, 동기화와 캐시 비용 때문에 더 낮다.

### 15.1 작업량과 임계 경로

- work: 모든 연산을 순차 실행했을 때의 총 작업량
- span: 의존성 때문에 반드시 순서대로 실행해야 하는 가장 긴 경로

이론적인 병렬성은 대략 `work / span`으로 볼 수 있다. 코어를 늘려도 임계 경로보다 빠르게 완료할 수는 없다.

### 15.2 강한 확장과 약한 확장

- strong scaling: 문제 크기를 고정하고 실행 자원을 늘렸을 때 얼마나 빨라지는가?
- weak scaling: 실행 자원과 함께 문제 크기도 늘렸을 때 실행 시간을 유지하는가?

## 16. 병렬 성능을 방해하는 요소

### 16.1 너무 작은 작업

작업 시간이 생성과 스케줄링 비용보다 짧으면 병렬화가 더 느릴 수 있다. 관련 연산을 묶어 적절한 grain size를 만든다.

### 16.2 락 경합

모든 작업자가 하나의 전역 락을 자주 획득하면 실질적으로 직렬 실행된다.

개선 방향:

- 임계 영역 축소
- 읽기 전용 데이터 사용
- 데이터 분할
- 지역 결과를 계산한 후 마지막에 병합
- 버킷별 또는 샤드별 락

### 16.3 부하 불균형

가장 늦게 끝나는 작업이 전체 완료 시간을 결정한다.

- 작업을 더 작은 단위로 나눈다.
- 동적 스케줄링이나 work stealing을 사용한다.
- 입력 데이터에 따른 비용 차이를 측정한다.

### 16.4 메모리 대역폭

모든 코어가 메모리에서 많은 데이터를 읽으면 연산 장치보다 메모리 대역폭이 먼저 포화될 수 있다. 이런 작업은 코어를 늘려도 성능이 거의 증가하지 않는다.

### 16.5 캐시와 false sharing

데이터 지역성이 나쁘거나 쓰기 캐시 라인이 계속 이동하면 코어 수 증가가 오히려 성능을 낮출 수 있다.

### 16.6 순차 병목

직렬 초기화, 최종 병합, 전역 로그, 단일 큐, 단일 파일 출력이 병렬 부분의 이득을 제한할 수 있다.

## 17. liveness 문제

| 문제 | 의미 |
|---|---|
| 교착 상태 | 여러 작업이 서로를 기다리며 모두 멈춤 |
| 기아 | 시스템은 진행하지만 특정 작업이 계속 기회를 얻지 못함 |
| 라이브락 | 작업들이 계속 반응하지만 유용한 진전이 없음 |
| 우선순위 역전 | 낮은 우선순위 작업이 가진 자원 때문에 높은 우선순위 작업이 대기 |

### 17.1 교착 상태 조건

다음 네 조건이 동시에 성립하면 교착 상태가 발생할 수 있다.

1. 상호 배제
2. 점유하며 대기
3. 비선점
4. 환형 대기

여러 mutex가 필요하면 `std::scoped_lock`으로 함께 획득하거나 시스템 전체에서 일관된 락 순서를 사용한다.

```cpp
std::scoped_lock lock(first_mutex, second_mutex);
```

### 17.2 라이브락 예시

두 작업이 충돌을 피하려고 동시에 양보하고 다시 동시에 재시도하는 패턴이다. 무작위 backoff, 우선순위 또는 중앙 조정으로 대칭을 깨뜨릴 수 있다.

## 18. 동시성 모델 선택 기준

| 상황 | 우선 고려할 모델 |
|---|---|
| 독립 작업의 장애 격리가 중요 | 다중 프로세스 |
| 큰 공유 자료 구조를 낮은 지연으로 접근 | 제한된 스레드 또는 작업 풀 |
| CPU 중심 데이터 처리 | 데이터 병렬성, fork-join |
| 많은 네트워크 연결과 짧은 처리 | 이벤트 루프, 비동기 I/O |
| 블로킹 라이브러리를 많이 사용 | 제한된 스레드 풀 |
| 여러 단계의 연속 처리 | 유한 큐를 둔 파이프라인 |
| 결과 하나를 나중에 회수 | future/promise 또는 task |
| 반복 계산의 단계 경계 | barrier |

선택 질문:

1. 작업은 CPU 중심인가, I/O 중심인가?
2. 작업끼리 어떤 데이터를 공유하는가?
3. 순서 의존성과 임계 경로는 무엇인가?
4. 장애를 어느 단위까지 격리해야 하는가?
5. 최대 동시 작업 수와 메모리 한도는 얼마인가?
6. 지연 시간과 처리량 중 어느 쪽이 더 중요한가?

## 19. 측정 방법

### 19.1 기준선

먼저 정확한 순차 버전의 실행 시간을 측정한다. 병렬 버전은 같은 결과를 생성하는지 확인한 뒤 비교한다.

### 19.2 측정 항목

- 전체 실행 시간
- 처리량과 지연 시간 분포
- CPU 이용률
- 실행 가능한 스레드 수
- 문맥 교환 수
- 락 대기 시간
- 캐시 미스
- 메모리 대역폭
- 작업 큐 길이
- 코어별 부하

### 19.3 speedup과 efficiency

```text
speedup(N) = 순차 실행 시간 / N개 자원 실행 시간
efficiency(N) = speedup(N) / N
```

효율이 코어 수 증가와 함께 빠르게 낮아지면 순차 병목, 동기화, 부하 불균형 또는 메모리 병목을 찾아야 한다.

### 19.4 벤치마크 주의사항

- release 최적화 빌드도 측정한다.
- 충분히 워밍업한다.
- 여러 번 반복하고 분포를 확인한다.
- 테스트 중 다른 시스템 부하를 기록한다.
- 작은 입력만으로 확장성을 판단하지 않는다.
- 로그 출력 시간을 계산 시간과 섞지 않는다.

## 20. 테스트와 디버깅

### 20.1 불변식 중심 테스트

가능한 모든 실행 순서를 나열하려 하지 말고 항상 성립해야 하는 불변식을 검사한다.

- 전체 합계가 보존되는가?
- 큐 크기가 용량 범위를 벗어나지 않는가?
- 같은 작업이 두 번 완료되지 않는가?
- 종료 후 미처리 작업이 남지 않는가?

### 20.2 실행 순서 다양화

- 작업 수와 스레드 수를 바꾼다.
- 작은 임의 지연과 yield를 삽입한 테스트를 별도로 실행한다.
- 높은 반복 횟수로 스트레스 테스트한다.
- 단일 코어와 멀티코어 환경을 모두 시험한다.

테스트용 지연을 실제 동기화 수단으로 사용해서는 안 된다.

### 20.3 도구

- ThreadSanitizer: 데이터 경쟁 탐지
- AddressSanitizer: 메모리 오류 탐지
- 운영체제 프로파일러: CPU, 스케줄링, 캐시, 락 경합 분석
- 구조화된 로그와 trace ID: 작업 간 인과 관계 추적

로그 출력 자체가 락과 I/O를 사용하여 문제의 타이밍을 바꿀 수 있다는 점도 주의한다.

## 21. 흔한 오해

### 스레드가 많을수록 빠르다

아니다. CPU 중심 작업에서는 과도한 스레드가 문맥 교환과 캐시 손실을 증가시킨다.

### atomic은 항상 mutex보다 빠르다

아니다. 경합이 심한 atomic도 캐시 라인을 계속 이동시키며, 복합 상태를 보호하려고 복잡한 lock-free 알고리즘을 만들면 오히려 느리고 위험할 수 있다.

### 서로 다른 변수를 쓰면 false sharing이 없다

아니다. 서로 다른 변수가 같은 캐시 라인에 있으면 성능 경합이 생길 수 있다.

### 비동기 코드는 자동으로 병렬 실행된다

아니다. 하나의 이벤트 루프에서 순차적으로 재개될 수 있다.

### 데이터 경쟁이 드물게만 발생하면 허용할 수 있다

아니다. C++의 데이터 경쟁은 undefined behavior다.

### sleep으로 실행 순서를 맞출 수 있다

아니다. 시스템 부하와 스케줄러에 따라 언제든 실패할 수 있다.

## 23. 핵심 요약

1. 동시성은 여러 작업을 함께 진전시키는 구조이고 병렬성은 실제 동시 실행이다.
2. 비동기는 기다리지 않는 인터페이스이며 병렬성과 같은 뜻이 아니다.
3. 병렬화는 작업, 데이터, 파이프라인 또는 fork-join 방식으로 분해할 수 있다.
4. 단일 큐는 균형이 쉽지만 경합이 크고, 작업자별 큐는 확장성이 좋지만 불균형이 생길 수 있다.
5. work stealing은 유휴 작업자가 다른 큐의 작업을 가져와 불균형을 줄인다.
6. 멀티코어 성능은 연산 수뿐 아니라 캐시, NUMA와 메모리 대역폭에 좌우된다.
7. 동시성 정확성은 원자성, 순서, 가시성의 관점에서 검토한다.
8. C++ 데이터 경쟁은 undefined behavior이며 happens-before로 접근을 정렬해야 한다.
9. 복합 공유 상태에는 mutex, 단일 원자 상태에는 atomic을 우선 검토한다.
10. 이벤트 기반 구조에서는 블로킹 호출과 긴 CPU 작업을 분리해야 한다.
11. Amdahl의 법칙 때문에 작은 순차 부분도 전체 speedup을 제한한다.
12. 성능은 추측이 아니라 순차 기준선, 프로파일링과 반복 측정으로 판단한다.
13. 캐시 일관성은 메모리 순서와 프로그램의 동기화를 대신하지 않는다.
