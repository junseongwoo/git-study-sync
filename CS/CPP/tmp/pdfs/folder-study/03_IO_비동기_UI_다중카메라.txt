3. 파일 I/O
3.1 파일 디스크립터는 파일 자체가 아니다
 open() 은 프로세스가 사용하는 파일 디스크립터를 반환한다. 파일 디스크립터는 열린 파일을 가리키는 정수형 핸들이
며, 커널의 열린 파일 상태와 연결된다.
CPP
#include <cerrno>
#include <cstddef>
#include <span>
#include <system_error>
#include <unistd.h>
std::size_t read_some(int fd, std::span<std::byte> out) {
    for (;;) {
        const auto n = ::read(fd, out.data(), out.size());
        if (n > 0) {
            return static_cast<std::size_t>(n);
        }
        if (n == 0) {
            return 0; // 일반 파일에서는 EOF
        }
        if (errno == EINTR) {
            continue; // signal로 중단되었으므로 재시도
        }
        throw std::system_error(errno, std::generic_category(), "read");
    }
}
 read() 의 반환값은 “요청한 크기”가 아니라 실제로 읽은 바이트 수다. 따라서 버퍼 전체가 채워졌다고 가정하면 안 된
다.

3.2 부분 읽기와 부분 쓰기
파일과 소켓 모두 한 번의 호출이 요청량 전체를 처리한다는 보장이 없는 경우가 있다. 특히 소켓, pipe, non-blocking 핸들
에서는 부분 처리가 정상적인 흐름이다.
CPP
#include <cerrno>
#include <cstddef>
#include <span>
#include <system_error>
#include <unistd.h>
void write_all(int fd, std::span<const std::byte> data) {
    std::size_t offset = 0;
    while (offset < data.size()) {
        const auto* begin = data.data() + offset;
        const auto left = data.size() - offset;
        const auto n = ::write(fd, begin, left);
        if (n > 0) {
            offset += static_cast<std::size_t>(n);
            continue;
        }
        if (n < 0 && errno == EINTR) {
            continue;
        }
        throw std::system_error(errno, std::generic_category(), "write");
    }
}
[!note] write() 성공과 영구 저장은 다르다
write() 가 성공해도 데이터는 메모리의 커널 버퍼에만 있을 수 있다. 전원 장애 뒤에도 유지되는 저장까지 필요하다면
파일 시스템과 API 계약에 따라 fsync() 같은 동기화가 추가로 필요하다. 즉 “애플리케이션 버퍼에서 커널이 인수함”과
“저장 장치에 영구 반영됨”을 구분해야 한다.

3.3 파일 핸들을 RAII로 관리하기
CPP
#include <unistd.h>
#include <utility>
class UniqueFd {
public:
    UniqueFd() noexcept = default;
    explicit UniqueFd(int fd) noexcept : fd_(fd) {}
    ~UniqueFd() {
        reset();
    }
    UniqueFd(const UniqueFd&) = delete;
    UniqueFd& operator=(const UniqueFd&) = delete;
    UniqueFd(UniqueFd&& other) noexcept
        : fd_(std::exchange(other.fd_, -1)) {}
    UniqueFd& operator=(UniqueFd&& other) noexcept {
        if (this != &other) {
            reset(std::exchange(other.fd_, -1));
        }
        return *this;
    }
    [[nodiscard]] int get() const noexcept { return fd_; }
    void reset(int next = -1) noexcept {
        if (fd_ != -1) {
            ::close(fd_);
        }
        fd_ = next;
    }
private:
    int fd_ = -1;
};
 UniqueFd 는 핸들의 소유권만 표현한다. 진행 중인 비동기 요청이 끝났다는 사실까지 보장하지는 않는다. 비동기 API에
서는 핸들 RAII 바깥에 요청 취소·완료 대기 프로토콜이 추가되어야 한다.

5. 비동기 I/O 요청과 버퍼
5.1 제출 시점부터 완료 시점까지
OSTEP의 POSIX AIO 예에서는 요청 구조체에 파일 디스크립터, offset, 길이와 함께 버퍼 위치가 들어간다. OS가 나중에 그
 위치에 데이터를 기록하므로, 함수의 지역 변수가 먼저 소멸하면 안 된다.
CPP
// 잘못된 구조를 보여 주는 개념 예시
void start_bad_async_read(AsyncFile& file) {
    std::array<std::byte, 4096> local{};
    file.async_read(local.data(), local.size(), on_complete);
} // local 소멸: 완료 전이라면 dangling buffer
안전한 요청 객체는 버퍼와 완료 상태를 함께 소유한다.
CPP
#include <cstddef>
#include <memory>
#include <vector>
struct ReadOperation {
    std::vector<std::byte> buffer;
    std::size_t transferred = 0;
    // 플랫폼별 요청 객체, offset, 오류 상태 등을 함께 둔다.
};
void start_read(AsyncFile& file, std::size_t size) {
    auto operation = std::make_shared<ReadOperation>();
    operation->buffer.resize(size);
    file.async_read(
        operation->buffer.data(),
        operation->buffer.size(),
        [operation](std::error_code ec, std::size_t n) {
            operation->transferred = n;
            if (!ec) {
                consume(std::span(operation->buffer).first(n));
            }
        });
}
이 예의  shared_ptr 는 “무조건 비동기는 shared ownership”이라는 뜻이 아니다. API의 callback 저장 방식에 맞춰 요청
 객체의 수명을 완료까지 연장하는 한 방법이다. 단일 소유 이벤트 루프라면  unique_ptr  요청을 completion map에 보
관하는 편이 더 명확할 수 있다.
5.2 취소 요청은 즉시 해제가 아니다
일반적인 안전 규칙은 다음과 같다.
1.
취소를 요청한다.
2.
completion 또는 별도의 동기화 수단으로 취소 완료를 확인한다.
3.
OS·드라이버·SDK가 더 이상 버퍼에 접근하지 않는다는 계약을 만족한다.
4.
그 뒤 요청 객체와 버퍼를 재사용하거나 해제한다.

5.3 DMA가 보여 주는 본질
DMA에서는 장치가 CPU 대신 메모리 위치와 길이를 이용해 데이터를 전송한다. 전송이 끝나기 전에 해당 메모리를 수정·
이동·해제하면 장치와 프로그램이 같은 저장 공간을 잘못 공유하게 된다.
이 원리는 카메라 프레임에도 그대로 적용된다.
•
SDK/드라이버가 버퍼를 채우는 동안 애플리케이션이 덮어쓰면 안 된다.
•
검사 스레드가 읽는 동안 SDK가 같은 버퍼를 다음 프레임용으로 재사용하면 안 된다.
•
재사용이 필요하다면 소유권 이전, retain/lock, reference count, requeue 같은 명시적 프로토콜이 있어야 한
다.

7. 카메라 콜백 버퍼: 세 가지 계약
카메라 SDK 이름을 모르는 상태에서는 다음 세 모델 중 어느 것인지 먼저 확인해야 한다.
7.1 모델 A — callback 동안만 빌린 버퍼
TEXT

  → callback 반환
  → SDK가 즉시 재사용 가능
이 모델에서는 검사 스레드에 pointer나  span 만 넘기면 안 된다. callback 안에서 애플리케이션 소유 버퍼로 복사한 뒤

장점은 수명 설계가 단순하고 SDK 종료와 검사 작업의 결합이 약하다는 것이다. 단점은 프레임당 메모리 복사 비용과 할당
 비용이다. 할당 비용은 미리 만든 buffer pool로 줄일 수 있다.

8. 질문별 결론
8.1 버퍼의 실제 소유자는 누구인가?
포인터를 전달받은 쪽이 아니라 할당·retain·release 계약에 기록된 주체다. callback 인수의  const void* 나  
unsigned char* 만으로는 소유권을 알 수 없다. SDK 문서에서 allocation, lifetime, ownership, buffer handling, 
requeue, release 항목을 확인한다.
8.2 콜백이 끝난 뒤에도 버퍼가 유효한가?
SDK 문서가 보장할 때만 유효하다. 보장이 없다면 callback 동안만 유효한 borrowed view로 취급하는 것이 안전하다.
callback이 끝난 뒤 사용할 때는 다음 중 하나가 필요하다.
•
callback 안에서 app-owned buffer로 복사
•
SDK의 retain/lock API로 수명 연장
•
소유권이 포함된 frame handle을 인수하고 나중에 SDK 함수로 반납

8.6 종료 시 카메라보다 검사 스레드를 먼저 종료해야 하는가?
“카메라 종료”를 두 단계로 나눠야 답이 명확하다.
1.
새 프레임 생산 중지: 검사 스레드 종료보다 먼저 한다.
2.
카메라/stream/SDK 객체 파괴: outstanding SDK frame이 모두 반납되고 검사 스레드가 종료된 뒤 한다.
권장 순서는 다음과 같다.
TEXT
새 작업 접수 중지
  → 카메라 acquisition 중지 / callback 등록 해제 시작
  → 실행 중 callback과 I/O의 완료·취소 완료 대기
  → frame queue close
  → 검사 스레드가 drain 또는 명시적 discard 후 종료(join)
  → outstanding SDK frame 전부 release/requeue
  → camera/stream/SDK destroy
SDK frame을 worker가 직접 보유한다면 카메라를 먼저 파괴해서는 안 된다. 반대로 callback에서 완전히 복사한
app-owned frame만 queue에 있다면 worker는 카메라 메모리에 의존하지 않지만, 새 callback과 종료가 경쟁하지 않도록
acquisition 중지와 callback quiescence는 여전히 먼저 수행해야 한다.

    // callback을 오래 막지 않도록 가득 차면 false를 반환한다.
    bool try_push(OwnedFrame frame) {
        {
            std::lock_guard lock(mutex_);
            if (closed_ || queue_.size() == capacity_) {
                return false;
            }
            queue_.push_back(std::move(frame));
        }
        not_empty_.notify_one();
        return true;
    }
    std::optional<OwnedFrame> pop() {
        std::unique_lock lock(mutex_);
        not_empty_.wait(lock, [this] {
            return closed_ || !queue_.empty();
        });
        if (queue_.empty()) {
            return std::nullopt;
        }
        OwnedFrame frame = std::move(queue_.front());
        queue_.pop_front();
        return frame;
    }
    void close() {
        {
            std::lock_guard lock(mutex_);
            closed_ = true;
        }
        not_empty_.notify_all();
    }
private:
    const std::size_t capacity_;
    std::mutex mutex_;
    std::condition_variable not_empty_;
    std::deque<OwnedFrame> queue_;

class InspectionPipeline {
public:
    explicit InspectionPipeline(std::size_t queue_capacity)
        : queue_(queue_capacity), worker_([this] { worker_loop(); }) {}
    // SDK callback 안에서 호출한다고 가정한다.
    void on_frame(BorrowedFrameView borrowed) {
        // callback 반환 전에 복사를 끝낸다.
        // 실패 시 drop-newest 정책을 사용한다.
        [[maybe_unused]] const bool accepted =
            queue_.try_push(copy_frame(borrowed));
    }
    void shutdown() {
        // 실제 프로그램에서는 이 함수 전에 다음을 수행한다.
        // 1) SDK acquisition 중지
        // 2) callback 진입 차단 및 실행 중 callback 종료 대기
        queue_.close();
        if (worker_.joinable()) {
            worker_.join();
        }
        // 그 뒤 camera/stream/SDK 객체를 파괴한다.
    }
    ~InspectionPipeline() {
        shutdown();
    }
    InspectionPipeline(const InspectionPipeline&) = delete;
    InspectionPipeline& operator=(const InspectionPipeline&) = delete;
private:
    void worker_loop() {
        while (auto frame = queue_.pop()) {
            inspect(*frame);
        }
    }
    FrameQueue queue_;
    std::thread worker_;
};

[!warning] callback 안에서 join하지 않는다
SDK callback을 실행하는 스레드가 자기 자신 또는 자신이 빠져나가야 끝나는 작업을 join 하면 deadlock이 된다. 종료
요청과 실제 join 위치를 분리하고, SDK가 어느 스레드에서 callback을 실행하는지 확인한다.
13. 흔한 실패 패턴
13.1 callback pointer만 queue로 전달
CPP
void on_frame(const std::byte* data, std::size_t size) {
    queue.push(std::span(data, size)); // callback 뒤 SDK 재사용이면 dangling/데이터 변조
}
 span  복사는 데이터 복사가 아니다. 주소와 길이만 복사한다.
13.2 지역 버퍼로 비동기 요청
CPP
void request() {
    std::vector<std::byte> bytes(4096);
    async_read(bytes.data(), bytes.size());
} // 완료 전에 bytes 소멸 가능
요청 객체가 버퍼를 소유하도록 만들고 completion까지 보관해야 한다.
13.3 SDK 포인터에 delete[]
CPP
void on_frame(unsigned char* sdk_buffer) {
    // ...
    delete[] sdk_buffer; // SDK 계약 없이는 금지
}
allocator mismatch, pool 손상, double free가 될 수 있다.

대신, 미리 정한 drop/backpressure 정책으로 부하를 제한해야 한다.

7. UI 정지 없는 pipeline
7.1 권장 흐름
TEXT
UI event
  -> 입력 검증
  -> image ownership 확보
  -> generation 증가
  -> 이전 token cancel
  -> latest job 교체
  -> worker notify
  -> 즉시 return
Worker
  -> latest job 인수
  -> tile/row마다 cancel 확인
  -> result 생성
  -> UI dispatcher에 callback 게시
UI callback
  -> controller alive 확인
  -> generation == latest 확인
  -> widget/model 갱신
7.2 generation이 필요한 이유
TEXT
generation 1: 큰 이미지, 먼저 시작했지만 늦게 완료
generation 2: 작은 이미지, 나중에 시작했지만 먼저 완료
완료 순서만 믿으면 generation 1이 마지막에 화면을 덮는다. submit 시 증가한 generation을 결과에 넣고 UI commit 직전
에 최신 값과 비교한다.

if (result.generation != latest_generation.load()) {

}
7.3 progress update를 너무 자주 보내지 않는다
worker가 pixel마다 UI event를 post하면 UI queue가 progress event로 가득 찬다. 다음 중 하나를 사용한다.
•
50~100 ms에 한 번만 게시
•
마지막 게시보다 일정 비율 이상 변했을 때만 게시
•
atomic progress 하나를 갱신하고 UI timer가 주기적으로 읽음
•
queue에서 이전 progress event를 최신 값으로 병합

외부 library가 thread-safe하지 않을 수 있음

4. 여러 카메라가 같은 데이터에 접근할 때 생기는 문제
4.1 data race와 undefined behavior
서로 다른 두 thread가 같은 메모리에 접근하고, 하나 이상이 쓰며, happens-before 관계가 없으면 C++ data race다. 결과
가 가끔 틀리는 정도가 아니라 undefined behavior다.
CPP
struct SharedResult {
    int camera_id;
    std::vector<std::uint8_t> pixels;
};
SharedResult latest;
// camera 1 thread
latest.camera_id = 1;
latest.pixels.assign(cam1_data, cam1_data + size);
// camera 2 thread: 동시에 같은 객체를 변경하면 data race
latest.camera_id = 2;
latest.pixels.assign(cam2_data, cam2_data + size);
 std::vector 는 여러 thread가 같은 객체의 크기와 storage를 동시에 변경하도록 보장하지 않는다. reallocation과 읽기
가 겹치면 iterator·pointer 무효화와 메모리 손상까지 이어질 수 있다.
4.2 data race가 없어도 논리적 race가 남을 수 있다
각 필드 접근에 mutex를 붙였더라도 하나의 논리적 snapshot을 여러 임계 영역으로 나누면 camera ID와 pixel이 서로 다
른 frame에서 올 수 있다.
CPP
set_camera_id(1);       // lock/unlock
set_pixels(cam1_frame); // lock/unlock 사이에 camera 2가 끼어들 수 있음
하나의 결과를 완성한 뒤 한 번에 교체한다.
CPP
Frame complete{camera_id, frame_id, owned_pixels};
{
    std::lock_guard lock(latest_mutex);
    latest = std::move(complete);
}
더 좋은 방법은 mutable “현재 작업 중 frame”을 공유하지 않고, queue가 완성된 값 객체의 소유권을 이동하도록 만드는 
것이다.

6. 검사 작업을 안전하게 취소하는 방법
6.1 취소 요청과 취소 완료는 다르다

•

•

•

•

10. 자주 하는 잘못된 해결
10.1 모든 곳에 하나의 전역 mutex 사용
data race 일부는 사라질 수 있지만 UI, callback, worker가 하나의 lock을 경쟁한다. lock 안에서 검사나 SDK 호출을 하면
정지와 교착 가능성이 커진다. 데이터 소유권을 분리하고 임계 영역을 작게 만든다.
10.2 volatile bool stop
 volatile 은 멀티스레드 원자성과 happens-before를 제공하지 않는다.  atomic , mutex-protected state,  
stop_token 을 사용한다.
10.3 thread를 강제 종료
lock, buffer, handle, 부분 결과의 정리 시점을 잃는다. 취소 가능한 I/O와 협력적 checkpoint를 설계한다.

10.4 camera callback에서 UI를 동기 호출
SDK 내부 lock과 UI 종료가 결합될 수 있다. callback은 소유권 확보와 enqueue만 하고 반환한다.
10.5 raw SDK pointer를 queue에 저장
포인터를 받았다는 사실은 소유권을 뜻하지 않는다. 복사하거나 공식 retain 계약을 RAII로 감싼다.
10.6 queue를 무한히 키움
drop을 피한 것이 아니라 실패 시점을 메모리 고갈까지 미룬 것이다. 용량과 overflow 정책을 명시한다.
10.7 취소 flag만 확인하고 UI 결과는 무조건 반영
검사가 취소 요청과 거의 동시에 끝나 UI queue에 결과를 넣을 수 있다. UI commit 시 generation과 lifetime을 다시 검사
한다.
10.8 로그가 없으니 deadlock이라고 단정
무한 I/O, lost notification, overload, memory corruption도 비슷하게 보인다. 모든 thread stack, queue metric, wait chain
으로 분류한다.

12. 핵심 결론
1.
UI thread는 event loop를 돌려야 하므로 카메라 수신·검사·동기 대기를 맡기면 안 된다.
2.
camera callback은 buffer 소유권을 확보해 bounded queue로 넘기고 빠르게 반환해야 한다.
3.
여러 camera는 완성된 독립 frame 값을 전달해야 하며 하나의 mutable buffer를 공유하지 않는다.
4.
mutex로 data race를 없애도 여러 단계의 논리적 race, lock 역전, stale result는 별도로 해결해야 한다.
5.
가끔 멈추는 이유는 scheduler와 외부 I/O가 오류가 발생하는 interleaving을 매번 다르게 만들기 때문이다.
6.
재현이 어렵다면 log를 늘리는 것만으로 끝내지 말고 thread stack, wait chain, queue depth, tail latency를
확보한다.
7.
안전한 취소는 강제 종료가 아니라 checkpoint, buffer 수명, 결과 폐기까지 포함하는 협력적 protocol이다.
8.
UI에 결과를 반영하는 마지막 순간에 lifetime과 generation을 다시 확인한다.
9.
종료할 때는 생산을 먼저 멈추고 callback 종료를 확인한 뒤 소비자를 drain/cancel하고 자원을 파괴한다.
10.
camera SDK의 buffer retain·반납·callback 종료 계약은 일반 C++ 원칙만으로 추론하지 말고 제조사 문서로
확정한다.
