1. 프로그램, 프로세스, 스레드
1.1 프로그램
프로그램(program)은 디스크에 저장된 실행 파일과 정적 데이터의 묶음이다. 아직 실행되지 않은 수동적인 존재다.
1.2 프로세스
프로세스(process)는 실행 중인 프로그램이다. 실행 코드뿐 아니라 운영체제가 프로그램을 실행하기 위해 관리하는 환경 
전체를 포함한다.
•
가상 주소 공간
•
코드와 전역 데이터
•
힙(heap)
•
하나 이상의 스택(stack)
•
CPU 레지스터와 프로그램 카운터
•
프로세스 ID
•
열린 파일과 소켓
•
보안 권한
•
스케줄링 정보
같은 프로그램을 두 번 실행하더라도 서로 다른 프로세스가 생성된다. 두 프로세스는 같은 실행 파일을 사용하지만 서로
다른 주소 공간과 실행 상태를 갖는다.
1.3 스레드
스레드(thread)는 프로세스 안에서 실제로 명령어를 실행하는 흐름이다. 하나의 프로세스는 하나 이상의 스레드를 가질 수
있다.
같은 프로세스의 스레드들이 공유하는 것:

•

•

•

[!important]
현대 운영체제에서 프로세스는 주로 자원과 보호의 단위, 커널 스레드는 CPU 스케줄링의 단위로 사용된다.
[!warning] 파일 공유의 함정
같은 프로세스의 스레드는 파일 디스크립터를 공유한다. 여러 스레드가 같은 파일 객체의 현재 오프셋을 동시에 변경하면
예상하지 못한 위치를 읽거나 쓸 수 있으므로 별도의 동기화 또는 위치 기반 I/O가 필요할 수 있다.
2. 병행성과 병렬성
2.1 병행성
병행성(concurrency)은 여러 작업의 실행 시간이 겹치는 성질이다. CPU가 하나여도 운영체제가 작업을 빠르게 번갈아 실행
하면 병행성이 생긴다.
TEXT
시간 ───────────────────────────────>
CPU  [스레드 A][스레드 B][스레드 A][스레드 B]
2.2 병렬성
병렬성(parallelism)은 여러 CPU 코어에서 실제로 작업이 동시에 실행되는 것이다.
TEXT
CPU 0 [────────── 스레드 A ──────────]
CPU 1 [────────── 스레드 B ──────────]
멀티스레드 프로그램이라고 반드시 병렬 실행되는 것은 아니다. 실제 병렬 실행 여부는 CPU 코어 수, 운영체제 스케줄링,
다른 작업의 부하에 따라 달라진다.

3. 프로세스 상태
대표적인 프로세스 상태는 다음과 같다.
•
New: 프로세스가 생성되는 중
•
Ready: CPU가 할당되면 실행할 수 있는 상태
•
Running: CPU에서 실행 중
•
Waiting/Blocked: I/O 완료나 특정 사건을 기다리는 상태
•
Terminated: 실행이 끝난 상태
TEXT
                  CPU 할당
          Ready ───────────> Running
            ^                   |
            |                   | I/O 요청 또는 조건 대기
            |                   v
            +─────────────── Waiting
                    I/O 완료
Running ── 선점 또는 타임 슬라이스 만료 ──> Ready
Running ── 정상 종료 또는 오류 ───────────> Terminated
3.1 Ready와 Waiting의 차이
•
Ready 상태는 CPU만 받으면 즉시 실행할 수 있다.
•
Waiting 상태는 CPU를 받아도 실행할 수 없다. I/O 완료나 특정 조건 충족이 먼저 필요하다.
3.2 스케줄링 큐
•
ready queue에는 CPU를 기다리는 실행 가능한 작업이 들어간다.
•
I/O wait queue에는 특정 장치나 사건의 완료를 기다리는 작업이 들어간다.
•
I/O가 완료되면 작업은 Waiting에서 Ready로 이동할 뿐 곧바로 실행된다고 보장되지는 않는다.
•
각 큐에서 다음 작업을 선택하는 기준이 스케줄링 정책이다.

스레드의 실행 문맥은 TCB(Thread Control Block) 또는 운영체제의 태스크 구조체에 저장할 수 있다.
4.2 문맥 교환
문맥 교환(context switch)은 현재 실행 중인 스레드의 실행 문맥을 저장하고 다른 스레드의 문맥을 복원하는 과정이다.
1.
현재 프로그램 카운터와 레지스터를 저장한다.
2.
현재 스레드의 상태를 변경한다.
3.
스케줄러가 다음 스레드를 선택한다.
4.
선택된 스레드의 레지스터와 실행 위치를 복원한다.
5.
해당 스레드의 실행을 재개한다.
문맥 교환은 응용 프로그램의 작업을 직접 진행하지 않는 오버헤드다. 프로세스 사이의 전환은 주소 공간, 페이지 테이블,
TLB 및 캐시에 영향을 주므로 같은 프로세스 내 스레드 전환보다 일반적으로 무겁다.
[!warning]
스레드 전환도 무료가 아니다. 캐시 손실, 커널 진입, 코어 이동, 락 경합으로 비용이 커질 수 있다.
5. 제한적 직접 실행
운영체제는 성능을 위해 사용자 프로그램의 명령어를 CPU에서 직접 실행한다. 하지만 프로그램에 CPU 전체 권한을 주면
시스템 보호와 제어가 불가능하다.
이를 해결하는 핵심 장치는 다음과 같다.
•
사용자 모드와 커널 모드

시스템 콜
•
trap 명령
•
인터럽트

5.1 시스템 콜
프로그램이 파일 읽기, 프로세스 생성, 네트워크 통신 같은 특권 작업을 요청하면 시스템 콜을 사용한다.

5.2 타이머 인터럽트
프로세스가 자발적으로 CPU를 반환하지 않더라도 타이머 인터럽트가 발생하면 운영체제가 다시 제어권을 얻는다. 이를 통
해 선점형 멀티태스킹이 가능해진다.
6. 프로세스 생성과 종료
Unix 계열 운영체제는 다음 API를 중심으로 프로세스를 관리한다.
•
 fork() : 현재 프로세스를 복제해 자식 프로세스를 생성한다.
•
 exec() : 현재 프로세스의 프로그램과 주소 공간을 새 프로그램으로 교체한다.
•
 wait() / waitpid() : 부모가 자식의 종료를 기다리고 종료 상태를 회수한다.
 fork()  이후에는 부모와 자식이 모두 다음 명령어부터 실행한다. 어느 프로세스가 먼저 실행될지는 운영체제 스케줄러
가 결정한다.
6.1 C++와 POSIX 프로세스 예제
[!note]
C++ 표준 라이브러리에는 범용적인 프로세스 생성 기능이 없다. 다음 코드는 Linux, macOS 또는 WSL에서 사용하는
POSIX 예제다.

CPP
#include <sys/types.h>
#include <sys/wait.h>
#include <unistd.h>
#include <cstring>
#include <iostream>
int main() {
    int fd[2];
    if (pipe(fd) == -1) {
        std::cerr << "pipe failed\n";
        return 1;
    }
    pid_t pid = fork();
    if (pid == -1) {
        std::cerr << "fork failed\n";
        return 1;
    }
    if (pid == 0) {
        close(fd[0]);
        const char* message = "message from child";
        write(fd[1], message, std::strlen(message));
        close(fd[1]);
        _exit(0);
    }
    close(fd[1]);
    char buffer[128]{};
    ssize_t size = read(fd[0], buffer, sizeof(buffer) - 1);
    if (size > 0) {
        std::cout << "parent received: " << buffer << '\n';
    }
    close(fd[0]);
    int status = 0;
    waitpid(pid, &status, 0);
    if (WIFEXITED(status)) {
        std::cout << "child exit status: "
                  << WEXITSTATUS(status) << '\n';
    }
}

6.2 종료 후의 상태
•
Unix에서 자식이 종료했지만 부모가 아직  wait() 로 종료 상태를 회수하지 않으면 zombie가 된다.
•
부모가 먼저 종료한 자식 프로세스는 orphan이 되며 운영체제의 지정된 프로세스가 부모 역할을 넘겨받아
종료 상태를 회수한다.
•
부모는 자식의 종료 상태를 회수해 프로세스 테이블의 항목이 정리되도록 해야 한다.
7. 프로세스 간 통신
분리된 주소 공간을 가진 프로세스끼리 데이터를 교환하려면 IPC(Inter-Process Communication)가 필요하다.
7.1 공유 메모리
여러 프로세스가 동일한 물리 메모리를 각자의 주소 공간에 매핑한다.
장점:
•
대량 데이터 전달이 빠르다.
•
반복적인 커널 복사 비용을 줄일 수 있다.
단점:
•
별도의 동기화가 필요하다.
•
경쟁 조건과 데이터 손상이 발생할 수 있다.

7.3 메시지 전달의 설계 선택
•

10. 스레드 생명주기와 암시적 스레딩
10.1 생성, 합류, 분리
•
생성: 새 실행 흐름과 스택을 준비한다.
•
 join() : 다른 스레드의 종료를 기다리고 실행 결과의 가시성을 확보한다.
•
 detach() : 스레드를 독립 실행시키지만 수명과 자원 관리가 어려워진다.
 std::thread  객체가 join 가능한 상태로 파괴되면  std::terminate() 가 호출된다. 직접 수명 관리를 해야 한다면 
모든 경로에서  join()  또는  detach() 가 호출되어야 한다. C++20에서는 자동 합류하는  std::jthread 를 우선 
고려한다.
10.2 fork와 멀티스레드 프로세스
POSIX 멀티스레드 프로세스가  fork() 를 호출하면 자식에는 호출한 스레드만 복제된다. 다른 스레드가 보유하던 
mutex 상태는 복사되지만 해당 스레드는 자식에 존재하지 않으므로 교착 상태 위험이 있다.
따라서 멀티스레드 프로그램에서  fork()  후  exec()  전까지는 POSIX가 허용한 async-signal-safe 함수만 사용하는 
것이 원칙이다.
10.3 스레드 지역 저장소
모든 스레드가 공유할 필요가 없는 상태는  thread_local 로 분리할 수 있다.

10.4 스레드 풀과 작업 기반 병렬성
작업마다 새 스레드를 만들면 생성·파괴 비용과 문맥 교환이 증가한다. 스레드 풀은 제한된 수의 작업자 스레드가 큐에서
작업을 가져가도록 한다.
TEXT
작업 제출자 ──> [공유 작업 큐] ──> 작업자 스레드 1
                                 ├─> 작업자 스레드 2
                                 └─> 작업자 스레드 N
관련 모델에는 스레드 풀, fork-join, OpenMP, 작업 스케줄러, Grand Central Dispatch 등이 있다. 핵심은 스레드 자체보다 
수행할 작업을 표현하고 런타임이 실행 자원을 관리하게 하는 것이다.
10.5 취소, 신호와 예외
•
스레드 취소는 자원과 불변식을 안전하게 정리할 수 있는 협력적 방식이 좋다.
•
POSIX 신호는 프로세스 전체 또는 특정 스레드에 전달될 수 있어 신호 마스크 설계가 필요하다.
•
한 C++ 스레드에서 처리되지 않은 예외가 스레드 함수 밖으로 빠져나가면  std::terminate() 가 호출된
다. 필요한 경우 스레드 내부에서 예외를 잡아  std::exception_ptr ,  std::promise  또는  
std::future 로 전달한다.
11. C++ 스레드 생성
C++20에서는  std::jthread 를 사용할 수 있다.  std::thread 와 달리 소멸 시 자동으로  join() 하고, 협력적 취
소를 위한 중지 토큰도 지원한다.


프로세스·스레드·동시성·동기화
12
CPP
#include <algorithm>
#include <iostream>
#include <numeric>
#include <thread>
#include <vector>
int main() {
    std::vector<int> values(1'000'000, 1);
    unsigned count =
        std::max(1u, std::thread::hardware_concurrency());
    count = std::min<unsigned>(
        count,
        static_cast<unsigned>(values.size())
    );
    std::vector<long long> partial(count);
    {
        std::vector<std::jthread> workers;
        workers.reserve(count);
        for (unsigned t = 0; t < count; ++t) {
            std::size_t begin = values.size() * t / count;
            std::size_t end = values.size() * (t + 1) / count;
            workers.emplace_back([&, t, begin, end] {
                partial[t] = std::accumulate(
                    values.begin() + begin,
                    values.begin() + end,
                    0LL
                );
            });
        }
    } // 모든 jthread가 join된다.
    long long total =
        std::accumulate(partial.begin(), partial.end(), 0LL);
    std::cout << total << '\n';
}
각 스레드는 서로 다른  partial[t] 만 변경하므로 논리적인 데이터 경쟁이 없다.
[!warning]
std::thread::hardware_concurrency() 는 하드웨어 스레드 수에 대한 힌트일 뿐이다. 0 을 반환할 수 있으며,
반환된 수만큼 스레드를 생성하는 것이 항상 가장 빠르다는 뜻도 아니다.
12. CPU 스케줄링
운영체제의 스케줄러는 준비 상태인 프로세스나 스레드 중 다음 실행 대상을 선택한다.
12.1 스케줄링이 일어나는 시점
스케줄링 결정은 다음과 같은 상태 전이에서 일어난다.

•
Running → Waiting: I/O 요청, 조건 대기
•
Running → Ready: 타이머 인터럽트에 의한 선점
•
Waiting → Ready: I/O 또는 사건 완료

스케줄러가 작업을 선택한 뒤 디스패처(dispatcher)가 문맥 교환, 사용자 모드 전환, 올바른 명령어 위치로의 이동을 수행한

12.4 멀티프로세서 스케줄링
멀티코어에서는 단순히 다음 작업을 고르는 것 외에 다음 문제가 추가된다.
•
캐시 친화성: 이전에 실행한 코어에서 다시 실행하면 따뜻한 캐시를 활용할 수 있다.
•
프로세서 affinity: 작업을 특정 코어 또는 코어 집합에 묶는다.
•
부하 균등화: 코어별 실행 큐의 부하를 맞춘다.
•
push migration: 바쁜 코어의 작업을 다른 코어로 밀어낸다.
•
pull migration/work stealing: 빈 코어가 다른 큐의 작업을 가져온다.
•
NUMA: 메모리가 가까운 CPU에서 실행해야 원격 메모리 접근을 줄일 수 있다.
•
SMT: 하나의 물리 코어가 여러 하드웨어 실행 문맥을 제공하므로 논리 CPU 수와 실제 코어 수가 다를 수 있
다.
CPU 중심 작업은 무작정 스레드를 늘리기보다 코어 수와 측정 결과를 기준으로 제한한다. I/O 중심 작업은 대기 시간 때문
에 더 많은 동시 작업이 유리할 수 있지만 스레드 과다 생성은 메모리와 문맥 교환 비용을 증가시킨다.
12.5 실시간 스케줄링
•
Rate-Monotonic은 주기가 짧은 주기 작업에 더 높은 고정 우선순위를 준다.
•
Earliest-Deadline-First는 마감 시간이 가장 가까운 작업을 동적으로 먼저 실행한다.
•
soft real-time은 지연을 최소화하지만 마감 준수를 절대 보장하지 않는다.
•
hard real-time은 최악 실행 시간과 자원 요구량을 분석하여 마감 준수를 보장해야 한다.
12.6 C++에서 주의할 점
CPP
std::thread a(taskA);
std::thread b(taskB);
이 코드에서  taskA() 가  taskB() 보다 먼저 실행된다는 보장은 없다. 실행 순서를 정해야 한다면 스케줄러의 우연한 
선택이 아니라  join() , 조건 변수, future 등의 동기화 도구를 사용해야 한다.
스레드 우선순위와 CPU affinity는 표준 C++ 기능이 아니다. 프로그램의 정확성을 특정 우선순위나 affinity에 의존시키면
안 된다.

    }

 ++counter 는 개념적으로 다음 연산으로 분리된다.
1.
 counter 를 레지스터로 읽는다.
2.
값을 1 증가시킨다.
3.
결과를 메모리에 저장한다.
두 스레드가 같은 값을 읽은 뒤 각각 증가시켜 저장하면 증가 연산 하나가 사라질 수 있다.
[!important]
C++에서 동기화되지 않은 데이터 경쟁은 단순히 결과가 부정확해지는 문제가 아니라 undefined behavior다.
13.1 mutex 사용
CPP
#include <mutex>
int counter = 0;
std::mutex counter_mutex;
void work() {
    for (int i = 0; i < 100'000; ++i) {
        std::lock_guard lock(counter_mutex);
        ++counter;
    }
}
 std::lock_guard 는 범위를 벗어날 때 자동으로 mutex를 해제한다. 예외나 조기  return 이 발생할 수 있으므로 수
동  lock() 과  unlock() 보다 안전하다.

13.2 atomic 사용
CPP
#include <atomic>
std::atomic<int> counter{0};
void work() {
    for (int i = 0; i < 100'000; ++i) {
        counter.fetch_add(1, std::memory_order_relaxed);

독립적인 통계 카운터처럼 최종 숫자의 원자성만 필요하다면  memory_order_relaxed 를 사용할 수 있다. 다른 데이터
의 공개와 실행 순서까지 전달해야 한다면 acquire/release 또는 기본 순차 일관성을 검토해야 한다.
 std::atomic 이라고 항상 lock-free인 것은 아니다.
13.3 volatile은 동기화가 아니다
 volatile 은 멀티스레드 원자성과 실행 순서를 제공하지 않는다.  volatile int counter 로 바꿔도 위의 경쟁 조
건은 해결되지 않는다.
13.4 C++ 메모리 모델과 happens-before
C++에서 데이터 경쟁은 다음 조건을 만족하는 두 메모리 접근이 있을 때 발생한다.
•
서로 다른 스레드에서 실행된다.
•
같은 메모리 위치에 접근한다.
•
하나 이상이 쓰기다.
•
두 접근이 원자 연산이 아니며 happens-before 관계로 정렬되지 않는다.
대표적인 happens-before 관계:
•
스레드를 시작하기 전에 수행한 작업은 새 스레드가 시작한 후 관찰할 수 있다.
•
스레드 안의 작업은 성공한  join()  이후의 코드보다 앞선다.
•
mutex의  unlock() 은 같은 mutex를 이후에 성공적으로 획득한  lock() 보다 앞선다.
•
release 저장은 그 값을 읽은 acquire 읽기보다 앞선다.


프로세스·스레드·동시성·동기화
17
CPP
#include <atomic>
#include <cassert>
#include <string>
#include <thread>
std::string payload;
std::atomic<bool> ready{false};
void producer() {
    payload = "complete";
    ready.store(true, std::memory_order_release);
}
void consumer() {
    while (!ready.load(std::memory_order_acquire)) {
        std::this_thread::yield();
    }
    assert(payload == "complete");
}
release/acquire는  ready  자체의 원자성뿐 아니라  payload  기록의 가시성도 전달한다. 단순 카운터에 사용한  
memory_order_relaxed 에는 이런 데이터 공개 기능이 없다.
[!tip]
메모리 순서를 정확히 증명해야 하는 특별한 이유가 없다면 먼저 mutex나 기본 원자 메모리 순서를 사용한다. 성능 측정
없이 약한 메모리 순서를 선택하면 이해하기 어려운 버그만 늘어날 수 있다.
14. 임계 영역과 락
임계 영역(critical section)은 여러 스레드가 동시에 실행하면 공유 상태가 손상될 수 있는 코드 구간이다.
올바른 임계 영역 해법이 가져야 할 성질:
•
상호 배제: 한 번에 하나의 스레드만 진입한다.
•
진행: 임계 영역이 비어 있을 때 진입 결정이 무한히 지연되지 않는다.
•
한정 대기: 특정 스레드가 무한히 기다리지 않는다.
락 구현의 기반에는 다음과 같은 하드웨어 원자 명령이 있다.
•
Test-And-Set
•
Compare-And-Swap
•
Fetch-And-Add
•
Load-Linked/Store-Conditional
14.1 스핀 락
스핀 락은 락이 풀릴 때까지 반복 검사한다. 임계 영역이 매우 짧고 현재 소유자가 곧 실행될 것이 확실한 저수준 환경에서
는 유용할 수 있다.
일반 응용 프로그램에서는 다음 문제가 발생하기 쉽다.

•
기다리는 동안 CPU를 계속 사용한다.
•
락 소유자가 선점되면 오랫동안 헛돌 수 있다.
•
스레드가 많을수록 메모리 버스와 캐시 경합이 커진다.

14.2 락 기반 자료 구조
자료 구조에 락 하나를 추가했다고 모든 사용 방식이 자동으로 안전해지는 것은 아니다.
•
거친 락(coarse-grained lock): 자료 구조 전체를 하나의 락으로 보호한다. 정확성은 이해하기 쉽지만 병렬성
이 낮다.
•
세밀한 락(fine-grained lock): 노드, 버킷 또는 영역별로 락을 둔다. 병렬성은 높지만 락 순서와 객체 수명 관
리가 어려워진다.
•
분할 자료 구조: 해시 테이블의 버킷별 락처럼 서로 독립적인 영역으로 경합을 분산한다.
•
지역 상태 + 주기적 병합: CPU 또는 스레드별 카운터를 두고 일정 시점에 전역 값으로 합쳐 정확성과 성능을
 절충한다.
개별 메서드가 thread-safe여도 여러 메서드의 조합은 원자적이지 않을 수 있다.
CPP
if (!queue.empty()) { // 이 검사 직후 다른 스레드가 pop할 수 있음
    auto value = queue.front();
    queue.pop();
}
이런 연산은  try_pop() 처럼 검사와 제거를 하나의 동기화된 메서드로 제공해야 한다.
인접한 스레드별 카운터는 서로 다른 객체여도 같은 캐시 라인에 놓여 false sharing을 일으킬 수 있다. 데이터 배치와 패딩
은 정확성 문제가 아니라 성능 문제이며 반드시 측정 후 조정한다.

15.1 생산자-소비자 유한 버퍼
CPP · 1/2
#include <condition_variable>
#include <deque>
#include <mutex>
#include <optional>
#include <stdexcept>
template<class T>
class BoundedBlockingQueue {
public:
    explicit BoundedBlockingQueue(std::size_t capacity)
        : capacity_(capacity) {
        if (capacity_ == 0) {
            throw std::invalid_argument("capacity must be positive");
        }
    }
    bool push(T value) {
        std::unique_lock lock(mutex_);
        not_full_.wait(lock, [this] {
            return closed_ || queue_.size() < capacity_;
        });
        if (closed_) {
            return false;
        }
        queue_.push_back(std::move(value));
        lock.unlock();
        not_empty_.notify_one();
        return true;
    }
    std::optional<T> pop() {
        std::unique_lock lock(mutex_);
        not_empty_.wait(lock, [this] {
            return closed_ || !queue_.empty();
        });
        if (queue_.empty()) {
            return std::nullopt;
        }


프로세스·스레드·동시성·동기화

        T value = std::move(queue_.front());
        queue_.pop_front();
        lock.unlock();
        not_full_.notify_one();
        return value;
    }
    void close() {
        {
            std::lock_guard lock(mutex_);
            closed_ = true;
        }
        not_empty_.notify_all();
        not_full_.notify_all();
    }
private:
    std::mutex mutex_;
    std::condition_variable not_empty_;
    std::condition_variable not_full_;
    std::deque<T> queue_;

•

 close() 는 양쪽 대기자를 모두 깨워 종료 조건을 다시 검사하게 한다. 알림 전에 mutex를 해제하면 깨어난 스레드가 
곧바로 mutex를 획득할 가능성이 높아지지만, 상태 변경 자체는 반드시 mutex를 보유한 상태에서 수행해야 한다.
15.2 조건 변수 규칙
•

•
 if  대신 predicate 또는  while 로 조건을 다시 검사한다.

•

16. 세마포어
세마포어는 정수 카운터와 대기 큐로 동시 접근 수를 제어한다.
•
 acquire() /wait/P: 값이 양수이면 감소하고 진행하고, 아니면 대기한다.
•
 release() /post/V: 값을 증가시키고 필요한 경우 대기자를 깨운다.

class Permit {

    explicit Permit(std::counting_semaphore<3>& semaphore)
        : semaphore_(semaphore) {
        semaphore_.acquire();
    }
    ~Permit() {
        semaphore_.release();
    }
    Permit(const Permit&) = delete;
    Permit& operator=(const Permit&) = delete;
private:
    std::counting_semaphore<3>& semaphore_;
};

    Permit permit(connection_slots);

•

•
일반적으로 mutex를 획득한 스레드가 해제해야 한다.
•
세마포어의  release() 는 다른 스레드가 호출할 수 있다.
•
mutex는 상호 배제에 적합하다.
•
세마포어는 자원 개수 제한이나 스레드 간 사건 전달에 적합하다.
16.2 고전적인 동기화 문제
유한 버퍼
생산자는 빈 슬롯을 기다리고 소비자는 채워진 슬롯을 기다린다. 버퍼 인덱스와 실제 자료의 변경은 mutex로 보호해야 한

시에 같은 위치를 조작할 수 있다.
Readers-Writers
여러 reader는 동시에 읽을 수 있지만 writer는 독점 접근해야 한다.

17. 교착 상태
교착 상태(deadlock)는 스레드들이 서로가 가진 자원을 기다리며 모두 진행하지 못하는 상태다.
17.1 Coffman의 네 조건
다음 네 조건이 동시에 성립하면 교착 상태가 발생할 수 있다.
1.
상호 배제: 자원을 한 번에 하나의 스레드만 사용한다.
2.
점유하며 대기: 자원을 가진 채 다른 자원을 기다린다.
3.
비선점: 보유한 자원을 강제로 회수할 수 없다.
4.
환형 대기: 스레드와 자원 사이에 원형 대기 관계가 존재한다.


프로세스·스레드·동시성·동기화

17.2 교착 상태가 가능한 코드

// 스레드 1
a.lock();

// 스레드 2

스레드 1이  a , 스레드 2가  b 를 획득하면 서로 상대방의 락을 기다릴 수 있다.
17.3 std::scoped_lock 사용
CPP
#include <mutex>
struct Account {
    int balance;
    std::mutex mutex;
};
void transfer(Account& from, Account& to, int amount) {
    if (&from == &to) {
        return;
    }
    std::scoped_lock lock(from.mutex, to.mutex);
    if (from.balance >= amount) {
        from.balance -= amount;
        to.balance += amount;
    }
}
 std::scoped_lock 은 여러 mutex를 교착 상태가 발생하지 않도록 획득한다.
17.4 교착 상태 방지 원칙
•
모든 락에 전역적인 획득 순서를 정한다.
•
락을 가진 채 I/O를 실행하지 않는다.
•
락을 가진 채 외부 콜백을 호출하지 않는다.
•
임계 영역을 짧게 유지한다.
•
중첩 락을 최소화한다.
•
여러 락은  std::scoped_lock 으로 한꺼번에 획득한다.
•
필요한 경우  try_lock() 과 재시도를 사용한다.
•
타임아웃은 근본적인 방지책보다 복구 수단으로 본다.

17.6 예방과 회피의 차이
•
예방(prevention): Coffman 조건 중 하나가 성립하지 않도록 시스템 규칙을 제한한다.
•
회피(avoidance): 각 작업의 최대 자원 요구량을 알고, 할당 후에도 안전 상태가 유지될 때만 자원을 준다.
안전 상태는 모든 프로세스가 일정한 순서로 필요한 자원을 얻어 종료할 수 있는 safe sequence가 존재하는 상태다. 불안
전 상태가 즉시 교착 상태라는 뜻은 아니지만 미래의 요청에 따라 교착 상태로 진행될 수 있다.
Banker's algorithm은 다음 정보를 이용해 할당 후의 안전 상태를 검사한다.
•
시스템이 보유한 전체 자원 수
•
현재 사용 가능한 자원 수
•
프로세스별 현재 할당량
•
프로세스별 최대 요구량
•
 Need = Max - Allocation 
현실의 일반 프로그램은 최대 요구량을 미리 알기 어렵기 때문에 모든 상황에 Banker's algorithm을 사용하지는 않는다.
17.7 탐지
교착 상태를 허용한 뒤 주기적으로 탐지할 수도 있다.
•
자원 종류마다 인스턴스가 하나라면 wait-for graph의 사이클을 탐지한다.
•
인스턴스가 여러 개라면 가용량, 현재 할당량, 남은 요청량을 이용한 탐지 알고리즘이 필요하다.
•
탐지 주기가 짧으면 검사 비용이 증가하고, 길면 교착 상태가 오래 유지되며 더 많은 작업이 얽힐 수 있다.
17.8 복구
교착 상태를 탐지한 뒤 사용할 수 있는 복구 방법:
•
관련 프로세스를 모두 종료한다.
•
하나씩 종료하며 사이클이 사라지는지 검사한다.
•
일부 자원을 선점하고 피해 프로세스를 롤백한다.
희생자를 선택할 때는 우선순위, 지금까지 실행한 시간, 남은 시간, 보유 자원, 종료 비용, 다른 프로세스에 미치는 영향을
함께 고려한다. 같은 프로세스가 계속 희생되지 않도록 롤백 횟수도 비용에 포함해야 한다.

#include <thread>
using namespace std::chrono_literals;
int main() {
    std::jthread worker([](std::stop_token stop) {

20. 프로세스와 스레드 선택 기준
프로세스가 적합한 경우
•
외부 코드나 플러그인을 격리해야 한다.
•
한 작업의 충돌이 전체 프로그램을 종료시키면 안 된다.
•
서로 다른 보안 권한이 필요하다.
•
독립 서비스로 배포해야 한다.
•
서로 다른 언어나 런타임을 사용한다.
스레드가 적합한 경우
•
큰 자료 구조를 자주 공유한다.
•
통신 지연이 작아야 한다.
•
하나의 작업을 여러 CPU 코어로 병렬화한다.
•
같은 응용 프로그램의 내부 작업이다.
이벤트 기반 구조가 적합한 경우
•
연결 수가 매우 많다.
•
각 요청이 주로 I/O를 기다린다.
•
작업이 짧고 블로킹 호출을 피할 수 있다.

•
처리기에서 블로킹 시스템 콜을 실행하면 전체 이벤트 루프가 멈춘다.
•
CPU 작업이 길면 다른 모든 사건의 응답 시간이 증가한다.
•
비동기 작업 전후의 상태를 명시적으로 저장해야 한다.
•
여러 CPU 코어를 활용하려면 이벤트 루프를 여러 개 두거나 작업을 스레드 풀로 전달해야 한다.

따라서 이벤트 처리기는 짧게 유지하고, 블로킹 또는 CPU 중심 작업은 제한된 작업자 풀로 넘기며, 완료 결과는 다시 이벤
트 루프로 전달하는 구조가 일반적이다.

22. 핵심 요약
1.
프로세스는 독립된 주소 공간과 자원을 가지며 장애 격리가 좋다.
2.
스레드는 프로세스의 자원을 공유하며 실행 문맥과 스택은 따로 가진다.
3.

4.

5.
공유 데이터를 동기화하지 않고 읽고 쓰면 C++ 데이터 경쟁이 발생한다.
6.
단순 값의 원자적 변경에는  std::atomic 을 사용할 수 있다.
7.
복합 불변식 보호에는 mutex가 필요하다.
8.
상태가 바뀔 때까지 기다리려면 조건 변수를 사용한다.
9.
자원의 동시 사용 개수를 제한하려면 세마포어를 사용할 수 있다.
10.
교착 상태는 락 순서를 통일하고  std::scoped_lock 을 사용해 예방한다.
11.
회피는 안전 상태를 유지하는 할당만 허용하고, 탐지는 교착 상태를 허용한 뒤 사이클이나 자원 상태를 검사
한다.
12.
멀티코어에서는 캐시 친화성, affinity, 부하 균등화, NUMA까지 고려한다.
13.
이벤트 기반 구조도 블로킹 호출과 긴 CPU 작업을 별도 작업자에게 넘겨야 한다.

1. 동시성과 병렬성의 차이
1.1 동시성
동시성(concurrency)은 둘 이상의 작업이 같은 시간 구간 안에서 진행되는 성질이다. 작업들이 반드시 같은 순간에 실행될
필요는 없다.
단일 코어에서도 운영체제가 실행 대상을 빠르게 바꾸면 여러 작업이 함께 진행되는 것처럼 보인다.
TEXT
시간 ─────────────────────────────────────>
CPU  [작업 A][작업 B][작업 A][작업 C][작업 B]
이 경우 한 순간에는 하나의 작업만 실행되지만 A, B, C의 실행 기간은 서로 겹친다.
1.2 병렬성
병렬성(parallelism)은 둘 이상의 작업이 여러 실행 자원에서 같은 순간에 실제로 실행되는 성질이다.
TEXT
시간 ─────────────────────────────────────>
CPU 0 [──────────── 작업 A ───────────────]
CPU 1 [──────────── 작업 B ───────────────]
CPU 2 [──────────── 작업 C ───────────────]
병렬 실행에는 여러 CPU 코어, 여러 프로세서, GPU 실행 유닛 또는 분산된 컴퓨터가 필요하다.

1.4 비결정성과 interleaving
동시 작업의 실제 실행 순서는 스케줄러, 인터럽트, 코어 수와 시스템 부하에 따라 달라진다. 같은 입력으로 실행해도 명령
어가 섞이는 순서(interleaving)가 달라질 수 있다.
올바른 동시성 프로그램은 특정 스레드가 먼저 실행될 것이라고 가정하지 않고, 동기화 규칙이 허용하는 모든 실행 순서에
서 불변식을 지켜야 한다.
[!important]
동시성은 프로그램 구조에 관한 성질이고, 병렬성은 실행 시점에 실제 자원을 사용하는 방식에 가깝다.
2. 비동기와 동시성
비동기(asynchronous)는 호출자가 작업 완료를 기다리지 않고 제어권을 돌려받는 인터페이스 또는 실행 방식이다.
TEXT
요청 시작 ──> 즉시 반환 ──> 다른 작업 수행 ──> 완료 통지
비동기는 동시성과 관련 있지만 같은 개념은 아니다.
•
단일 스레드 이벤트 루프도 비동기 I/O로 동시성을 제공할 수 있다.
•
비동기 API가 내부적으로 별도 스레드를 사용할 수도 있다.
•
비동기라고 해서 반드시 여러 코어에서 병렬 실행되는 것은 아니다.
•
여러 스레드를 사용해도 호출자가 즉시 결과를 기다리면 비동기성이 거의 드러나지 않을 수 있다.
CPP
auto future = std::async(std::launch::async, calculate);
do_other_work();
auto result = future.get();
 get() 을 바로 호출하면 계산과 다른 작업을 겹칠 기회를 잃는다.
3. 동시성이 필요한 이유
3.1 응답성
오래 걸리는 작업과 사용자 입력 처리를 분리하면 작업이 진행되는 동안 UI가 멈추지 않는다.
3.2 지연 시간 숨기기
한 작업이 디스크, 네트워크 또는 외부 장치를 기다리는 동안 다른 작업을 실행한다.


프로세스·스레드·동시성·동기화
32
TEXT
작업 A: [CPU][──── I/O 대기 ────][CPU]
작업 B:       [CPU][CPU][CPU]
3.3 처리량 향상
서로 독립적인 요청을 겹쳐 처리하면 단위 시간당 더 많은 요청을 완료할 수 있다.
3.4 멀티코어 활용
CPU 중심 작업을 독립적인 부분으로 나누어 여러 코어에 배치하면 완료 시간을 줄일 수 있다.
3.5 자연스러운 문제 구조 표현
웹 서버의 연결, 게임의 여러 시스템, GUI 이벤트, 생산자와 소비자처럼 본질적으로 독립적인 활동을 별도 작업으로 표현할
 수 있다.
[!warning]
동시성 자체가 자동으로 성능을 높이지는 않는다. 작업 생성, 문맥 교환, 동기화, 캐시 미스와 통신 비용이 실제 이득보다
클 수 있다.
4. 작업을 나누는 방법
4.1 작업 병렬성
서로 다른 종류의 작업을 동시에 실행한다.
TEXT
작업 1: 네트워크 요청 수신
작업 2: 데이터 파싱
작업 3: 로그 기록
각 작업의 처리 시간과 자원 요구가 다르므로 파이프라인이나 작업 큐와 함께 사용하는 경우가 많다.
4.2 데이터 병렬성
같은 연산을 서로 다른 데이터 구간에 적용한다.
TEXT
배열: [ 0 ... 249 ][250 ... 499][500 ... 749][750 ... 999]
코어:       0             1            2            3
이미지 처리, 벡터 연산, 통계 계산처럼 요소 간 의존성이 적은 작업에 적합하다.
4.3 파이프라인 병렬성
작업을 여러 단계로 나누고 각 단계가 서로 다른 입력을 동시에 처리한다.


프로세스·스레드·동시성·동기화
33
TEXT
입력 → [읽기] → [파싱] → [계산] → [저장]
파이프라인 처리량은 가장 느린 단계에 의해 제한된다. 단계 사이에는 유한 큐를 두어 무제한 메모리 증가를 방지하고 역
압력(backpressure)을 전달해야 한다.
4.4 fork-join
큰 작업을 여러 하위 작업으로 나누어 실행한 뒤 결과를 합친다.
TEXT
                 ┌─ 작업 A ─┐
큰 작업 ─ fork ──┼─ 작업 B ─┼─ join ─> 결과
                 └─ 작업 C ─┘
분할 정복, 병렬 합계, 병렬 정렬 등에 적합하다.
4.5 데이터 분해와 기능 분해
•
데이터 분해: 데이터 영역을 여러 작업에 나눈다.
•
기능 분해: 서로 다른 기능을 별도 작업으로 나눈다.
데이터 분해는 부하 균등화가 비교적 쉽지만 경계 데이터의 의존성이 문제가 될 수 있다. 기능 분해는 구조가 자연스럽지
만 단계별 처리량 차이 때문에 병목이 생길 수 있다.
4.6 멀티코어 프로그래밍의 다섯 과제
1.
작업 식별: 서로 독립적으로 실행할 수 있는 부분을 찾아야 한다.
2.
균형: 각 작업의 실행량이 비슷해야 일부 코어만 오래 일하는 상황을 줄일 수 있다.
3.
데이터 분할: 작업이 처리할 데이터를 충돌 없이 나누어야 한다.
4.
데이터 의존성: 한 작업의 입력이 다른 작업의 출력에 의존하는지 확인해야 한다.
5.
테스트와 디버깅: 가능한 실행 순서가 많고 재현이 어려우므로 순차 프로그램과 다른 검증 전략이 필요하다.
5. 동시성 실행 모델
5.1 프로세스 기반
각 작업을 독립된 프로세스로 실행한다.
•
주소 공간이 분리되어 장애 격리가 좋다.
•
통신에는 파이프, 소켓, 공유 메모리 같은 IPC가 필요하다.
•
프로세스 생성과 전환 비용이 상대적으로 크다.
5.2 스레드 기반
하나의 프로세스 안에서 여러 스레드가 주소 공간을 공유한다.


프로세스·스레드·동시성·동기화
34
•
데이터 공유와 통신이 빠르다.
•
공유 상태 때문에 데이터 경쟁과 교착 상태 위험이 크다.
•
한 스레드의 메모리 오류가 프로세스 전체에 영향을 줄 수 있다.
5.3 작업 기반
프로그래머는 스레드보다 수행할 작업을 표현하고 런타임이 작업을 제한된 작업자에게 배치한다.
•
스레드 풀
•
fork-join 프레임워크
•
work stealing 스케줄러
•
OpenMP와 작업 그래프
작업 기반 모델은 스레드의 생성·소멸을 반복하지 않고 실행 자원의 수를 통제하기 쉽다.
5.4 이벤트 기반
이벤트 루프가 준비된 사건을 하나씩 가져와 처리한다.
TEXT
while (running) {
    events = wait_for_events();
    for (event : events) {
        process(event);
    }
}
단일 이벤트 루프는 매 순간 하나의 처리기만 실행하므로 공유 상태의 락을 줄일 수 있다. 그러나 처리기에서 블로킹 호출
이나 긴 CPU 계산을 실행하면 전체 이벤트 루프가 멈춘다.
5.5 코루틴
코루틴은 실행을 중단하고 나중에 재개할 수 있는 함수다. 비동기 흐름을 순차 코드처럼 표현하는 데 도움이 되지만 코루
틴 자체가 스레드는 아니며 병렬 실행을 자동으로 제공하지 않는다.
[!important]
실행 모델과 실행 자원을 구분해야 한다. 코루틴 수천 개가 하나의 스레드에서 동작할 수도 있고, 작업 런타임이 여러
스레드에 작업을 병렬 배치할 수도 있다.
6. 멀티코어 하드웨어에서 생기는 문제
6.1 코어와 하드웨어 스레드
물리 코어는 실제 실행 자원을 제공한다. SMT 또는 Hyper-Threading은 한 물리 코어가 여러 논리 CPU 문맥을 노출하게 한
다.
논리 CPU가 두 배라고 CPU 계산 성능이 정확히 두 배가 되는 것은 아니다. 논리 CPU들은 실행 유닛과 캐시 같은 자원을
일부 공유한다.
6.2 캐시 계층
CPU는 메인 메모리보다 훨씬 빠른 캐시를 사용한다.


프로세스·스레드·동시성·동기화
35
TEXT
레지스터 → L1 → L2 → L3 → 메인 메모리
 빠름                           느림
 작음                           큼
병렬 프로그램의 성능은 연산 수뿐 아니라 데이터가 어느 캐시에 존재하는지에 크게 영향을 받는다.
6.3 캐시 일관성
여러 코어가 같은 메모리를 캐시에 보관할 수 있으므로 하드웨어는 캐시 일관성 프로토콜로 동일한 메모리 위치의 변경을
전달한다.
캐시 일관성은 같은 메모리 위치의 값이 모순되지 않도록 돕지만 다음을 자동으로 해결하지는 않는다.
•
프로그램의 데이터 경쟁
•
여러 연산의 원자성
•
원하는 실행 순서
•
고수준 자료 구조의 불변식
6.4 캐시 일관성과 메모리 일관성
•
cache coherence는 주로 하나의 메모리 위치에 대한 여러 코어의 읽기·쓰기 값이 어떻게 일치하는지를 다룬
다.
•
memory consistency는 서로 다른 메모리 위치를 포함한 여러 연산의 관찰 순서를 다룬다.
하드웨어의 캐시 일관성 프로토콜이 있어도 다른 스레드가 모든 쓰기를 소스 코드 순서대로 관찰한다고 보장되지는 않는
다. C++ 메모리 모델의 mutex, atomic, acquire/release 같은 동기화가 필요한 이유다.
6.5 false sharing
서로 다른 스레드가 논리적으로 다른 변수만 변경하더라도 변수가 같은 캐시 라인에 있으면 캐시 라인이 코어 사이에서 계
속 이동할 수 있다.
CPP
#include <atomic>
struct alignas(64) PaddedCounter {
    std::atomic<long long> value{0};
};
PaddedCounter counters[8];
 64 는 흔한 캐시 라인 크기를 가정한 교육용 예시다. 실제 값과 효과는 하드웨어 및 데이터 배치에 따라 다르므로 반드시
 측정해야 한다.
6.6 NUMA
NUMA 시스템에서는 CPU와 가까운 메모리와 멀리 있는 메모리의 접근 비용이 다르다. 작업을 다른 NUMA 노드로 이동시
키면 데이터 접근 비용이 증가할 수 있다.

7. 작업 배치와 스케줄링
7.1 단일 작업 큐
OSTEP은 이 구조를 SQMS(Single-Queue Multiprocessor Scheduling)라고 설명한다.
모든 작업자가 하나의 큐에서 작업을 가져온다.
장점:
•
구현이 단순하다.
•
전체 부하를 균등하게 나누기 쉽다.
단점:
•
큐의 락과 캐시 라인에 경합이 집중된다.
•
작업이 여러 CPU를 이동해 캐시 친화성이 낮아질 수 있다.
7.2 작업자별 큐
OSTEP은 CPU별로 큐를 두는 구조를 MQMS(Multi-Queue Multiprocessor Scheduling)라고 설명한다.
각 작업자가 자신의 큐를 사용한다.
장점:
•
공유 큐 경합이 줄어든다.
•
작업이 같은 CPU에서 실행되어 캐시를 재사용하기 쉽다.
단점:
•
작업 분배가 잘못되면 어떤 CPU는 놀고 다른 CPU는 바빠진다.
7.3 work stealing
할 일이 없는 작업자가 다른 작업자의 큐에서 작업을 가져온다.
TEXT
Worker 0: [A][B][C][D]
Worker 1: []  ── steal ──> [D]
도둑질 빈도가 너무 높으면 큐 검사와 동기화 비용이 증가하고, 너무 낮으면 부하 불균형이 오래 유지된다.


프로세스·스레드·동시성·동기화
37
7.4 affinity와 migration
•
affinity는 작업을 이전에 실행한 CPU에 유지하여 캐시 재사용을 높인다.
•
migration은 작업을 다른 CPU로 옮겨 부하 불균형을 해소한다.
•
두 목표는 충돌할 수 있으므로 스케줄러가 캐시 친화성과 균형 사이에서 절충한다.
7.5 oversubscription
실행 가능한 CPU 중심 스레드가 논리 CPU보다 훨씬 많으면 문맥 교환과 캐시 손실이 늘어난다.
•
CPU 중심 작업: 보통 사용 가능한 코어 수 근처에서 시작해 측정한다.
•
I/O 중심 작업: 대기 시간이 길어 더 많은 동시 작업이 유리할 수 있다.
•
스레드 수는 하드웨어 수만이 아니라 작업의 CPU/I/O 비율과 외부 제한을 반영해야 한다.
8. 동시성 정확성의 세 문제
8.1 원자성
여러 연산이 다른 스레드가 끼어들 수 없는 하나의 단위처럼 실행되어야 하는 문제다.
CPP
if (balance >= amount) {
    balance -= amount;
}
검사와 변경 사이에 다른 스레드가 끼어들면 잔액 불변식이 깨질 수 있다.
8.2 순서
A가 B보다 먼저 일어나야 하지만 그 순서가 강제되지 않은 문제다.
TEXT
생산자: 데이터 작성 → 준비 완료 표시
소비자: 준비 완료 확인 → 데이터 사용
준비 표시와 데이터 가시성 사이에 올바른 동기화가 필요하다.
8.3 가시성
한 코어의 스레드가 변경한 값을 다른 코어의 스레드가 언제 관찰할 수 있는가에 관한 문제다. 컴파일러 최적화, CPU의 메
모리 순서, 캐시 때문에 소스 코드의 단순한 줄 순서만으로는 스레드 간 가시성이 보장되지 않는다.
8.4 데이터 경쟁
C++에서 다음 조건을 만족하면 데이터 경쟁(data race)이 발생한다.
•
서로 다른 스레드가 같은 메모리 위치에 접근한다.
•
접근 중 하나 이상이 쓰기다.
•
원자 연산이 아니며 happens-before로 정렬되지 않는다.

C++의 데이터 경쟁은 undefined behavior다.

9. C++ 메모리 모델
9.1 happens-before
happens-before는 한 스레드의 연산 결과가 다른 연산에 관찰 가능하도록 순서를 연결하는 관계다. 단순한 실제 시각의 선
후 관계보다 강한 의미를 가진다.
대표적인 관계:
•
스레드 생성 전의 연산은 새 스레드 시작 이후보다 앞선다.
•
스레드 내부 연산은 성공한  join()  이후보다 앞선다.
•
mutex의  unlock() 은 같은 mutex를 이후에 획득한  lock() 보다 앞선다.
•
release 저장은 그 값을 관찰한 acquire 읽기보다 앞선다.
•
barrier의 한 단계 도착 전 연산은 다음 단계 진행 이후에 관찰 가능하다.
9.2 release와 acquire
CPP
#include <atomic>
#include <cassert>
#include <string>
#include <thread>
std::string payload;
std::atomic<bool> ready{false};
void producer() {
    payload = "complete";
    ready.store(true, std::memory_order_release);
}
void consumer() {
    while (!ready.load(std::memory_order_acquire)) {
        std::this_thread::yield();
    }
    assert(payload == "complete");
}
consumer가 release 저장을 acquire로 관찰하면 그보다 앞서 수행된  payload  기록도 관찰할 수 있다.
9.3 relaxed
 memory_order_relaxed 는 해당 원자 객체의 원자성만 보장한다. 다른 메모리 위치의 변경을 함께 공개하는 순서는 제
공하지 않는다.
독립적인 통계 카운터처럼 다른 데이터와 순서 관계가 필요하지 않은 경우에 적합할 수 있다.

9.4 volatile
 volatile 은 멀티스레드 동기화 도구가 아니다. 메모리 맵 I/O나 구현이 정의한 특별한 접근에는 쓰일 수 있지만 C++ 
스레드 사이의 원자성이나 happens-before를 만들지 않는다.
[!tip]
약한 메모리 순서를 직접 사용하기 전에 mutex나 기본 순차 일관성 원자로 정확하게 구현하고 성능을 측정한다.

정성 보장은 처리량이나 캐시 지역성을 낮출 수 있다.
11. C++ 병렬 합계 예제
다음 예제는 배열을 둘로 나누어 한쪽은 비동기 작업으로, 다른 쪽은 현재 스레드에서 계산한다.


프로세스·스레드·동시성·동기화
41
CPP
#include <future>
#include <numeric>
#include <span>
long long parallel_sum(std::span<const int> values) {
    constexpr std::size_t threshold = 50'000;
    if (values.size() <= threshold) {
        return std::accumulate(values.begin(), values.end(), 0LL);
    }
    const std::size_t middle = values.size() / 2;
    auto left_values = values.first(middle);
    auto right_values = values.subspan(middle);
    auto left = std::async(
        std::launch::async,
        [left_values] {
            return parallel_sum(left_values);
        }
    );
    long long right_result = parallel_sum(right_values);
    return left.get() + right_result;
}
핵심 사항:
•
 std::launch::async 를 명시해 별도 비동기 실행을 요청한다.
•
작은 구간은 순차 실행해 작업 생성 비용을 제한한다.
•
서로 겹치지 않는 읽기 전용 구간을 사용하므로 데이터 경쟁이 없다.
•
threshold가 너무 작으면 작업이 과도하게 생성될 수 있다.
•
실제 서비스에서는 스레드 수를 제어하는 작업 풀이나 검증된 병렬 런타임이 더 적합하다.
사용 예:
CPP
#include <iostream>
#include <vector>
int main() {
    std::vector<int> values(1'000'000, 1);
    std::cout << parallel_sum(values) << '\n';
}
12. C++ 단계 병렬화 예제
 std::barrier 는 여러 스레드가 현재 단계를 모두 마친 뒤 다음 단계로 진행하게 한다.


프로세스·스레드·동시성·동기화
42
CPP
#include <barrier>
#include <cassert>
#include <thread>
#include <vector>
int main() {
    constexpr int worker_count = 4;
    std::vector<int> values(worker_count, 0);
    std::barrier phase(worker_count);
    std::vector<std::jthread> workers;
    for (int id = 0; id < worker_count; ++id) {
        workers.emplace_back([&, id] {
            values[id] = id + 1;       // 1단계
            phase.arrive_and_wait();
            values[id] *= 10;          // 2단계
            phase.arrive_and_wait();
        });
    }
    workers.clear(); // jthread를 join
    assert((values == std::vector<int>{10, 20, 30, 40}));
}
barrier는 단계 경계를 만들지만 각 단계 안에서 여러 스레드가 같은 요소를 변경하면 별도의 동기화가 필요하다.

13.1 Readers-Writers
여러 reader는 동시에 공유 데이터를 읽을 수 있지만 writer는 독점 접근해야 한다. reader 선호 정책은 writer 기아를, 
writer 선호 정책은 reader 지연을 일으킬 수 있다. 읽기가 많다고 항상  std::shared_mutex 가 더 빠른 것은 아니므로 
임계 영역 길이와 경합을 측정해야 한다.
13.2 식사하는 철학자
각 작업이 자원 하나를 보유한 채 다음 자원을 기다리면 환형 대기가 만들어진다. 자원 획득 순서를 통일하거나 필요한 자
원을 함께 획득하여 교착 상태를 예방할 수 있다.
14. 이벤트 기반 동시성
14.1 장점
•
단일 이벤트 루프에서는 처리기 사이의 공유 상태 동기화를 줄일 수 있다.
•
많은 연결마다 스레드를 하나씩 만들 필요가 없다.
•
프로그램이 어떤 사건을 언제 처리할지 비교적 직접 제어할 수 있다.
14.2 블로킹 호출 문제
하나의 처리기가 파일 I/O나 긴 계산으로 멈추면 전체 이벤트 루프가 진행하지 못한다.
해결 방법:
•
non-blocking I/O
•
asynchronous I/O
•
readiness notification
•
블로킹 작업 전용 스레드 풀
•
CPU 작업 전용 작업자 풀
명시적으로 호출한 I/O만 블로킹 원인이 되는 것은 아니다. 이벤트 처리 중 페이지 폴트가 발생하거나, 이전에는
non-blocking이던 라이브러리 함수가 구현 변경으로 블로킹 동작을 하게 되어도 이벤트 루프 전체가 지연될 수 있다.
14.3 상태 관리
스레드 기반 코드에서는 호출 스택과 지역 변수가 중단된 작업의 상태를 자연스럽게 보관한다. 이벤트 기반 코드에서는 완
료 후 이어서 실행할 상태를 별도 객체나 continuation으로 보존해야 한다.
코루틴은 이러한 상태 기계를 컴파일러가 생성하도록 도와주지만, 공유 상태와 병렬 실행의 동기화 문제를 없애지는 않는
다.
14.4 멀티코어 이벤트 루프
여러 코어를 사용하려고 이벤트 루프를 여러 개 실행하면 처리기들이 동시에 공유 상태에 접근할 수 있으므로 다시 동기화
가 필요하다.

15. 확장성과 Amdahl의 법칙
프로그램의 일부만 병렬화할 수 있다면 코어 수를 늘려도 최대 성능 향상에는 한계가 있다.
병렬화 가능한 비율을 $P$, 실행 자원 수를 $N$이라고 하면 이상적인 최대 속도 향상은 다음과 같다.
프로그램의 90%를 병렬화하고 8개 실행 자원을 사용한다면:
코어는 8개지만 최대 속도 향상은 약 4.71배다. 실제로는 작업 생성, 통신, 동기화와 캐시 비용 때문에 더 낮다.
15.1 작업량과 임계 경로
•
work: 모든 연산을 순차 실행했을 때의 총 작업량
•
span: 의존성 때문에 반드시 순서대로 실행해야 하는 가장 긴 경로
이론적인 병렬성은 대략  work / span 으로 볼 수 있다. 코어를 늘려도 임계 경로보다 빠르게 완료할 수는 없다.

15.2 강한 확장과 약한 확장
•

16. 병렬 성능을 방해하는 요소
16.1 너무 작은 작업
작업 시간이 생성과 스케줄링 비용보다 짧으면 병렬화가 더 느릴 수 있다. 관련 연산을 묶어 적절한 grain size를 만든다.
16.2 락 경합
모든 작업자가 하나의 전역 락을 자주 획득하면 실질적으로 직렬 실행된다.
개선 방향:
•
임계 영역 축소
•
읽기 전용 데이터 사용
•
데이터 분할
•
지역 결과를 계산한 후 마지막에 병합
•
버킷별 또는 샤드별 락
16.3 부하 불균형
가장 늦게 끝나는 작업이 전체 완료 시간을 결정한다.
•
작업을 더 작은 단위로 나눈다.
•
동적 스케줄링이나 work stealing을 사용한다.
•
입력 데이터에 따른 비용 차이를 측정한다.
16.4 메모리 대역폭
모든 코어가 메모리에서 많은 데이터를 읽으면 연산 장치보다 메모리 대역폭이 먼저 포화될 수 있다. 이런 작업은 코어를
늘려도 성능이 거의 증가하지 않는다.
16.5 캐시와 false sharing
데이터 지역성이 나쁘거나 쓰기 캐시 라인이 계속 이동하면 코어 수 증가가 오히려 성능을 낮출 수 있다.
16.6 순차 병목
직렬 초기화, 최종 병합, 전역 로그, 단일 큐, 단일 파일 출력이 병렬 부분의 이득을 제한할 수 있다.

8.

9.

1.2 Critical section
critical section은 공유 불변식을 읽거나 변경하여 동시에 실행되면 안 되는 구간이다. 중요한 점은 mutex가 코드 줄을 보
호하는 것이 아니라 데이터와 불변식을 보호한다는 것이다.
TEXT
mutex M이 보호하는 상태
┌────────────────────────────────────┐
│ queue, size, closed, 통계 카운터     │
│ 불변식: size == queue.size()         │
│ 불변식: closed면 새 push를 받지 않음 │
└────────────────────────────────────┘
같은 상태를 어떤 경로에서는 mutex 없이 접근하거나 서로 다른 mutex로 보호하면 계약이 깨진다.
2. Mutex의 의미
mutex는 mutual exclusion의 줄임말이다. 한 스레드가 소유한 동안 다른 스레드의 획득을 막는다.


프로세스·스레드·동시성·동기화

    std::lock_guard lock{mutex};
    ++counter;
}
2.1 세 가지 핵심 속성
•
상호 배제: 임계 영역에는 한 번에 한 스레드만 진입한다.
•
소유권: mutex를 성공적으로 lock한 스레드가 unlock해야 한다.
•
동기화: 한 스레드의 unlock은 같은 mutex를 나중에 성공적으로 lock한 스레드와 happens-before 관계를 만
든다.
마지막 속성 때문에 mutex는 단순한 “입장권”이 아니다. 임계 영역의 쓰기가 다음 소유자에게 올바르게 보이도록 메모리
가시성과 순서도 제공한다.

7. 왜 while 인가
7.1 Mesa semantics
현대의 일반적인 condition variable은 notification을 받은 스레드가 즉시 실행되고 상태를 독점한다고 보장하지 않는다.
TEXT
Producer: 상태 변경 → notify Consumer A
Consumer A: ready queue에서 대기
Consumer B: 먼저 mutex 획득 → 상태 소비
Consumer A: 나중에 mutex 획득 → 조건이 다시 거짓일 수 있음
notification은 “조건이 참이다”라는 증명서가 아니라 상태가 변했을 가능성이 있다는 힌트다. OSTEP은 이를 Mesa 
semantics로 설명한다.
7.2 Spurious wakeup
스레드는 대응하는 notification이 없어도  wait 에서 깨어날 수 있다. 표준 API가 허용하는 현상이므로 이유를 추측하지 
말고 predicate를 재검사한다.
CPP
// 잘못된 패턴

    changed.wait(lock);
}
use_ready_state(); // 깨어난 뒤 ready가 거짓일 수 있음
CPP
// 올바른 패턴
changed.wait(lock, [&] { return ready; });
use_ready_state();

8. Lost Wakeup
condition variable의 가장 중요한 함정은 notification을 상태처럼 사용하는 것이다.
8.1 상태 없이 알림만 보내는 오류
CPP

// 나중에 시작한 waiter

changed.wait(lock); // 영원히 기다릴 수 있음
알림 이전에 waiter가 없으면 notification은 축적되지 않는다. 그래서 “일이 끝났다”, “큐에 항목이 있다”, “종료했다” 같은
사실을 공유 상태에 기록해야 한다.
8.2 검사와 sleep 사이의 경쟁
다음과 같이 조건 검사와 대기를 mutex 없이 분리하면 lost wakeup이 생길 수 있다.
조건 검사, wait의 atomic unlock-and-sleep, 상태 변경을 같은 mutex 프로토콜 안에 넣어야 한다.
8.3 Condition variable has no memory
기억을 갖는 것은 predicate 상태다.

9.1 notify_one

•

•

9.3 알림은 lock 안에서 해야 하는가
공유 상태 변경은 반드시 mutex 아래에서 수행한다. notification은 상황에 따라 lock 안이나 밖에서 호출할 수 있다.

    std::lock_guard lock{mutex};
    queue.push(value);
}
not_empty.notify_one();

아니라 다음 계약에 의존한다.
•
predicate 상태는 같은 mutex로 보호한다.
•
waiter는 mutex를 잡고 predicate를 검사한다.
•
waiter는 predicate 기반 wait를 사용한다.
수명 관리나 특수한 프로토콜 때문에 lock 안에서 notify해야 하는 설계도 가능하다. 코드 전체의 불변식을 기준으로 판단

11. 종료 가능한 Bounded Queue
생산자-소비자 예제에서 종료를 정확히 표현하려면 알림 횟수나 처리 개수를 추측하지 말고  closed  상태를 둔다.


프로세스·스레드·동시성·동기화
62
CPP · 1/2
#include <condition_variable>
#include <cstddef>
#include <deque>
#include <mutex>
#include <optional>
#include <stdexcept>
#include <type_traits>
#include <utility>
template <class T>
class BoundedQueue {
    static_assert(std::is_nothrow_move_constructible_v<T>,
                  "T must be nothrow move constructible");
public:
    explicit BoundedQueue(std::size_t capacity) : capacity_{capacity} {
        if (capacity == 0) {
            throw std::invalid_argument{"capacity must be positive"};
        }
    }
    BoundedQueue(const BoundedQueue&) = delete;
    BoundedQueue& operator=(const BoundedQueue&) = delete;
    bool push(T value) {
        std::unique_lock lock{mutex_};
        not_full_.wait(lock, [&] {
            return closed_ || queue_.size() < capacity_;
        });
        if (closed_) {
            return false;
        }
        queue_.push_back(std::move(value));
        lock.unlock();
        not_empty_.notify_one();
        return true;
    }
    std::optional<T> pop() {
        std::unique_lock lock{mutex_};
        not_empty_.wait(lock, [&] {
            return closed_ || !queue_.empty();
        });


프로세스·스레드·동시성·동기화
63
CPP · 2/2
        if (queue_.empty()) {
            return std::nullopt; // closed이며 남은 항목도 없음
        }
        T value = std::move(queue_.front());
        queue_.pop_front();
        lock.unlock();
        not_full_.notify_one();
        return value;
    }
    void close() {
        {
            std::lock_guard lock{mutex_};
            closed_ = true;
        }
        not_empty_.notify_all();
        not_full_.notify_all();
    }
private:
    const std::size_t capacity_;
    std::mutex mutex_;
    std::condition_variable not_empty_;
    std::condition_variable not_full_;
    std::deque<T> queue_;
    bool closed_ = false;
};

하나의 condition variable로도 구현할 수 있지만, 소비자가 다른 소비자만 깨우거나 생산자가 다른 생산자만 깨우는 불필
요한 wakeup이 늘 수 있다. OSTEP의 bounded-buffer 분석처럼 서로 다른 predicate 집합을 분리하면 의도가 명확하다.
11.3 왜 close() 는 둘 다 notify_all 하는가
종료는 빈 큐를 기다리는 모든 소비자와 가득 찬 큐를 기다리는 모든 생산자의 predicate를 바꾼다. 모두 깨어나  
closed_ 를 확인해야 한다.

11.4 왜 느린 작업은 lock 밖에서 하는가
 pop() 은 항목을 지역 변수로 이동하고 mutex를 푼 뒤 실제 처리를 맡긴다. I/O나 큰 계산을 임계 영역 안에서 하면 다
른 생산자와 소비자가 모두 막힌다.
예제는 항목 이동 중 예외가 나서 queue 앞 원소가 부분적으로 변경되는 상황을 피하도록  T 의 이동 생성자가  
noexcept 일 것을 요구한다. 범용 라이브러리라면 복사 가능성, allocator, 예외 보장까지 타입 정책으로 설계해야 한다.
12. Bounded Queue 사용 예
CPP
#include <atomic>
#include <cassert>
#include <thread>
#include <vector>
int main() {
    BoundedQueue<int> queue{8};
    std::atomic<long long> sum{0};
    std::thread producer{[&] {
        for (int value = 1; value <= 1'000; ++value) {
            bool accepted = queue.push(value);
            assert(accepted);
        }
        queue.close();
    }};
    std::vector<std::thread> consumers;
    for (int i = 0; i < 4; ++i) {
        consumers.emplace_back([&] {
            while (auto value = queue.pop()) {
                sum.fetch_add(*value, std::memory_order_relaxed);
            }
        });
    }
    producer.join();
    for (auto& consumer : consumers) {
        consumer.join();
    }
    assert(sum.load() == 500'500);
}
queue의 내부 정확성은 mutex와 condition variable이 담당한다. 합계는 여러 소비자가 동시에 갱신하는 단일 값이므로
atomic을 사용했다. 복합 불변식과 대기 조건은 mutex가, 단순 누적 연산은 atomic이 담당하는 예다.

13. 시간 제한 대기
13.1 Predicate가 있는 wait_for
CPP
using namespace std::chrono_literals;
std::unique_lock lock{mutex};
if (!condition.wait_for(lock, 500ms, [&] { return ready; })) {
    // 500ms 안에 ready가 참이 되지 않음
    return Timeout{};
}
predicate overload는 spurious wakeup이 있어도 남은 시간을 관리하며 조건을 재검사한다.
13.2 직접 반복한다면 absolute deadline
상대 시간  wait_for(500ms) 를 루프마다 처음부터 다시 적용하면 spurious wakeup마다 전체 대기 시간이 늘어날 수 
있다. 복잡한 반복 제어가 필요하면 한 번 계산한 deadline과  wait_until 을 사용한다.
CPP
auto deadline = std::chrono::steady_clock::now() + 500ms;
while (!ready) {
    if (condition.wait_until(lock, deadline) == std::cv_status::timeout) {
        if (!ready) {
            return Timeout{};
        }
    }
}
경과 시간 제한에는 시스템 시각 조정의 영향을 피하기 위해  steady_clock 을 우선한다.
14. Memory Ordering과 가시성
다음 패턴에서 consumer가  ready == true 를 보고도 오래된  data 를 읽는지 걱정할 수 있다.
CPP
// producer
{
    std::lock_guard lock{mutex};
    data = make_data();
    ready = true;
}
condition.notify_one();
// consumer
std::unique_lock lock{mutex};
condition.wait(lock, [&] { return ready; });
use(data);
동일한 mutex의 unlock과 뒤이은 lock이 synchronization을 형성하므로 producer의 임계 영역 쓰기는 consumer에게 보인
다. notification 자체가 데이터를 publish하는 것이 아니라 공유 mutex 프로토콜이 가시성을 제공한다.

•

17. 흔한 잘못된 패턴
17.1 if 로 wait
CPP
if (queue.empty()) {
    condition.wait(lock);
}
Mesa semantics, 다른 consumer의 선점, spurious wakeup 때문에 틀릴 수 있다. predicate 기반 wait를 쓴다.
17.2 공유 상태 없이 notification만 사용
notification은 저장되지 않는다. 완료 여부나 queue 상태를 별도 predicate로 둔다.
17.3 predicate를 mutex 밖에서 읽음
CPP
while (!stopped) { // stopped가 같은 mutex나 atomic으로 보호되지 않으면 data race
    std::unique_lock lock{mutex};
    condition.wait(lock);
}
predicate 읽기와 쓰기를 같은 mutex 계약에 넣는다.
17.4 서로 다른 mutex로 같은 상태 보호
producer는 M1, consumer는 M2로 같은 queue를 보호하면 상호 배제가 성립하지 않는다. 상태마다 담당 mutex를 문서화
한다.
17.5 lock을 가진 채 느린 작업
네트워크, 파일 I/O, 큰 계산, logging callback을 임계 영역 밖으로 옮긴다. 필요한 값을 지역 객체로 복사/이동한 뒤 unlock
한다.
17.6 수동 unlock 누락
RAII wrapper를 사용한다.  unique_lock::unlock() 이 필요해도 객체 소멸 시 남은 소유권은 안전하게 해제된다.
17.7 notify_all 로 논리 버그 숨기기
 notify_one 에서는 멈추고  notify_all 에서만 동작한다면 waiter 종류와 predicate 설계를 다시 본다. 여러 조건을 
하나의 CV에 섞었는지, 상태 변경이 누락됐는지 확인한다.
17.8 객체를 파괴하는 동안 waiter가 남아 있음
mutex와 condition variable은 사용하는 모든 스레드보다 오래 살아야 한다. 소유 객체를 파괴하기 전에 종료 상태 설정,  
notify_all , 스레드 join을 완료한다. 자세한 객체 수명 원칙은 00.메모리·객체 수명·RAII를 참고한다.

22. 자주 나오는 질문
Q1. mutex가 있으면 condition variable은 왜 필요한가?
mutex는 현재 접근할 권리를 조정하지만 “조건이 나중에 참이 될 때까지 CPU를 양보하며 기다리기”를 직접 표현하지 않는
다. condition variable은 mutex로 보호된 상태 변화를 효율적으로 기다리게 한다.
Q2. notify_one() 을 먼저 호출하고 나중에 wait해도 되는가?
notification 자체는 보관되지 않는다. 하지만 상태를 먼저 변경했다면 나중 waiter가 predicate를 확인하고 기다리지 않으
므로 문제없다. 그래서 상태가 기억을 담당한다.
Q3. 깨운 스레드는 즉시 실행되는가?
아니다. ready 상태가 될 뿐이며 scheduler와 mutex 경쟁을 거쳐 나중에 실행될 수 있다. 그 사이 predicate가 바뀔 수 있어
 재검사가 필요하다.
Q4. notify할 때 mutex를 꼭 잡아야 하는가?
공유 상태 변경은 mutex 아래에서 해야 한다. notify 자체는 올바른 프로토콜에서는 unlock 뒤에 할 수 있다. 단순 규칙보다
 상태·수명·predicate의 전체 계약이 중요하다.
Q5. volatile 로 ready를 선언하면 되는가?
아니다. C++의  volatile 은 스레드 간 원자성이나 happens-before를 제공하지 않는다. mutex 또는 적절한 atomic을 
사용한다.
Q6. recursive_mutex 가 deadlock을 해결하는가?
같은 스레드의 자기 재획득만 허용할 뿐 스레드 사이 lock cycle은 해결하지 않는다. 오히려 불분명한 재진입 구조를 숨길
수 있다.
Q7. condition variable이 FIFO로 깨우는가?
표준적으로 그런 공정성을 기대할 수 없다. 특정 순서가 정확성 요구라면 별도의 queue와 sequence 상태를 설계한다.
Q8. atomic이면 mutex보다 항상 빠른가?
아니다. atomic도 cache line 경쟁을 만들며 복합 불변식을 표현하기 어렵다. 올바른 추상화를 선택하고 실제 workload로
측정한다.

23. 최종 압축 정리
1.
mutex는 공유 상태와 불변식에 대한 상호 배제와 메모리 가시성을 제공한다.
2.
C++의 data race는 단순히 결과가 틀리는 문제가 아니라 undefined behavior다.
3.
mutex 소유권은  lock_guard ,  unique_lock ,  scoped_lock 으로 RAII화한다.
4.
condition variable은 조건을 저장하지 않으며 waiter를 재검사 시점까지 재운다.
5.
실제 기억은 mutex로 보호되는 predicate 상태가 담당한다.
6.
wait는 대기 등록과 mutex unlock을 원자적으로 연결하고, 반환 전에 mutex를 재획득한다.
7.
Mesa semantics와 spurious wakeup 때문에 predicate는 항상 반복해서 검사한다.
8.
 wait(lock, predicate) 를 기본 패턴으로 사용한다.
9.
notification은 축적되지 않으므로 상태 없는 notify는 lost wakeup을 만들 수 있다.
10.
항목 하나에는 보통  notify_one , 종료처럼 전체 predicate가 바뀌면  notify_all 을 쓴다.
11.
bounded queue는  not_empty ,  not_full ,  closed  상태로 설계하면 종료까지 명확해진다.
12.
lock을 가진 채 느린 작업이나 알 수 없는 callback을 실행하지 않는다.
13.
여러 mutex는  scoped_lock  또는 일관된 순서로 획득한다.
14.
정확성을 먼저 확보하고 경합, hold time, wakeup 수를 측정해 최적화한다.
[!tip] 실전 기본형
공유 상태를 mutex 아래에서 바꾸고, condition.wait(lock, predicate) 로 기다리며, 상태 변경 후 필요한 범위만
notify_one/all 한다. 알림이 아니라 predicate가 진실의 원천이다.
