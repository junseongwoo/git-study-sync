메모리·객체 수명·RAII: C++와 운영체제를 함께 보는 법
[!summary] 한 문장 정리
운영체제는 프로세스에 가상 주소 공간과 페이지를 제공하고, C++는 그 저장 공간 위에서 객체의 수명과 자원 소유권을
관리한다. 안전한 C++의 핵심은 주소를 직접 관리하는 것이 아니라 소유권을 타입으로 표현하고 RAII 객체의 수명에
자원의 수명을 결합하는 것이다.
관련 노트: 01.프로세스와 스레드 · 02.동시성과 병렬성 · OS 공부

•
가상 주소 공간, 스택, 힙, 저장 기간, 객체 수명, 소유권을 서로 구분한다.
•
 new 가 곧바로 운영체제의 페이지 할당을 뜻하지 않는 이유를 설명한다.
•
포인터와 참조가 객체를 소유하는지 단지 관찰하는지를 API에 드러낸다.

저장 공간이 있다고 객체가 살아 있는 것은 아니다. 반대로 객체의 수명이 끝난 직후에도 그 주소의 바이트는 할당자나 스

CPP

// 이 시점부터 int 객체의 수명이 시작됨

// 저장 공간은 남아 있지만 int 객체의 수명은 끝남

원소인지 알 수 없다. 그래서 현대 C++에서는 타입과 API로 소유권을 표현한다.
2. 프로세스 주소 공간과 가상 메모리
2.1 가상 주소 공간
사용자 프로그램이 다루는 주소는 일반적으로 가상 주소다. 운영체제와 MMU는 각 프로세스가 크고 연속적이며 사적인 주
소 공간을 가진 것처럼 보이게 한다. 실제 물리 메모리의 프레임은 흩어져 있어도 된다.

2.2 가상 메모리가 제공하는 것
•
격리: 한 프로세스가 다른 프로세스의 주소 공간을 임의로 읽고 쓰지 못하게 한다.
•
보호: 페이지마다 읽기, 쓰기, 실행 권한을 둔다.
•
재배치의 투명성: 프로그램의 가상 주소와 물리 주소를 분리한다.
•
희소한 주소 공간: 사용하지 않는 구간까지 물리 RAM을 미리 제공할 필요가 없다.
•
공유: 같은 실행 파일 코드나 공유 라이브러리 페이지를 여러 프로세스가 공유할 수 있다.
•
요구 페이징: 실제 접근할 때 페이지를 준비할 수 있다.
•
copy-on-write(COW): 처음에는 같은 물리 페이지를 읽기 전용으로 공유하고, 쓰기가 생길 때 복사한다.
2.3 주소 변환과 페이지 폴트
가상 주소는 보통  가상 페이지 번호(VPN) + 페이지 내부 오프셋 으로 나뉜다. 페이지 테이블은 VPN을 물리 프레임 
번호(PFN)와 권한 정보에 대응시킨다. TLB는 최근 주소 변환을 캐시한다.
TEXT
C++ 포인터의 가상 주소
        │
        ▼
   TLB에서 변환 검색 ── hit ──> 물리 주소로 접근
        │ miss
        ▼
   페이지 테이블 확인
        ├─ 유효 + present  ──> TLB 갱신 후 재시도
        ├─ 유효 + not present -> page fault, OS가 페이지 준비
        └─ 무효/권한 위반 ────> fault, 보통 프로세스 종료
페이지 폴트가 언제나 버그인 것은 아니다. 요구 페이징이나 COW 때문에 발생한 합법적인 폴트는 OS가 처리하고 명령을 
재실행한다. 반면 매핑되지 않은 주소나 쓰기 금지 페이지를 접근하면 보통 접근 위반 또는 segmentation fault로 이어진다.

2.4 예약, 커밋, 실제 상주 메모리
“1 GiB를 할당했다”는 말은 다음을 구분해야 한다.
•
가상 주소 범위를 예약했는가?
•
OS가 그 범위에 backing store를 약속했는가?
•
실제 페이지를 처음 접근했는가?
•
현재 물리 RAM에 상주하는가?
운영체제 정책에 따라 큰 가상 영역을 얻어도 실제 물리 페이지는 첫 접근 때 준비될 수 있다. 따라서 주소 공간 크기, 커밋
 크기, RSS(상주 집합 크기)는 같은 값이 아니다.
2.5 C++ 할당에서 물리 메모리까지
TEXT
new T
  → T를 위한 operator new 호출
  → C++ 런타임/힙 할당자가 free list 또는 arena에서 블록 검색
  → 부족하면 OS에 더 큰 가상 메모리 영역 요청
  → T의 생성자 실행
  → 최초 페이지 접근 시 필요하면 page fault
  → OS가 물리 프레임 연결 및 페이지 테이블 갱신
역방향도 단순하지 않다.
TEXT
delete p
  → T의 소멸자 실행
  → operator delete가 블록을 할당자에 반환
  → 할당자는 재사용을 위해 보관할 수 있음
  → OS에 즉시 페이지를 돌려준다는 보장은 없음
따라서  delete  뒤 작업 관리자에서 RSS가 바로 감소하지 않아도 누수라고 단정할 수 없다. 반대로 RSS가 안정적이어도
 객체나 자원의 논리적 누수가 없다고 단정할 수 없다.
2.6 OS의 copy-on-write와 C++ 복사는 다른 개념
운영체제의 COW는 가상 메모리 최적화다. 예를 들어  fork  직후 부모와 자식의 가상 페이지를 같은 물리 프레임에 읽기
 전용으로 연결하고, 어느 한쪽이 쓸 때 page fault를 발생시켜 그 페이지를 복사할 수 있다.
이때 C++ 객체별 복사 생성자는 호출되지 않는다. 반대로  Widget b = a; 가 실행되어 C++ 복사 생성자가 호출돼도 
OS가 반드시 COW page fault를 일으키는 것은 아니다.

3. Stack과 Heap
3.1 스택
호출 스택은 함수 호출의 실행 문맥을 저장한다. ABI에 따라 반환 주소, 보존 레지스터, 인자, 지역 변수, 정렬용 패딩 등이
스택 프레임에 놓일 수 있다. 최적화된 변수는 레지스터에만 있을 수도 있으므로 “지역 변수는 반드시 물리적인 스택에 있
다”는 표현은 지나치게 단순하다.
CPP
int square(int x) {
    int result = x * x; // 자동 저장 기간. 실제 배치는 최적화와 ABI에 좌우됨
    return result;
} // result의 수명 종료
특징:
•
각 스레드는 독립적인 호출 스택을 가진다.
•
함수 진입과 복귀에 맞춰 저장 공간을 효율적으로 재사용한다.
•
자동 저장 기간 객체는 블록을 벗어날 때 역순으로 파괴된다.
•
무한 재귀나 지나치게 큰 지역 배열은 stack overflow를 일으킬 수 있다.
•
운영체제는 스택 끝에 guard page를 두어 초과 접근을 감지할 수 있다.
3.2 힙과 자유 저장소
일상적으로 C++의 동적 할당 영역을 힙이라고 부른다. 엄밀하게 C++ 표준의 free store와 운영체제/할당자 구현의 heap
은 완전히 같은 표준 용어가 아니다. 실무에서는  new 가 사용하는 동적 저장 공간을 힙이라고 설명해도 되지만, 구현 세
부와 언어 규칙을 구분해야 한다.
CPP
auto p = std::make_unique<int>(42); // 동적 저장 기간 객체
// p는 자동 저장 기간을 갖는 소유 핸들
// int 객체는 p가 소유하는 동적 객체
힙 할당자는 요청마다 시스템 콜을 하지 않는다. 큰 영역을 OS에서 얻어 작은 블록으로 나누고, 반환된 블록을 free list나
size class에 보관해 재사용한다. 이 과정에서 내부/외부 단편화와 메타데이터 비용이 발생할 수 있다.

[!important] 흔한 오해
스택 객체가 무조건 빠르고 힙 객체가 무조건 느린 것은 아니다. 성능은 할당 횟수, 캐시 지역성, 객체 크기, 할당자, 스레드
경쟁, 페이지 폴트에 좌우된다. 우선 수명과 소유권에 맞는 설계를 하고 측정으로 최적화한다.
3.4 스택에 둘지 힙에 둘지
•
작고 수명이 현재 범위에 한정되면 값 또는 지역 객체가 자연스럽다.
•
선택적 값은 먼저  std::optional<T> 를 고려한다.
•
가변 길이 연속 데이터는  std::vector<T> , 문자열은  std::string 을 고려한다.
•
동적 다형성과 단독 소유권이 필요하면  std::unique_ptr<Base> 가 자연스럽다.
•
객체가 매우 크거나 주소 안정성이 필요하거나 범위를 넘어 소유권을 이전해야 하면 동적 저장이 유용하다.
•
단지 “복사를 피하려고” 모든 객체를 힙에 두지 않는다. 이동과 copy elision이 있다.

4.7 이미 확보한 저장 공간에 객체 만들기
allocator, arena, 컨테이너 구현에서는 저장 공간 확보와 객체 생성을 분리한다. C++20에서는  std::construct_at 과 
 std::destroy_at 이 의도를 잘 드러낸다.
CPP
void* raw = ::operator new(sizeof(Widget), std::align_val_t{alignof(Widget)});
Widget* widget = nullptr;
static_assert(std::is_nothrow_destructible_v<Widget>);
try {
    widget = std::construct_at(static_cast<Widget*>(raw));
    use(*widget);
    std::destroy_at(widget); // 객체 수명 종료
    widget = nullptr;
    ::operator delete(raw, std::align_val_t{alignof(Widget)}); // 저장 공간 반환
} catch (...) {
    if (widget != nullptr) {
        std::destroy_at(widget);
    }
    ::operator delete(raw, std::align_val_t{alignof(Widget)});
    throw;
}
위 코드는 두 계층을 보여 주기 위한 저수준 예시다. 실전에서는 생성 성공 여부까지 소유하는 RAII 래퍼 또는
allocator-aware 컨테이너를 사용한다. 핵심은 다음 두 동작이 별개라는 점이다.
•
 destroy_at : 객체의 수명을 끝내지만 저장 공간은 남긴다.
•
 operator delete : 저장 공간을 반환하지만 그 전에 살아 있는 비자명 객체를 알아서 파괴하지 않는다.
같은 저장 공간을 다른 타입이나 새 객체에 재사용하면 이전 객체를 가리키던 포인터를 무조건 새 객체 접근에 사용할 수 
있는 것은 아니다. 투명하게 교체 가능한 조건과  std::launder 가 필요한 경우가 있으므로, 이 수준의 코드는 표준 컨
테이너·allocator 구현처럼 제한된 경계 안에 둔다.

6. RAII
RAII(Resource Acquisition Is Initialization)는 자원을 획득한 성공적인 객체의 수명과 자원의 유효 기간을 결합하는 C++ 설
계 원칙이다.
1.
생성자 또는 팩터리가 자원을 획득한다.
2.
객체가 유효한 동안 불변식을 유지한다.
3.
소멸자가 자원을 정확히 한 번 반환한다.
4.
복사와 이동 정책이 소유권 의미를 따른다.
자원은 메모리만 뜻하지 않는다. 파일, 소켓, 뮤텍스 잠금, 데이터베이스 트랜잭션, GPU 버퍼, 스레드 조인 책임도 포함한다.
6.1 예외와 조기 반환에 강한 이유
CPP
void update(Account& account) {
    std::lock_guard lock{account.mutex()};
    // 이 아래에서 return하거나 예외가 발생해도 lock의 소멸자가 unlock
    account.apply_interest();
}
명시적  lock() / unlock()  사이에 여러 반환 경로가 있으면 해제를 빠뜨리기 쉽다. RAII 객체는 스택 되감기(stack 
unwinding) 과정에서 파괴되므로 각 경로에 정리 코드를 복제하지 않는다.
6.2 파일 RAII

6.3 소멸자 원칙
•
소멸자는 일반적으로 예외를 밖으로 던지면 안 된다.
•
이미 stack unwinding 중인데 소멸자가 다시 예외를 던지면  std::terminate 로 이어질 수 있다.
•
실패 가능한 “마무리/커밋”은 명시적 멤버 함수로 제공하고, 소멸자는 최소한의 무실패 정리만 수행한다.
•
소멸자는 소유한 멤버의 소멸을 중복 구현하지 않는다. RAII 멤버가 알아서 정리한다.
6.4 RAII와 운영체제의 프로세스 정리는 다르다
프로세스가 정상적으로 범위를 빠져나가면 C++ 소멸자가 결정적인 정리를 한다. 그러나 강제 종료, 전원 차단,  
std::abort , 일부 비정상 종료에서는 모든 자동/정적 객체의 소멸자가 실행된다고 기대할 수 없다.
OS는 프로세스 종료 시 주소 공간의 페이지와 커널 핸들을 회수할 수 있지만, 다음과 같은 프로그램 의미의 정리를 대신하
지 못한다.
•
파일 형식의 footer 기록
•
데이터베이스 commit/rollback 프로토콜
•
다른 프로세스에 보내야 할 종료 메시지
•
공유 메모리 안의 논리 상태 복구
•
원격 서버의 세션 종료
즉 RAII는 정상적인 C++ 제어 흐름에서 강력하지만, 크래시 일관성은 별도의 프로토콜 문제다.

8.2 이동
이동은 원본의 자원을 새 객체로 이전해 비싼 복사를 피할 기회를 준다.
CPP
std::vector<int> source{1, 2, 3};
std::vector<int> target = std::move(source);
 std::move 는 실제 이동 작업을 하지 않는다. 인자를 우측값으로 취급할 수 있게 캐스팅할 뿐이다. 그 뒤 선택된 이동 
생성자/대입 연산자가 자원을 이전한다.
이동된 표준 라이브러리 객체는 보통 유효하지만 값은 미지정(valid but unspecified) 상태다. 소멸하거나 새 값을 대입할 
수 있지만, 비어 있다고 가정하지 않는다. 특정 타입이 더 강한 사후 조건을 문서화하면 그 계약을 따른다.
8.3 이동 연산과 noexcept
 vector 가 재할당할 때 기존 원소를 새 저장 공간으로 옮겨야 한다. 이동 생성자가 예외를 던질 수 있으면 강한 예외 보
장을 지키기 위해 복사를 선택할 수 있다. 자원 핸들의 이동이 실제로 실패하지 않는다면  noexcept 로 선언하는 것이 중
요하다.
CPP
Handle(Handle&&) noexcept = default;
Handle& operator=(Handle&&) noexcept = default;
8.4 copy elision과 반환
현대 C++에서는 지역 객체를 값으로 반환하는 것이 자연스럽다.
CPP
std::vector<int> make_data() {
    std::vector<int> result(1'000);
    return result; // NRVO 가능. 불필요한 std::move를 쓰지 않음
}
 return std::move(result); 는 오히려 NRVO를 방해할 수 있다. 소유 객체는 값으로 반환하고 컴파일러의 copy 
elision과 이동을 활용한다.
8.5 Rule of Zero, Three, Five
•

•
Rule of Three: 소멸자, 복사 생성자, 복사 대입 중 하나를 직접 정의해야 한다면 나머지도 검토한다.
•
Rule of Five: C++11 이후에는 이동 생성자와 이동 대입까지 함께 검토한다.

9.1 얕은 복사가 위험한 경우

class BadBuffer {
    std::size_t size_;

    explicit BadBuffer(std::size_t n)
        : size_{n}, data_{new int[n]{}} {}

CPP

두 객체가 같은 배열을 자신이 소유한다고 믿는다. 하나가 파괴되면 다른 하나는 dangling pointer를 가지며, 나머지가 파
괴될 때 double free가 된다.
9.2 깊은 복사 구현
교육 목적으로  unique_ptr<T[]> 를 사용해 독립 복사 의미를 구현하면 다음과 같다.


C++ 메모리·객체 수명·설계
16
CPP
#include <algorithm>
#include <cstddef>
#include <memory>
#include <stdexcept>
#include <utility>
class Buffer {
    std::size_t size_{};
    std::unique_ptr<int[]> data_;
public:
    explicit Buffer(std::size_t size)
        : size_{size}, data_{std::make_unique<int[]>(size)} {}
    Buffer(const Buffer& other) : Buffer(other.size_) {
        std::copy_n(other.data_.get(), size_, data_.get());
    }
    Buffer& operator=(const Buffer& other) {
        if (this != &other) {
            Buffer copy{other};
            swap(copy); // copy-and-swap: 성공한 뒤에만 상태 교체
        }
        return *this;
    }
    Buffer(Buffer&&) noexcept = default;
    Buffer& operator=(Buffer&&) noexcept = default;
    ~Buffer() = default;
    void swap(Buffer& other) noexcept {
        std::swap(size_, other.size_);
        data_.swap(other.data_);
    }
    int& at(std::size_t index) {
        if (index >= size_) {
            throw std::out_of_range{"Buffer::at"};
        }
        return data_[index];
    }
};
실무에서는 특별한 요구가 없다면 이 구현보다  std::vector<int> 를 멤버로 둔 Rule of Zero 버전이 단순하고 안전하
다.
9.3 얕은 복사가 항상 잘못은 아니다

10.1 Memory Leak

        throw std::length_error{"allocation size overflow"};

11. Memory Alignment
11.1 정렬이 필요한 이유
타입은 주소가 특정 배수에 놓이기를 요구할 수 있다. CPU가 정렬된 접근을 더 효율적으로 처리하거나, 어떤 명령은 잘못
정렬된 접근에서 fault를 발생시킬 수 있다. C++ 객체 모델에서도 요구 정렬을 만족하지 않는 저장 공간에 객체를 잘못 놓
고 접근하면 undefined behavior다.
CPP
#include <cstddef>
struct Example {
    char tag;   // 1 byte
    int value;  // 보통 더 강한 정렬 필요
};
static_assert(alignof(Example) >= alignof(int));
컴파일러는  tag 와  value  사이 및 객체 끝에 padding을 넣을 수 있다. 끝 padding은  Example[]  배열의 각 원소
가 올바르게 정렬되도록 한다. 그래서 멤버 크기의 합과  sizeof(Example) 이 다를 수 있다.
11.2 alignof 와 alignas
CPP
struct alignas(64) CacheLineData {
    std::atomic<std::uint64_t> value{0};
};
static_assert(alignof(CacheLineData) >= 64);
 alignas 는 최소 정렬 요구를 지정한다. 캐시 라인 정렬은 false sharing 완화에 사용할 수 있지만, 실제 하드웨어의 간섭
 크기는  std::hardware_destructive_interference_size  지원 여부와 측정으로 확인해야 한다. 자세한 병렬성 
맥락은 02.동시성과 병렬성을 참고한다.
11.3 동적 할당과 과도 정렬
일반  new 는 할당 대상 타입에 필요한 정렬을 만족한다. 과도 정렬(over-aligned) 타입은 정렬 인자를 받는  operator 
new  경로가 사용될 수 있다. 직접 바이트 버퍼나 사용자 정의 allocator를 만들 때는 크기뿐 아니라 정렬과 객체 수명 시작
 규칙까지 책임져야 한다.
CPP
struct alignas(64) Packet { std::byte data[64]; };
auto packet = std::make_unique<Packet>(); // Packet의 정렬 요구를 만족
직렬화된 바이트에서  reinterpret_cast<T*> 로 바로 읽는 것은 정렬, 객체 수명, aliasing 문제를 동시에 만들 수 있다.
 바이트 표현을  std::memcpy 로 적절한  T  객체에 복사하는 방법을 우선 검토한다.

12. Undefined Behavior
Undefined behavior(UB)는 표준이 그 상황의 동작을 규정하지 않는다는 뜻이다. “예외가 발생한다”나 “항상 크래시한다”는
뜻이 아니다. 컴파일러는 올바른 프로그램에는 UB가 없다고 가정하고 최적화할 수 있으므로, 디버그 빌드에서 우연히 보
인 결과를 신뢰할 수 없다.
대표적인 메모리 관련 UB:
•
배열이나 객체 범위를 벗어난 접근
•
수명이 끝난 객체를 통한 접근, UAF
•
같은 할당의 double delete/free
•
널 포인터 역참조
•
잘못 정렬된 포인터를 통한 객체 접근
•
초기화되지 않은 값의 부적절한 읽기
•
 new[]/delete ,  malloc/delete  같은 불일치
•
유효하지 않은 downcast 또는 잘못된 타입으로 객체 접근
•
signed integer overflow
•
동기화 없는 data race
12.1 OS fault와 UB는 같은 개념이 아니다
•
UB는 C++ 언어 의미의 문제다.
•
page fault/access violation/segmentation fault는 하드웨어·OS가 관찰한 사건이다.
UB가 OS fault로 나타날 수 있지만 반드시 그렇지는 않다. 버퍼를 한 칸 넘겨 썼는데 그 주소가 같은 쓰기 가능 페이지 안
이라면 OS는 막지 못한다. 언어적으로는 이미 UB다. 반대로 합법적인 요구 페이징 page fault는 UB가 아니다.
12.2 “메모리에 값이 아직 남아 있다”는 변명이 안 되는 이유
객체 수명이 끝나도 비트가 즉시 지워지지 않을 수 있다. 그러나 C++ 추상 기계에서 그 객체는 더 이상 존재하지 않는다.
할당자는 언제든 같은 바이트를 다른 용도로 쓸 수 있고 컴파일러도 수명 규칙을 기반으로 최적화한다. 물리적 잔존과 언
어적 유효성은 다르다.

13.1 std::unique_ptr : 기본 선택

CPP
auto first = std::make_unique<Widget>();
auto second = std::move(first);
// first는 이제 소유하지 않음. second가 유일한 소유자
장점:

•
비용 모델이 raw pointer와 가깝다.
•
소유자가 명확하다.
•
범위를 벗어날 때 정확히 한 번 삭제한다.

배열에는  unique_ptr<T[]> 가 있지만 크기·반복·복사 의미가 필요하면  vector<T> 가 대개 더 좋다.
13.2 std::shared_ptr : 공동 소유가 실제 요구일 때
 shared_ptr  복사본들은 control block을 공유한다. control block에는 강한 참조 수, 약한 참조 수, deleter 등의 정보가 
있다. 마지막 강한 소유자가 사라지면 객체가 파괴된다.
CPP
auto a = std::make_shared<Widget>();
auto b = a; // 같은 객체와 control block 공동 소유
주의:
•
reference count 갱신 비용과 control block 메모리 비용이 있다.
•
참조 수 조작이 스레드 안전하다는 것과  Widget  객체의 멤버 접근이 스레드 안전하다는 것은 별개다.
•
수명 종료 시점이 분산되어 결정성이 약해질 수 있다.
•
소유권 문제를 설계하지 않고  shared_ptr 로 덮으면 순환 참조와 장기 보유가 생긴다.
13.3 하나의 객체에 control block을 두 개 만들지 않는다
CPP
Widget* raw = new Widget;
std::shared_ptr<Widget> a{raw};
// std::shared_ptr<Widget> b{raw}; // 서로 다른 control block: 마지막에 double delete
처음부터  make_shared 를 사용하고 그  shared_ptr 를 복사한다.
CPP
auto a = std::make_shared<Widget>();
auto b = a;
객체가 자기 자신의  shared_ptr 를 얻어야 한다면  std::enable_shared_from_this<T> 와  
shared_from_this() 를 사용한다.  shared_ptr<T>(this) 를 새로 만들면 안 된다. 또한 해당 객체가 이미  
shared_ptr 에 의해 관리되고 있다는 전제도 지켜야 한다.
13.4 make_shared 의 장점과 트레이드오프
 make_shared<T> 는 일반적으로 객체와 control block을 한 번의 할당으로 묶어 지역성과 예외 안전성을 개선한다. 다만
 약한 참조가 오래 남으면 객체는 이미 파괴되었더라도 결합된 할당 블록 전체의 반환이 늦어질 수 있다. 매우 큰 객체에서
 이것이 중요하면 별도 할당을 검토할 수 있다.

13.5 std::weak_ptr : 순환을 끊는 관찰자

두  Person 이 서로를  shared_ptr 로 가리키면 외부 소유자가 사라져도 참조 수가 0이 되지 않는다. 한쪽 또는 양쪽의
 비소유 관계를  weak_ptr 로 표현한다.

struct Person {
    std::string name;
    std::weak_ptr<Person> partner; // 관찰만 함

            std::cout << p->name;

};

확인하는 방식이 안전하다.

15. 성능과 메모리 지역성
안전한 소유권은 성능과 대립하지 않는다. 오히려 값과 컨테이너 중심 설계는 연속 배치와 명확한 수명 때문에 최적화하기
 쉽다.
15.1 vector 와 포인터 그래프
 vector<T> 는 원소를 연속 저장해 캐시 지역성과 prefetch에 유리하다. 각 원소를 개별  new 로 만들고 포인터로 연결
하면 할당 비용, 단편화, cache miss가 늘 수 있다.
15.2 재할당과 무효화
CPP
std::vector<int> values;
values.push_back(1);
int* p = &values[0];
values.push_back(2); // capacity가 부족하면 재할당 가능
// p는 재할당이 있었다면 dangling
필요 크기를 알면  reserve 로 재할당 횟수를 줄일 수 있지만, reserve 뒤에도 그 capacity를 넘으면 무효화된다. 포인터
를 장기 보관하지 않는 설계가 우선이다.
15.3 allocator, pool, arena
많은 작은 객체를 일정한 단계에서 한꺼번에 버린다면 pool/arena가 유용할 수 있다. C++의  std::pmr 은 메모리 자원 
정책을 컨테이너와 분리한다. 하지만 arena가 객체 소멸자의 의미를 없애는 것은 아니다. 비메모리 자원이나 비자명한 소
멸이 있다면 올바른 파괴 순서를 보장해야 한다.
15.4 working set과 thrashing
프로그램의 활성 페이지 집합이 물리 메모리에 맞지 않으면 page fault와 교체가 반복되어 성능이 급락할 수 있다. 이를
thrashing이라고 한다. 메모리 사용량만 줄이는 것뿐 아니라 접근 패턴과 지역성 개선이 중요하다.

17.1 요청 메시지를 안전하게 처리하기
CPP
#include <cstddef>
#include <span>
#include <stdexcept>
#include <vector>
class Message {
    std::vector<std::byte> payload_; // 값 소유, Rule of Zero
public:
    explicit Message(std::span<const std::byte> input)
        : payload_{input.begin(), input.end()} {
        if (payload_.size() > 1'048'576) {
            throw std::length_error{"message too large"};
        }
    }
    std::span<const std::byte> payload() const noexcept {
        return payload_;
    }
};
void inspect(const Message& message) {
    for (std::byte b : message.payload()) {
        (void)b;
    }
}
이 설계에서:

•

•
길이가 함께 전달되므로 raw pointer만 전달하는 것보다 범위 계약이 분명하다.
•
소멸, 복사, 이동은  vector 에 맡겨 Rule of Zero를 지킨다.

17.3 비동기 작업의 수명
CPP
class Worker : public std::enable_shared_from_this<Worker> {
public:
    void start(Executor& executor) {
        auto self = shared_from_this();
        executor.post([self] {
            self->do_work();
        });
    }
private:
    void do_work();
};
비동기 callback이 실행될 때까지 객체가 반드시 살아 있어야 한다면 작업이  shared_ptr 를 캡처해 수명을 연장할 수 
있다. 반대로 작업 때문에 객체가 무한히 살아 있으면 안 된다면  weak_ptr 를 캡처하고 실행 시  lock() 한다. 어느 쪽
이 맞는지는 “작업이 객체를 소유하는가?”라는 설계 질문으로 결정한다.
18. 자주 나오는 질문
Q1. 지역 객체는 항상 스택에 있는가?
언어적으로는 automatic storage duration이라고 말하는 것이 정확하다. 최적화에 따라 레지스터에만 있거나 객체 자체가
제거될 수 있다. 관념적 호출 스택과 실제 기계 배치를 구분한다.
Q2. new 는 시스템 콜인가?
보통 아니다.  new  표현식은 저장 공간을 얻는  operator new 와 객체 생성으로 구성된다. 런타임 할당자는 이미 확보
한 블록을 반환할 수 있고, 부족할 때만 OS API를 통해 더 큰 영역을 요청한다.


C++ 메모리·객체 수명·설계
28
Q3. delete 하면 물리 메모리가 바로 줄어드는가?
보장되지 않는다. 블록이 할당자에 반환되어 같은 프로세스의 다음 할당에 재사용될 수 있다. 큰 매핑이나 할당자 정책에
따라 OS로 일부 반환될 수 있다.
Q4. 프로세스가 끝나면 OS가 다 회수하는데 누수를 왜 신경 쓰는가?
장기 실행 프로세스는 종료 전 메모리가 고갈될 수 있다. 또한 소멸자는 메모리 외 자원의 의미 있는 정리를 수행한다. 테스
트 가능성, 조기 해제, 라이브러리 재사용, 종료 절차의 정확성도 중요하다.
Q5. shared_ptr 면 dangling pointer가 사라지는가?
아니다. 그  shared_ptr 가 공동 소유하는 객체의 수명만 관리한다. 객체 내부의 raw pointer, 뷰, 외부 자원은 여전히 
dangling이 될 수 있다.  get() 으로 얻은 포인터를 소유자보다 오래 보관해도 위험하다.
Q6. nullptr 로 만들면 UAF가 해결되는가?
한 변수의 실수는 줄일 수 있지만 같은 객체를 가리키는 다른 alias는 그대로다. 소유권을 하나로 만들고 비소유 접근 범위
를 짧게 하는 것이 해결책이다.
Q7. 참조는 포인터보다 무조건 안전한가?
참조는 필수 대상과 재바인딩 불가라는 의도를 더 잘 표현하지만 수명은 늘리지 않는다. dangling reference도 UB를 만든
다.
Q8. OS가 buffer overflow를 막아 주지 않는가?
페이지 권한 경계를 넘으면 막을 수 있지만 같은 유효 페이지 안에서 인접 객체를 덮는 것은 알지 못한다. C++ 범위 규칙,
안전한 타입, sanitizer가 필요하다.

20. 최종 압축 정리
1.
포인터 값은 가상 주소이며 소유권 정보가 아니다.
2.
스택/힙은 저장 공간 관점이고 객체 수명은 C++ 언어 규칙이다.
3.
저장 공간이 남아 있어도 객체의 수명이 끝났다면 접근할 수 없다.
4.
 new 는 객체 생성까지,  delete 는 객체 소멸 후 저장 공간 반환까지 수행한다.
5.
할당자는 OS와 프로그램 사이에서 블록을 캐시하므로  delete 와 RSS 감소는 일대일이 아니다.
6.
RAII는 자원 수명을 객체 수명에 결합해 정상 반환, 조기 반환, 예외에서 같은 정리 규칙을 적용한다.
7.
값과 표준 컨테이너를 우선하고 동적 다형성에는  unique_ptr 를 기본으로 쓴다.
8.
 shared_ptr 는 실제 공동 소유에만 쓰고 순환은  weak_ptr 로 끊는다.
9.
복사는 의미를 복제하고 이동은 자원을 이전한다.  std::move  자체는 이동하지 않는다.
10.
얕은 복사가 단독 소유 raw pointer를 복제하면 double free와 UAF가 된다.
11.
buffer overflow와 UAF는 OS가 항상 감지하지 못하는 C++ UB다.
12.
정렬, 범위, 객체 수명, aliasing 규칙은 최적화 빌드에서도 지켜야 하는 언어 계약이다.
13.
컴파일 성공은 충분하지 않다. 경고, 테스트, sanitizer, 장기 관찰로 검증한다.
[!tip] 가장 실용적인 기본 규칙
직접 new / delete 를 쓰지 말고 값, 표준 컨테이너, unique_ptr , 범위 뷰를 조합하라. raw pointer와 reference는
짧은 비소유 관찰자로 사용하고, 소유권과 수명 계약을 함수 서명에서 읽을 수 있게 만들어라.

4. 힙 할당기의 빈 공간 관리
4.1 malloc 은 시스템 콜 자체가 아니다
OSTEP은  malloc() 과  free() 를 사용자 수준 라이브러리 함수로 설명한다. 할당 라이브러리는 프로세스 가상 주소 
공간의 일부를 관리하고, 더 큰 영역이 필요할 때 운영체제의 지원을 받는다.
C++의  new  표현식도 단순히 “OS에서 페이지 하나를 받는다”는 뜻으로 해석하면 안 된다. 00번의 C++ 할당에서 물리 
메모리까지와 연결해 다음처럼 기억한다.
반환된 저장 공간은 먼저 할당기의 빈 공간으로 돌아갈 수 있다. 이 사실과 객체 수명 종료는 별개의 사건이다.
4.2 할당기의 header
 free(void* ptr) 는 크기를 별도 인자로 받지 않는다. OSTEP의 할당기 설명에서는 할당된 청크 앞의 header에 크기 
같은 정보를 저장하여, 반환 시 해당 영역의 크기를 알아내는 방식을 보여 준다.

4.3 Splitting
빈 청크가 요청 크기보다 크다면 할당기는 청크를 둘로 나눌 수 있다.
TEXT
할당 전: [             빈 청크 30             ]
요청 12: [ 사용 12 ][          빈 청크 18       ]
요청을 만족한 앞부분은 호출자에게 주고, 나머지는 빈 공간 자료 구조에 남긴다. 이것이 splitting이다.
4.4 Coalescing
서로 인접한 빈 청크를 그대로 따로 두면 큰 요청을 만족하지 못할 수 있다.
TEXT

병합 후: [             빈 30             ]
전체 빈 공간이 30이어도 10짜리 청크 세 개로만 인식하면 20짜리 연속 요청은 실패한다. 반환된 청크의 이웃이 비어 있을
 때 하나로 합치는 것이 coalescing이다.

5. 가상 주소 접근의 실제 경로
5.1 TLB hit
CPU가 가상 주소를 만들면 하드웨어는 가상 페이지 번호(VPN)에 해당하는 변환 정보가 TLB에 있는지 먼저 확인한다.
TEXT
가상 주소
  ↓ VPN 추출
TLB 조회 -- hit --> 물리 프레임 번호(PFN)
                         ↓
                     실제 메모리 접근
TLB hit이면 페이지 테이블을 추가로 읽지 않고 물리 주소를 얻을 수 있다. OCS는 이 적중률이 실질 메모리 접근 시간에 직
접 영향을 준다는 계산 예를 제시한다.
5.2 TLB miss
TLB에 변환 정보가 없으면 페이지 테이블에서 PTE를 확인해야 한다.
TEXT
TLB miss
  ↓
페이지 테이블에서 PTE 조회
  ↓
PTE가 유효하고 페이지가 메모리에 존재
  ↓
PFN을 TLB에 적재
  ↓
명령 재실행
TLB miss는 곧바로 “잘못된 포인터”를 뜻하지 않는다. 필요한 주소 변환 정보가 TLB에 없어서 페이지 테이블을 추가로 확인
해야 한다는 뜻이다.

5.3 Present bit와 page fault
PTE의 present bit는 해당 페이지가 현재 물리 메모리에 존재하는지를 표현한다.
•
present bit가 설정되어 있으면 PTE에서 PFN을 얻어 접근을 계속할 수 있다.
•
페이지가 유효하지만 현재 물리 메모리에 없다면 운영체제의 page-fault handler가 필요한 처리를 한다.
•
요구 페이징에서는 필요한 페이지가 처음 접근될 때 메모리에 적재될 수 있다.
따라서 page fault는 언제나 C++ 버그를 뜻하지 않는다. 요구 페이징에서 아직 적재되지 않은 유효한 페이지를 처음 접근
할 때도 발생할 수 있다.
반대로 C++의 dangling pointer나 out-of-bounds 접근이 항상 page fault로 발견되는 것도 아니다. 잘못된 접근 주소가 우
연히 매핑된 페이지 안에 있으면 하드웨어 주소 변환은 성공할 수 있다. C++ 객체 수명과 범위 규칙은 OS의 페이지 존재
검사보다 더 세밀한 규칙이다.

6.1 unique_ptr : move 는 소유권 이전
PDF의  unique_ptr  설명은 복사를 금지하고 이동으로 유일한 소유권을 이전한다.

CPP
#include <memory>
#include <utility>
struct Resource {
    int id;
};
void consume(std::unique_ptr<Resource> resource) {
    // resource가 이 범위에서 소유권을 가짐
}
int main() {
    auto owner = std::make_unique<Resource>(Resource{7});
    consume(std::move(owner));
    // owner는 더 이상 객체를 소유하지 않음
}
함수가  unique_ptr<T> 를 값으로 받으면 호출자가 소유권을 넘긴다는 사실이 형식에 드러난다.
6.2 unique_ptr::get() : 소유권 없는 일시 접근
PDF는  get() 을 통해 실제 객체 주소를 얻어 일반 포인터 인자에 전달하는 예를 보여 준다.
CPP
#include <memory>
struct Resource {
    int id;
};
int inspect(const Resource* resource) {
    return resource == nullptr ? -1 : resource->id;
}
int main() {
    auto owner = std::make_unique<Resource>(Resource{7});
    const Resource* borrowed = owner.get();
    return inspect(borrowed) == 7 ? 0 : 1;
}
 borrowed 는 객체를 삭제하지 않으며 수명을 늘리지도 않는다.  owner 가 객체를 계속 소유하는 동안만 사용할 수 있
다.
[!warning] get() 의 결과를 오래 보관하지 않는다
get() 은 소유권을 복제하지 않는다. 소유 unique_ptr 가 파괴되거나 이동되면 이전에 얻은 raw pointer를 계속 사용할
수 없다.
6.3 shared_ptr : 객체가 아니라 control block을 함께 공유
 shared_ptr  복사본은 같은 대상과 control block을 공유한다. control block의 강한 참조 수가 마지막 소유자를 판단한
다.


C++ 메모리·객체 수명·설계
37
CPP
#include <memory>
struct Resource {
    int id;
};
int main() {
    auto first = std::make_shared<Resource>(Resource{7});
    auto second = first; // 같은 control block을 공유
    return first->id == second->id ? 0 : 1;
}
PDF는  make_shared<T> 가 객체와 control block을 한 번의 동적 할당으로 함께 만드는 방식을 설명한다.
6.4 같은 raw pointer로 별도 shared_ptr 를 만들면 안 되는 이유
다음 두  shared_ptr 는 같은 주소를 받았지만 서로의 존재를 모르는 별도 control block을 만든다.
CPP
Resource* raw = new Resource{7};
std::shared_ptr<Resource> first{raw};
// std::shared_ptr<Resource> second{raw}; // 별도 control block: 금지
각 control block은 자신이 마지막 소유자라고 판단할 수 있으므로 같은 객체를 두 번 삭제하는 문제가 발생한다. 최초 소
유  shared_ptr 를 만든 뒤에는 그  shared_ptr 를 복사해야 한다.
CPP
auto first = std::make_shared<Resource>(Resource{7});
auto second = first; // 올바른 control block 공유
6.5 weak_ptr : 확인과 사용을 lock() 한 번으로 묶기
 weak_ptr 는 강한 참조 수를 늘리지 않는다. 대상에 접근하려면  lock() 으로 임시  shared_ptr 를 얻는다.
CPP
#include <memory>
struct Resource {
    int id;
};
int read_if_alive(const std::weak_ptr<Resource>& observer) {
    if (auto owner = observer.lock()) {
        return owner->id; // 이 블록 동안 owner가 수명을 유지
    }
    return -1;
}

 lock() 이 빈  shared_ptr 를 반환하면 대상은 이미 소멸된 상태다. 성공했다면 반환된  shared_ptr 가 사용 중 수
명을 유지한다.
6.6 소유 그래프에서 shared_ptr 와 weak_ptr
부모가 자식을 소유하고 자식은 부모를 관찰하는 트리는 다음처럼 표현할 수 있다.
CPP
#include <memory>
#include <vector>
struct Node {
    std::vector<std::shared_ptr<Node>> children;
    std::weak_ptr<Node> parent;
};
int main() {
    auto parent = std::make_shared<Node>();
    auto child = std::make_shared<Node>();
    parent->children.push_back(child); // 부모가 자식을 공동 소유
    child->parent = parent;            // 자식은 부모를 관찰
    if (auto p = child->parent.lock()) {
        return p->children.size() == 1 ? 0 : 1;
    }
    return 1;
}
자식의  parent 까지  shared_ptr 로 만들면 부모와 자식이 서로 강하게 소유하는 순환이 될 수 있다. PDF는 이 순환
에서 참조 수가 0이 되지 않아 객체가 소멸되지 않는 문제와 이를  weak_ptr 로 끊는 방법을 설명한다.

    return owned->id;

9. 보완된 오해 정리
“힙의 남은 용량 합계가 요청 크기보다 크면 할당된다”
항상 그렇지 않다. 외부 단편화 때문에 필요한 연속 빈 청크가 없을 수 있다.
“ delete 하면 그 페이지가 즉시 물리 메모리에서 사라진다”
 delete 는 C++ 객체 파괴와 저장 공간 반환의 의미를 가진다. 반환된 청크를 할당기가 다시 보유할 수 있고, OS의 페이
지 상주 상태는 별도 계층에서 관리된다.
“page fault는 잘못된 포인터의 증거다”
항상 그렇지 않다. 요구 페이징에서는 유효하지만 아직 물리 메모리에 없는 페이지를 접근해도 page fault가 발생한다.
“segmentation fault가 없으면 포인터는 유효하다”
그렇지 않다. C++ 객체 수명이나 배열 범위를 위반해도 접근 주소가 매핑된 페이지 안이면 하드웨어 예외가 즉시 발생하
지 않을 수 있다.
“ weak_ptr 가 대상을 안전하게 계속 살려 둔다”
아니다.  weak_ptr 는 강한 참조 수를 늘리지 않는다.  lock() 이 성공해 반환한  shared_ptr 만 해당 작업 동안 수
명을 유지한다.
“같은 raw pointer로 만든 shared_ptr 들은 자동으로 서로를 안다”
아니다. 별도로 생성하면 서로 다른 control block을 가질 수 있다. 기존  shared_ptr 를 복사해야 같은 소유권 그룹에 참
여한다.

2. 객체지향과 인터페이스
2.1 객체지향의 목적
객체는 단순히 데이터와 함수를 한 클래스에 넣은 것이 아니다. 좋은 객체는 다음을 함께 가진다.
•
책임: 이 객체가 해야 하는 일
•
상태: 책임을 수행하는 데 필요한 데이터
•
불변식: public 함수 전후에 항상 만족해야 하는 조건
•
소유권: 어떤 자원의 수명을 책임지는가
예를 들어 bounded queue의 불변식은 다음처럼 표현할 수 있다.
클래스의 public API는 이 불변식을 깨뜨릴 수 있는 내부 상태를 직접 노출하지 않아야 한다.
2.2 상속은 is-a, 구성은 has-a
C++ PDF는 상속을 is-a 관계, 멤버 포함을 has-a 관계로 설명한다.
•
 Manager is an Employee : 대체 가능성이 성립하면 public 상속 후보
•
 Car has an Engine : 기능을 소유하거나 사용한다면 구성 후보
코드 재사용만을 위해 상속하면 기반 클래스의 내부 변화와 파생 클래스가 강하게 결합된다. 실행기, 카메라, 저장소 같은
협력 객체는 대개 has-a 구성과 의존성 주입이 적합하다.

3. 예외 처리
3.1 예외는 정상 결과와 다른 실패 경로다
C++ PDF는  throw  뒤 가장 가까운 호환  catch 까지 제어가 이동하고, 그 사이 stack 객체의 destructor가 호출되는 
stack unwinding을 설명한다.
예외는 다음 상황에 잘 맞는다.
•
현재 함수가 정상 결과를 만들 수 없음
•
호출자가 더 높은 수준에서 복구 정책을 결정해야 함
•
생성자가 유효한 객체를 만들 수 없음
다음은 예외보다 명시적 결과가 더 적합할 수 있다.
•
파일 끝, 검색 결과 없음처럼 예상되는 분기
•
매우 빈번하게 발생하는 정상적인 재시도 상태
•
ABI나 언어 경계를 넘는 C callback
•
실시간 경로에서 예외 사용이 프로젝트 정책상 금지된 경우
3.2 예외와 오류 코드를 섞지 않는다
한 추상화 계층 안에서는 실패 표현을 일관되게 정한다.
CPP
Frame read_frame();                       // 실패 시 예외
std::optional<Frame> try_read_frame();    // 없음이 정상 상태
std::expected<Frame, ReadError> read();   // C++23: 오류를 값으로 표현
함수 이름과 반환형만 보고도 계약을 이해할 수 있어야 한다.

3.5 destructor와 예외
destructor는 원칙적으로 예외를 밖으로 내보내지 않아야 한다. stack unwinding 도중 destructor가 다시 예외를 던지면 프

CPP
class FileLog {
public:
    ~FileLog() noexcept {
        try {
            flush_if_needed();
        } catch (...) {
            // destructor에서는 기록 가능한 최소 수단을 사용하고 삼킨다.
        }
    }
};
중요한 저장 실패를 destructor에서 처음 발견하도록 설계하지 말고, 호출자가 결과를 확인할 수 있는 명시적  flush()

실패가 드물고 여러 호출 계층을 건너 정책 지점까지 전달되어야 하면 예외가 편리하다.
•
실패가 정상적인 분기이고 호출자가 즉시 처리해야 하면  expected /오류 값이 명시적이다.
•
C callback·SDK 경계를 넘기 전에는 예외를 catch해 상태 코드로 변환한다.
•
어느 방식을 택하든 RAII로 자원 안전을 유지한다.
10.3 virtual interface의 성능이 걱정될 때
먼저 실제 측정으로 병목인지 확인한다. 이미지 처리처럼 큰 연산을 한 번 호출하는 경계에서는 가상 호출 한 번보다
buffer 복사·cache miss·알고리즘 비용이 훨씬 클 수 있다. 작은 함수가 매우 빈번한 hot loop라면 template 정책이나 값 타
입을 검토한다.

11.4 destructor에서 join 없는 std::thread
joinable thread의 destructor는 프로그램 종료를 일으킬 수 있다. thread 소유 객체는 stop/join 정책을 가져야 한다.

CPP

느린 CI나 scheduler 상황에 따라 실패한다. inline executor, latch, future, condition variable처럼 완료를 의미하는 동기화
수단을 사용한다.
11.6 mutex를 잡고 callback 호출
callback 구현을 알 수 없으므로 재진입 deadlock과 장시간 lock 점유가 생긴다. 내부 상태를 확정한 뒤 lock을 풀고
callback을 호출한다.
11.7 shared_ptr 로 모든 수명 문제를 덮음
소유자가 불명확해지고 순환 참조와 예측하기 어려운 파괴 thread가 생긴다. 기본은 단일 소유이며 observer에는 
reference나  weak_ptr 를 사용한다.

13. 핵심 결론
1.
객체지향의 핵심은 클래스 수가 아니라 책임·불변식·소유권의 경계다.
2.
interface는 구현 교체보다 먼저 계약과 의존 방향을 명확하게 만든다.
3.
예외 안전성은  catch 의 개수가 아니라 stack unwinding 중에도 자원이 정리되는 RAII에서 시작한다.
4.
메모리뿐 아니라 thread, file, socket, SDK frame도 소유 자원이다.
5.
비동기 코드는 요청 상태, callback 수명, 취소 완료, 오류 전달을 명시해야 한다.
6.
멀티스레드의 핵심은 thread 생성이 아니라 공유 상태와 종료 protocol이다.
7.
executor와 외부 adapter를 분리하면 업무 규칙을 thread·장비 없이 테스트할 수 있다.
8.
단위 테스트와 실제 thread component test는 목적이 다르므로 분리한다.
