성을 효율적으로 처리할 수 있는 기법도 제공한다. 그러나 이러한 가상 메모리는 구현하
기 어렵고, 만약 잘못 A卜&하게 된다면 성능이 현저히 저하될 수 있다. 가상 메모리에 대

10.1 배경 Background
9징에서 살펴본 메모리 관리 일고리즘들은 현재 실행되고 있는 코드는 반드시 물리 메
모리에 존재해야 한다는 기본적인 요구 조건을 만족히는 데 필요하였다. 이 요구 조건
을 가장 쉽게 만족시카는 방법은 전체 프로세스를 메모리에 올리는 것이다. 동적 적재
(dynamic loadmg) 방법을 시용하면 전체 프로세스를 메모리에 올려야 한다는 제약을
어느 정도 완화하는 데는 도움이 되지만, 이 방법은 일반적으로 프로그래머에게 특별한
주의와 추가적인 작업을 요구한다.
실행 중인 코드는 반드시 물리 메모리에 있어야 한다는 것은 일견 필요하고 타당한
요구 조건으로 보이지만, 프로그램의 크기를 물리 메모리의 크기로 제한한다는 점 때문
에 환영할만한 요구 조건은 아니다. 시실 실제 프로그램들을 살펴보면 많은 경우에 프로
그램 전체가 한꺼번에 메모리에 늘 올라와 있어야 하는 것은 아니라는 사실을 쉽게 발견
할 수 있다. 예를 들면, 다음과 같은 점들을 생각해보자.
• 프로그램에는 잘 발생하지 않는 오류 상황을 처리하는 코드가 종종 존재한다. 이러
한 오류들은 실질적으로 거의 발생하지 않으므로, 이 코드(code)들은 거의 실행되
지 않는다.
• 배열(arrays), 리스트(lists), 테이*(table) 등은 필요 이상으로 많은 공간을 점유하
는 수가 있다. 가령 배열이 실제로는 거의 10 x 10 정도만 시용되는데도 100 x 100
으로 선언될 수 있다.
• 프로그램 내의 어떤 옵션(optlon)이나 기능 들은 거의 시용되지 않는다. 예를 들면,
미국 정부 컴퓨터의 예산 관련 루틴들은 가끔가다 한 번씩 시용될 뿐이다. 또한, 전
체 프로그램이 필요한 경우에도 그 프로그램의 모든 부분이 모두 동시에 요구되지
않을 수 있다.
만일 프로그램을 일부분만 메모리에 올려놓고 실행할 수 있다면 다음과 같은 많은 이점
이 있다.
• 프로그램은 물리 메모리 크기에 의해 더는 제약받지 않게 된다. 사용자들은 매우 큰
가상 주소 공간을 가정하고 프로그램을 만들 수 있으므로, 프로그래밍 작업이 간단
해진다.
• 각 프로그램이 더 작은 메모리를 자지하므로 더 많은 프로그램을 동시에 수행할 수
있게 된다. 이에 따라 응답 시간(response time, turn around time)은 늘어나지
않으면서도 CPU 이용률(utilization)과 처리율(throughput)이 높아진다.
• 프로그램을 메모리에 올리고 스#(swap)히는 데 필요한 I/O 회수가 줄어들기 때문
에 프로그램들이 보다 빨리 실행된다.

10.2 요구 페이징 Demand Paging
어떻게 실행 프로그램을 보조저장장지에서 메모리로 적재할 수 있을지 생각해 보자. 한
가지 방법은 프로그램 실행 시작 시 프로그램의 전부를 물리 메모리에 적재하는 것이다.
그러나 이 방법의 문제는 초기에는 프로그램의 전체가 메모리에 있을 필요는 없을지도
모른다는 점이다. 시작 시에 사용자가 여러 옵션 중에서 원하는 것을 선택하게 되어 있
는 프로그램을 생각해 보자. 전체 프로그램을 적재하게 되면 실제 A卜&자가 선택하느나
의 여부와는 상관없이 모든 옵션에 대한 코드를 적재하는 것이 된다.
다른 전략은 필요한 페이지만 적재하는 것이다. 이 기법을 요구 페이징(demand
paging)이라고 하며 가상 메모리 시스템에서 일반적으로 사용된다. 요구 페이징 가상
메모리를 시용하면 프로그램 실행 중 필요할 때만 페이지가 적재된다. 따라서 접근되지
않은 페이지는 물리 메모리로 적재되지 않는다. 요구 페이징 시스템은 프로세스가 보조
메모리(일반적으로 HDD 또는 NVM 장치)에 상주하는 스와핑(9.5.2절)을 사용하는 페
이정 시스템과 유사하다. 요구 페이징은 가상 메모리의 주요 이점 중 하나를 설명한다.
필요한 프로그램의 일부만 적재하여 메모리가 더 효율적으로 사용된다.

와 OPT 알고리즘의 결정적인 차이는 (시간상으로 과거와 미래를 본다는 것을 제외하고)

방법은 우선순위가 낮은 프로세스를 희생시켜서 우선순위가 높은 프로세스가 더 많은
프레임을 할당받을 수 있게 해준다. 반면에 지역 교체 방법에서는 프로세스에 할당된 프
레임의 수는 변하지 않는다. 전역 교체하에서는 한 프로세스에 할당된 프레임의 수는 바
뀔 수 있다. 전역 교체 방법에서는 프로세스가 매번 다른 프로세스의 프레임을 할당받게

프로세스에 “충분한” 프레임이 없는 경우, 즉 작업 집합의 페이지를 지원하는 데 필요한

적으로 바로바로 반복해서 페이지 폴트가 발생하며 교체된 페이지는 다시 얼마 지나지
않아 읽어올 필요가 생긴다.
이러한 과도한 페이징 작업을 스래å(thrashlng)이라고 부른다. 어떤 프로세스가
실제 실행보다 더 많은 시간을 페이징에 사용하고 있으면 스래싱이 발생했다고 한다. 예
상대뢰 스래싱은 심각한 성능 문제를 야기한다.
10.6.1 스래싱의 원인 cause of Thrashing
초기의 페이징 시스템에서 실제로 있었던 다음 경우를 보자. 운영체제는 CPU의 이펑뤁
(utilizaåon)을 감시한다. 만약에 CPU 이펑뤁이 너무 낮아지면 새로운 프로세스를 시
스템에 더 추가해서 다중 프로그래밍의 정도(degree of multiprogramming)를 높인
다. 이때 전역 페이지 교체 알고리즘을 사용하여 어떤 프로세스의 페이지인지에 대한 고
려 없이 교체를 수행한다. 이제 어떤 프로세스가 새로운 실행 단계로 진입하여 더 많은
프레임이 필요하다고 가정하자. 페이지 폴트가 발생하면서 다른 프로세스로부터 프레임
들 을 가져오게 될 것이다. 그런데, 교체된 페이지들이 해당 프로세스에서 필요로 하는 것
이었다면 그 프로세스 역시 페이지 폴트를 발생시기고 또 다른 프로세스에서 프레임을
가져온다. 이러한 프로세스들이 페이지 스왑인, 스욉아못을 위해 페이징 장치를 A卜&해
야 한다. 페이징 장치에 대한 큐잉이 진행되면서 준비 큐는 비게 된다. 프로세스들이 페
이정 장치를 기다리는 동안 CPU 이용률은 떨어진다.
CPU 스케줄러는 이용률이 떨어지는 것을 보고, 이용률을 높이기 위하여 새로운 프
로세스를 추가하여 다중 프로그래밍의 정도를 더 높인다 새로 시작하는 프로세스는 실
행 중인 프로세스들로부터 프레임을 가져오고자 하며 더 많은 페이지 폴트와 더 긴 페이
징 장치 대기 시간을 야기한다. 결과적으로 CPU 이용률은 더욱 떨어지고 CPU 스케줄
러는 다중 프로그래밍 정도를 더욱 높이려고 한다. 결국 스래싱이 일어나게 되어 시스템
의 처리율은 대단히 낮아지고 페이지 폴트는 상당히 늘어난다. 실질 메모리 접근 시간은
증가하고 프로세스들은 페이징하는 데 시간을 다 소비하게 되어 아무런 일도 할 수 없게
된다.

시간은 전송된 연즉, 페이지 크기)에 비례한다. 즉, 작은 페이지 크기를 옹호하는 사실

당 50 MB의 전송 속도에서 512바이트를 전송하는 데 0.01밀리초만 걸린다. 그러나 지
연시간은 아마도 3밀리초이며 탐색 시간은 5밀리초이다. 따라서 총 1/0 시간 (8.01 밀리
초) 중 약 0.1%만이 전송 시간이다. 페이지 크기를 두 배로 늘리면 I/O 시간이 8.02밀

려는 목적은 더 큰 페이지 크기를 옹호한다.
그러나, 작은 페이지 크기를 갖는 경우 지역성이 향상되어 전체 I/O는 더 줄어들 것
이다. 작은 페이지는 각 페이지가 프로그램의 지역성을 더욱 정확히 추적하도록 해 준다.
예를 들에 200 KB 중 실제로 100 KB만이 실제로 A卜혐되는 프로세스를 생각해 보자.
시스템에 매우 큰 페이지 하나만 존재하는 경우 200 KB의 전체 페이지를 읽어 들어야

10.9.3 TLB Reach
9장에서는 TLB의 적중률(hit ratio) 개념을 설명하였다. TLB hit ratio는 전체 가상
메모리 참조 중 페이지 테이블에 가지 않더라도, TLB상에서 주소 변환을 수행할 수 있
는 경우의 비율로 나타낸 것이다. 당연히 적중률은 TLB의 항목 수와 연관성을 갖는다.
TLB 항목의 개수를 늘리면 적중률은 올라가게 된다. 그러나 TLB를 크게 만드는 것은
쉬운 일이 아니다. 왜냐하면 TLB에 사용되는 연관 메모리(assoclative memory) 자체
가 비싸고 전력도 많이 소모하기 때문이다.
적중률과 연관된 잣대로는 TLB reach라는 것이 있다. TLB reach는 TLB로부터
액세스할 수 있는 메모리 공간의 크기를 뜻한다. 이것은 TLB에 있는 항목 수에 페이지
크기를 곱한 것이다. 이상적으로는 한 프로세스의 작업 집합이 TLB에 다 들어올 수 있
으면 가장 좋다. 그렇지 못하다면 프로세스는 수행하면서 매우 많은 메모리 참조를 TLB
에서 해결하지 못하고 페이지 테이블까지 가야만 하고, 이렇게 해서 수행 시간이 매우
느려지게 된다. TLB 그기를 두 배로 늘리면 TLB reach 크기도 두 배 늘어난다. 그러나
메모리를 매우 많이 필요로 하는 프로세스에는 이렇게 늘려도 그 프로세스의 작업 집합
을 모두 담기에 부쪽할 수 있다.
TLB reach를 늘리는 또 다른 방법은 페이지 크기를 늘리거나 여러 페이지 크기를
제공하는 것이다. 페이지 크기를 4 KB에서 16 KB로 늘리면 TLB reach가 4배가 된다.
그러나, 이렇게 큰 페이지 크기가 필요하지 않은 일부 응용 프로그램의 경우 단편화가
증가할 수 있다. 대안으로 대부부 아키텍처는 여러 페이지 크기를 지원하며 이 지원을
활용하도록 운영체제를 구성할 수 있다. 예를 들어, Linux 시스템의 기본 페이지 크기는
4 KB이다. 그러나 Linux는 더 큰 페이지(예, 2MB)가 사용될 수 있는 물리 메모리 영역
을 지정하는 거대 페이지(huge page) 기능도 제공한다.

10.9.4 역 페이지 테이블 Table
9.4.3절에서 역 페이지 테이블의 개념을 소개했다. 이 페이지 관리 방식의 목적은 가상-
물리 주소 변환을 추적하는 데 필요한 물리 메모리의 양을 줄이는 것이다. 이 테이블은
〈process-id, page-number〉에 의해 색인되며 각 물리 메모리마다 한 항목을 갖는다.

되므로 필요한 물리 메모리 양을 줄인다. 그렇지만 역 페이지 테이블이 전체 가상 주소
공간에 대한 정보는 더는 유지하지 않으므로, 참조된 페이지가 현재 메모리에 없을 때에
는 문제가 된다. 요구된 페이지가 디스크 내 어디에 있는지를 알 수가 없기 때문이다. 이
정보를 공급하기 위해서는 프로세스당 하나씩 확장된 페이지 테이%(extended page
table)을 유지해야 한다.

용방식에 관해 자신이 제일 잘 알고 있으므로 메모리와 보조저장장치 사이의 블록을 이
동시기는 데 이러한 필요한 메모리 영역을 직접 관리하기를 원할 수 있다. 이러한 페이
지 고정(pmnmg)은 널리 시용되며 대부분의 운영체제에는 -응용이 자신의 영역을 메모
리에 고정할 수 있도록 요청하는 시스템 콜이 한한다. 이러한 기능은 악용될 수 있으
며 메모리 관리 알고리즘에 부담을 준다. 따라서 메모리 고정 요청을 하기 위해서 응용
은 특권을 가지고 있어야 한다.
잠금 비트의 일반적인 페이지 교체 시의 사용 예를 보자. 우선순위가 낮은 프로세스
가 페이지 폴트를 발생, 필요한 페이지를 메모리로 읽어 들인다. 이어서 이 우선순위가
낮은 프로세스는 대기 큐에 들어가 CPU를 기다리게 된다. 우선순위가 낮기 때문에 이
프로세스는 한동안 CPU를 久卜&하지 못할 수 있다. 그동안 우선순위가 높은 프로세스가
들어와 실행하다가 페이지 폴트를 일으킨다. 빼앗을 페이지를 찾다가 위의 페이지가 한
번도 사용이 안 된 상태인 것을 발견하곤 빼앗아간다. 사실 이 페이지는 우선순위가 낮
은 프로세스가 방금 읽어 들인 페이지이다. 외견상으로는 이 페이지는 변경되지도 않아
쓰기 작업이 필요하지 않고 한동안 접근되지도 않은 것처럼 보여서 가장 완벽한 교체 대
상으로 보인다.
높은 우선순위의 프로세스가 낮은 우선순위 프로세스의 페이지를 교체할 수 있느냐
하는 것은 정책적인 선택 사항이다. 결국, 이 경유는 높은 우선순위 프로세스를 위해 낮
은 우선선위 프로세스의 실행을 지연시킨 것이다. 그러나 낮은 우선순위 프로세스의 페
이지를 읽어 들이기 위해 많은 자원을 사용하였다. 최소한 한 번이라도 久卜우될 때까지는
새롭게 읽힌 페이지를 교체하지 못하도록 하고 싶으면 잠금 비트를 사용할 수 있다. 페
이지가 선택되어 교체되면 잠금 비트를 켜고 부재를 발생시킨 프로세스가 대시 실행될
때까지 남아있도록 할 수 있다.
잠금 비트 사용이 위험한 상황을 만들 수 있다. 잠금 비트는 일단 1로 세팅되고 나
서 언젠가는 해제되어야 하는데 그렇지 않을 수 있다. 이런 상황이 일어나면(예를 들어
운영체제의 버그로 인해) 잠금된 프레임은 영원히 사용할 수 없게 된다. 예를 들어, 노)-
laris는 잠금 “힌트” 기능을 제공하여 빈 페이지 풀(free page pool)이 너무 적거나, 개
개의 프로세스들이 페이지 잠금을 너무 많이 요구하면 이를 적절히 무시할 수 있게 되어
있다.

10.11 요약 summary
• 가상 메모리는 물리 메모리를 매우 큰 균일한 저장장소 배열로 추상화한다.
• 가상 메모리의 이점은 다음과 같다. (1) 프로그램이 물리 메모리보다 클 수 있음, (2)
프로그램 전체가 메모리에 있을 필요는 없음, (3) 프로세스가 메모리를 공유할 수 있
음 및 (4) 프로세스를 보다 효율적으로 생성할 수 있다.
