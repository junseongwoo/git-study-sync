그림 14.10 통합 버퍼 개시를 시용하지 않는 입출력
합 버퍼 개시가 없으면 우리는 그림 14.10과 비슷한 상황을 맞게 될 것이다. 이 예에서
read()와vrite() 시스템 콜은 버퍼 개시를 시용한다. 메모리 매핑 호출은 페이지 개
시와 버퍼 개시의 두 가지 개시를 시용할 것을 요구한다. 메모리 매핑은 파일 시스템으
로부터 디스크를 읽고, 버퍼 개시에 저장함으로써 진행된다. 가상 메모리 시스템은 버퍼
개시와 인터페이스 할수 없기 때문에 버퍼 개시에 있는 파일이 페이지 개시에 복사되어
야만 한다. 이런 현상은 이중 lß(double caching)으로 알려져 있으며, 파일 시스템
데이터를 두 번 개성해야 한다. 이것은 메모리 당비일 뿐 아니라, 시스템 메모리 내에서
필요 없는 데이터 이동으로 인해 CPU와 1/0 사이클을 낭비하게 된다. 또한 두 개시 사
이의 비일관성은 파일에 문제를 야기할 수도 있다. 통합 버퍼 개시를 제공함으로써 메모
리 매핑과read()와vrite() 시스템 콜은 같은 페이지 개시를 사용하게 된다. 이는 이
중 개시 단점을 극복하며, 가상 메모리 시스템이 파일 시스템 데이터를 관리할 수 있도
록 해준다. 통합 버퍼 개시는 그림 14.11과 같다.
저장장치 블록을 개성하는 페이지를 개성하든, LRU (10.5.4절)는 블록 또는 페이지
교제에 이상적인 범용 알고리즘이다. 그러나 Solaris 페이지 개성 알고리즘의 발전은 알
고리즘 선택이 얼마나 어려운지 보인다. Solaris는 프로세스와 페이지 개시가 시용되지
않는 메모리를 공유하게 하였다. Solaris 25.1 이전 버전에서는 프로세스나 페이지 개
시에 페이지 할당하는 데 있어 아무런 차이가 없었다. 그 결과, 많은 입출력 작업을 수행
하는 시스템은 대부분의 사용 기능한 메모리를 페이지를 개싱히는 데 사용한다. 높은 입
출력률 때문에 페이지 스개너(10.10.3절)는 시용 기능한 메모리가 적을 때, 페이지 개시
