# 파일·소켓·비동기 I/O와 Buffer

> [!summary] 이 문서의 핵심
> I/O 코드는 **핸들 수명**, **요청 수명**, **버퍼 수명**, **완료 통지 수명**을 따로 추적해야 한다. 특히 비동기 I/O나 카메라 콜백에서는 포인터를 받았다는 사실이 소유권을 뜻하지 않는다. 버퍼를 작업 스레드로 넘기려면 ① 애플리케이션 소유 메모리로 복사하거나, ② SDK가 공식적으로 제공하는 retain/lock/requeue 계약을 RAII로 감싸야 한다.

## 2. 한 번의 I/O에는 네 가지 수명이 있다

I/O 문제를 “포인터 하나”로 보면 수명 오류가 생긴다. 다음 네 대상을 분리해서 봐야 한다.

| 대상 | 예 | 종료 조건 |
|---|---|---|
| 핸들(handle) | 파일 디스크립터, socket, camera handle | `close`, SDK close/destroy가 완료될 때 |
| 요청(operation/request) | `read`, overlapped request, AIO control block, frame acquisition | 성공·실패·취소의 **완료가 확인될 때** |
| 버퍼(storage) | `std::vector<std::byte>`, SDK frame memory, DMA 대상 메모리 | 마지막 접근 주체가 사용을 끝낼 때 |
| 완료 통지(completion) | callback, event, future, completion queue item | 소비자가 결과를 인수하고 필요한 후처리를 끝낼 때 |

이 관계는 다음처럼 이해할 수 있다.

```text
핸들 열기
   │
   ├─ 요청 제출 ────────┐
   │                    │ OS/드라이버/SDK가 버퍼 접근 가능
   │                    │
   │             성공·실패·취소 완료 확인
   │                    │
   └─ 새 요청 가능       └─ 버퍼 재사용·해제 가능

핸들 닫기는 진행 중인 요청과 콜백이 모두 정리되는 시점과 조정해야 한다.
```

가장 중요한 규칙은 다음과 같다.

> **요청을 제출한 함수가 반환한 시점이 아니라, 그 요청의 완료 또는 취소 완료가 확인된 시점까지 요청 객체와 버퍼가 살아 있어야 한다.**

단, 동기 `read()`처럼 함수 반환 자체가 해당 호출의 완료를 뜻하는 API는 반환 뒤 버퍼를 사용할 수 있다. API마다 “완료”의 정의가 다르므로 계약을 확인해야 한다.

## 3. 파일 I/O

### 3.1 파일 디스크립터는 파일 자체가 아니다

`open()`은 프로세스가 사용하는 파일 디스크립터를 반환한다. 파일 디스크립터는 열린 파일을 가리키는 정수형 핸들이며, 커널의 열린 파일 상태와 연결된다.

```cpp
#include <cerrno>
#include <cstddef>
#include <span>
#include <system_error>
#include <unistd.h>

std::size_t read_some(int fd, std::span<std::byte> out) {
    for (;;) {
        const auto n = ::read(fd, out.data(), out.size());
        if (n > 0) {
            return static_cast<std::size_t>(n);
        }
        if (n == 0) {
            return 0; // 일반 파일에서는 EOF
        }
        if (errno == EINTR) {
            continue; // signal로 중단되었으므로 재시도
        }
        throw std::system_error(errno, std::generic_category(), "read");
    }
}
```

`read()`의 반환값은 “요청한 크기”가 아니라 **실제로 읽은 바이트 수**다. 따라서 버퍼 전체가 채워졌다고 가정하면 안 된다.

### 3.2 부분 읽기와 부분 쓰기

파일과 소켓 모두 한 번의 호출이 요청량 전체를 처리한다는 보장이 없는 경우가 있다. 특히 소켓, pipe, non-blocking 핸들에서는 부분 처리가 정상적인 흐름이다.

```cpp
#include <cerrno>
#include <cstddef>
#include <span>
#include <system_error>
#include <unistd.h>

void write_all(int fd, std::span<const std::byte> data) {
    std::size_t offset = 0;

    while (offset < data.size()) {
        const auto* begin = data.data() + offset;
        const auto left = data.size() - offset;
        const auto n = ::write(fd, begin, left);

        if (n > 0) {
            offset += static_cast<std::size_t>(n);
            continue;
        }
        if (n < 0 && errno == EINTR) {
            continue;
        }
        throw std::system_error(errno, std::generic_category(), "write");
    }
}
```

> [!note] `write()` 성공과 영구 저장은 다르다
> `write()`가 성공해도 데이터는 메모리의 커널 버퍼에만 있을 수 있다. 전원 장애 뒤에도 유지되는 저장까지 필요하다면 파일 시스템과 API 계약에 따라 `fsync()` 같은 동기화가 추가로 필요하다. 즉 “애플리케이션 버퍼에서 커널이 인수함”과 “저장 장치에 영구 반영됨”을 구분해야 한다.

### 3.3 파일 핸들을 RAII로 관리하기

```cpp
#include <unistd.h>
#include <utility>

class UniqueFd {
public:
    UniqueFd() noexcept = default;
    explicit UniqueFd(int fd) noexcept : fd_(fd) {}

    ~UniqueFd() {
        reset();
    }

    UniqueFd(const UniqueFd&) = delete;
    UniqueFd& operator=(const UniqueFd&) = delete;

    UniqueFd(UniqueFd&& other) noexcept
        : fd_(std::exchange(other.fd_, -1)) {}

    UniqueFd& operator=(UniqueFd&& other) noexcept {
        if (this != &other) {
            reset(std::exchange(other.fd_, -1));
        }
        return *this;
    }

    [[nodiscard]] int get() const noexcept { return fd_; }

    void reset(int next = -1) noexcept {
        if (fd_ != -1) {
            ::close(fd_);
        }
        fd_ = next;
    }

private:
    int fd_ = -1;
};
```

`UniqueFd`는 핸들의 소유권만 표현한다. **진행 중인 비동기 요청이 끝났다는 사실까지 보장하지는 않는다.** 비동기 API에서는 핸들 RAII 바깥에 요청 취소·완료 대기 프로토콜이 추가되어야 한다.

## 4. 소켓 I/O

### 4.1 소켓은 통신의 endpoint다

소켓은 통신의 한쪽 끝을 나타내는 핸들이다. TCP는 연결을 만들고 바이트 흐름을 주고받는 방식이며, UDP는 개별 datagram을 주고받는 방식이다.

| 항목 | TCP | UDP |
|---|---|---|
| 연결 | 연결 기반 | 비연결형 사용 가능 |
| 데이터 관점 | 연속된 바이트 스트림 | datagram 단위 |
| 애플리케이션 경계 | 별도 framing 필요 | datagram 경계가 존재 |
| 일반적인 처리 | 부분 `send`/`recv`, 연결 종료 처리 | datagram 크기·유실·순서 정책 처리 |

TCP의 한 번의 `recv()` 결과를 하나의 완성된 메시지로 간주하면 안 된다. 길이 prefix, 구분자, 고정 길이처럼 애플리케이션 프로토콜이 메시지 경계를 정의해야 한다.

### 4.2 준비 상태는 작업 완료와 다르다

`select()`/`poll()`/플랫폼별 이벤트 API가 알려 주는 것은 보통 “지금 해당 연산을 시도하면 block되지 않을 가능성이 있는 상태”다.

```text
readable 알림
    │
    ├─ 읽을 데이터가 있음
    ├─ peer가 정상 종료하여 EOF를 읽을 수 있음
    └─ 오류 상태를 관찰할 수 있음

readable ≠ 애플리케이션 메시지 하나가 완전히 도착함
```

따라서 이벤트 루프에는 다음 상태가 함께 있어야 한다.

- 연결별 수신 버퍼
- 현재까지 받은 바이트 수
- 다음 메시지에 필요한 길이
- 부분 전송의 offset
- 연결 종료 및 오류 상태

### 4.3 non-blocking은 asynchronous와 같지 않다

| 방식 | 호출자가 기다리는가? | 실제 작업 완료를 어떻게 아는가? | 버퍼 수명 |
|---|---|---|---|
| blocking | 호출 스레드가 기다림 | 함수 반환 | 반환까지 유효 |
| non-blocking | 즉시 반환 | 현재 처리량 또는 `EAGAIN`/`EWOULDBLOCK`; readiness 뒤 재시도 | 각 호출이 접근하는 동안 유효 |
| readiness 기반 | 이벤트 대기와 실제 `read`/`write`가 분리 | 알림 뒤 호출하여 처리 | 연결별 누적 상태가 계속 유효해야 함 |
| completion 기반 async | 요청을 제출하고 반환 | callback/event/completion queue/future | **완료 또는 취소 완료까지 유효** |

> [!important] `std::async`와 OS 비동기 I/O
> `std::async([&] { blocking_read(); })`는 blocking 호출을 다른 실행 주체에서 수행하게 만들 수 있지만, 그 자체가 커널의 completion 기반 비동기 I/O로 바뀌는 것은 아니다. C++ 작업 비동기화와 운영체제 I/O 모델을 구분해야 한다.

## 5. 비동기 I/O 요청과 버퍼

### 5.1 제출 시점부터 완료 시점까지

OSTEP의 POSIX AIO 예에서는 요청 구조체에 파일 디스크립터, offset, 길이와 함께 버퍼 위치가 들어간다. OS가 나중에 그 위치에 데이터를 기록하므로, 함수의 지역 변수가 먼저 소멸하면 안 된다.

```cpp
// 잘못된 구조를 보여 주는 개념 예시
void start_bad_async_read(AsyncFile& file) {
    std::array<std::byte, 4096> local{};
    file.async_read(local.data(), local.size(), on_complete);
} // local 소멸: 완료 전이라면 dangling buffer
```

안전한 요청 객체는 버퍼와 완료 상태를 함께 소유한다.

```cpp
#include <cstddef>
#include <memory>
#include <vector>

struct ReadOperation {
    std::vector<std::byte> buffer;
    std::size_t transferred = 0;
    // 플랫폼별 요청 객체, offset, 오류 상태 등을 함께 둔다.
};

void start_read(AsyncFile& file, std::size_t size) {
    auto operation = std::make_shared<ReadOperation>();
    operation->buffer.resize(size);

    file.async_read(
        operation->buffer.data(),
        operation->buffer.size(),
        [operation](std::error_code ec, std::size_t n) {
            operation->transferred = n;
            if (!ec) {
                consume(std::span(operation->buffer).first(n));
            }
        });
}
```

이 예의 `shared_ptr`는 “무조건 비동기는 shared ownership”이라는 뜻이 아니다. API의 callback 저장 방식에 맞춰 요청 객체의 수명을 완료까지 연장하는 한 방법이다. 단일 소유 이벤트 루프라면 `unique_ptr` 요청을 completion map에 보관하는 편이 더 명확할 수 있다.

### 5.2 취소 요청은 즉시 해제가 아니다

일반적인 안전 규칙은 다음과 같다.

1. 취소를 **요청**한다.
2. completion 또는 별도의 동기화 수단으로 취소 **완료**를 확인한다.
3. OS·드라이버·SDK가 더 이상 버퍼에 접근하지 않는다는 계약을 만족한다.
4. 그 뒤 요청 객체와 버퍼를 재사용하거나 해제한다.

`cancel()`이 반환했다는 이유만으로 즉시 버퍼를 해제할 수 있는지는 API 계약에 달려 있다. “취소 요청 접수”와 “접근 종료”를 혼동하면 use-after-free가 된다.

### 5.3 DMA가 보여 주는 본질

DMA에서는 장치가 CPU 대신 메모리 위치와 길이를 이용해 데이터를 전송한다. 전송이 끝나기 전에 해당 메모리를 수정·이동·해제하면 장치와 프로그램이 같은 저장 공간을 잘못 공유하게 된다.

이 원리는 카메라 프레임에도 그대로 적용된다.

- SDK/드라이버가 버퍼를 채우는 동안 애플리케이션이 덮어쓰면 안 된다.
- 검사 스레드가 읽는 동안 SDK가 같은 버퍼를 다음 프레임용으로 재사용하면 안 된다.
- 재사용이 필요하다면 소유권 이전, retain/lock, reference count, requeue 같은 명시적 프로토콜이 있어야 한다.

## 6. Buffer: 소유 메모리와 빌린 view를 구분하기

### 6.1 타입으로 표현하기

```cpp
#include <cstddef>
#include <cstdint>
#include <span>
#include <vector>

struct BorrowedFrameView {
    std::span<const std::byte> pixels; // 소유하지 않음
    std::uint32_t width{};
    std::uint32_t height{};
    std::uint32_t stride{};
    std::uint64_t sequence{};
};

struct OwnedFrame {
    std::vector<std::byte> pixels; // 애플리케이션이 소유
    std::uint32_t width{};
    std::uint32_t height{};
    std::uint32_t stride{};
    std::uint64_t sequence{};
};
```

- `std::span`은 범위를 표현하지만 수명을 연장하지 않는다.
- `std::vector`는 자기 저장 공간을 소유하고 이동할 수 있다.
- raw pointer와 `span`이 존재한다고 해서 그 메모리를 `delete`할 권리가 생기지 않는다.

### 6.2 실제 소유자를 판별하는 질문

버퍼의 실제 소유자는 “현재 포인터를 들고 있는 코드”가 아니라 다음 계약으로 결정된다.

1. 누가 메모리를 할당했는가?
2. 누가 언제 재사용할 수 있는가?
3. 누가 마지막 사용을 선언하는가?
4. 어떤 함수로 반납·해제해야 하는가?
5. retain/lock/reference count를 증가시킬 수 있는가?
6. callback 반환이 자동 반납을 의미하는가?

| 생성 방식 | 일반적인 소유자 | 해제/반납 원칙 |
|---|---|---|
| 애플리케이션의 `new[]` | 애플리케이션 | 대응되는 `delete[]` |
| `std::vector` 내부 저장 공간 | 해당 `vector` | 자동 소멸; `data()`에 `delete` 금지 |
| C `malloc` | 할당 계약의 소유자 | `free` |
| SDK가 만든 frame/buffer | SDK 또는 SDK에서 lease를 받은 앱 | SDK 전용 release/requeue 함수 |
| 앱이 SDK에 등록한 buffer | 저장 공간은 앱 소유, 사용 권한은 작업 중 SDK와 조정 | 완료 전 수정·해제·unregister 금지 |

> [!danger] 할당자와 해제자를 섞지 않는다
> SDK가 준 포인터에 임의로 `delete`, `delete[]`, `free`를 호출하면 안 된다. C++에서 해제 함수는 포인터 타입이 아니라 **할당·반납 계약**으로 결정된다.

## 7. 카메라 콜백 버퍼: 세 가지 계약

카메라 SDK 이름을 모르는 상태에서는 다음 세 모델 중 어느 것인지 먼저 확인해야 한다.

### 7.1 모델 A — callback 동안만 빌린 버퍼

```text
SDK가 프레임 버퍼 소유
  → callback에 view 전달
  → callback 반환
  → SDK가 즉시 재사용 가능
```

이 모델에서는 검사 스레드에 pointer나 `span`만 넘기면 안 된다. callback 안에서 애플리케이션 소유 버퍼로 복사한 뒤 그 소유 객체를 queue로 이동해야 한다.

장점은 수명 설계가 단순하고 SDK 종료와 검사 작업의 결합이 약하다는 것이다. 단점은 프레임당 메모리 복사 비용과 할당 비용이다. 할당 비용은 미리 만든 buffer pool로 줄일 수 있다.

### 7.2 모델 B — retain/lock/requeue 가능한 SDK frame

```text
SDK frame 획득
  → retain/lock 또는 소유 handle 인수
  → callback 반환 뒤에도 검사 스레드가 사용
  → 검사 완료
  → SDK release/requeue
```

SDK가 이 계약을 명시적으로 제공한다면 복사를 피할 수 있다. 대신 다음 제약이 생긴다.

- 모든 retained frame을 반납하기 전 카메라·stream·SDK 객체를 파괴하면 안 된다.
- 검사 지연이 길면 SDK buffer pool이 고갈될 수 있다.
- queue 크기를 제한하고 drop/backpressure 정책을 정해야 한다.
- 반납 함수는 RAII deleter에 정확히 연결해야 한다.

### 7.3 모델 C — 애플리케이션이 버퍼를 등록

애플리케이션이 버퍼를 할당해 SDK에 등록했더라도, 제출 뒤 완료 전까지는 마음대로 재사용하거나 해제할 수 없다. 저장 공간의 소유권과 특정 기간의 접근 권한은 별개다.

```text
앱이 buffer 소유
  → SDK에 등록/queue
  → 카메라·DMA가 기록
  → 완료 callback
  → 앱이 처리
  → 다시 SDK에 requeue
```

동일한 버퍼를 requeue한 순간부터 다음 완료까지 검사 스레드가 계속 읽으면 race가 된다. requeue 전에 검사를 끝내거나, 별도 버퍼로 복사하거나, SDK가 허용하는 다중 버퍼 pool을 운영해야 한다.

## 8. 질문별 결론

### 8.1 버퍼의 실제 소유자는 누구인가?

포인터를 전달받은 쪽이 아니라 **할당·retain·release 계약에 기록된 주체**다. callback 인수의 `const void*`나 `unsigned char*`만으로는 소유권을 알 수 없다. SDK 문서에서 allocation, lifetime, ownership, buffer handling, requeue, release 항목을 확인한다.

### 8.2 콜백이 끝난 뒤에도 버퍼가 유효한가?

SDK 문서가 보장할 때만 유효하다. 보장이 없다면 callback 동안만 유효한 borrowed view로 취급하는 것이 안전하다. callback이 끝난 뒤 사용할 때는 다음 중 하나가 필요하다.

- callback 안에서 app-owned buffer로 복사
- SDK의 retain/lock API로 수명 연장
- 소유권이 포함된 frame handle을 인수하고 나중에 SDK 함수로 반납

### 8.3 검사 스레드로 넘길 때 복사가 필요한가?

| 조건 | 복사 필요 여부 |
|---|---|
| callback 동안만 유효 | 필요 |
| SDK가 callback 반환 뒤 즉시 재사용 가능 | 필요 |
| 공식 retain/lock 후 worker가 사용 가능 | 필수 아님 |
| 소유 frame handle을 worker에게 이동 가능 | 필수 아님 |
| app buffer이지만 requeue 즉시 SDK가 덮어씀 | requeue 전에 검사 완료하거나 복사 필요 |

복사를 피하는 것이 항상 더 빠른 것은 아니다. zero-copy로 인해 SDK buffer pool이 고갈되어 촬영이 멈추거나 프레임이 누락되면 전체 처리량은 더 나빠질 수 있다.

### 8.4 이미지 처리 중 카메라 SDK가 버퍼를 재사용하지 않는가?

일반 PDF만으로는 특정 SDK의 동작을 확정할 수 없다. ring buffer, buffer pool, callback 반환 시 자동 반납, 명시적 requeue 중 어떤 모델인지 제조사 문서로 확인해야 한다.

확인 전에는 다음 보수적 규칙을 사용한다.

> callback에서 받은 borrowed buffer는 callback 반환 뒤 SDK가 재사용할 수 있다고 보고, 장기 작업에는 pointer만 저장하지 않는다.

### 8.5 해제 함수는 `delete`인가, SDK 전용 함수인가?

- `new T`로 직접 만들었다면 `delete`
- `new T[]`로 직접 만들었다면 `delete[]`
- `malloc` 계열이면 `free`
- SDK가 생성·획득·대여한 frame이면 문서가 정한 SDK `release`/`unlock`/`requeue`
- `vector.data()`는 직접 해제하지 않음

함수 이름이 `GetBuffer()`라고 해서 호출자가 `delete`할 수 있는 것은 아니다.

### 8.6 종료 시 카메라보다 검사 스레드를 먼저 종료해야 하는가?

“카메라 종료”를 두 단계로 나눠야 답이 명확하다.

1. **새 프레임 생산 중지**: 검사 스레드 종료보다 먼저 한다.
2. **카메라/stream/SDK 객체 파괴**: outstanding SDK frame이 모두 반납되고 검사 스레드가 종료된 뒤 한다.

권장 순서는 다음과 같다.

```text
새 작업 접수 중지
  → 카메라 acquisition 중지 / callback 등록 해제 시작
  → 실행 중 callback과 I/O의 완료·취소 완료 대기
  → frame queue close
  → 검사 스레드가 drain 또는 명시적 discard 후 종료(join)
  → outstanding SDK frame 전부 release/requeue
  → camera/stream/SDK destroy
```

SDK frame을 worker가 직접 보유한다면 카메라를 먼저 파괴해서는 안 된다. 반대로 callback에서 완전히 복사한 app-owned frame만 queue에 있다면 worker는 카메라 메모리에 의존하지 않지만, 새 callback과 종료가 경쟁하지 않도록 acquisition 중지와 callback quiescence는 여전히 먼저 수행해야 한다.

## 9. C++ 설계 1 — callback에서 복사해 소유권 넘기기

다음 예시는 특정 SDK API가 아니라 수명 구조를 보여 주는 C++20 예제다.

```cpp
#include <algorithm>
#include <condition_variable>
#include <cstddef>
#include <cstdint>
#include <deque>
#include <mutex>
#include <optional>
#include <span>
#include <thread>
#include <utility>
#include <vector>

struct BorrowedFrameView {
    std::span<const std::byte> pixels;
    std::uint32_t width{};
    std::uint32_t height{};
    std::uint32_t stride{};
    std::uint64_t sequence{};
};

struct OwnedFrame {
    std::vector<std::byte> pixels;
    std::uint32_t width{};
    std::uint32_t height{};
    std::uint32_t stride{};
    std::uint64_t sequence{};
};

OwnedFrame copy_frame(BorrowedFrameView source) {
    return OwnedFrame{
        std::vector<std::byte>(source.pixels.begin(), source.pixels.end()),
        source.width,
        source.height,
        source.stride,
        source.sequence
    };
}

class FrameQueue {
public:
    explicit FrameQueue(std::size_t capacity) : capacity_(capacity) {}

    // callback을 오래 막지 않도록 가득 차면 false를 반환한다.
    bool try_push(OwnedFrame frame) {
        {
            std::lock_guard lock(mutex_);
            if (closed_ || queue_.size() == capacity_) {
                return false;
            }
            queue_.push_back(std::move(frame));
        }
        not_empty_.notify_one();
        return true;
    }

    std::optional<OwnedFrame> pop() {
        std::unique_lock lock(mutex_);
        not_empty_.wait(lock, [this] {
            return closed_ || !queue_.empty();
        });

        if (queue_.empty()) {
            return std::nullopt;
        }

        OwnedFrame frame = std::move(queue_.front());
        queue_.pop_front();
        return frame;
    }

    void close() {
        {
            std::lock_guard lock(mutex_);
            closed_ = true;
        }
        not_empty_.notify_all();
    }

private:
    const std::size_t capacity_;
    std::mutex mutex_;
    std::condition_variable not_empty_;
    std::deque<OwnedFrame> queue_;
    bool closed_ = false;
};

void inspect(const OwnedFrame& frame) {
    // pixels는 OwnedFrame이 소유하므로 이 함수가 실행되는 동안 유효하다.
    [[maybe_unused]] const auto size = frame.pixels.size();
}

class InspectionPipeline {
public:
    explicit InspectionPipeline(std::size_t queue_capacity)
        : queue_(queue_capacity), worker_([this] { worker_loop(); }) {}

    // SDK callback 안에서 호출한다고 가정한다.
    void on_frame(BorrowedFrameView borrowed) {
        // callback 반환 전에 복사를 끝낸다.
        // 실패 시 drop-newest 정책을 사용한다.
        [[maybe_unused]] const bool accepted =
            queue_.try_push(copy_frame(borrowed));
    }

    void shutdown() {
        // 실제 프로그램에서는 이 함수 전에 다음을 수행한다.
        // 1) SDK acquisition 중지
        // 2) callback 진입 차단 및 실행 중 callback 종료 대기
        queue_.close();
        if (worker_.joinable()) {
            worker_.join();
        }
        // 그 뒤 camera/stream/SDK 객체를 파괴한다.
    }

    ~InspectionPipeline() {
        shutdown();
    }

    InspectionPipeline(const InspectionPipeline&) = delete;
    InspectionPipeline& operator=(const InspectionPipeline&) = delete;

private:
    void worker_loop() {
        while (auto frame = queue_.pop()) {
            inspect(*frame);
        }
    }

    FrameQueue queue_;
    std::thread worker_;
};
```

이 구조의 핵심은 callback의 `BorrowedFrameView`가 queue에 들어가지 않는다는 점이다. queue에는 오직 `OwnedFrame`만 들어가며, 이동 후에는 worker가 그 객체의 유일한 소유자가 된다.

### 9.1 복사형 설계에서 추가로 정할 정책

- queue가 찼을 때 callback을 block할지, newest/oldest frame을 버릴지
- 이미지 크기 변화가 가능한지
- `stride * height`와 실제 payload 크기를 어떻게 검증할지
- 프레임 번호 누락을 어떻게 기록할지
- 매 프레임 할당을 피하기 위해 buffer pool을 쓸지
- 검사 실패와 카메라 연결 해제를 어떤 상태 머신으로 처리할지

카메라 callback을 오래 block하면 SDK 내부 buffer 반환이 늦어질 수 있으므로, 실시간 시스템에서는 짧은 복사·enqueue 뒤 빠르게 반환하는 설계가 보통 이해하기 쉽다. 단, 최종 정책은 SDK의 callback threading 규칙과 허용 blocking 시간을 확인해야 한다.

## 10. C++ 설계 2 — SDK frame을 RAII lease로 넘기기

SDK가 callback 이후 사용 가능한 frame handle과 전용 release 함수를 공식 제공할 때만 적용한다.

```cpp
#include <memory>
#include <utility>

struct SdkFrame; // SDK가 정의하는 불투명 frame이라고 가정

// 실제 코드에서는 정확한 SDK 함수와 필요한 camera/stream context를 보관한다.
void sdk_release_frame(SdkFrame* frame) noexcept;

struct SdkFrameReleaser {
    void operator()(SdkFrame* frame) const noexcept {
        if (frame != nullptr) {
            sdk_release_frame(frame); // delete가 아님
        }
    }
};

using FrameLease = std::unique_ptr<SdkFrame, SdkFrameReleaser>;

void enqueue_for_inspection(FrameLease frame) {
    // queue.push(std::move(frame));
    // 검사 완료 또는 queue에서 폐기될 때 SDK 전용 releaser가 정확히 한 번 실행된다.
}
```

`FrameLease`는 다음을 표현한다.

- 복사 금지: 하나의 frame을 두 주체가 중복 반납하지 않음
- 이동 가능: callback에서 queue, queue에서 worker로 소유권 이전
- scope 종료 시 자동 반납
- `delete` 대신 SDK 전용 함수를 호출

하지만 `unique_ptr`만으로는 충분하지 않다. deleter가 사용하는 camera/stream context가 frame보다 오래 살아 있어야 한다. 따라서 객체 파괴 순서는 보통 다음 의존성을 따라야 한다.

```text
FrameLease들 → FrameQueue/Workers → Stream/Camera → SDK runtime

왼쪽 객체를 먼저 정리하고 오른쪽 객체를 나중에 파괴한다.
```

## 11. Buffer pool과 backpressure

프레임 생성 속도가 검사 속도보다 빠르면 메모리를 무한히 늘려 해결할 수 없다.

| 정책 | 장점 | 위험/비용 |
|---|---|---|
| producer block | 프레임 보존 | callback 또는 카메라 pipeline 정지 가능 |
| drop newest | 기존 순서 유지 | 최신 프레임 유실 |
| drop oldest | 최신 상태 우선 | 진행 중 판단과 시간 순서 정책 필요 |
| camera trigger 감속 | 근본적인 입력률 제어 | 장비·공정 요구와 조정 필요 |
| 고정 buffer pool | 할당 변동 감소, 메모리 상한 명확 | pool 고갈 정책 필요 |

안전한 buffer pool의 버퍼 상태는 최소한 다음처럼 관리한다.

```text
Free → Filling by SDK → Ready → Inspecting → Free
```

하나의 버퍼가 동시에 `Filling`과 `Inspecting` 상태에 있으면 설계 오류다. 상태 전이는 mutex/atomic/SDK requeue 계약 중 하나로 동기화해야 한다.

## 12. 오류 처리와 종료 상태 머신

단순한 `bool running` 하나보다 상태를 나누면 종료 경쟁을 줄일 수 있다.

```text
Running
  → StopRequested
  → AcquisitionStopped
  → CallbacksQuiesced
  → QueueClosed
  → WorkersJoined
  → FramesReleased
  → CameraDestroyed
```

종료 구현에서 확인할 불변식은 다음과 같다.

- `QueueClosed` 뒤 새 frame이 enqueue되지 않는다.
- `WorkersJoined` 뒤 검사 함수가 frame에 접근하지 않는다.
- `FramesReleased` 뒤 outstanding SDK frame 수가 0이다.
- `CameraDestroyed` 시점에는 callback과 deleter가 camera context를 사용하지 않는다.
- destructor는 가능하면 예외를 던지지 않는다.
- 종료 함수가 두 번 호출되어도 double close/double release가 생기지 않는다.

> [!warning] callback 안에서 join하지 않는다
> SDK callback을 실행하는 스레드가 자기 자신 또는 자신이 빠져나가야 끝나는 작업을 `join`하면 deadlock이 된다. 종료 요청과 실제 join 위치를 분리하고, SDK가 어느 스레드에서 callback을 실행하는지 확인한다.

## 13. 흔한 실패 패턴

### 13.1 callback pointer만 queue로 전달

```cpp
void on_frame(const std::byte* data, std::size_t size) {
    queue.push(std::span(data, size)); // callback 뒤 SDK 재사용이면 dangling/데이터 변조
}
```

`span` 복사는 데이터 복사가 아니다. 주소와 길이만 복사한다.

### 13.2 지역 버퍼로 비동기 요청

```cpp
void request() {
    std::vector<std::byte> bytes(4096);
    async_read(bytes.data(), bytes.size());
} // 완료 전에 bytes 소멸 가능
```

요청 객체가 버퍼를 소유하도록 만들고 completion까지 보관해야 한다.

### 13.3 SDK 포인터에 `delete[]`

```cpp
void on_frame(unsigned char* sdk_buffer) {
    // ...
    delete[] sdk_buffer; // SDK 계약 없이는 금지
}
```

allocator mismatch, pool 손상, double free가 될 수 있다.

### 13.4 카메라부터 파괴

```text
camera.destroy()
worker.join()  // worker가 SDK frame/deleter를 사용하면 너무 늦음
```

먼저 생산과 callback을 멈추고, worker가 frame을 모두 반납한 뒤 카메라를 파괴해야 한다.

### 13.5 unbounded queue

검사보다 촬영이 빠른 상황에서 queue가 무한히 늘면 지연과 메모리 사용량이 함께 증가한다. 메모리가 다 찬 뒤의 장애 대신, 미리 정한 drop/backpressure 정책으로 부하를 제한해야 한다.

## 14. SDK 문서에서 반드시 찾을 문장

실제 카메라 SDK를 적용할 때 아래 항목을 체크리스트로 사용한다.

- [ ] callback buffer의 유효 기간이 명시되어 있는가?
- [ ] callback 반환 시 자동으로 buffer가 재사용되는가?
- [ ] frame retain/lock API가 있는가?
- [ ] release/unlock/requeue 중 정확히 어떤 함수를 호출해야 하는가?
- [ ] 같은 thread에서만 release해야 하는가?
- [ ] callback 안에서 허용되는 작업과 금지되는 blocking 호출은 무엇인가?
- [ ] buffer alignment, stride, pixel format, payload size 규칙은 무엇인가?
- [ ] acquisition stop이 진행 중 callback의 종료까지 기다리는가?
- [ ] unregister callback 뒤 이미 진입한 callback이 남을 수 있는가?
- [ ] cancel/stop 완료를 확인하는 API가 있는가?
- [ ] camera/stream handle이 frame release보다 오래 살아야 하는가?
- [ ] SDK 종료 전 outstanding buffer를 조회할 수 있는가?

문서가 모호하면 SDK 지원팀에 다음처럼 구체적으로 질문한다.

> callback으로 받은 image pointer를 callback 반환 뒤 다른 스레드에서 읽어도 되는가? 가능하다면 어떤 retain 함수가 필요하며, 어느 함수로 언제 반납해야 하는가? acquisition stop과 camera destroy는 outstanding frame의 반납을 기다리는가?

## 15. 설계 선택표

| 상황 | 권장 전달 방식 | 종료 시 핵심 |
|---|---|---|
| SDK 수명 계약을 아직 모름 | callback 안에서 app buffer로 복사 | callback 종료 대기 후 queue close |
| callback 동안만 유효 | 복사 후 `OwnedFrame` 이동 | app-owned frame drain 뒤 worker join |
| 공식 retain/release 제공 | move-only `FrameLease` | 모든 lease 반납 후 camera destroy |
| 앱 등록 buffer + requeue | 상태가 있는 pool 또는 복사 | `Inspecting` 버퍼가 0일 때 unregister/destroy |
| 검사보다 입력이 빠름 | bounded queue + 명시적 drop/backpressure | 종료 시 정책대로 drain 또는 discard |
| 내구성이 필요한 파일 저장 | partial write 처리 + 필요 시 sync | close만으로 요구 충족 여부 검토 |

## 16. 최종 점검 요약

1. raw pointer, `span`, 파일 디스크립터는 기본적으로 소유권을 자동 표현하지 않는다.
2. blocking I/O는 함수 반환이 해당 호출의 완료지만, completion 기반 async I/O는 완료·취소 완료까지 버퍼를 유지해야 한다.
3. readiness 알림은 완성된 메시지 하나가 도착했다는 뜻이 아니다.
4. callback 뒤 버퍼 유효성은 SDK 계약 없이는 가정하지 않는다.
5. borrowed callback buffer를 검사 스레드로 넘길 때는 복사하거나 공식 frame lease를 인수한다.
6. SDK가 만든 버퍼는 `delete`하지 않고 정확한 SDK release/requeue 함수를 사용한다.
7. 종료 때는 새 생산을 먼저 멈추고 callback을 정지시킨 뒤 queue를 닫고 worker를 join한다.
8. SDK frame이 모두 반납된 뒤 camera/stream/SDK를 파괴한다.
9. queue와 buffer pool에는 용량 상한과 overload 정책이 있어야 한다.
10. 특정 카메라에 적용하기 전 제조사 문서의 lifetime·threading·shutdown 계약을 다시 확인한다.
