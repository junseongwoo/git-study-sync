## 1. 프로그램, 프로세스, 스레드

### 1.1 프로그램

프로그램(program)은 디스크에 저장된 실행 파일과 정적 데이터의 묶음이다. 아직 실행되지 않은 수동적인 존재다.

### 1.2 프로세스

프로세스(process)는 **실행 중인 프로그램**이다. 실행 코드뿐 아니라 운영체제가 프로그램을 실행하기 위해 관리하는 환경 전체를 포함한다.

- 가상 주소 공간
- 코드와 전역 데이터
- 힙(heap)
- 하나 이상의 스택(stack)
- CPU 레지스터와 프로그램 카운터
- 프로세스 ID
- 열린 파일과 소켓
- 보안 권한
- 스케줄링 정보

같은 프로그램을 두 번 실행하더라도 서로 다른 프로세스가 생성된다. 두 프로세스는 같은 실행 파일을 사용하지만 서로 다른 주소 공간과 실행 상태를 갖는다.

### 1.3 스레드

스레드(thread)는 프로세스 안에서 실제로 명령어를 실행하는 흐름이다. 하나의 프로세스는 하나 이상의 스레드를 가질 수 있다.

같은 프로세스의 스레드들이 공유하는 것:

- 코드
- 전역 변수와 정적 변수
- 힙
- 열린 파일과 소켓
- 프로세스의 주소 공간

각 스레드가 별도로 갖는 것:

- 프로그램 카운터
- CPU 레지스터
- 스택
- 스레드 ID
- 스레드 지역 저장소
- 실행 및 스케줄링 상태

### 1.4 프로세스와 스레드 비교

| 구분 | 프로세스 사이 | 같은 프로세스의 스레드 사이 |
|---|---|---|
| 가상 주소 공간 | 기본적으로 분리하되 공유 메모리 매핑 가능 | 공유 |
| 전역 변수와 힙 | 분리 | 공유 |
| 스택 | 프로세스별 분리 | 스레드별 분리 |
| 열린 파일 | 기본적으로 별도 관리하나 `fork()` 시 파일 디스크립터가 상속될 수 있음 | 프로세스의 파일 디스크립터 테이블 공유 |
| 데이터 교환 | IPC 필요 | 공유 메모리로 간단 |
| 생성 및 전환 비용 | 상대적으로 큼 | 상대적으로 작음 |
| 장애 격리 | 좋음 | 나쁨 |
| 주요 위험 | IPC 복잡성 | 데이터 경쟁과 교착 상태 |

> [!important]
> 현대 운영체제에서 프로세스는 주로 **자원과 보호의 단위**, 커널 스레드는 **CPU 스케줄링의 단위**로 사용된다.

> [!warning] 파일 공유의 함정
> 같은 프로세스의 스레드는 파일 디스크립터를 공유한다. 여러 스레드가 같은 파일 객체의 현재 오프셋을 동시에 변경하면 예상하지 못한 위치를 읽거나 쓸 수 있으므로 별도의 동기화 또는 위치 기반 I/O가 필요할 수 있다.

## 2. 병행성과 병렬성

### 2.1 병행성

병행성(concurrency)은 여러 작업의 실행 시간이 겹치는 성질이다. CPU가 하나여도 운영체제가 작업을 빠르게 번갈아 실행하면 병행성이 생긴다.

```text
시간 ───────────────────────────────>
CPU  [스레드 A][스레드 B][스레드 A][스레드 B]
```

### 2.2 병렬성

병렬성(parallelism)은 여러 CPU 코어에서 실제로 작업이 동시에 실행되는 것이다.

```text
CPU 0 [────────── 스레드 A ──────────]
CPU 1 [────────── 스레드 B ──────────]
```

멀티스레드 프로그램이라고 반드시 병렬 실행되는 것은 아니다. 실제 병렬 실행 여부는 CPU 코어 수, 운영체제 스케줄링, 다른 작업의 부하에 따라 달라진다.

## 3. 프로세스 상태

대표적인 프로세스 상태는 다음과 같다.

- **New**: 프로세스가 생성되는 중
- **Ready**: CPU가 할당되면 실행할 수 있는 상태
- **Running**: CPU에서 실행 중
- **Waiting/Blocked**: I/O 완료나 특정 사건을 기다리는 상태
- **Terminated**: 실행이 끝난 상태

```text
                  CPU 할당
          Ready ───────────> Running
            ^                   |
            |                   | I/O 요청 또는 조건 대기
            |                   v
            +─────────────── Waiting
                    I/O 완료

Running ── 선점 또는 타임 슬라이스 만료 ──> Ready
Running ── 정상 종료 또는 오류 ───────────> Terminated
```

### 3.1 Ready와 Waiting의 차이

- Ready 상태는 CPU만 받으면 즉시 실행할 수 있다.
- Waiting 상태는 CPU를 받아도 실행할 수 없다. I/O 완료나 특정 조건 충족이 먼저 필요하다.

## 4. PCB와 문맥 교환

### 4.1 PCB

운영체제는 각 프로세스의 정보를 PCB(Process Control Block)에 저장한다.

- 현재 상태
- 프로그램 카운터
- CPU 레지스터
- 스케줄링 우선순위
- 메모리 관리 정보
- 열린 파일 정보
- CPU 사용량
- 부모와 자식 관계

스레드의 실행 문맥은 TCB(Thread Control Block) 또는 운영체제의 태스크 구조체에 저장할 수 있다.

### 4.2 문맥 교환

문맥 교환(context switch)은 현재 실행 중인 스레드의 실행 문맥을 저장하고 다른 스레드의 문맥을 복원하는 과정이다.

1. 현재 프로그램 카운터와 레지스터를 저장한다.
2. 현재 스레드의 상태를 변경한다.
3. 스케줄러가 다음 스레드를 선택한다.
4. 선택된 스레드의 레지스터와 실행 위치를 복원한다.
5. 해당 스레드의 실행을 재개한다.

문맥 교환은 응용 프로그램의 작업을 직접 진행하지 않는 오버헤드다. 프로세스 사이의 전환은 주소 공간, 페이지 테이블, TLB 및 캐시에 영향을 주므로 같은 프로세스 내 스레드 전환보다 일반적으로 무겁다.

> [!warning]
> 스레드 전환도 무료가 아니다. 캐시 손실, 커널 진입, 코어 이동, 락 경합으로 비용이 커질 수 있다.

## 5. 제한적 직접 실행

운영체제는 성능을 위해 사용자 프로그램의 명령어를 CPU에서 직접 실행한다. 하지만 프로그램에 CPU 전체 권한을 주면 시스템 보호와 제어가 불가능하다.

이를 해결하는 핵심 장치는 다음과 같다.

- 사용자 모드와 커널 모드
- 시스템 콜
- trap 명령
- 인터럽트
- 타이머 인터럽트

### 5.1 시스템 콜

프로그램이 파일 읽기, 프로세스 생성, 네트워크 통신 같은 특권 작업을 요청하면 시스템 콜을 사용한다.

```text
사용자 코드
   │
   │ 시스템 콜
   v
trap 명령 실행
   │
   v
커널 모드의 시스템 콜 처리기
   │
   v
return-from-trap
   │
   v
사용자 코드로 복귀
```

### 5.2 타이머 인터럽트

프로세스가 자발적으로 CPU를 반환하지 않더라도 타이머 인터럽트가 발생하면 운영체제가 다시 제어권을 얻는다. 이를 통해 선점형 멀티태스킹이 가능해진다.

## 6. 프로세스 생성과 종료

Unix 계열 운영체제는 다음 API를 중심으로 프로세스를 관리한다.

- `fork()`: 현재 프로세스를 복제해 자식 프로세스를 생성한다.
- `exec()`: 현재 프로세스의 프로그램과 주소 공간을 새 프로그램으로 교체한다.
- `wait()`/`waitpid()`: 부모가 자식의 종료를 기다리고 종료 상태를 회수한다.

`fork()` 이후에는 부모와 자식이 모두 다음 명령어부터 실행한다. 어느 프로세스가 먼저 실행될지는 운영체제 스케줄러가 결정한다.

### 6.1 C++와 POSIX 프로세스 예제

> [!note]
> C++ 표준 라이브러리에는 범용적인 프로세스 생성 기능이 없다. 다음 코드는 Linux, macOS 또는 WSL에서 사용하는 POSIX 예제다.

```cpp
#include <sys/types.h>
#include <sys/wait.h>
#include <unistd.h>

#include <cstring>
#include <iostream>

int main() {
    int fd[2];

    if (pipe(fd) == -1) {
        std::cerr << "pipe failed\n";
        return 1;
    }

    pid_t pid = fork();

    if (pid == -1) {
        std::cerr << "fork failed\n";
        return 1;
    }

    if (pid == 0) {
        close(fd[0]);

        const char* message = "message from child";
        write(fd[1], message, std::strlen(message));

        close(fd[1]);
        _exit(0);
    }

    close(fd[1]);

    char buffer[128]{};
    ssize_t size = read(fd[0], buffer, sizeof(buffer) - 1);

    if (size > 0) {
        std::cout << "parent received: " << buffer << '\n';
    }

    close(fd[0]);

    int status = 0;
    waitpid(pid, &status, 0);

    if (WIFEXITED(status)) {
        std::cout << "child exit status: "
                  << WEXITSTATUS(status) << '\n';
    }
}
```

```bash
g++ -std=c++20 -O2 process.cpp -o process
```

Windows에서는 `fork()` 대신 `CreateProcessW()`, 파이프에는 `CreatePipe()`를 사용한다.

## 7. 프로세스 간 통신

분리된 주소 공간을 가진 프로세스끼리 데이터를 교환하려면 IPC(Inter-Process Communication)가 필요하다.

### 7.1 공유 메모리

여러 프로세스가 동일한 물리 메모리를 각자의 주소 공간에 매핑한다.

장점:

- 대량 데이터 전달이 빠르다.
- 반복적인 커널 복사 비용을 줄일 수 있다.

단점:

- 별도의 동기화가 필요하다.
- 경쟁 조건과 데이터 손상이 발생할 수 있다.

### 7.2 메시지 전달

프로세스가 `send()`와 `receive()` 형태로 메시지를 주고받는다.

- 익명 파이프
- 이름 있는 파이프
- 메시지 큐
- Unix 도메인 소켓
- TCP/UDP 소켓

| 상황 | 적합한 방식 |
|---|---|
| 부모와 자식 사이의 단순 통신 | 파이프 |
| 같은 컴퓨터의 독립 서비스 | Unix 도메인 소켓 또는 named pipe |
| 원격 컴퓨터와 통신 | TCP/UDP |
| 매우 큰 데이터 공유 | 공유 메모리 + 동기화 도구 |

## 8. 멀티스레딩의 장점과 위험

### 8.1 장점

- **응답성**: 한 작업이 기다리는 동안 UI나 다른 요청을 처리한다.
- **자원 공유**: 같은 주소 공간을 사용하므로 데이터 교환이 간단하다.
- **경제성**: 프로세스보다 생성과 전환 비용이 작은 편이다.
- **확장성**: 여러 CPU 코어를 활용할 수 있다.
- **I/O 중첩**: 한 스레드가 I/O를 기다릴 때 다른 스레드가 실행된다.

### 8.2 위험

- 데이터 경쟁
- 원자성 위반
- 실행 순서 위반
- 교착 상태
- 기아
- 라이브락
- 스레드 과다 생성
- 캐시 경합과 false sharing

## 9. 사용자 스레드와 커널 스레드

### 9.1 사용자 스레드

사용자 스레드(user thread)는 사용자 공간의 스레드 라이브러리가 생성과 전환을 관리한다.

- 커널 진입 없이 전환할 수 있어 빠를 수 있다.
- 운영체제가 각 사용자 스레드를 직접 알지 못할 수 있다.
- 구현 모델에 따라 한 스레드의 블로킹 시스템 콜이 프로세스 전체를 멈출 수 있다.

### 9.2 커널 스레드

커널 스레드(kernel thread)는 운영체제가 직접 관리하고 스케줄링한다.

- 한 스레드가 블로킹되어도 같은 프로세스의 다른 스레드를 실행할 수 있다.
- 여러 CPU 코어에서 실제 병렬 실행할 수 있다.
- 생성과 전환에 커널의 관리 비용이 든다.

### 9.3 매핑 모델

| 모델 | 구조 | 장점 | 단점 |
|---|---|---|---|
| 다대일 | 여러 사용자 스레드 → 하나의 커널 스레드 | 사용자 공간에서 관리가 빠름 | 한 스레드가 블로킹되면 전체가 멈출 수 있고 멀티코어 병렬성이 제한됨 |
| 일대일 | 사용자 스레드 하나 → 커널 스레드 하나 | 블로킹 격리와 멀티코어 병렬 실행 | 스레드 수가 많으면 커널 관리 비용 증가 |
| 다대다 | 여러 사용자 스레드 → 여러 커널 스레드 | 병렬성과 사용자 수준 관리의 유연성 | 런타임과 운영체제 구현이 복잡 |
| 2단계 | 다대다 + 일부 사용자/커널 스레드 고정 | 특정 작업에 커널 실행 단위를 보장 | 구현 복잡성 증가 |

현대 데스크톱 운영체제에서 `std::thread`는 일반적으로 네이티브 커널 스레드와 연결된다. 다만 정확한 구현 세부 사항은 C++ 표준이 아니라 표준 라이브러리와 운영체제가 결정한다.

## 10. 스레드 생명주기와 암시적 스레딩

### 10.1 생성, 합류, 분리

- 생성: 새 실행 흐름과 스택을 준비한다.
- `join()`: 다른 스레드의 종료를 기다리고 실행 결과의 가시성을 확보한다.
- `detach()`: 스레드를 독립 실행시키지만 수명과 자원 관리가 어려워진다.

`std::thread` 객체가 join 가능한 상태로 파괴되면 `std::terminate()`가 호출된다. 직접 수명 관리를 해야 한다면 모든 경로에서 `join()` 또는 `detach()`가 호출되어야 한다. C++20에서는 자동 합류하는 `std::jthread`를 우선 고려한다.

### 10.2 fork와 멀티스레드 프로세스

POSIX 멀티스레드 프로세스가 `fork()`를 호출하면 자식에는 호출한 스레드만 복제된다. 다른 스레드가 보유하던 mutex 상태는 복사되지만 해당 스레드는 자식에 존재하지 않으므로 교착 상태 위험이 있다.

따라서 멀티스레드 프로그램에서 `fork()` 후 `exec()` 전까지는 POSIX가 허용한 async-signal-safe 함수만 사용하는 것이 원칙이다.

### 10.3 스레드 지역 저장소

모든 스레드가 공유할 필요가 없는 상태는 `thread_local`로 분리할 수 있다.

```cpp
thread_local unsigned request_count = 0;

void handle_request() {
    ++request_count; // 현재 스레드만의 값
}
```

`thread_local`은 데이터 경쟁을 줄일 수 있지만, 모든 스레드의 값을 합산하거나 일관되게 초기화·정리하는 설계가 추가로 필요할 수 있다.

### 10.4 스레드 풀과 작업 기반 병렬성

작업마다 새 스레드를 만들면 생성·파괴 비용과 문맥 교환이 증가한다. 스레드 풀은 제한된 수의 작업자 스레드가 큐에서 작업을 가져가도록 한다.

```text
작업 제출자 ──> [공유 작업 큐] ──> 작업자 스레드 1
                                 ├─> 작업자 스레드 2
                                 └─> 작업자 스레드 N
```

관련 모델에는 스레드 풀, fork-join, OpenMP, 작업 스케줄러, Grand Central Dispatch 등이 있다. 핵심은 **스레드 자체보다 수행할 작업을 표현하고 런타임이 실행 자원을 관리하게 하는 것**이다.

### 10.5 취소, 신호와 예외

- 스레드 취소는 자원과 불변식을 안전하게 정리할 수 있는 협력적 방식이 좋다.
- POSIX 신호는 프로세스 전체 또는 특정 스레드에 전달될 수 있어 신호 마스크 설계가 필요하다.
- 한 C++ 스레드에서 처리되지 않은 예외가 스레드 함수 밖으로 빠져나가면 `std::terminate()`가 호출된다. 필요한 경우 스레드 내부에서 예외를 잡아 `std::exception_ptr`, `std::promise` 또는 `std::future`로 전달한다.

## 11. C++ 스레드 생성

C++20에서는 `std::jthread`를 사용할 수 있다. `std::thread`와 달리 소멸 시 자동으로 `join()`하고, 협력적 취소를 위한 중지 토큰도 지원한다.

```cpp
#include <algorithm>
#include <iostream>
#include <numeric>
#include <thread>
#include <vector>

int main() {
    std::vector<int> values(1'000'000, 1);

    unsigned count =
        std::max(1u, std::thread::hardware_concurrency());

    count = std::min<unsigned>(count, values.size());

    std::vector<long long> partial(count);

    {
        std::vector<std::jthread> workers;
        workers.reserve(count);

        for (unsigned t = 0; t < count; ++t) {
            std::size_t begin = values.size() * t / count;
            std::size_t end = values.size() * (t + 1) / count;

            workers.emplace_back([&, t, begin, end] {
                partial[t] = std::accumulate(
                    values.begin() + begin,
                    values.begin() + end,
                    0LL
                );
            });
        }
    } // 모든 jthread가 join된다.

    long long total =
        std::accumulate(partial.begin(), partial.end(), 0LL);

    std::cout << total << '\n';
}
```

각 스레드는 서로 다른 `partial[t]`만 변경하므로 논리적인 데이터 경쟁이 없다.

> [!warning]
> `std::thread::hardware_concurrency()`는 하드웨어 스레드 수에 대한 힌트일 뿐이다. `0`을 반환할 수 있으며, 반환된 수만큼 스레드를 생성하는 것이 항상 가장 빠르다는 뜻도 아니다.

## 12. CPU 스케줄링

운영체제의 스케줄러는 준비 상태인 프로세스나 스레드 중 다음 실행 대상을 선택한다.

### 12.1 스케줄링이 일어나는 시점

스케줄링 결정은 다음과 같은 상태 전이에서 일어난다.

- Running → Waiting: I/O 요청, 조건 대기
- Running → Ready: 타이머 인터럽트에 의한 선점
- Waiting → Ready: I/O 또는 사건 완료
- Running → Terminated: 작업 종료

비선점형 스케줄링은 실행 중인 작업이 스스로 CPU를 반환할 때까지 기다린다. 선점형 스케줄링은 타이머 인터럽트 등을 이용해 운영체제가 실행 중인 작업의 CPU를 회수할 수 있다.

스케줄러가 작업을 선택한 뒤 디스패처(dispatcher)가 문맥 교환, 사용자 모드 전환, 올바른 명령어 위치로의 이동을 수행한다. 실행 중단부터 새 작업이 실제로 실행될 때까지의 시간을 dispatch latency라고 한다.

### 12.2 주요 평가 기준

- CPU 이용률
- 처리량
- 반환 시간
- 대기 시간
- 응답 시간
- 공정성
- 예측 가능성

주요 시간은 다음처럼 구분한다.

```text
반환 시간 = 완료 시각 - 도착 시각
응답 시간 = 최초 실행 시각 - 도착 시각
대기 시간 = 준비 큐에서 기다린 시간의 합
```

### 12.3 대표 알고리즘

| 정책 | 핵심 | 장점 | 단점 |
|---|---|---|---|
| FCFS/FIFO | 도착 순서대로 실행 | 단순함 | 긴 작업 때문에 짧은 작업이 밀릴 수 있음 |
| SJF | 가장 짧은 작업 우선 | 평균 반환 시간에 유리 | 실행 시간을 미리 알기 어려움 |
| SRTF | 남은 시간이 짧은 작업 선점 | 짧은 작업에 유리 | 긴 작업의 기아 가능 |
| Round Robin | 일정 시간씩 순환 | 응답성이 좋음 | 퀀텀이 작으면 문맥 교환 증가 |
| Priority | 높은 우선순위부터 실행 | 중요 작업 우대 | 낮은 우선순위의 기아 가능 |
| MLFQ | 과거 행동으로 우선순위 변경 | 대화형 작업에 빠른 응답 | 정책과 매개변수가 복잡함 |
| 비례 배분 | CPU 지분을 비율로 배분 | 자원 비율을 보장 | 정확한 비율 유지 비용 |
| 실시간 스케줄링 | 마감 시간 중심 | 시간 제약 처리 | 분석과 보장이 어려움 |

우선순위가 낮은 작업의 기아는 오래 기다린 작업의 우선순위를 올리는 aging으로 완화할 수 있다.

#### MLFQ 핵심 규칙

MLFQ(Multi-Level Feedback Queue)는 작업의 미래 실행 시간을 알 수 없다는 문제를 과거 행동으로 근사한다.

1. 우선순위가 높은 큐의 작업을 먼저 실행한다.
2. 같은 큐에서는 보통 Round Robin을 사용한다.
3. 새 작업은 높은 우선순위에서 시작한다.
4. CPU를 오래 사용한 작업은 낮은 큐로 이동한다.
5. 오래 기다린 작업은 주기적인 priority boost로 기아를 방지한다.
6. 타임 슬라이스가 끝나기 직전에 I/O를 요청하는 방식으로 우선순위를 독점하지 못하도록 누적 CPU 사용량을 계산한다.

### 12.4 멀티프로세서 스케줄링

멀티코어에서는 단순히 다음 작업을 고르는 것 외에 다음 문제가 추가된다.

- **캐시 친화성**: 이전에 실행한 코어에서 다시 실행하면 따뜻한 캐시를 활용할 수 있다.
- **프로세서 affinity**: 작업을 특정 코어 또는 코어 집합에 묶는다.
- **부하 균등화**: 코어별 실행 큐의 부하를 맞춘다.
- **push migration**: 바쁜 코어의 작업을 다른 코어로 밀어낸다.
- **pull migration/work stealing**: 빈 코어가 다른 큐의 작업을 가져온다.
- **NUMA**: 메모리가 가까운 CPU에서 실행해야 원격 메모리 접근을 줄일 수 있다.
- **SMT**: 하나의 물리 코어가 여러 하드웨어 실행 문맥을 제공하므로 논리 CPU 수와 실제 코어 수가 다를 수 있다.

CPU 중심 작업은 무작정 스레드를 늘리기보다 코어 수와 측정 결과를 기준으로 제한한다. I/O 중심 작업은 대기 시간 때문에 더 많은 동시 작업이 유리할 수 있지만 스레드 과다 생성은 메모리와 문맥 교환 비용을 증가시킨다.

### 12.5 실시간 스케줄링

- Rate-Monotonic은 주기가 짧은 주기 작업에 더 높은 고정 우선순위를 준다.
- Earliest-Deadline-First는 마감 시간이 가장 가까운 작업을 동적으로 먼저 실행한다.
- soft real-time은 지연을 최소화하지만 마감 준수를 절대 보장하지 않는다.
- hard real-time은 최악 실행 시간과 자원 요구량을 분석하여 마감 준수를 보장해야 한다.

### 12.6 C++에서 주의할 점

```cpp
std::thread a(taskA);
std::thread b(taskB);
```

이 코드에서 `taskA()`가 `taskB()`보다 먼저 실행된다는 보장은 없다. 실행 순서를 정해야 한다면 스케줄러의 우연한 선택이 아니라 `join()`, 조건 변수, future 등의 동기화 도구를 사용해야 한다.

스레드 우선순위와 CPU affinity는 표준 C++ 기능이 아니다. 프로그램의 정확성을 특정 우선순위나 affinity에 의존시키면 안 된다.

## 13. 경쟁 조건과 원자성

다음 코드는 안전하지 않다.

```cpp
int counter = 0;

void work() {
    for (int i = 0; i < 100'000; ++i) {
        ++counter;
    }
}
```

`++counter`는 개념적으로 다음 연산으로 분리된다.

1. `counter`를 레지스터로 읽는다.
2. 값을 1 증가시킨다.
3. 결과를 메모리에 저장한다.

두 스레드가 같은 값을 읽은 뒤 각각 증가시켜 저장하면 증가 연산 하나가 사라질 수 있다.

> [!important]
> C++에서 동기화되지 않은 데이터 경쟁은 단순히 결과가 부정확해지는 문제가 아니라 **undefined behavior**다.

### 13.1 mutex 사용

```cpp
#include <mutex>

int counter = 0;
std::mutex counter_mutex;

void work() {
    for (int i = 0; i < 100'000; ++i) {
        std::lock_guard lock(counter_mutex);
        ++counter;
    }
}
```

`std::lock_guard`는 범위를 벗어날 때 자동으로 mutex를 해제한다. 예외나 조기 `return`이 발생할 수 있으므로 수동 `lock()`과 `unlock()`보다 안전하다.

### 13.2 atomic 사용

```cpp
#include <atomic>

std::atomic<int> counter{0};

void work() {
    for (int i = 0; i < 100'000; ++i) {
        counter.fetch_add(1, std::memory_order_relaxed);
    }
}
```

독립적인 통계 카운터처럼 최종 숫자의 원자성만 필요하다면 `memory_order_relaxed`를 사용할 수 있다. 다른 데이터의 공개와 실행 순서까지 전달해야 한다면 acquire/release 또는 기본 순차 일관성을 검토해야 한다.

`std::atomic`이라고 항상 lock-free인 것은 아니다.

### 13.3 volatile은 동기화가 아니다

`volatile`은 멀티스레드 원자성과 실행 순서를 제공하지 않는다. `volatile int counter`로 바꿔도 위의 경쟁 조건은 해결되지 않는다.

### 13.4 C++ 메모리 모델과 happens-before

C++에서 데이터 경쟁은 다음 조건을 만족하는 두 메모리 접근이 있을 때 발생한다.

- 서로 다른 스레드에서 실행된다.
- 같은 메모리 위치에 접근한다.
- 하나 이상이 쓰기다.
- 두 접근이 원자 연산이 아니며 happens-before 관계로 정렬되지 않는다.

대표적인 happens-before 관계:

- 스레드를 시작하기 전에 수행한 작업은 새 스레드가 시작한 후 관찰할 수 있다.
- 스레드 안의 작업은 성공한 `join()` 이후의 코드보다 앞선다.
- mutex의 `unlock()`은 같은 mutex를 이후에 성공적으로 획득한 `lock()`보다 앞선다.
- release 저장은 그 값을 읽은 acquire 읽기보다 앞선다.

```cpp
#include <atomic>
#include <cassert>
#include <string>
#include <thread>

std::string payload;
std::atomic<bool> ready{false};

void producer() {
    payload = "complete";
    ready.store(true, std::memory_order_release);
}

void consumer() {
    while (!ready.load(std::memory_order_acquire)) {
        std::this_thread::yield();
    }

    assert(payload == "complete");
}
```

release/acquire는 `ready` 자체의 원자성뿐 아니라 `payload` 기록의 가시성도 전달한다. 단순 카운터에 사용한 `memory_order_relaxed`에는 이런 데이터 공개 기능이 없다.

> [!tip]
> 메모리 순서를 정확히 증명해야 하는 특별한 이유가 없다면 먼저 mutex나 기본 원자 메모리 순서를 사용한다. 성능 측정 없이 약한 메모리 순서를 선택하면 이해하기 어려운 버그만 늘어날 수 있다.

## 14. 임계 영역과 락

임계 영역(critical section)은 여러 스레드가 동시에 실행하면 공유 상태가 손상될 수 있는 코드 구간이다.

올바른 임계 영역 해법이 가져야 할 성질:

- **상호 배제**: 한 번에 하나의 스레드만 진입한다.
- **진행**: 임계 영역이 비어 있을 때 진입 결정이 무한히 지연되지 않는다.
- **한정 대기**: 특정 스레드가 무한히 기다리지 않는다.

락 구현의 기반에는 다음과 같은 하드웨어 원자 명령이 있다.

- Test-And-Set
- Compare-And-Swap
- Fetch-And-Add
- Load-Linked/Store-Conditional

### 14.1 스핀 락

스핀 락은 락이 풀릴 때까지 반복 검사한다. 임계 영역이 매우 짧고 현재 소유자가 곧 실행될 것이 확실한 저수준 환경에서는 유용할 수 있다.

일반 응용 프로그램에서는 다음 문제가 발생하기 쉽다.

- 기다리는 동안 CPU를 계속 사용한다.
- 락 소유자가 선점되면 오랫동안 헛돌 수 있다.
- 스레드가 많을수록 메모리 버스와 캐시 경합이 커진다.

따라서 일반적인 C++ 응용 프로그램에서는 먼저 `std::mutex`를 고려한다.

### 14.2 락 기반 자료 구조

자료 구조에 락 하나를 추가했다고 모든 사용 방식이 자동으로 안전해지는 것은 아니다.

- **거친 락(coarse-grained lock)**: 자료 구조 전체를 하나의 락으로 보호한다. 정확성은 이해하기 쉽지만 병렬성이 낮다.
- **세밀한 락(fine-grained lock)**: 노드, 버킷 또는 영역별로 락을 둔다. 병렬성은 높지만 락 순서와 객체 수명 관리가 어려워진다.
- **분할 자료 구조**: 해시 테이블의 버킷별 락처럼 서로 독립적인 영역으로 경합을 분산한다.
- **지역 상태 + 주기적 병합**: CPU 또는 스레드별 카운터를 두고 일정 시점에 전역 값으로 합쳐 정확성과 성능을 절충한다.

개별 메서드가 thread-safe여도 여러 메서드의 조합은 원자적이지 않을 수 있다.

```cpp
if (!queue.empty()) { // 이 검사 직후 다른 스레드가 pop할 수 있음
    auto value = queue.front();
    queue.pop();
}
```

이런 연산은 `try_pop()`처럼 검사와 제거를 하나의 동기화된 메서드로 제공해야 한다.

인접한 스레드별 카운터는 서로 다른 객체여도 같은 캐시 라인에 놓여 false sharing을 일으킬 수 있다. 데이터 배치와 패딩은 정확성 문제가 아니라 성능 문제이며 반드시 측정 후 조정한다.

## 15. 조건 변수

조건 변수는 특정 상태가 될 때까지 스레드를 잠들게 한다.

- mutex: 공유 상태에 대한 상호 배제를 제공한다.
- condition variable: 공유 상태가 원하는 조건이 될 때까지 기다린다.

### 15.1 생산자-소비자 유한 버퍼

```cpp
#include <condition_variable>
#include <deque>
#include <mutex>
#include <optional>
#include <stdexcept>

template<class T>
class BoundedBlockingQueue {
public:
    explicit BoundedBlockingQueue(std::size_t capacity)
        : capacity_(capacity) {
        if (capacity_ == 0) {
            throw std::invalid_argument("capacity must be positive");
        }
    }

    bool push(T value) {
        std::unique_lock lock(mutex_);

        not_full_.wait(lock, [this] {
            return closed_ || queue_.size() < capacity_;
        });

        if (closed_) {
            return false;
        }

        queue_.push_back(std::move(value));
        lock.unlock();

        not_empty_.notify_one();
        return true;
    }

    std::optional<T> pop() {
        std::unique_lock lock(mutex_);

        not_empty_.wait(lock, [this] {
            return closed_ || !queue_.empty();
        });

        if (queue_.empty()) {
            return std::nullopt;
        }

        T value = std::move(queue_.front());
        queue_.pop_front();
        lock.unlock();

        not_full_.notify_one();
        return value;
    }

    void close() {
        {
            std::lock_guard lock(mutex_);
            closed_ = true;
        }

        not_empty_.notify_all();
        not_full_.notify_all();
    }

private:
    std::mutex mutex_;
    std::condition_variable not_empty_;
    std::condition_variable not_full_;
    std::deque<T> queue_;
    const std::size_t capacity_;
    bool closed_ = false;
};
```

이 예제에는 두 조건이 있다.

- 소비자는 큐가 비어 있지 않을 때까지 `not_empty_`에서 기다린다.
- 생산자는 큐에 빈자리가 생길 때까지 `not_full_`에서 기다린다.

`close()`는 양쪽 대기자를 모두 깨워 종료 조건을 다시 검사하게 한다. 알림 전에 mutex를 해제하면 깨어난 스레드가 곧바로 mutex를 획득할 가능성이 높아지지만, 상태 변경 자체는 반드시 mutex를 보유한 상태에서 수행해야 한다.

### 15.2 조건 변수 규칙

- 조건에 사용되는 상태를 같은 mutex로 보호한다.
- `if` 대신 predicate 또는 `while`로 조건을 다시 검사한다.
- 깨어났다고 조건이 반드시 참인 것은 아니다.
- `notify_one()` 자체는 프로그램 상태를 저장하지 않는다.
- `wait()`는 mutex를 원자적으로 해제하고 잠든다.
- 깨어날 때 `wait()`는 mutex를 다시 획득한 뒤 반환한다.

## 16. 세마포어

세마포어는 정수 카운터와 대기 큐로 동시 접근 수를 제어한다.

- `acquire()`/wait/P: 값이 양수이면 감소하고 진행하고, 아니면 대기한다.
- `release()`/post/V: 값을 증가시키고 필요한 경우 대기자를 깨운다.

초기값이 1이면 이진 세마포어처럼 사용할 수 있다. 초기값이 N이면 동시에 N개의 스레드만 자원에 접근하도록 제한한다.

```cpp
#include <semaphore>

std::counting_semaphore<3> connection_slots{3};

class Permit {
public:
    explicit Permit(std::counting_semaphore<3>& semaphore)
        : semaphore_(semaphore) {
        semaphore_.acquire();
    }

    ~Permit() {
        semaphore_.release();
    }

    Permit(const Permit&) = delete;
    Permit& operator=(const Permit&) = delete;

private:
    std::counting_semaphore<3>& semaphore_;
};

void use_server() {
    Permit permit(connection_slots);

    perform_request(); // 동시에 최대 3개만 실행
} // 정상 반환과 예외 모두 여기서 release
```

RAII 객체를 사용했기 때문에 `perform_request()`가 예외를 던져도 permit이 반환된다.

### 16.1 mutex와 세마포어 차이

- mutex에는 소유자 개념이 있다.
- 일반적으로 mutex를 획득한 스레드가 해제해야 한다.
- 세마포어의 `release()`는 다른 스레드가 호출할 수 있다.
- mutex는 상호 배제에 적합하다.
- 세마포어는 자원 개수 제한이나 스레드 간 사건 전달에 적합하다.

## 17. 교착 상태

교착 상태(deadlock)는 스레드들이 서로가 가진 자원을 기다리며 모두 진행하지 못하는 상태다.

### 17.1 Coffman의 네 조건

다음 네 조건이 동시에 성립하면 교착 상태가 발생할 수 있다.

1. **상호 배제**: 자원을 한 번에 하나의 스레드만 사용한다.
2. **점유하며 대기**: 자원을 가진 채 다른 자원을 기다린다.
3. **비선점**: 보유한 자원을 강제로 회수할 수 없다.
4. **환형 대기**: 스레드와 자원 사이에 원형 대기 관계가 존재한다.

### 17.2 교착 상태가 가능한 코드

```cpp
// 스레드 1
a.lock();
b.lock();

// 스레드 2
b.lock();
a.lock();
```

스레드 1이 `a`, 스레드 2가 `b`를 획득하면 서로 상대방의 락을 기다릴 수 있다.

### 17.3 std::scoped_lock 사용

```cpp
#include <mutex>

struct Account {
    int balance;
    std::mutex mutex;
};

void transfer(Account& from, Account& to, int amount) {
    if (&from == &to) {
        return;
    }

    std::scoped_lock lock(from.mutex, to.mutex);

    if (from.balance >= amount) {
        from.balance -= amount;
        to.balance += amount;
    }
}
```

`std::scoped_lock`은 여러 mutex를 교착 상태가 발생하지 않도록 획득한다.

### 17.4 교착 상태 방지 원칙

- 모든 락에 전역적인 획득 순서를 정한다.
- 락을 가진 채 I/O를 실행하지 않는다.
- 락을 가진 채 외부 콜백을 호출하지 않는다.
- 임계 영역을 짧게 유지한다.
- 중첩 락을 최소화한다.
- 여러 락은 `std::scoped_lock`으로 한꺼번에 획득한다.
- 필요한 경우 `try_lock()`과 재시도를 사용한다.
- 타임아웃은 근본적인 방지책보다 복구 수단으로 본다.

## 18. 교착 상태 이외의 병행성 오류

### 18.1 원자성 위반

함께 실행되어야 하는 연산 사이에 다른 스레드가 끼어드는 문제다.

```cpp
if (pointer != nullptr) {
    use(pointer);
}
```

검사와 사용 사이에 다른 스레드가 객체를 제거할 수 있다. 검사와 사용을 같은 mutex로 보호하거나 `std::shared_ptr`처럼 객체 수명을 안전하게 관리해야 한다.

### 18.2 순서 위반

A 작업이 B보다 먼저 실행되어야 하지만 그 순서가 강제되지 않은 문제다.

잘못된 방법:

```cpp
std::this_thread::sleep_for(std::chrono::milliseconds(100));
// 이제 다른 스레드가 끝났을 것이라고 추측
```

올바른 동기화 도구:

- `join()`
- `std::condition_variable`
- `std::future`와 `std::promise`
- `std::latch`
- `std::barrier`
- 메시지 큐

`sleep()`은 실행 순서를 보장하지 않는다.

## 19. 스레드 종료와 협력적 취소

스레드를 강제로 종료하면 다음 문제가 발생할 수 있다.

- mutex를 가진 채 종료
- 메모리와 파일 누수
- 자료 구조가 절반만 변경된 상태로 남음
- 프로그램의 불변식 훼손

C++20에서는 `std::jthread`와 `std::stop_token`을 이용한 협력적 취소를 사용할 수 있다.

```cpp
#include <chrono>
#include <thread>

using namespace std::chrono_literals;

int main() {
    std::jthread worker([](std::stop_token stop) {
        while (!stop.stop_requested()) {
            perform_one_unit();
        }

        cleanup();
    });

    std::this_thread::sleep_for(1s);
    worker.request_stop();
}
```

스레드가 무한 블로킹 I/O에서 기다리면 중지 요청을 확인하지 못할 수 있다. 이때는 타임아웃, 취소 가능한 I/O, 소켓 종료 같은 운영체제별 방법이 필요하다.

## 20. 프로세스와 스레드 선택 기준

### 프로세스가 적합한 경우

- 외부 코드나 플러그인을 격리해야 한다.
- 한 작업의 충돌이 전체 프로그램을 종료시키면 안 된다.
- 서로 다른 보안 권한이 필요하다.
- 독립 서비스로 배포해야 한다.
- 서로 다른 언어나 런타임을 사용한다.

### 스레드가 적합한 경우

- 큰 자료 구조를 자주 공유한다.
- 통신 지연이 작아야 한다.
- 하나의 작업을 여러 CPU 코어로 병렬화한다.
- 같은 응용 프로그램의 내부 작업이다.

### 이벤트 기반 구조가 적합한 경우

- 연결 수가 매우 많다.
- 각 요청이 주로 I/O를 기다린다.
- 작업이 짧고 블로킹 호출을 피할 수 있다.

실제 서버에서는 다음처럼 여러 모델을 조합할 수 있다.

```text
여러 프로세스
  └─ 프로세스마다 이벤트 루프
       └─ CPU 작업용 제한된 스레드 풀
```

## 22. 핵심 요약

1. 프로세스는 독립된 주소 공간과 자원을 가지며 장애 격리가 좋다.
2. 스레드는 프로세스의 자원을 공유하며 실행 문맥과 스택은 따로 가진다.
3. 운영체제는 타이머 인터럽트와 문맥 교환으로 CPU를 가상화한다.
4. 스케줄링 순서는 비결정적이므로 코드가 특정 실행 순서를 가정하면 안 된다.
5. 공유 데이터를 동기화하지 않고 읽고 쓰면 C++ 데이터 경쟁이 발생한다.
6. 단순 값의 원자적 변경에는 `std::atomic`을 사용할 수 있다.
7. 복합 불변식 보호에는 mutex가 필요하다.
8. 상태가 바뀔 때까지 기다리려면 조건 변수를 사용한다.
9. 자원의 동시 사용 개수를 제한하려면 세마포어를 사용할 수 있다.
10. 교착 상태는 락 순서를 통일하고 `std::scoped_lock`을 사용해 예방한다.
