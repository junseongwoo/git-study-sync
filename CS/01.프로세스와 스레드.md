## 1. 프로그램, 프로세스, 스레드

### 1.1 프로그램

프로그램(program)은 디스크에 저장된 실행 파일과 정적 데이터의 묶음이다. 아직 실행되지 않은 수동적인 존재다.

### 1.2 프로세스

프로세스(process)는 **실행 중인 프로그램**이다. 실행 코드뿐 아니라 운영체제가 프로그램을 실행하기 위해 관리하는 환경 전체를 포함한다.

- 가상 주소 공간
- 코드와 전역 데이터
- 힙(heap)
- 하나 이상의 스택(stack)
- CPU 레지스터와 프로그램 카운터
- 프로세스 ID
- 열린 파일과 소켓
- 보안 권한
- 스케줄링 정보

같은 프로그램을 두 번 실행하더라도 서로 다른 프로세스가 생성된다. 두 프로세스는 같은 실행 파일을 사용하지만 서로 다른 주소 공간과 실행 상태를 갖는다.

### 1.3 스레드

스레드(thread)는 프로세스 안에서 실제로 명령어를 실행하는 흐름이다. 하나의 프로세스는 하나 이상의 스레드를 가질 수 있다.

같은 프로세스의 스레드들이 공유하는 것:

- 코드
- 전역 변수와 정적 변수
- 힙
- 열린 파일과 소켓
- 프로세스의 주소 공간

각 스레드가 별도로 갖는 것:

- 프로그램 카운터
- CPU 레지스터
- 스택
- 스레드 ID
- 스레드 지역 저장소
- 실행 및 스케줄링 상태

### 1.4 프로세스와 스레드 비교

| 구분 | 프로세스 사이 | 같은 프로세스의 스레드 사이 |
|---|---|---|
| 가상 주소 공간 | 기본적으로 분리 | 공유 |
| 전역 변수와 힙 | 분리 | 공유 |
| 스택 | 프로세스별 분리 | 스레드별 분리 |
| 열린 파일 | 별개의 테이블 또는 IPC 필요 | 프로세스의 파일을 공유 |
| 데이터 교환 | IPC 필요 | 공유 메모리로 간단 |
| 생성 및 전환 비용 | 상대적으로 큼 | 상대적으로 작음 |
| 장애 격리 | 좋음 | 나쁨 |
| 주요 위험 | IPC 복잡성 | 데이터 경쟁과 교착 상태 |

> [!important]
> 현대 운영체제에서 프로세스는 주로 **자원과 보호의 단위**, 커널 스레드는 **CPU 스케줄링의 단위**로 사용된다.

## 2. 병행성과 병렬성

### 2.1 병행성

병행성(concurrency)은 여러 작업의 실행 시간이 겹치는 성질이다. CPU가 하나여도 운영체제가 작업을 빠르게 번갈아 실행하면 병행성이 생긴다.

```text
시간 ───────────────────────────────>
CPU  [스레드 A][스레드 B][스레드 A][스레드 B]
```

### 2.2 병렬성

병렬성(parallelism)은 여러 CPU 코어에서 실제로 작업이 동시에 실행되는 것이다.

```text
CPU 0 [────────── 스레드 A ──────────]
CPU 1 [────────── 스레드 B ──────────]
```

멀티스레드 프로그램이라고 반드시 병렬 실행되는 것은 아니다. 실제 병렬 실행 여부는 CPU 코어 수, 운영체제 스케줄링, 다른 작업의 부하에 따라 달라진다.

## 3. 프로세스 상태

대표적인 프로세스 상태는 다음과 같다.

- **New**: 프로세스가 생성되는 중
- **Ready**: CPU가 할당되면 실행할 수 있는 상태
- **Running**: CPU에서 실행 중
- **Waiting/Blocked**: I/O 완료나 특정 사건을 기다리는 상태
- **Terminated**: 실행이 끝난 상태

```text
                  CPU 할당
          Ready ───────────> Running
            ^                   |
            |                   | I/O 요청 또는 조건 대기
            |                   v
            +─────────────── Waiting
                    I/O 완료

Running ── 선점 또는 타임 슬라이스 만료 ──> Ready
Running ── 정상 종료 또는 오류 ───────────> Terminated
```

### 3.1 Ready와 Waiting의 차이

- Ready 상태는 CPU만 받으면 즉시 실행할 수 있다.
- Waiting 상태는 CPU를 받아도 실행할 수 없다. I/O 완료나 특정 조건 충족이 먼저 필요하다.

## 4. PCB와 문맥 교환

### 4.1 PCB

운영체제는 각 프로세스의 정보를 PCB(Process Control Block)에 저장한다.

- 현재 상태
- 프로그램 카운터
- CPU 레지스터
- 스케줄링 우선순위
- 메모리 관리 정보
- 열린 파일 정보
- CPU 사용량
- 부모와 자식 관계

스레드의 실행 문맥은 TCB(Thread Control Block) 또는 운영체제의 태스크 구조체에 저장할 수 있다.

### 4.2 문맥 교환

문맥 교환(context switch)은 현재 실행 중인 스레드의 실행 문맥을 저장하고 다른 스레드의 문맥을 복원하는 과정이다.

1. 현재 프로그램 카운터와 레지스터를 저장한다.
2. 현재 스레드의 상태를 변경한다.
3. 스케줄러가 다음 스레드를 선택한다.
4. 선택된 스레드의 레지스터와 실행 위치를 복원한다.
5. 해당 스레드의 실행을 재개한다.

문맥 교환은 응용 프로그램의 작업을 직접 진행하지 않는 오버헤드다. 프로세스 사이의 전환은 주소 공간, 페이지 테이블, TLB 및 캐시에 영향을 주므로 같은 프로세스 내 스레드 전환보다 일반적으로 무겁다.

> [!warning]
> 스레드 전환도 무료가 아니다. 캐시 손실, 커널 진입, 코어 이동, 락 경합으로 비용이 커질 수 있다.

## 5. 제한적 직접 실행

운영체제는 성능을 위해 사용자 프로그램의 명령어를 CPU에서 직접 실행한다. 하지만 프로그램에 CPU 전체 권한을 주면 시스템 보호와 제어가 불가능하다.

이를 해결하는 핵심 장치는 다음과 같다.

- 사용자 모드와 커널 모드
- 시스템 콜
- trap 명령
- 인터럽트
- 타이머 인터럽트

### 5.1 시스템 콜

프로그램이 파일 읽기, 프로세스 생성, 네트워크 통신 같은 특권 작업을 요청하면 시스템 콜을 사용한다.

```text
사용자 코드
   │
   │ 시스템 콜
   v
trap 명령 실행
   │
   v
커널 모드의 시스템 콜 처리기
   │
   v
return-from-trap
   │
   v
사용자 코드로 복귀
```

### 5.2 타이머 인터럽트

프로세스가 자발적으로 CPU를 반환하지 않더라도 타이머 인터럽트가 발생하면 운영체제가 다시 제어권을 얻는다. 이를 통해 선점형 멀티태스킹이 가능해진다.

## 6. 프로세스 생성과 종료

Unix 계열 운영체제는 다음 API를 중심으로 프로세스를 관리한다.

- `fork()`: 현재 프로세스를 복제해 자식 프로세스를 생성한다.
- `exec()`: 현재 프로세스의 프로그램과 주소 공간을 새 프로그램으로 교체한다.
- `wait()`/`waitpid()`: 부모가 자식의 종료를 기다리고 종료 상태를 회수한다.

`fork()` 이후에는 부모와 자식이 모두 다음 명령어부터 실행한다. 어느 프로세스가 먼저 실행될지는 운영체제 스케줄러가 결정한다.

### 6.1 C++와 POSIX 프로세스 예제

> [!note]
> C++ 표준 라이브러리에는 범용적인 프로세스 생성 기능이 없다. 다음 코드는 Linux, macOS 또는 WSL에서 사용하는 POSIX 예제다.

```cpp
#include <sys/types.h>
#include <sys/wait.h>
#include <unistd.h>

#include <cstring>
#include <iostream>

int main() {
    int fd[2];

    if (pipe(fd) == -1) {
        std::cerr << "pipe failed\n";
        return 1;
    }

    pid_t pid = fork();

    if (pid == -1) {
        std::cerr << "fork failed\n";
        return 1;
    }

    if (pid == 0) {
        close(fd[0]);

        const char* message = "message from child";
        write(fd[1], message, std::strlen(message));

        close(fd[1]);
        _exit(0);
    }

    close(fd[1]);

    char buffer[128]{};
    ssize_t size = read(fd[0], buffer, sizeof(buffer) - 1);

    if (size > 0) {
        std::cout << "parent received: " << buffer << '\n';
    }

    close(fd[0]);

    int status = 0;
    waitpid(pid, &status, 0);

    if (WIFEXITED(status)) {
        std::cout << "child exit status: "
                  << WEXITSTATUS(status) << '\n';
    }
}
```

```bash
g++ -std=c++20 -O2 process.cpp -o process
```

Windows에서는 `fork()` 대신 `CreateProcessW()`, 파이프에는 `CreatePipe()`를 사용한다.

## 7. 프로세스 간 통신

분리된 주소 공간을 가진 프로세스끼리 데이터를 교환하려면 IPC(Inter-Process Communication)가 필요하다.

### 7.1 공유 메모리

여러 프로세스가 동일한 물리 메모리를 각자의 주소 공간에 매핑한다.

장점:

- 대량 데이터 전달이 빠르다.
- 반복적인 커널 복사 비용을 줄일 수 있다.

단점:

- 별도의 동기화가 필요하다.
- 경쟁 조건과 데이터 손상이 발생할 수 있다.

### 7.2 메시지 전달

프로세스가 `send()`와 `receive()` 형태로 메시지를 주고받는다.

- 익명 파이프
- 이름 있는 파이프
- 메시지 큐
- Unix 도메인 소켓
- TCP/UDP 소켓

| 상황 | 적합한 방식 |
|---|---|
| 부모와 자식 사이의 단순 통신 | 파이프 |
| 같은 컴퓨터의 독립 서비스 | Unix 도메인 소켓 또는 named pipe |
| 원격 컴퓨터와 통신 | TCP/UDP |
| 매우 큰 데이터 공유 | 공유 메모리 + 동기화 도구 |

## 8. 멀티스레딩의 장점과 위험

### 8.1 장점

- **응답성**: 한 작업이 기다리는 동안 UI나 다른 요청을 처리한다.
- **자원 공유**: 같은 주소 공간을 사용하므로 데이터 교환이 간단하다.
- **경제성**: 프로세스보다 생성과 전환 비용이 작은 편이다.
- **확장성**: 여러 CPU 코어를 활용할 수 있다.
- **I/O 중첩**: 한 스레드가 I/O를 기다릴 때 다른 스레드가 실행된다.

### 8.2 위험

- 데이터 경쟁
- 원자성 위반
- 실행 순서 위반
- 교착 상태
- 기아
- 라이브락
- 스레드 과다 생성
- 캐시 경합과 false sharing

## 9. C++ 스레드 생성

C++20에서는 `std::jthread`를 사용할 수 있다. `std::thread`와 달리 소멸 시 자동으로 `join()`하고, 협력적 취소를 위한 중지 토큰도 지원한다.

```cpp
#include <algorithm>
#include <iostream>
#include <numeric>
#include <thread>
#include <vector>

int main() {
    std::vector<int> values(1'000'000, 1);

    unsigned count =
        std::max(1u, std::thread::hardware_concurrency());

    count = std::min<unsigned>(count, values.size());

    std::vector<long long> partial(count);

    {
        std::vector<std::jthread> workers;
        workers.reserve(count);

        for (unsigned t = 0; t < count; ++t) {
            std::size_t begin = values.size() * t / count;
            std::size_t end = values.size() * (t + 1) / count;

            workers.emplace_back([&, t, begin, end] {
                partial[t] = std::accumulate(
                    values.begin() + begin,
                    values.begin() + end,
                    0LL
                );
            });
        }
    } // 모든 jthread가 join된다.

    long long total =
        std::accumulate(partial.begin(), partial.end(), 0LL);

    std::cout << total << '\n';
}
```

각 스레드는 서로 다른 `partial[t]`만 변경하므로 논리적인 데이터 경쟁이 없다.

> [!warning]
> `std::thread::hardware_concurrency()`는 하드웨어 스레드 수에 대한 힌트일 뿐이다. `0`을 반환할 수 있으며, 반환된 수만큼 스레드를 생성하는 것이 항상 가장 빠르다는 뜻도 아니다.

## 10. CPU 스케줄링

운영체제의 스케줄러는 준비 상태인 프로세스나 스레드 중 다음 실행 대상을 선택한다.

### 10.1 주요 평가 기준

- CPU 이용률
- 처리량
- 반환 시간
- 대기 시간
- 응답 시간
- 공정성
- 예측 가능성

### 10.2 대표 알고리즘

| 정책 | 핵심 | 장점 | 단점 |
|---|---|---|---|
| FCFS/FIFO | 도착 순서대로 실행 | 단순함 | 긴 작업 때문에 짧은 작업이 밀릴 수 있음 |
| SJF | 가장 짧은 작업 우선 | 평균 반환 시간에 유리 | 실행 시간을 미리 알기 어려움 |
| SRTF | 남은 시간이 짧은 작업 선점 | 짧은 작업에 유리 | 긴 작업의 기아 가능 |
| Round Robin | 일정 시간씩 순환 | 응답성이 좋음 | 퀀텀이 작으면 문맥 교환 증가 |
| Priority | 높은 우선순위부터 실행 | 중요 작업 우대 | 낮은 우선순위의 기아 가능 |
| MLFQ | 과거 행동으로 우선순위 변경 | 대화형 작업에 빠른 응답 | 정책과 매개변수가 복잡함 |
| 비례 배분 | CPU 지분을 비율로 배분 | 자원 비율을 보장 | 정확한 비율 유지 비용 |
| 실시간 스케줄링 | 마감 시간 중심 | 시간 제약 처리 | 분석과 보장이 어려움 |

우선순위가 낮은 작업의 기아는 오래 기다린 작업의 우선순위를 올리는 aging으로 완화할 수 있다.

### 10.3 C++에서 주의할 점

```cpp
std::thread a(taskA);
std::thread b(taskB);
```

이 코드에서 `taskA()`가 `taskB()`보다 먼저 실행된다는 보장은 없다. 실행 순서를 정해야 한다면 스케줄러의 우연한 선택이 아니라 `join()`, 조건 변수, future 등의 동기화 도구를 사용해야 한다.

스레드 우선순위와 CPU affinity는 표준 C++ 기능이 아니다. 프로그램의 정확성을 특정 우선순위나 affinity에 의존시키면 안 된다.

## 11. 경쟁 조건과 원자성

다음 코드는 안전하지 않다.

```cpp
int counter = 0;

void work() {
    for (int i = 0; i < 100'000; ++i) {
        ++counter;
    }
}
```

`++counter`는 개념적으로 다음 연산으로 분리된다.

1. `counter`를 레지스터로 읽는다.
2. 값을 1 증가시킨다.
3. 결과를 메모리에 저장한다.

두 스레드가 같은 값을 읽은 뒤 각각 증가시켜 저장하면 증가 연산 하나가 사라질 수 있다.

> [!important]
> C++에서 동기화되지 않은 데이터 경쟁은 단순히 결과가 부정확해지는 문제가 아니라 **undefined behavior**다.

### 11.1 mutex 사용

```cpp
#include <mutex>

int counter = 0;
std::mutex counter_mutex;

void work() {
    for (int i = 0; i < 100'000; ++i) {
        std::lock_guard lock(counter_mutex);
        ++counter;
    }
}
```

`std::lock_guard`는 범위를 벗어날 때 자동으로 mutex를 해제한다. 예외나 조기 `return`이 발생할 수 있으므로 수동 `lock()`과 `unlock()`보다 안전하다.

### 11.2 atomic 사용

```cpp
#include <atomic>

std::atomic<int> counter{0};

void work() {
    for (int i = 0; i < 100'000; ++i) {
        counter.fetch_add(1, std::memory_order_relaxed);
    }
}
```

독립적인 통계 카운터처럼 최종 숫자의 원자성만 필요하다면 `memory_order_relaxed`를 사용할 수 있다. 다른 데이터의 공개와 실행 순서까지 전달해야 한다면 acquire/release 또는 기본 순차 일관성을 검토해야 한다.

`std::atomic`이라고 항상 lock-free인 것은 아니다.

### 11.3 volatile은 동기화가 아니다

`volatile`은 멀티스레드 원자성과 실행 순서를 제공하지 않는다. `volatile int counter`로 바꿔도 위의 경쟁 조건은 해결되지 않는다.

## 12. 임계 영역과 락

임계 영역(critical section)은 여러 스레드가 동시에 실행하면 공유 상태가 손상될 수 있는 코드 구간이다.

올바른 임계 영역 해법이 가져야 할 성질:

- **상호 배제**: 한 번에 하나의 스레드만 진입한다.
- **진행**: 임계 영역이 비어 있을 때 진입 결정이 무한히 지연되지 않는다.
- **한정 대기**: 특정 스레드가 무한히 기다리지 않는다.

락 구현의 기반에는 다음과 같은 하드웨어 원자 명령이 있다.

- Test-And-Set
- Compare-And-Swap
- Fetch-And-Add
- Load-Linked/Store-Conditional

### 12.1 스핀 락

스핀 락은 락이 풀릴 때까지 반복 검사한다. 임계 영역이 매우 짧고 현재 소유자가 곧 실행될 것이 확실한 저수준 환경에서는 유용할 수 있다.

일반 응용 프로그램에서는 다음 문제가 발생하기 쉽다.

- 기다리는 동안 CPU를 계속 사용한다.
- 락 소유자가 선점되면 오랫동안 헛돌 수 있다.
- 스레드가 많을수록 메모리 버스와 캐시 경합이 커진다.

따라서 일반적인 C++ 응용 프로그램에서는 먼저 `std::mutex`를 고려한다.

## 13. 조건 변수

조건 변수는 특정 상태가 될 때까지 스레드를 잠들게 한다.

- mutex: 공유 상태에 대한 상호 배제를 제공한다.
- condition variable: 공유 상태가 원하는 조건이 될 때까지 기다린다.

### 13.1 생산자-소비자 큐

```cpp
#include <condition_variable>
#include <deque>
#include <mutex>
#include <optional>

template<class T>
class BlockingQueue {
public:
    void push(T value) {
        {
            std::lock_guard lock(mutex_);

            if (closed_) {
                return;
            }

            queue_.push_back(std::move(value));
        }

        not_empty_.notify_one();
    }

    std::optional<T> pop() {
        std::unique_lock lock(mutex_);

        not_empty_.wait(lock, [this] {
            return closed_ || !queue_.empty();
        });

        if (queue_.empty()) {
            return std::nullopt;
        }

        T value = std::move(queue_.front());
        queue_.pop_front();
        return value;
    }

    void close() {
        {
            std::lock_guard lock(mutex_);
            closed_ = true;
        }

        not_empty_.notify_all();
    }

private:
    std::mutex mutex_;
    std::condition_variable not_empty_;
    std::deque<T> queue_;
    bool closed_ = false;
};
```

### 13.2 조건 변수 규칙

- 조건에 사용되는 상태를 같은 mutex로 보호한다.
- `if` 대신 predicate 또는 `while`로 조건을 다시 검사한다.
- 깨어났다고 조건이 반드시 참인 것은 아니다.
- `notify_one()` 자체는 프로그램 상태를 저장하지 않는다.
- `wait()`는 mutex를 원자적으로 해제하고 잠든다.
- 깨어날 때 `wait()`는 mutex를 다시 획득한 뒤 반환한다.

## 14. 세마포어

세마포어는 정수 카운터와 대기 큐로 동시 접근 수를 제어한다.

- `acquire()`/wait/P: 값이 양수이면 감소하고 진행하고, 아니면 대기한다.
- `release()`/post/V: 값을 증가시키고 필요한 경우 대기자를 깨운다.

초기값이 1이면 이진 세마포어처럼 사용할 수 있다. 초기값이 N이면 동시에 N개의 스레드만 자원에 접근하도록 제한한다.

```cpp
#include <semaphore>

std::counting_semaphore<3> connection_slots{3};

void use_server() {
    connection_slots.acquire();

    perform_request(); // 동시에 최대 3개만 실행

    connection_slots.release();
}
```

실제 코드에서는 예외가 발생해도 `release()`가 실행되도록 RAII 래퍼를 만드는 것이 안전하다.

### 14.1 mutex와 세마포어 차이

- mutex에는 소유자 개념이 있다.
- 일반적으로 mutex를 획득한 스레드가 해제해야 한다.
- 세마포어의 `release()`는 다른 스레드가 호출할 수 있다.
- mutex는 상호 배제에 적합하다.
- 세마포어는 자원 개수 제한이나 스레드 간 사건 전달에 적합하다.

## 15. 교착 상태

교착 상태(deadlock)는 스레드들이 서로가 가진 자원을 기다리며 모두 진행하지 못하는 상태다.

### 15.1 Coffman의 네 조건

다음 네 조건이 동시에 성립하면 교착 상태가 발생할 수 있다.

1. **상호 배제**: 자원을 한 번에 하나의 스레드만 사용한다.
2. **점유하며 대기**: 자원을 가진 채 다른 자원을 기다린다.
3. **비선점**: 보유한 자원을 강제로 회수할 수 없다.
4. **환형 대기**: 스레드와 자원 사이에 원형 대기 관계가 존재한다.

### 15.2 교착 상태가 가능한 코드

```cpp
// 스레드 1
a.lock();
b.lock();

// 스레드 2
b.lock();
a.lock();
```

스레드 1이 `a`, 스레드 2가 `b`를 획득하면 서로 상대방의 락을 기다릴 수 있다.

### 15.3 std::scoped_lock 사용

```cpp
#include <mutex>

struct Account {
    int balance;
    std::mutex mutex;
};

void transfer(Account& from, Account& to, int amount) {
    if (&from == &to) {
        return;
    }

    std::scoped_lock lock(from.mutex, to.mutex);

    if (from.balance >= amount) {
        from.balance -= amount;
        to.balance += amount;
    }
}
```

`std::scoped_lock`은 여러 mutex를 교착 상태가 발생하지 않도록 획득한다.

### 15.4 교착 상태 방지 원칙

- 모든 락에 전역적인 획득 순서를 정한다.
- 락을 가진 채 I/O를 실행하지 않는다.
- 락을 가진 채 외부 콜백을 호출하지 않는다.
- 임계 영역을 짧게 유지한다.
- 중첩 락을 최소화한다.
- 여러 락은 `std::scoped_lock`으로 한꺼번에 획득한다.
- 필요한 경우 `try_lock()`과 재시도를 사용한다.
- 타임아웃은 근본적인 방지책보다 복구 수단으로 본다.

## 16. 교착 상태 이외의 병행성 오류

### 16.1 원자성 위반

함께 실행되어야 하는 연산 사이에 다른 스레드가 끼어드는 문제다.

```cpp
if (pointer != nullptr) {
    use(pointer);
}
```

검사와 사용 사이에 다른 스레드가 객체를 제거할 수 있다. 검사와 사용을 같은 mutex로 보호하거나 `std::shared_ptr`처럼 객체 수명을 안전하게 관리해야 한다.

### 16.2 순서 위반

A 작업이 B보다 먼저 실행되어야 하지만 그 순서가 강제되지 않은 문제다.

잘못된 방법:

```cpp
std::this_thread::sleep_for(std::chrono::milliseconds(100));
// 이제 다른 스레드가 끝났을 것이라고 추측
```

올바른 동기화 도구:

- `join()`
- `std::condition_variable`
- `std::future`와 `std::promise`
- `std::latch`
- `std::barrier`
- 메시지 큐

`sleep()`은 실행 순서를 보장하지 않는다.

## 17. 스레드 종료와 협력적 취소

스레드를 강제로 종료하면 다음 문제가 발생할 수 있다.

- mutex를 가진 채 종료
- 메모리와 파일 누수
- 자료 구조가 절반만 변경된 상태로 남음
- 프로그램의 불변식 훼손

C++20에서는 `std::jthread`와 `std::stop_token`을 이용한 협력적 취소를 사용할 수 있다.

```cpp
#include <chrono>
#include <thread>

using namespace std::chrono_literals;

int main() {
    std::jthread worker([](std::stop_token stop) {
        while (!stop.stop_requested()) {
            perform_one_unit();
        }

        cleanup();
    });

    std::this_thread::sleep_for(1s);
    worker.request_stop();
}
```

스레드가 무한 블로킹 I/O에서 기다리면 중지 요청을 확인하지 못할 수 있다. 이때는 타임아웃, 취소 가능한 I/O, 소켓 종료 같은 운영체제별 방법이 필요하다.

## 18. 프로세스와 스레드 선택 기준

### 프로세스가 적합한 경우

- 외부 코드나 플러그인을 격리해야 한다.
- 한 작업의 충돌이 전체 프로그램을 종료시키면 안 된다.
- 서로 다른 보안 권한이 필요하다.
- 독립 서비스로 배포해야 한다.
- 서로 다른 언어나 런타임을 사용한다.

### 스레드가 적합한 경우

- 큰 자료 구조를 자주 공유한다.
- 통신 지연이 작아야 한다.
- 하나의 작업을 여러 CPU 코어로 병렬화한다.
- 같은 응용 프로그램의 내부 작업이다.

### 이벤트 기반 구조가 적합한 경우

- 연결 수가 매우 많다.
- 각 요청이 주로 I/O를 기다린다.
- 작업이 짧고 블로킹 호출을 피할 수 있다.

실제 서버에서는 다음처럼 여러 모델을 조합할 수 있다.

```text
여러 프로세스
  └─ 프로세스마다 이벤트 루프
       └─ CPU 작업용 제한된 스레드 풀
```

## 20. 핵심 요약

1. 프로세스는 독립된 주소 공간과 자원을 가지며 장애 격리가 좋다.
2. 스레드는 프로세스의 자원을 공유하며 실행 문맥과 스택은 따로 가진다.
3. 운영체제는 타이머 인터럽트와 문맥 교환으로 CPU를 가상화한다.
4. 스케줄링 순서는 비결정적이므로 코드가 특정 실행 순서를 가정하면 안 된다.
5. 공유 데이터를 동기화하지 않고 읽고 쓰면 C++ 데이터 경쟁이 발생한다.
6. 단순 값의 원자적 변경에는 `std::atomic`을 사용할 수 있다.
7. 복합 불변식 보호에는 mutex가 필요하다.
8. 상태가 바뀔 때까지 기다리려면 조건 변수를 사용한다.
9. 자원의 동시 사용 개수를 제한하려면 세마포어를 사용할 수 있다.
10. 교착 상태는 락 순서를 통일하고 `std::scoped_lock`을 사용해 예방한다.

  → CPU 스케줄링
  → 스레드와 공유 메모리
  → mutex와 atomic
  → 조건 변수와 세마포어
  → 교착 상태
