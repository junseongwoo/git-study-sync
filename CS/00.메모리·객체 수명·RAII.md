# 메모리·객체 수명·RAII: C++와 운영체제를 함께 보는 법

> [!summary] 한 문장 정리
> **운영체제는 프로세스에 가상 주소 공간과 페이지를 제공하고, C++는 그 저장 공간 위에서 객체의 수명과 자원 소유권을 관리한다. 안전한 C++의 핵심은 주소를 직접 관리하는 것이 아니라 소유권을 타입으로 표현하고 RAII 객체의 수명에 자원의 수명을 결합하는 것이다.**

관련 노트: [[01.프로세스와 스레드]] · [[02.동시성과 병렬성]] · [[OS 공부]]

## 학습 목표

- 가상 주소 공간, 스택, 힙, 저장 기간, 객체 수명, 소유권을 서로 구분한다.
- `new`가 곧바로 운영체제의 페이지 할당을 뜻하지 않는 이유를 설명한다.
- 포인터와 참조가 객체를 소유하는지 단지 관찰하는지를 API에 드러낸다.
- 생성자·소멸자와 예외 처리를 RAII 관점에서 설명한다.
- 복사·이동·얕은 복사·깊은 복사를 자원 소유권과 연결한다.
- 누수, dangling pointer, double free, buffer overflow, use-after-free를 원인부터 예방까지 설명한다.
- 정렬과 객체 모델을 이해하고 undefined behavior를 피한다.
- `unique_ptr`, `shared_ptr`, `weak_ptr`를 각각 필요한 경우에만 사용한다.

## 1. 먼저 분리해야 할 세 개념

메모리 버그의 상당수는 다음 세 층을 하나로 생각해서 생긴다.

| 층 | 핵심 질문 | 관리 주체 | 예 |
|---|---|---|---|
| 저장 공간(storage) | 바이트를 놓을 장소가 있는가? | OS, 런타임, 할당자 | 가상 페이지, 스택 프레임, 힙 블록 |
| 객체 수명(lifetime) | 그 바이트에 지금 `T` 객체가 살아 있는가? | C++ 객체 모델 | 생성 완료부터 소멸 또는 저장 공간 재사용까지 |
| 소유권(ownership) | 누가 자원을 최종 정리할 책임이 있는가? | 프로그램 설계와 타입 | 지역 객체, `unique_ptr`, `shared_ptr` |

저장 공간이 있다고 객체가 살아 있는 것은 아니다. 반대로 객체의 수명이 끝난 직후에도 그 주소의 바이트는 할당자나 스택에 남아 있을 수 있다. 그 값을 읽을 수 있다는 뜻은 아니다.

```cpp
alignas(int) std::byte storage[sizeof(int)]; // int를 둘 수 있는 저장 공간만 존재
int* p = std::construct_at(reinterpret_cast<int*>(storage), 42);
// 이 시점부터 int 객체의 수명이 시작됨
std::destroy_at(p);
// 저장 공간은 남아 있지만 int 객체의 수명은 끝남
```

소유권도 주소 자체에 들어 있지 않다. `T*`라는 비트열만 보고 그 포인터를 `delete`해야 하는지, 빌린 것인지, 배열 첫 원소인지 알 수 없다. 그래서 현대 C++에서는 타입과 API로 소유권을 표현한다.

## 2. 프로세스 주소 공간과 가상 메모리

### 2.1 가상 주소 공간

사용자 프로그램이 다루는 주소는 일반적으로 **가상 주소**다. 운영체제와 MMU는 각 프로세스가 크고 연속적이며 사적인 주소 공간을 가진 것처럼 보이게 한다. 실제 물리 메모리의 프레임은 흩어져 있어도 된다.

```text
높은 가상 주소
┌──────────────────────────┐
│ 스레드별 스택 / guard page │  호출 프레임, 자동 변수
├──────────────────────────┤
│ mmap 영역, 공유 라이브러리  │  파일 매핑, 큰 할당, shared library
├──────────────────────────┤
│ 동적 할당 영역(관념적 heap) │  allocator가 관리하는 블록
├──────────────────────────┤
│ .bss                     │  0으로 초기화되는 전역/정적 데이터
│ .data                    │  초기값이 있는 전역/정적 데이터
│ .rodata                  │  읽기 전용 상수
│ .text                    │  실행 코드
└──────────────────────────┘
낮은 가상 주소
```

이 그림은 대표적 배치다. 실제 순서, 성장 방향, 구간 수, 주소는 ABI와 운영체제에 따라 달라지고 ASLR 때문에 실행할 때마다 바뀔 수 있다. 큰 동적 할당이 전통적 heap 구간이 아니라 별도 메모리 매핑으로 만들어질 수도 있다.

### 2.2 가상 메모리가 제공하는 것

- **격리**: 한 프로세스가 다른 프로세스의 주소 공간을 임의로 읽고 쓰지 못하게 한다.
- **보호**: 페이지마다 읽기, 쓰기, 실행 권한을 둔다.
- **재배치의 투명성**: 프로그램의 가상 주소와 물리 주소를 분리한다.
- **희소한 주소 공간**: 사용하지 않는 구간까지 물리 RAM을 미리 제공할 필요가 없다.
- **공유**: 같은 실행 파일 코드나 공유 라이브러리 페이지를 여러 프로세스가 공유할 수 있다.
- **요구 페이징**: 실제 접근할 때 페이지를 준비할 수 있다.
- **copy-on-write(COW)**: 처음에는 같은 물리 페이지를 읽기 전용으로 공유하고, 쓰기가 생길 때 복사한다.

### 2.3 주소 변환과 페이지 폴트

가상 주소는 보통 `가상 페이지 번호(VPN) + 페이지 내부 오프셋`으로 나뉜다. 페이지 테이블은 VPN을 물리 프레임 번호(PFN)와 권한 정보에 대응시킨다. TLB는 최근 주소 변환을 캐시한다.

```text
C++ 포인터의 가상 주소
        │
        ▼
   TLB에서 변환 검색 ── hit ──> 물리 주소로 접근
        │ miss
        ▼
   페이지 테이블 확인
        ├─ 유효 + present  ──> TLB 갱신 후 재시도
        ├─ 유효 + not present -> page fault, OS가 페이지 준비
        └─ 무효/권한 위반 ────> fault, 보통 프로세스 종료
```

**페이지 폴트가 언제나 버그인 것은 아니다.** 요구 페이징이나 COW 때문에 발생한 합법적인 폴트는 OS가 처리하고 명령을 재실행한다. 반면 매핑되지 않은 주소나 쓰기 금지 페이지를 접근하면 보통 접근 위반 또는 segmentation fault로 이어진다.

### 2.4 예약, 커밋, 실제 상주 메모리

“1 GiB를 할당했다”는 말은 다음을 구분해야 한다.

- 가상 주소 범위를 예약했는가?
- OS가 그 범위에 backing store를 약속했는가?
- 실제 페이지를 처음 접근했는가?
- 현재 물리 RAM에 상주하는가?

운영체제 정책에 따라 큰 가상 영역을 얻어도 실제 물리 페이지는 첫 접근 때 준비될 수 있다. 따라서 주소 공간 크기, 커밋 크기, RSS(상주 집합 크기)는 같은 값이 아니다.

### 2.5 C++ 할당에서 물리 메모리까지

```text
new T
  → T를 위한 operator new 호출
  → C++ 런타임/힙 할당자가 free list 또는 arena에서 블록 검색
  → 부족하면 OS에 더 큰 가상 메모리 영역 요청
  → T의 생성자 실행
  → 최초 페이지 접근 시 필요하면 page fault
  → OS가 물리 프레임 연결 및 페이지 테이블 갱신
```

역방향도 단순하지 않다.

```text
delete p
  → T의 소멸자 실행
  → operator delete가 블록을 할당자에 반환
  → 할당자는 재사용을 위해 보관할 수 있음
  → OS에 즉시 페이지를 돌려준다는 보장은 없음
```

따라서 `delete` 뒤 작업 관리자에서 RSS가 바로 감소하지 않아도 누수라고 단정할 수 없다. 반대로 RSS가 안정적이어도 객체나 자원의 논리적 누수가 없다고 단정할 수 없다.

### 2.6 OS의 copy-on-write와 C++ 복사는 다른 개념

운영체제의 COW는 가상 메모리 최적화다. 예를 들어 `fork` 직후 부모와 자식의 가상 페이지를 같은 물리 프레임에 읽기 전용으로 연결하고, 어느 한쪽이 쓸 때 page fault를 발생시켜 그 페이지를 복사할 수 있다.

이때 C++ 객체별 복사 생성자는 호출되지 않는다. 반대로 `Widget b = a;`가 실행되어 C++ 복사 생성자가 호출돼도 OS가 반드시 COW page fault를 일으키는 것은 아니다.

| 용어 | 계층 | 단위 | 관찰되는 시점 |
|---|---|---|---|
| C++ copy constructor | 언어/객체 | 객체와 그 의미 | 객체 초기화 표현식 |
| C++ move constructor | 언어/객체 | 소유 상태 이전 | 우측값으로 새 객체 초기화 |
| OS copy-on-write | 가상 메모리 | 보통 페이지 | 공유된 페이지에 처음 쓰기 |

세 기법 모두 “복사 비용을 다룬다”는 공통점만 있을 뿐 계약과 동작 단위가 다르다.

## 3. Stack과 Heap

### 3.1 스택

호출 스택은 함수 호출의 실행 문맥을 저장한다. ABI에 따라 반환 주소, 보존 레지스터, 인자, 지역 변수, 정렬용 패딩 등이 스택 프레임에 놓일 수 있다. 최적화된 변수는 레지스터에만 있을 수도 있으므로 “지역 변수는 반드시 물리적인 스택에 있다”는 표현은 지나치게 단순하다.

```cpp
int square(int x) {
    int result = x * x; // 자동 저장 기간. 실제 배치는 최적화와 ABI에 좌우됨
    return result;
} // result의 수명 종료
```

특징:

- 각 스레드는 독립적인 호출 스택을 가진다.
- 함수 진입과 복귀에 맞춰 저장 공간을 효율적으로 재사용한다.
- 자동 저장 기간 객체는 블록을 벗어날 때 역순으로 파괴된다.
- 무한 재귀나 지나치게 큰 지역 배열은 stack overflow를 일으킬 수 있다.
- 운영체제는 스택 끝에 guard page를 두어 초과 접근을 감지할 수 있다.

### 3.2 힙과 자유 저장소

일상적으로 C++의 동적 할당 영역을 힙이라고 부른다. 엄밀하게 C++ 표준의 **free store**와 운영체제/할당자 구현의 **heap**은 완전히 같은 표준 용어가 아니다. 실무에서는 `new`가 사용하는 동적 저장 공간을 힙이라고 설명해도 되지만, 구현 세부와 언어 규칙을 구분해야 한다.

```cpp
auto p = std::make_unique<int>(42); // 동적 저장 기간 객체
// p는 자동 저장 기간을 갖는 소유 핸들
// int 객체는 p가 소유하는 동적 객체
```

힙 할당자는 요청마다 시스템 콜을 하지 않는다. 큰 영역을 OS에서 얻어 작은 블록으로 나누고, 반환된 블록을 free list나 size class에 보관해 재사용한다. 이 과정에서 내부/외부 단편화와 메타데이터 비용이 발생할 수 있다.

### 3.3 비교

| 항목 | 스택/자동 객체 | 힙/동적 객체 |
|---|---|---|
| 수명 결정 | 블록과 객체 규칙에 의해 결정적 | 소유 객체가 해제할 때까지 |
| 관리 | 컴파일러가 생성한 코드와 ABI | 할당자 + 프로그램의 소유권 설계 |
| 크기 | 스레드 스택 제한의 영향 | 주소 공간과 시스템 메모리의 영향 |
| 할당 비용 | 대개 스택 포인터 조정 | 크기 분류, free list, 동기화 등이 필요할 수 있음 |
| 주소 안정성 | 블록 종료 시 즉시 무효 | 해제 전까지 존재하지만 컨테이너 이동 등은 별개 |
| 대표 위험 | 반환된 지역 주소, stack overflow | 누수, UAF, double free, 단편화 |

> [!important] 흔한 오해
> 스택 객체가 무조건 빠르고 힙 객체가 무조건 느린 것은 아니다. 성능은 할당 횟수, 캐시 지역성, 객체 크기, 할당자, 스레드 경쟁, 페이지 폴트에 좌우된다. 우선 수명과 소유권에 맞는 설계를 하고 측정으로 최적화한다.

### 3.4 스택에 둘지 힙에 둘지

- 작고 수명이 현재 범위에 한정되면 값 또는 지역 객체가 자연스럽다.
- 선택적 값은 먼저 `std::optional<T>`를 고려한다.
- 가변 길이 연속 데이터는 `std::vector<T>`, 문자열은 `std::string`을 고려한다.
- 동적 다형성과 단독 소유권이 필요하면 `std::unique_ptr<Base>`가 자연스럽다.
- 객체가 매우 크거나 주소 안정성이 필요하거나 범위를 넘어 소유권을 이전해야 하면 동적 저장이 유용하다.
- 단지 “복사를 피하려고” 모든 객체를 힙에 두지 않는다. 이동과 copy elision이 있다.

### 3.5 `new/delete`와 `malloc/free`를 정확히 구분하기

| 연산 | 저장 공간 | 객체 생성/소멸 | 실패 방식 |
|---|---|---|---|
| `new T(args...)` | `operator new`로 확보 | `T` 생성자 실행 | 기본적으로 `std::bad_alloc` 또는 생성자 예외 |
| `delete p` | 소멸 후 `operator delete`에 반환 | `T` 소멸자 실행 | 정상적인 소멸자는 예외를 내보내지 않아야 함 |
| `malloc(n)` | 정렬된 바이트 블록 확보 | C++ 클래스 생성자 실행 안 함 | 실패 시 null pointer |
| `free(p)` | `malloc` 계열 블록 반환 | C++ 클래스 소멸자 실행 안 함 | 잘못된 포인터면 UB |

`new` 표현식은 **저장 공간 확보와 객체 생성**을 합친다. 저장 공간 확보 후 생성자가 예외를 던지면 대응하는 deallocation function이 호출되어 확보한 공간을 반환하므로, 성공한 포인터를 받기도 전에 그 블록이 새지 않는다.

```cpp
auto* a = new int;    // 기본 초기화: 값이 초기화되지 않음
auto* b = new int{};  // 값 초기화: 0

delete a;
delete b;
delete nullptr;       // 아무 동작도 하지 않음
```

배열은 `new T[n]`과 `delete[]`가 짝이다. 구현은 원소 수나 파괴 정보를 위한 메타데이터를 별도로 둘 수 있으므로 `delete`와 바꿔 쓸 수 없다. 현대 C++에서는 이 저수준 짝을 직접 쓰기보다 `vector<T>`, `make_unique<T>()`, `make_unique<T[]>(n)`을 사용한다.

`new (std::nothrow) T`는 할당 실패 시 null pointer를 반환하도록 요청할 수 있지만, 생성자가 던지는 예외까지 모두 null로 바꾸는 장치는 아니다. 일반적으로 예외 기반 기본 `new`와 RAII를 일관되게 사용하는 편이 단순하다.

## 4. 저장 기간과 객체 수명

### 4.1 네 가지 저장 기간

| 저장 기간 | 대표 예 | 저장 공간이 유지되는 기간 |
|---|---|---|
| automatic | 지역 변수, 함수 인자 | 블록 또는 호출과 연관 |
| static | 전역 변수, 함수 내부 `static` | 프로그램 실행 기간 |
| thread | `thread_local` | 해당 스레드 실행 기간 |
| dynamic | `new`, 할당자가 제공한 저장 공간 | 명시적으로 해제될 때까지 |

저장 기간은 **저장 공간**에 관한 분류다. 객체 수명은 그 저장 공간 안의 특정 타입 객체가 유효한 기간이다.

### 4.2 수명의 시작과 끝

일반적인 클래스 객체의 수명은 필요한 초기화가 끝나고 생성자가 성공적으로 완료된 뒤 시작한다. 수명은 다음과 같은 때 끝난다.

- 비클래스 객체가 파괴될 때
- 클래스 객체의 소멸자 호출이 시작될 때
- 저장 공간이 해제되거나 다른 객체에 재사용될 때

생성자가 예외를 던지면 그 객체 자체의 소멸자는 호출되지 않는다. 아직 완성된 객체가 아니기 때문이다. 그러나 이미 생성된 기반 클래스와 멤버 객체는 자동으로 파괴된다. 그래서 멤버 자체가 RAII 객체라면 부분 생성 실패도 안전하다.

### 4.3 생성과 소멸 순서

생성 순서:

1. 가상 기반 클래스
2. 직접 기반 클래스
3. 멤버가 **클래스에 선언된 순서대로**
4. 생성자 본문

소멸은 정확히 역순이다. 생성자 초기화 목록에 적은 순서가 멤버 생성 순서를 바꾸지 않는다.

```cpp
class Session {
    Logger logger_;     // 먼저 생성
    Connection conn_;  // 나중 생성
public:
    Session() : conn_{}, logger_{} {} // 실제 순서는 logger_ → conn_
}; // 소멸 순서는 conn_ → logger_
```

컴파일러 경고를 켜면 초기화 순서 착각을 발견하는 데 도움이 된다.

### 4.4 임시 객체

임시 객체는 보통 그것을 포함하는 full-expression의 끝에서 파괴된다.

```cpp
std::string make_name();

const std::string& ok = make_name();
// 이 직접 바인딩에서는 임시 string의 수명이 ok의 수명까지 연장됨

std::string_view bad = make_name();
// string_view는 소유하지 않음. 문장이 끝나면 임시 string이 파괴되어 bad는 dangling
```

참조를 반환한다고 임시나 지역 객체의 수명이 연장되지는 않는다.

```cpp
const std::string& wrong() {
    std::string local = "dead soon";
    return local; // 반환 즉시 local 파괴: dangling reference
}
```

### 4.5 정적 객체의 초기화와 종료

서로 다른 번역 단위에 있는 정적 객체의 동적 초기화 순서는 의존하기 어렵다. 이를 static initialization order fiasco라고 부른다. 필요할 때 생성되는 함수 지역 `static`으로 의존성을 국소화할 수 있다.

```cpp
Registry& registry() {
    static Registry instance;
    return instance;
}
```

C++11부터 함수 지역 정적 객체의 최초 초기화는 스레드 안전하다. 다만 종료 시 다른 정적 객체를 소멸자에서 참조하는 순서 문제는 여전히 설계해야 한다.

### 4.6 다형적 기반 클래스의 소멸자

기반 포인터로 파생 객체를 삭제한다면 기반 클래스의 소멸자는 `virtual`이어야 한다.

```cpp
struct Base {
    virtual ~Base() = default;
};

struct Derived final : Base {
    std::vector<int> data;
};

std::unique_ptr<Base> p = std::make_unique<Derived>();
// Base의 virtual destructor를 통해 Derived까지 올바르게 파괴
```

### 4.7 이미 확보한 저장 공간에 객체 만들기

allocator, arena, 컨테이너 구현에서는 저장 공간 확보와 객체 생성을 분리한다. C++20에서는 `std::construct_at`과 `std::destroy_at`이 의도를 잘 드러낸다.

```cpp
void* raw = ::operator new(sizeof(Widget), std::align_val_t{alignof(Widget)});
Widget* widget = nullptr;
static_assert(std::is_nothrow_destructible_v<Widget>);

try {
    widget = std::construct_at(static_cast<Widget*>(raw));
    use(*widget);
    std::destroy_at(widget); // 객체 수명 종료
    widget = nullptr;
    ::operator delete(raw, std::align_val_t{alignof(Widget)}); // 저장 공간 반환
} catch (...) {
    if (widget != nullptr) {
        std::destroy_at(widget);
    }
    ::operator delete(raw, std::align_val_t{alignof(Widget)});
    throw;
}
```

위 코드는 두 계층을 보여 주기 위한 저수준 예시다. 실전에서는 생성 성공 여부까지 소유하는 RAII 래퍼 또는 allocator-aware 컨테이너를 사용한다. 핵심은 다음 두 동작이 별개라는 점이다.

- `destroy_at`: 객체의 수명을 끝내지만 저장 공간은 남긴다.
- `operator delete`: 저장 공간을 반환하지만 그 전에 살아 있는 비자명 객체를 알아서 파괴하지 않는다.

같은 저장 공간을 다른 타입이나 새 객체에 재사용하면 이전 객체를 가리키던 포인터를 무조건 새 객체 접근에 사용할 수 있는 것은 아니다. 투명하게 교체 가능한 조건과 `std::launder`가 필요한 경우가 있으므로, 이 수준의 코드는 표준 컨테이너·allocator 구현처럼 제한된 경계 안에 둔다.

## 5. Pointer와 Reference

### 5.1 핵심 비교

| 속성 | `T*` | `T&` |
|---|---|---|
| 반드시 즉시 대상 필요 | 아니오 | 예 |
| 빈 상태 표현 | `nullptr` | 정상적인 언어 사용에서는 없음 |
| 다른 대상을 다시 가리킴 | 가능 | 불가능; 대입은 대상 객체에 대입 |
| 포인터 산술 | 가능 | 불가능 |
| 소유권 표현 | 자체로 표현하지 못함 | 소유하지 않음 |
| 대표 의미 | 선택적 관찰, 배열 위치, 저수준 핸들 | 반드시 존재하는 빌린 객체 |

참조도 대상보다 오래 살아남으면 dangling이 된다. 구현이 참조를 포인터처럼 표현할 수 있지만, 언어 차원에서 참조는 “널이 될 수 있는 포인터”가 아니다. 널 포인터를 역참조해 참조를 만드는 것부터 undefined behavior다.

### 5.2 `const`의 위치

```cpp
const int* p1;       // 가리키는 int를 p1을 통해 변경하지 않음
int* const p2 = ...; // p2 자체를 다른 주소로 바꿀 수 없음
const int* const p3 = ...; // 둘 다 const
```

`const T&`는 읽기 전용 관찰을 표현하며 불필요한 복사를 피한다. 그러나 그 참조를 보관한다면 호출자가 넘긴 객체의 수명이 충분한지 별도 계약이 필요하다.

### 5.3 포인터는 소유권이 아니다

```cpp
void draw(const Widget& widget); // 반드시 존재, 빌림
void draw(const Widget* widget); // nullptr 가능, 빌림
void consume(std::unique_ptr<Widget> widget); // 소유권을 넘겨받음
void share(std::shared_ptr<Widget> widget);    // 공동 소유에 참여
```

함수 인자로 받은 raw pointer를 근거 없이 `delete`하면 안 된다. 외부 API가 명시적으로 소유권 이전을 계약한 경우가 아니라면 raw pointer/reference는 관찰자라고 간주하는 설계가 안전하다.

### 5.4 배열과 뷰

포인터 하나에는 길이 정보가 없다. 연속 범위를 전달할 때는 `std::span<T>`가 포인터와 길이를 함께 전달한다.

```cpp
int sum(std::span<const int> values) {
    return std::accumulate(values.begin(), values.end(), 0);
}
```

`span`, `string_view`, 반복자는 모두 비소유 뷰다. 원본 객체 파괴뿐 아니라 `vector` 재할당, `string` 변경처럼 저장 위치가 바뀌어도 무효화될 수 있다.

## 6. RAII

RAII(Resource Acquisition Is Initialization)는 **자원을 획득한 성공적인 객체의 수명과 자원의 유효 기간을 결합**하는 C++ 설계 원칙이다.

1. 생성자 또는 팩터리가 자원을 획득한다.
2. 객체가 유효한 동안 불변식을 유지한다.
3. 소멸자가 자원을 정확히 한 번 반환한다.
4. 복사와 이동 정책이 소유권 의미를 따른다.

자원은 메모리만 뜻하지 않는다. 파일, 소켓, 뮤텍스 잠금, 데이터베이스 트랜잭션, GPU 버퍼, 스레드 조인 책임도 포함한다.

### 6.1 예외와 조기 반환에 강한 이유

```cpp
void update(Account& account) {
    std::lock_guard lock{account.mutex()};
    // 이 아래에서 return하거나 예외가 발생해도 lock의 소멸자가 unlock
    account.apply_interest();
}
```

명시적 `lock()`/`unlock()` 사이에 여러 반환 경로가 있으면 해제를 빠뜨리기 쉽다. RAII 객체는 스택 되감기(stack unwinding) 과정에서 파괴되므로 각 경로에 정리 코드를 복제하지 않는다.

### 6.2 파일 RAII

```cpp
#include <cstdio>
#include <memory>
#include <stdexcept>

struct FileCloser {
    void operator()(std::FILE* file) const noexcept {
        if (file != nullptr) {
            std::fclose(file);
        }
    }
};

using File = std::unique_ptr<std::FILE, FileCloser>;

File open_file(const char* path, const char* mode) {
    File file{std::fopen(path, mode)};
    if (!file) {
        throw std::runtime_error{"failed to open file"};
    }
    return file; // 이동 또는 copy elision
}
```

`File`은 복사할 수 없고 이동할 수 있다. 반환 경로, 예외, 정상 종료 모두에서 열린 파일은 소유 객체가 파괴될 때 닫힌다.

### 6.3 소멸자 원칙

- 소멸자는 일반적으로 예외를 밖으로 던지면 안 된다.
- 이미 stack unwinding 중인데 소멸자가 다시 예외를 던지면 `std::terminate`로 이어질 수 있다.
- 실패 가능한 “마무리/커밋”은 명시적 멤버 함수로 제공하고, 소멸자는 최소한의 무실패 정리만 수행한다.
- 소멸자는 소유한 멤버의 소멸을 중복 구현하지 않는다. RAII 멤버가 알아서 정리한다.

### 6.4 RAII와 운영체제의 프로세스 정리는 다르다

프로세스가 정상적으로 범위를 빠져나가면 C++ 소멸자가 결정적인 정리를 한다. 그러나 강제 종료, 전원 차단, `std::abort`, 일부 비정상 종료에서는 모든 자동/정적 객체의 소멸자가 실행된다고 기대할 수 없다.

OS는 프로세스 종료 시 주소 공간의 페이지와 커널 핸들을 회수할 수 있지만, 다음과 같은 **프로그램 의미의 정리**를 대신하지 못한다.

- 파일 형식의 footer 기록
- 데이터베이스 commit/rollback 프로토콜
- 다른 프로세스에 보내야 할 종료 메시지
- 공유 메모리 안의 논리 상태 복구
- 원격 서버의 세션 종료

즉 RAII는 정상적인 C++ 제어 흐름에서 강력하지만, 크래시 일관성은 별도의 프로토콜 문제다.

## 7. 소유권 모델

### 7.1 네 가지 역할

| 역할 | 의미 | 대표 타입 |
|---|---|---|
| 값 소유 | 객체 자체를 직접 가짐 | `T`, `vector<T>`, `string` |
| 단독 소유 | 정확히 하나의 소유자가 책임 | `unique_ptr<T>` |
| 공동 소유 | 마지막 소유자가 정리 | `shared_ptr<T>` |
| 비소유 관찰 | 수명을 늘리지 않고 잠시 접근 | `T&`, `T*`, `span`, `string_view`, `weak_ptr` |

기본 선택 순서는 **값 → `unique_ptr` → 정말 필요한 경우 `shared_ptr`**다. 소유 관계가 불명확하다는 이유로 `shared_ptr`부터 사용하면 구조가 더 불명확해진다.

### 7.2 API 서명으로 의도를 표현하기

| 서명 | 일반적인 의미 |
|---|---|
| `void f(T value)` | 복사/이동하여 독립 값을 받음 |
| `void f(const T& value)` | 필수 읽기 전용 빌림 |
| `void f(T& value)` | 필수 수정 가능한 빌림 |
| `void f(const T* value)` | 선택적 읽기 전용 빌림 |
| `void f(unique_ptr<T> value)` | 소유권을 소비함 |
| `void f(const unique_ptr<T>&)` | 포인터 객체를 빌림; 대개 `T&`가 더 직접적 |
| `void f(shared_ptr<T> value)` | 공동 소유 기간을 늘림 |
| `void f(const shared_ptr<T>&)` | shared_ptr 자체를 관찰; 공동 소유 의도가 약하면 `T&` 검토 |
| `weak_ptr<T>` 보관 | 공동 소유 그래프의 비소유 링크 |

### 7.3 소유권 그래프

트리의 부모가 자식을 `unique_ptr`로 소유하고 자식이 부모를 raw pointer로 관찰하는 구조는 명확하다.

```cpp
struct Node {
    Node* parent = nullptr; // 비소유
    std::vector<std::unique_ptr<Node>> children; // 단독 소유

    Node& add_child() {
        auto child = std::make_unique<Node>();
        child->parent = this;
        children.push_back(std::move(child));
        return *children.back();
    }
};
```

`parent`가 안전하려면 부모가 모든 자식보다 오래 산다는 트리 불변식이 필요하다. 비소유 포인터라고 자동으로 안전해지는 것은 아니다.

## 8. 복사와 이동

### 8.1 복사

복사는 원본과 목적지가 이후 독립적으로 유효하다는 의미가 보통 기대된다.

- 복사 생성자: 새 객체를 기존 객체로 초기화
- 복사 대입: 이미 살아 있는 객체의 값을 다른 객체 값으로 바꿈

```cpp
T b = a; // 복사 생성
b = a;   // 복사 대입
```

### 8.2 이동

이동은 원본의 자원을 새 객체로 이전해 비싼 복사를 피할 기회를 준다.

```cpp
std::vector<int> source{1, 2, 3};
std::vector<int> target = std::move(source);
```

`std::move`는 실제 이동 작업을 하지 않는다. 인자를 우측값으로 취급할 수 있게 캐스팅할 뿐이다. 그 뒤 선택된 이동 생성자/대입 연산자가 자원을 이전한다.

이동된 표준 라이브러리 객체는 보통 **유효하지만 값은 미지정(valid but unspecified)** 상태다. 소멸하거나 새 값을 대입할 수 있지만, 비어 있다고 가정하지 않는다. 특정 타입이 더 강한 사후 조건을 문서화하면 그 계약을 따른다.

### 8.3 이동 연산과 `noexcept`

`vector`가 재할당할 때 기존 원소를 새 저장 공간으로 옮겨야 한다. 이동 생성자가 예외를 던질 수 있으면 강한 예외 보장을 지키기 위해 복사를 선택할 수 있다. 자원 핸들의 이동이 실제로 실패하지 않는다면 `noexcept`로 선언하는 것이 중요하다.

```cpp
Handle(Handle&&) noexcept = default;
Handle& operator=(Handle&&) noexcept = default;
```

### 8.4 copy elision과 반환

현대 C++에서는 지역 객체를 값으로 반환하는 것이 자연스럽다.

```cpp
std::vector<int> make_data() {
    std::vector<int> result(1'000);
    return result; // NRVO 가능. 불필요한 std::move를 쓰지 않음
}
```

`return std::move(result);`는 오히려 NRVO를 방해할 수 있다. 소유 객체는 값으로 반환하고 컴파일러의 copy elision과 이동을 활용한다.

### 8.5 Rule of Zero, Three, Five

- **Rule of Zero**: 자원 관리를 RAII 멤버에 맡기고 특수 멤버 함수를 직접 작성하지 않는다. 가장 권장된다.
- **Rule of Three**: 소멸자, 복사 생성자, 복사 대입 중 하나를 직접 정의해야 한다면 나머지도 검토한다.
- **Rule of Five**: C++11 이후에는 이동 생성자와 이동 대입까지 함께 검토한다.

```cpp
class Buffer {
    std::vector<std::byte> data_;
public:
    explicit Buffer(std::size_t size) : data_(size) {}
};
// vector가 소멸·복사·이동을 모두 올바르게 처리: Rule of Zero
```

## 9. 얕은 복사와 깊은 복사

### 9.1 얕은 복사가 위험한 경우

```cpp
class BadBuffer {
    std::size_t size_;
    int* data_;
public:
    explicit BadBuffer(std::size_t n)
        : size_{n}, data_{new int[n]{}} {}

    ~BadBuffer() { delete[] data_; }
    // 컴파일러 생성 복사는 data_ 주소만 복사한다.
};
```

```cpp
BadBuffer a{10};
BadBuffer b = a; // a.data_ == b.data_
```

두 객체가 같은 배열을 자신이 소유한다고 믿는다. 하나가 파괴되면 다른 하나는 dangling pointer를 가지며, 나머지가 파괴될 때 double free가 된다.

### 9.2 깊은 복사 구현

교육 목적으로 `unique_ptr<T[]>`를 사용해 독립 복사 의미를 구현하면 다음과 같다.

```cpp
#include <algorithm>
#include <cstddef>
#include <memory>
#include <stdexcept>
#include <utility>

class Buffer {
    std::size_t size_{};
    std::unique_ptr<int[]> data_;

public:
    explicit Buffer(std::size_t size)
        : size_{size}, data_{std::make_unique<int[]>(size)} {}

    Buffer(const Buffer& other) : Buffer(other.size_) {
        std::copy_n(other.data_.get(), size_, data_.get());
    }

    Buffer& operator=(const Buffer& other) {
        if (this != &other) {
            Buffer copy{other};
            swap(copy); // copy-and-swap: 성공한 뒤에만 상태 교체
        }
        return *this;
    }

    Buffer(Buffer&&) noexcept = default;
    Buffer& operator=(Buffer&&) noexcept = default;
    ~Buffer() = default;

    void swap(Buffer& other) noexcept {
        std::swap(size_, other.size_);
        data_.swap(other.data_);
    }

    int& at(std::size_t index) {
        if (index >= size_) {
            throw std::out_of_range{"Buffer::at"};
        }
        return data_[index];
    }
};
```

실무에서는 특별한 요구가 없다면 이 구현보다 `std::vector<int>`를 멤버로 둔 Rule of Zero 버전이 단순하고 안전하다.

### 9.3 얕은 복사가 항상 잘못은 아니다

공유가 타입의 의도라면 여러 객체가 같은 상태를 참조하는 복사가 맞을 수 있다. 예를 들어 불변 데이터 공유나 copy-on-write 구현이다. 핵심은 “포인터만 복사했는가”가 아니라 다음이다.

- 복사 후 두 객체의 의미가 독립인가, 공유인가?
- 공유라면 수명은 누가 보장하는가?
- 수정은 공유되는가, 복사되는가?
- 마지막 해제 책임을 어떻게 한 번만 실행하는가?

## 10. 메모리 오류 분류

### 10.1 Memory Leak

더 이상 필요하지 않은 자원에 도달할 방법이나 정리 경로를 잃은 상태다.

```cpp
void leak() {
    auto* p = new int[100];
    p = new int[200]; // 첫 블록 주소를 잃음
    delete[] p;       // 두 번째 블록만 해제
}
```

예방:

- `vector`, `string`, `unique_ptr` 같은 RAII 타입을 사용한다.
- 소유 raw pointer를 만들지 않는다.
- 장기 실행 테스트에서 메모리 사용 추세를 관찰한다.
- AddressSanitizer/LeakSanitizer나 플랫폼 진단 도구를 사용한다.

프로세스 종료 시 OS가 주소 공간을 회수해도 실행 중 누수의 위험과 자원 소멸자의 의미가 사라지는 것은 아니다. `shared_ptr` 순환처럼 포인터가 남아 있어 논리적으로 쓸 수 없는 객체도 누수다.

### 10.2 Dangling Pointer와 Dangling Reference

대상의 수명이 끝났는데 주소나 참조만 남은 상태다.

```cpp
int* wrong() {
    int local = 42;
    return &local; // 함수 반환 후 local의 수명 종료
}
```

발생 원인:

- 지역 객체 주소 반환
- `delete`/`free` 후 포인터 보관
- 컨테이너 재할당 뒤 원소 포인터·참조·반복자 사용
- 임시 `string`에서 만든 `string_view`
- 소유자보다 오래 사는 callback이나 비동기 작업의 참조 캡처

`p = nullptr`는 같은 포인터의 재사용을 막는 데 일부 도움이 되지만 다른 alias까지 null로 만들지 않는다. 핵심 해결책은 수명 구조를 바꾸는 것이다.

### 10.3 Use After Free

해제된 동적 저장 공간을 다시 읽거나 쓰는 dangling 사용이다.

```cpp
int* p = new int{7};
delete p;
// std::cout << *p; // UB: use after free
```

할당자는 그 블록을 이미 다른 객체나 내부 메타데이터로 재사용했을 수 있다. 실행이 “잘 되는 것처럼” 보여도 올바르지 않다. UAF는 제어 데이터나 함수 포인터가 덮일 수 있어 심각한 보안 취약점이 된다.

### 10.4 Double Free

같은 할당을 두 번 반환하는 오류다.

```cpp
int* p = new int{1};
int* alias = p;
delete p;
// delete alias; // UB: 같은 블록을 두 번 해제
```

할당자의 free list나 메타데이터가 손상될 수 있다. 얕은 복사된 소유 raw pointer와 서로 독립적으로 만든 `shared_ptr` control block이 대표 원인이다.

### 10.5 Buffer Overflow

버퍼의 유효 범위를 넘어 쓰는 오류다.

```cpp
std::array<int, 4> values{};
// values[4] = 10; // UB: 유효 인덱스는 0..3
```

스택 버퍼 overflow와 힙 버퍼 overflow는 저장 위치만 다를 뿐 둘 다 범위 밖 쓰기다. 인접 객체, 반환 주소, 할당자 메타데이터를 손상시킬 수 있다.

예방:

- 포인터와 길이를 따로 전달하지 말고 `span`, `array`, `vector`, `string`을 쓴다.
- 외부 입력 길이와 산술 overflow를 먼저 검증한다.
- 디버그 시 `.at()`처럼 범위를 검사하는 인터페이스를 활용한다.
- 문자열의 종료 문자와 바이트/원소 단위를 혼동하지 않는다.

### 10.6 Invalid Free와 할당 방식 불일치

다음은 모두 잘못이다.

```cpp
int* a = new int[10];
// delete a;       // new[]와 delete 불일치

int* b = new int;
// std::free(b);   // new와 free 불일치

int* c = a + 3;
// delete[] c;     // 할당 시작 주소가 아님
```

짝은 `new/delete`, `new[]/delete[]`, `malloc/free`다. 가장 좋은 예방은 이 짝 자체를 사용자 코드에서 없애는 것이다.

### 10.7 Uninitialized Read

기본 초기화된 일부 스칼라나 `malloc`으로 얻은 바이트에는 불확정 값이 있을 수 있다. 그런 값을 읽는 것은 오류이며 상황에 따라 undefined behavior가 된다.

```cpp
int x;              // 자동 지역 int, 값 초기화 안 됨
// int y = x + 1;   // 잘못된 읽기

auto p = std::make_unique<int[]>(10); // int 배열은 값 초기화되어 0
```

선언과 동시에 의미 있는 값으로 초기화하고, 메모리를 초기화했는지가 아니라 객체의 불변식이 성립하는지를 확인한다.

### 10.8 크기 계산 overflow와 범위 착각

버퍼를 할당하기 전 `count * sizeof(T)`가 정수 범위를 넘으면 실제보다 작은 블록을 얻은 뒤 정상 크기라고 믿고 쓸 수 있다.

```cpp
std::size_t bytes_for(std::size_t count, std::size_t element_size) {
    if (element_size != 0 &&
        count > std::numeric_limits<std::size_t>::max() / element_size) {
        throw std::length_error{"allocation size overflow"};
    }
    return count * element_size;
}
```

직접 바이트 수를 계산할 이유가 없다면 `vector<T>(count)`처럼 원소 수를 받는 표준 타입에 맡긴다. 그래도 외부 입력으로 들어오는 `count`의 업무상 최대치는 먼저 제한해야 한다. “주소 공간에 들어갈 수 있다”와 “서비스가 받아들여야 할 합리적인 크기다”는 다른 조건이다.

## 11. Memory Alignment

### 11.1 정렬이 필요한 이유

타입은 주소가 특정 배수에 놓이기를 요구할 수 있다. CPU가 정렬된 접근을 더 효율적으로 처리하거나, 어떤 명령은 잘못 정렬된 접근에서 fault를 발생시킬 수 있다. C++ 객체 모델에서도 요구 정렬을 만족하지 않는 저장 공간에 객체를 잘못 놓고 접근하면 undefined behavior다.

```cpp
#include <cstddef>

struct Example {
    char tag;   // 1 byte
    int value;  // 보통 더 강한 정렬 필요
};

static_assert(alignof(Example) >= alignof(int));
```

컴파일러는 `tag`와 `value` 사이 및 객체 끝에 padding을 넣을 수 있다. 끝 padding은 `Example[]` 배열의 각 원소가 올바르게 정렬되도록 한다. 그래서 멤버 크기의 합과 `sizeof(Example)`이 다를 수 있다.

### 11.2 `alignof`와 `alignas`

```cpp
struct alignas(64) CacheLineData {
    std::atomic<std::uint64_t> value{0};
};

static_assert(alignof(CacheLineData) >= 64);
```

`alignas`는 최소 정렬 요구를 지정한다. 캐시 라인 정렬은 false sharing 완화에 사용할 수 있지만, 실제 하드웨어의 간섭 크기는 `std::hardware_destructive_interference_size` 지원 여부와 측정으로 확인해야 한다. 자세한 병렬성 맥락은 [[02.동시성과 병렬성]]을 참고한다.

### 11.3 동적 할당과 과도 정렬

일반 `new`는 할당 대상 타입에 필요한 정렬을 만족한다. 과도 정렬(over-aligned) 타입은 정렬 인자를 받는 `operator new` 경로가 사용될 수 있다. 직접 바이트 버퍼나 사용자 정의 allocator를 만들 때는 크기뿐 아니라 정렬과 객체 수명 시작 규칙까지 책임져야 한다.

```cpp
struct alignas(64) Packet { std::byte data[64]; };
auto packet = std::make_unique<Packet>(); // Packet의 정렬 요구를 만족
```

직렬화된 바이트에서 `reinterpret_cast<T*>`로 바로 읽는 것은 정렬, 객체 수명, aliasing 문제를 동시에 만들 수 있다. 바이트 표현을 `std::memcpy`로 적절한 `T` 객체에 복사하는 방법을 우선 검토한다.

## 12. Undefined Behavior

Undefined behavior(UB)는 표준이 그 상황의 동작을 규정하지 않는다는 뜻이다. “예외가 발생한다”나 “항상 크래시한다”는 뜻이 아니다. 컴파일러는 올바른 프로그램에는 UB가 없다고 가정하고 최적화할 수 있으므로, 디버그 빌드에서 우연히 보인 결과를 신뢰할 수 없다.

대표적인 메모리 관련 UB:

- 배열이나 객체 범위를 벗어난 접근
- 수명이 끝난 객체를 통한 접근, UAF
- 같은 할당의 double delete/free
- 널 포인터 역참조
- 잘못 정렬된 포인터를 통한 객체 접근
- 초기화되지 않은 값의 부적절한 읽기
- `new[]/delete`, `malloc/delete` 같은 불일치
- 유효하지 않은 downcast 또는 잘못된 타입으로 객체 접근
- signed integer overflow
- 동기화 없는 data race

### 12.1 OS fault와 UB는 같은 개념이 아니다

- UB는 C++ 언어 의미의 문제다.
- page fault/access violation/segmentation fault는 하드웨어·OS가 관찰한 사건이다.

UB가 OS fault로 나타날 수 있지만 반드시 그렇지는 않다. 버퍼를 한 칸 넘겨 썼는데 그 주소가 같은 쓰기 가능 페이지 안이라면 OS는 막지 못한다. 언어적으로는 이미 UB다. 반대로 합법적인 요구 페이징 page fault는 UB가 아니다.

### 12.2 “메모리에 값이 아직 남아 있다”는 변명이 안 되는 이유

객체 수명이 끝나도 비트가 즉시 지워지지 않을 수 있다. 그러나 C++ 추상 기계에서 그 객체는 더 이상 존재하지 않는다. 할당자는 언제든 같은 바이트를 다른 용도로 쓸 수 있고 컴파일러도 수명 규칙을 기반으로 최적화한다. 물리적 잔존과 언어적 유효성은 다르다.

## 13. 스마트 포인터

### 13.1 `std::unique_ptr`: 기본 선택

단독 소유권을 표현한다. 복사는 금지되고 이동으로 소유권을 이전한다.

```cpp
auto first = std::make_unique<Widget>();
auto second = std::move(first);
// first는 이제 소유하지 않음. second가 유일한 소유자
```

장점:

- 비용 모델이 raw pointer와 가깝다.
- 소유자가 명확하다.
- 범위를 벗어날 때 정확히 한 번 삭제한다.
- 사용자 정의 deleter로 파일, 소켓 등에도 사용할 수 있다.

배열에는 `unique_ptr<T[]>`가 있지만 크기·반복·복사 의미가 필요하면 `vector<T>`가 대개 더 좋다.

### 13.2 `std::shared_ptr`: 공동 소유가 실제 요구일 때

`shared_ptr` 복사본들은 control block을 공유한다. control block에는 강한 참조 수, 약한 참조 수, deleter 등의 정보가 있다. 마지막 강한 소유자가 사라지면 객체가 파괴된다.

```cpp
auto a = std::make_shared<Widget>();
auto b = a; // 같은 객체와 control block 공동 소유
```

주의:

- reference count 갱신 비용과 control block 메모리 비용이 있다.
- 참조 수 조작이 스레드 안전하다는 것과 `Widget` 객체의 멤버 접근이 스레드 안전하다는 것은 별개다.
- 수명 종료 시점이 분산되어 결정성이 약해질 수 있다.
- 소유권 문제를 설계하지 않고 `shared_ptr`로 덮으면 순환 참조와 장기 보유가 생긴다.

### 13.3 하나의 객체에 control block을 두 개 만들지 않는다

```cpp
Widget* raw = new Widget;
std::shared_ptr<Widget> a{raw};
// std::shared_ptr<Widget> b{raw}; // 서로 다른 control block: 마지막에 double delete
```

처음부터 `make_shared`를 사용하고 그 `shared_ptr`를 복사한다.

```cpp
auto a = std::make_shared<Widget>();
auto b = a;
```

객체가 자기 자신의 `shared_ptr`를 얻어야 한다면 `std::enable_shared_from_this<T>`와 `shared_from_this()`를 사용한다. `shared_ptr<T>(this)`를 새로 만들면 안 된다. 또한 해당 객체가 이미 `shared_ptr`에 의해 관리되고 있다는 전제도 지켜야 한다.

### 13.4 `make_shared`의 장점과 트레이드오프

`make_shared<T>`는 일반적으로 객체와 control block을 한 번의 할당으로 묶어 지역성과 예외 안전성을 개선한다. 다만 약한 참조가 오래 남으면 객체는 이미 파괴되었더라도 결합된 할당 블록 전체의 반환이 늦어질 수 있다. 매우 큰 객체에서 이것이 중요하면 별도 할당을 검토할 수 있다.

### 13.5 `std::weak_ptr`: 순환을 끊는 관찰자

```cpp
struct Person {
    std::string name;
    std::shared_ptr<Person> partner;
};
```

두 `Person`이 서로를 `shared_ptr`로 가리키면 외부 소유자가 사라져도 참조 수가 0이 되지 않는다. 한쪽 또는 양쪽의 비소유 관계를 `weak_ptr`로 표현한다.

```cpp
struct Person {
    std::string name;
    std::weak_ptr<Person> partner; // 관찰만 함

    void greet_partner() const {
        if (auto p = partner.lock()) { // 성공 시 작업 중 수명을 유지
            std::cout << p->name;
        }
    }
};
```

`expired()` 확인 후 별도로 사용하면 그 사이 수명이 끝날 수 있다. `lock()` 결과의 `shared_ptr`가 비어 있는지 확인하는 방식이 안전하다.

### 13.6 스마트 포인터가 필요 없는 곳

- 지역 값 객체
- `vector`, `string`, `map` 등 컨테이너가 직접 소유하는 원소
- 수명을 늘리지 않는 함수 인자: `T&`, `const T&`, `T*`
- 다른 객체의 멤버로 직접 포함할 수 있는 경우

모든 raw pointer가 나쁜 것은 아니다. **소유 raw pointer**가 특히 위험하다. 비소유 raw pointer도 수명 계약이 분명해야 한다.

## 14. 예외 안전성과 트랜잭션적 갱신

| 보장 | 의미 |
|---|---|
| no-throw guarantee | 연산이 예외를 던지지 않음 |
| strong guarantee | 실패하면 관찰 가능한 상태가 연산 전과 같음 |
| basic guarantee | 실패해도 불변식과 자원 안전은 유지됨 |
| no guarantee | 실패 후 상태나 자원 안전을 보장하지 못함 |

RAII는 자원 누수를 막는 기반이고, strong guarantee는 상태 변경 순서까지 설계해야 한다.

```cpp
void Config::replace(std::vector<Entry> next) {
    validate(next);       // 실패 가능 작업을 먼저
    entries_.swap(next);  // no-throw commit
}
```

앞의 `Buffer` 복사 대입도 임시 복사에 성공한 뒤 `swap`하는 copy-and-swap으로 strong guarantee를 제공한다.

## 15. 성능과 메모리 지역성

안전한 소유권은 성능과 대립하지 않는다. 오히려 값과 컨테이너 중심 설계는 연속 배치와 명확한 수명 때문에 최적화하기 쉽다.

### 15.1 `vector`와 포인터 그래프

`vector<T>`는 원소를 연속 저장해 캐시 지역성과 prefetch에 유리하다. 각 원소를 개별 `new`로 만들고 포인터로 연결하면 할당 비용, 단편화, cache miss가 늘 수 있다.

### 15.2 재할당과 무효화

```cpp
std::vector<int> values;
values.push_back(1);
int* p = &values[0];
values.push_back(2); // capacity가 부족하면 재할당 가능
// p는 재할당이 있었다면 dangling
```

필요 크기를 알면 `reserve`로 재할당 횟수를 줄일 수 있지만, reserve 뒤에도 그 capacity를 넘으면 무효화된다. 포인터를 장기 보관하지 않는 설계가 우선이다.

### 15.3 allocator, pool, arena

많은 작은 객체를 일정한 단계에서 한꺼번에 버린다면 pool/arena가 유용할 수 있다. C++의 `std::pmr`은 메모리 자원 정책을 컨테이너와 분리한다. 하지만 arena가 객체 소멸자의 의미를 없애는 것은 아니다. 비메모리 자원이나 비자명한 소멸이 있다면 올바른 파괴 순서를 보장해야 한다.

### 15.4 working set과 thrashing

프로그램의 활성 페이지 집합이 물리 메모리에 맞지 않으면 page fault와 교체가 반복되어 성능이 급락할 수 있다. 이를 thrashing이라고 한다. 메모리 사용량만 줄이는 것뿐 아니라 접근 패턴과 지역성 개선이 중요하다.

## 16. 도구로 검증하기

컴파일 성공과 한 번의 정상 실행은 메모리 안전의 증거가 아니다.

### 16.1 컴파일러 경고

MSVC 예:

```powershell
cl /std:c++20 /EHsc /W4 /permissive- example.cpp
```

GCC/Clang 예:

```bash
c++ -std=c++20 -Wall -Wextra -Wpedantic -Wconversion example.cpp
```

### 16.2 Sanitizer

GCC/Clang 계열 예:

```bash
c++ -std=c++20 -g -O1 \
  -fsanitize=address,undefined \
  -fno-omit-frame-pointer example.cpp
```

- AddressSanitizer: out-of-bounds, UAF, 일부 double free
- UndefinedBehaviorSanitizer: 여러 UB 범주
- LeakSanitizer: 누수
- MemorySanitizer: 초기화되지 않은 읽기, 지원 환경 제한
- ThreadSanitizer: data race; AddressSanitizer와 보통 별도 실행

MSVC도 지원 버전에서 `/fsanitize=address`를 사용할 수 있다. 도구마다 탐지 범위와 플랫폼 제한이 있으므로 여러 구성과 테스트를 조합한다.

### 16.3 테스트해야 할 경계

- 크기 0, 1, 최대 허용 크기
- 복사 후 원본/복사본 독립 수정
- 자기 대입과 자기 이동을 요구하는지
- 예외가 생성 중간에 발생하는 경우
- 컨테이너 재할당 뒤 핸들 무효화
- 소유자 파괴 전후 callback과 비동기 작업
- 순환 소유 그래프
- 여러 스레드에서 같은 객체를 접근하는 경우

## 17. 실전 설계 예제

### 17.1 요청 메시지를 안전하게 처리하기

```cpp
#include <cstddef>
#include <span>
#include <stdexcept>
#include <vector>

class Message {
    std::vector<std::byte> payload_; // 값 소유, Rule of Zero

public:
    explicit Message(std::span<const std::byte> input)
        : payload_{input.begin(), input.end()} {
        if (payload_.size() > 1'048'576) {
            throw std::length_error{"message too large"};
        }
    }

    std::span<const std::byte> payload() const noexcept {
        return payload_;
    }
};

void inspect(const Message& message) {
    for (std::byte b : message.payload()) {
        (void)b;
    }
}
```

이 설계에서:

- 입력 `span`은 함수 호출 중 빌림이다.
- `Message`는 필요한 바이트를 `vector`로 독립 소유한다.
- 길이가 함께 전달되므로 raw pointer만 전달하는 것보다 범위 계약이 분명하다.
- 소멸, 복사, 이동은 `vector`에 맡겨 Rule of Zero를 지킨다.

### 17.2 polymorphic task의 소유권 이전

```cpp
#include <memory>
#include <utility>
#include <vector>

struct Task {
    virtual ~Task() = default;
    virtual void run() = 0;
};

class Scheduler {
    std::vector<std::unique_ptr<Task>> queue_;
public:
    void submit(std::unique_ptr<Task> task) {
        queue_.push_back(std::move(task));
    }
};
```

`submit`의 서명만 보아도 호출자가 소유권을 넘긴다는 것을 알 수 있다. 공동 소유 요구가 없으므로 `shared_ptr`를 사용하지 않는다.

### 17.3 비동기 작업의 수명

```cpp
class Worker : public std::enable_shared_from_this<Worker> {
public:
    void start(Executor& executor) {
        auto self = shared_from_this();
        executor.post([self] {
            self->do_work();
        });
    }
private:
    void do_work();
};
```

비동기 callback이 실행될 때까지 객체가 반드시 살아 있어야 한다면 작업이 `shared_ptr`를 캡처해 수명을 연장할 수 있다. 반대로 작업 때문에 객체가 무한히 살아 있으면 안 된다면 `weak_ptr`를 캡처하고 실행 시 `lock()`한다. 어느 쪽이 맞는지는 “작업이 객체를 소유하는가?”라는 설계 질문으로 결정한다.

## 18. 자주 나오는 질문

### Q1. 지역 객체는 항상 스택에 있는가?

언어적으로는 automatic storage duration이라고 말하는 것이 정확하다. 최적화에 따라 레지스터에만 있거나 객체 자체가 제거될 수 있다. 관념적 호출 스택과 실제 기계 배치를 구분한다.

### Q2. `new`는 시스템 콜인가?

보통 아니다. `new` 표현식은 저장 공간을 얻는 `operator new`와 객체 생성으로 구성된다. 런타임 할당자는 이미 확보한 블록을 반환할 수 있고, 부족할 때만 OS API를 통해 더 큰 영역을 요청한다.

### Q3. `delete`하면 물리 메모리가 바로 줄어드는가?

보장되지 않는다. 블록이 할당자에 반환되어 같은 프로세스의 다음 할당에 재사용될 수 있다. 큰 매핑이나 할당자 정책에 따라 OS로 일부 반환될 수 있다.

### Q4. 프로세스가 끝나면 OS가 다 회수하는데 누수를 왜 신경 쓰는가?

장기 실행 프로세스는 종료 전 메모리가 고갈될 수 있다. 또한 소멸자는 메모리 외 자원의 의미 있는 정리를 수행한다. 테스트 가능성, 조기 해제, 라이브러리 재사용, 종료 절차의 정확성도 중요하다.

### Q5. `shared_ptr`면 dangling pointer가 사라지는가?

아니다. 그 `shared_ptr`가 공동 소유하는 객체의 수명만 관리한다. 객체 내부의 raw pointer, 뷰, 외부 자원은 여전히 dangling이 될 수 있다. `get()`으로 얻은 포인터를 소유자보다 오래 보관해도 위험하다.

### Q6. `nullptr`로 만들면 UAF가 해결되는가?

한 변수의 실수는 줄일 수 있지만 같은 객체를 가리키는 다른 alias는 그대로다. 소유권을 하나로 만들고 비소유 접근 범위를 짧게 하는 것이 해결책이다.

### Q7. 참조는 포인터보다 무조건 안전한가?

참조는 필수 대상과 재바인딩 불가라는 의도를 더 잘 표현하지만 수명은 늘리지 않는다. dangling reference도 UB를 만든다.

### Q8. OS가 buffer overflow를 막아 주지 않는가?

페이지 권한 경계를 넘으면 막을 수 있지만 같은 유효 페이지 안에서 인접 객체를 덮는 것은 알지 못한다. C++ 범위 규칙, 안전한 타입, sanitizer가 필요하다.

## 19. 리뷰 체크리스트

### 소유권

- [ ] 각 자원에 최종 정리 책임자가 정확히 하나 또는 명시된 공동 소유자로 존재한다.
- [ ] owning raw pointer가 없다.
- [ ] `shared_ptr` 사용 이유가 “여러 곳에서 쓴다”가 아니라 실제 공동 수명 요구다.
- [ ] 순환 참조를 `weak_ptr` 또는 비소유 관계로 끊었다.
- [ ] API 서명에서 소비, 공유, 필수 빌림, 선택적 빌림이 드러난다.

### 객체 수명

- [ ] 반환하는 reference/view가 지역 또는 임시 객체를 가리키지 않는다.
- [ ] callback과 비동기 작업이 캡처한 대상의 수명이 충분하다.
- [ ] `vector`/`string` 재할당 후 포인터, 참조, 반복자를 재사용하지 않는다.
- [ ] 다형적 기반 포인터로 삭제한다면 소멸자가 virtual이다.
- [ ] 생성자 실패 중 이미 획득한 자원은 RAII 멤버가 정리한다.

### 복사와 이동

- [ ] 복사가 독립 값인지 공유 값인지 의미가 명확하다.
- [ ] 자원 관리 클래스는 Rule of Zero를 우선한다.
- [ ] 이동 후 원본에 문서화되지 않은 상태를 가정하지 않는다.
- [ ] 실패하지 않는 이동 연산은 `noexcept`인지 검토한다.
- [ ] 반환 지역 객체에 불필요한 `std::move`를 쓰지 않는다.

### 경계와 UB

- [ ] 포인터와 길이가 분리되어 불일치할 수 있는 API를 피한다.
- [ ] 크기 계산의 정수 overflow를 확인한다.
- [ ] 초기화되지 않은 값을 읽지 않는다.
- [ ] `new/delete`, `new[]/delete[]`, `malloc/free`를 섞지 않는다.
- [ ] 정렬과 실제 객체 수명을 만족하지 않는 타입 punning을 하지 않는다.
- [ ] 공유 메모리 접근에 data race가 없다.

### 검증

- [ ] 높은 경고 수준으로 빌드했다.
- [ ] 경계값과 예외 경로를 테스트했다.
- [ ] 가능한 플랫폼에서 ASan/UBSan/LSan 또는 동등 도구를 실행했다.
- [ ] 장기 실행에서 메모리와 핸들 증가 추세를 측정했다.

## 20. 최종 압축 정리

1. 포인터 값은 가상 주소이며 소유권 정보가 아니다.
2. 스택/힙은 저장 공간 관점이고 객체 수명은 C++ 언어 규칙이다.
3. 저장 공간이 남아 있어도 객체의 수명이 끝났다면 접근할 수 없다.
4. `new`는 객체 생성까지, `delete`는 객체 소멸 후 저장 공간 반환까지 수행한다.
5. 할당자는 OS와 프로그램 사이에서 블록을 캐시하므로 `delete`와 RSS 감소는 일대일이 아니다.
6. RAII는 자원 수명을 객체 수명에 결합해 정상 반환, 조기 반환, 예외에서 같은 정리 규칙을 적용한다.
7. 값과 표준 컨테이너를 우선하고 동적 다형성에는 `unique_ptr`를 기본으로 쓴다.
8. `shared_ptr`는 실제 공동 소유에만 쓰고 순환은 `weak_ptr`로 끊는다.
9. 복사는 의미를 복제하고 이동은 자원을 이전한다. `std::move` 자체는 이동하지 않는다.
10. 얕은 복사가 단독 소유 raw pointer를 복제하면 double free와 UAF가 된다.
11. buffer overflow와 UAF는 OS가 항상 감지하지 못하는 C++ UB다.
12. 정렬, 범위, 객체 수명, aliasing 규칙은 최적화 빌드에서도 지켜야 하는 언어 계약이다.
13. 컴파일 성공은 충분하지 않다. 경고, 테스트, sanitizer, 장기 관찰로 검증한다.

> [!tip] 가장 실용적인 기본 규칙
> **직접 `new`/`delete`를 쓰지 말고 값, 표준 컨테이너, `unique_ptr`, 범위 뷰를 조합하라. raw pointer와 reference는 짧은 비소유 관찰자로 사용하고, 소유권과 수명 계약을 함수 서명에서 읽을 수 있게 만들어라.**
