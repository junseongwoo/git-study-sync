# Mutex와 Condition Variable

> [!summary] 한 문장 정리
> **mutex는 공유 상태를 한 번에 한 스레드만 검사·변경하게 하고, condition variable은 그 mutex로 보호되는 predicate가 참이 될 때까지 스레드를 원자적으로 재우고 다시 깨우는 대기 도구다.**

관련 노트: [[00.메모리·객체 수명·RAII]] · [[01.프로세스와 스레드]] · [[02.동시성과 병렬성]]

## 학습 목표

- data race, race condition, critical section을 구분한다.
- mutex가 보호하는 대상이 코드가 아니라 공유 상태와 불변식임을 이해한다.
- `lock_guard`, `unique_lock`, `scoped_lock`을 목적에 맞게 사용한다.
- condition variable의 wait가 왜 mutex를 원자적으로 풀고 다시 획득하는지 설명한다.
- predicate, lost wakeup, spurious wakeup, Mesa semantics를 연결해서 이해한다.
- `notify_one`과 `notify_all`의 의미와 비용을 구분한다.
- 종료 가능한 bounded queue를 C++로 구현한다.
- deadlock, starvation, lock convoy, priority inversion을 구분하고 예방한다.

## 1. 문제의 출발점: 공유 상태

여러 스레드가 같은 메모리를 사용한다는 사실 자체는 문제가 아니다. 다음 조건이 겹치면 문제가 된다.

1. 둘 이상의 스레드가 같은 메모리 위치에 접근한다.
2. 그중 하나 이상이 쓰기다.
3. 충돌 접근 중 하나 이상이 비원자(non-atomic) 접근이다.
4. 접근 사이에 적절한 동기화가 없다.

C++에서 이런 충돌 접근은 **data race**이며 프로그램 전체가 undefined behavior가 된다.

```cpp
int counter = 0;

void increment() {
    ++counter; // 여러 스레드가 동시에 실행하면 data race
}
```

`++counter`는 소스 코드 한 줄이지만 반드시 하나의 원자적 기계 명령은 아니다. 개념적으로 읽기, 증가, 쓰기로 나뉠 수 있다.

```text
Thread A: read 0 ── add 1 ───────── write 1
Thread B: ───────── read 0 ─ add 1 ─ write 1
결과: 두 번 증가했지만 1
```

### 1.1 Data race와 race condition

| 용어 | 의미 |
|---|---|
| data race | C++ 메모리 모델에서 동기화되지 않은 충돌 접근. UB |
| race condition | 실행 순서에 따라 결과의 정확성이 달라지는 더 넓은 논리 오류 |

mutex를 사용해 모든 메모리 접근의 data race를 없애도 “잔액 확인 후 송금” 같은 여러 단계의 논리가 서로 다른 임계 영역으로 찢어져 있으면 race condition이 남을 수 있다.

### 1.2 Critical section

critical section은 공유 불변식을 읽거나 변경하여 동시에 실행되면 안 되는 구간이다. 중요한 점은 **mutex가 코드 줄을 보호하는 것이 아니라 데이터와 불변식을 보호한다**는 것이다.

```text
mutex M이 보호하는 상태
┌────────────────────────────────────┐
│ queue, size, closed, 통계 카운터     │
│ 불변식: size == queue.size()         │
│ 불변식: closed면 새 push를 받지 않음 │
└────────────────────────────────────┘
```

같은 상태를 어떤 경로에서는 mutex 없이 접근하거나 서로 다른 mutex로 보호하면 계약이 깨진다.

## 2. Mutex의 의미

mutex는 mutual exclusion의 줄임말이다. 한 스레드가 소유한 동안 다른 스레드의 획득을 막는다.

```cpp
#include <mutex>

std::mutex mutex;
int counter = 0;

void increment() {
    std::lock_guard lock{mutex};
    ++counter;
}
```

### 2.1 세 가지 핵심 속성

- **상호 배제**: 임계 영역에는 한 번에 한 스레드만 진입한다.
- **소유권**: mutex를 성공적으로 lock한 스레드가 unlock해야 한다.
- **동기화**: 한 스레드의 unlock은 같은 mutex를 나중에 성공적으로 lock한 스레드와 happens-before 관계를 만든다.

마지막 속성 때문에 mutex는 단순한 “입장권”이 아니다. 임계 영역의 쓰기가 다음 소유자에게 올바르게 보이도록 메모리 가시성과 순서도 제공한다.

### 2.2 `std::mutex` 기본 연산

| 연산 | 의미 |
|---|---|
| `lock()` | 획득할 때까지 대기 |
| `try_lock()` | 즉시 시도하고 실패하면 `false` |
| `unlock()` | 현재 스레드가 가진 소유권 해제 |

직접 `lock()`/`unlock()`을 짝짓는 코드는 예외와 조기 반환에 취약하다.

```cpp
mutex.lock();
update(); // 예외가 발생하면 unlock에 도달하지 못함
mutex.unlock();
```

따라서 RAII lock wrapper를 기본으로 사용한다.

## 3. RAII lock wrapper

### 3.1 `std::lock_guard`

범위 전체에서 하나의 mutex를 소유하면 가장 단순한 선택이다.

```cpp
void update(State& state) {
    std::lock_guard lock{state.mutex};
    state.recalculate();
} // 자동 unlock
```

- 생성할 때 lock한다.
- 소멸할 때 unlock한다.
- 중간에 명시적으로 unlock하거나 다시 lock할 수 없다.
- 단순함이 장점이다.

### 3.2 `std::unique_lock`

소유권을 이동하거나 lock/unlock 시점을 바꿔야 할 때 사용한다.

```cpp
std::unique_lock lock{mutex};
prepare_shared_state();
lock.unlock();
perform_slow_io();
```

`condition_variable::wait`는 잠드는 동안 mutex를 풀고 깨어날 때 다시 획득해야 하므로 `unique_lock<mutex>`를 받는다.

지원하는 대표 기능:

- deferred locking: `std::defer_lock`
- 이미 획득한 mutex 인수: `std::adopt_lock`
- 즉시 시도: `std::try_to_lock`
- `lock()`, `unlock()`, `owns_lock()`
- 이동 가능한 lock 소유권

`adopt_lock`은 현재 스레드가 정말 mutex를 소유할 때만 사용한다. 계약이 틀리면 undefined behavior로 이어질 수 있다.

### 3.3 `std::scoped_lock`

여러 mutex를 함께 획득할 때 교착 회피 알고리즘을 적용한다.

```cpp
void transfer(Account& from, Account& to, int amount) {
    if (&from == &to) {
        return;
    }

    std::scoped_lock lock{from.mutex, to.mutex};
    from.balance -= amount;
    to.balance += amount;
}
```

반대 순서로 두 mutex를 직접 획득하는 것보다 안전하다. 여러 코드 경로가 동일한 mutex 집합을 획득한다면 `scoped_lock` 또는 전역적으로 일관된 lock ordering을 사용한다.

### 3.4 lock wrapper 선택

| 필요 | 선택 |
|---|---|
| 범위 동안 mutex 하나를 단순 소유 | `lock_guard` |
| condition variable 대기 | `unique_lock` |
| 중간 unlock/relock, 이동, 지연 획득 | `unique_lock` |
| mutex 여러 개를 함께 획득 | `scoped_lock` |

## 4. Mutex는 OS에서 어떻게 기다리는가

표준은 구현 방식을 강제하지 않지만 일반적인 mutex는 두 경로를 조합한다.

```text
lock 요청
  ├─ 비경합 fast path: 원자 연산으로 사용자 공간에서 즉시 획득
  └─ 경합 slow path:
       짧게 spin할 수 있음
       → 계속 실패하면 커널 대기 큐에 park/block
       → unlock 시 대기자 중 하나를 깨움
```

운영체제와 런타임은 futex 계열, 주소 기반 대기, 커널 객체 같은 기법을 사용할 수 있다. 정확한 구현은 플랫폼과 라이브러리에 따라 다르다.

### 4.1 Spin과 sleep

| 방식 | 장점 | 단점 |
|---|---|---|
| spin | context switch 없이 곧바로 재시도 | 기다리는 동안 CPU 소비 |
| sleep/block | CPU를 다른 작업에 양보 | 커널 진입·스케줄링·깨우기 비용 |

임계 영역이 매우 짧고 소유자가 다른 코어에서 곧 unlock할 가능성이 높으면 짧은 spin이 이득일 수 있다. 일반 애플리케이션은 `std::mutex` 구현에 맡기고 직접 spinlock을 만들지 않는 것이 좋다.

### 4.2 경합이 비싼 이유

- 캐시 라인 소유권 이동
- 원자적 read-modify-write
- 대기 큐 관리
- context switch와 scheduler 지연
- 깨어난 뒤 다시 mutex를 얻기 위한 경쟁

mutex가 있다는 이유보다 **경합하는 mutex**와 긴 임계 영역이 문제다.

## 5. Mutex만으로 부족한 문제

공유 큐가 비어 있을 때 소비자는 무엇을 해야 할까?

### 5.1 Busy waiting

```cpp
for (;;) {
    std::lock_guard lock{mutex};
    if (!queue.empty()) {
        break;
    }
}
```

조건이 바뀌지 않았는데도 lock, 검사, unlock을 반복해 CPU와 캐시를 낭비한다.

### 5.2 Sleep polling

```cpp
for (;;) {
    {
        std::lock_guard lock{mutex};
        if (!queue.empty()) {
            break;
        }
    }
    std::this_thread::sleep_for(std::chrono::milliseconds{10});
}
```

CPU 낭비는 줄지만 지연과 polling 주기 선택 문제가 남는다. 너무 짧으면 낭비하고 너무 길면 준비된 작업을 늦게 처리한다.

원하는 것은 “상태가 바뀔 때까지 재우고, 바뀌면 다시 검사”하는 기능이다. condition variable이 이 역할을 한다.

## 6. Condition Variable의 정체

condition variable은 조건 그 자체를 저장하지 않는다. **조건을 기다리는 스레드들의 대기 지점**이다.

```cpp
std::mutex mutex;
std::condition_variable changed;
bool ready = false; // 실제 조건을 표현하는 공유 상태
```

여기서 기억해야 할 것은 다음이다.

- 상태: `ready`
- 상태 보호: `mutex`
- 상태 변경 알림: `changed`

notification은 상태가 아니다. 알림을 받은 횟수를 기록하거나 미래 waiter를 위해 보관하지 않는다.

### 6.1 기본 패턴

대기자:

```cpp
std::unique_lock lock{mutex};
changed.wait(lock, [&] { return ready; });
use_ready_state(); // mutex를 다시 소유한 상태
```

변경자:

```cpp
{
    std::lock_guard lock{mutex};
    ready = true;
}
changed.notify_one();
```

### 6.2 `wait`의 핵심 원자 동작

대기자가 predicate가 거짓임을 확인한 뒤 mutex를 풀기 전에 변경자가 상태를 바꾸고 알림을 보내면 알림을 놓칠 수 있다. 이를 막기 위해 wait는 다음 전이를 하나의 대기 프로토콜로 수행한다.

```text
mutex를 소유한 대기자
  → condition 대기 큐 등록과 mutex unlock을 원자적으로 연결
  → 스레드 block
  → notification 또는 spurious wakeup
  → mutex를 다시 lock
  → predicate 재검사
```

`wait`에서 반환했다는 것은 notification을 받았다는 뜻보다 **mutex를 다시 소유한다**는 뜻이 중요하다. predicate가 참인지는 다시 확인해야 한다.

### 6.3 Predicate overload

```cpp
changed.wait(lock, predicate);
```

개념적으로 다음과 같다.

```cpp
while (!predicate()) {
    changed.wait(lock);
}
```

항상 predicate overload를 우선 사용하면 `while` 재검사 규칙을 코드에 내장할 수 있다.

## 7. 왜 `while`인가

### 7.1 Mesa semantics

현대의 일반적인 condition variable은 notification을 받은 스레드가 즉시 실행되고 상태를 독점한다고 보장하지 않는다.

```text
Producer: 상태 변경 → notify Consumer A
Consumer A: ready queue에서 대기
Consumer B: 먼저 mutex 획득 → 상태 소비
Consumer A: 나중에 mutex 획득 → 조건이 다시 거짓일 수 있음
```

notification은 “조건이 참이다”라는 증명서가 아니라 **상태가 변했을 가능성이 있다는 힌트**다. OSTEP은 이를 Mesa semantics로 설명한다.

### 7.2 Spurious wakeup

스레드는 대응하는 notification이 없어도 `wait`에서 깨어날 수 있다. 표준 API가 허용하는 현상이므로 이유를 추측하지 말고 predicate를 재검사한다.

```cpp
// 잘못된 패턴
if (!ready) {
    changed.wait(lock);
}
use_ready_state(); // 깨어난 뒤 ready가 거짓일 수 있음
```

```cpp
// 올바른 패턴
changed.wait(lock, [&] { return ready; });
use_ready_state();
```

### 7.3 여러 waiter 사이의 경쟁

`notify_one`이 어떤 waiter를 고르는지는 일반적으로 보장되지 않는다. 선택된 waiter가 원하는 세부 조건을 만족하지 못하거나, 깨어난 뒤 다른 스레드가 상태를 먼저 소비할 수 있다. predicate는 항상 최종 판단자다.

## 8. Lost Wakeup

condition variable의 가장 중요한 함정은 notification을 상태처럼 사용하는 것이다.

### 8.1 상태 없이 알림만 보내는 오류

```cpp
// notifier
changed.notify_one(); // 현재 waiter가 없으면 효과가 사라짐

// 나중에 시작한 waiter
std::unique_lock lock{mutex};
changed.wait(lock); // 영원히 기다릴 수 있음
```

알림 이전에 waiter가 없으면 notification은 축적되지 않는다. 그래서 “일이 끝났다”, “큐에 항목이 있다”, “종료했다” 같은 사실을 공유 상태에 기록해야 한다.

### 8.2 검사와 sleep 사이의 경쟁

다음과 같이 조건 검사와 대기를 mutex 없이 분리하면 lost wakeup이 생길 수 있다.

```text
Waiter: ready == false 확인
Notifier: ready = true, notify
Waiter: wait 시작
결과: 앞으로 알릴 스레드가 없어 영원히 대기 가능
```

조건 검사, wait의 atomic unlock-and-sleep, 상태 변경을 같은 mutex 프로토콜 안에 넣어야 한다.

### 8.3 Condition variable has no memory

기억을 갖는 것은 predicate 상태다.

```text
잘못된 모델: notify가 토큰을 저장한다
올바른 모델: shared state가 사실을 저장하고 notify는 재검사를 촉진한다
```

토큰 누적 자체가 필요하다면 semaphore, queue, future 같은 다른 추상화가 더 적합할 수 있다.

## 9. `notify_one`과 `notify_all`

### 9.1 `notify_one`

대기자 중 하나를 깨우도록 시도한다.

적합한 경우:

- 항목 하나가 추가되어 소비자 하나만 진행할 수 있음
- 작업 하나를 worker 하나가 처리함
- 같은 predicate를 기다리는 waiter 중 하나면 충분함

선택되는 스레드의 공정성이나 순서는 기대하지 않는다.

### 9.2 `notify_all`

모든 대기자를 깨워 각각 predicate를 재검사하게 한다.

적합한 경우:

- `closed`, `shutdown`, `cancelled`처럼 모든 waiter의 진행 조건이 바뀜
- 여러 waiter가 동시에 진행할 수 있는 상태 변화
- 서로 다른 세부 predicate를 하나의 condition variable에서 기다리는 covering condition

단점은 thundering herd다. 많은 스레드가 깨어나 mutex 하나를 놓고 경쟁한 뒤 대부분 다시 잠들 수 있다.

### 9.3 알림은 lock 안에서 해야 하는가

공유 상태 변경은 반드시 mutex 아래에서 수행한다. notification은 상황에 따라 lock 안이나 밖에서 호출할 수 있다.

```cpp
{
    std::lock_guard lock{mutex};
    queue.push(value);
}
not_empty.notify_one();
```

먼저 unlock한 뒤 notify하면 깨어난 스레드가 즉시 mutex를 얻을 가능성이 커진다. 그러나 정확성은 “notify 위치” 요령이 아니라 다음 계약에 의존한다.

- predicate 상태는 같은 mutex로 보호한다.
- waiter는 mutex를 잡고 predicate를 검사한다.
- waiter는 predicate 기반 wait를 사용한다.

수명 관리나 특수한 프로토콜 때문에 lock 안에서 notify해야 하는 설계도 가능하다. 코드 전체의 불변식을 기준으로 판단한다.

---

## 10. `condition_variable`과 `unique_lock`

`std::condition_variable`의 wait 함수는 `std::unique_lock<std::mutex>&`를 받는다.

```cpp
std::unique_lock lock{mutex};
condition.wait(lock, predicate);
```

`lock_guard`를 받지 않는 이유는 wait가 다음 동작을 해야 하기 때문이다.

1. 현재 mutex 소유 확인
2. 대기 등록과 함께 unlock
3. block
4. 깨어난 후 다시 lock
5. 소유권을 호출자에게 돌려줌

`unique_lock`은 unlock/relock과 소유 상태 추적을 지원한다.

### 10.1 `condition_variable_any`

`condition_variable_any`는 `unique_lock<mutex>` 외의 BasicLockable 형태도 사용할 수 있는 더 일반적인 도구다. 유연한 대신 구현 비용이 더 클 수 있다. 평범한 `std::mutex`라면 `std::condition_variable`을 기본으로 선택한다.

## 11. 종료 가능한 Bounded Queue

생산자-소비자 예제에서 종료를 정확히 표현하려면 알림 횟수나 처리 개수를 추측하지 말고 `closed` 상태를 둔다.

```cpp
#include <condition_variable>
#include <cstddef>
#include <deque>
#include <mutex>
#include <optional>
#include <stdexcept>
#include <type_traits>
#include <utility>

template <class T>
class BoundedQueue {
    static_assert(std::is_nothrow_move_constructible_v<T>,
                  "T must be nothrow move constructible");

public:
    explicit BoundedQueue(std::size_t capacity) : capacity_{capacity} {
        if (capacity == 0) {
            throw std::invalid_argument{"capacity must be positive"};
        }
    }

    BoundedQueue(const BoundedQueue&) = delete;
    BoundedQueue& operator=(const BoundedQueue&) = delete;

    bool push(T value) {
        std::unique_lock lock{mutex_};
        not_full_.wait(lock, [&] {
            return closed_ || queue_.size() < capacity_;
        });

        if (closed_) {
            return false;
        }

        queue_.push_back(std::move(value));
        lock.unlock();
        not_empty_.notify_one();
        return true;
    }

    std::optional<T> pop() {
        std::unique_lock lock{mutex_};
        not_empty_.wait(lock, [&] {
            return closed_ || !queue_.empty();
        });

        if (queue_.empty()) {
            return std::nullopt; // closed이며 남은 항목도 없음
        }

        T value = std::move(queue_.front());
        queue_.pop_front();
        lock.unlock();
        not_full_.notify_one();
        return value;
    }

    void close() {
        {
            std::lock_guard lock{mutex_};
            closed_ = true;
        }
        not_empty_.notify_all();
        not_full_.notify_all();
    }

private:
    const std::size_t capacity_;
    std::mutex mutex_;
    std::condition_variable not_empty_;
    std::condition_variable not_full_;
    std::deque<T> queue_;
    bool closed_ = false;
};
```

### 11.1 보호되는 불변식

mutex가 보호하는 것은 다음 전체 상태다.

- `queue_`
- `closed_`
- `queue_.size() <= capacity_`
- 닫힌 뒤에는 새 항목을 받지 않는다는 규칙

### 11.2 왜 condition variable이 두 개인가

- `not_empty_`: 소비자가 기다리는 조건
- `not_full_`: 생산자가 기다리는 조건

하나의 condition variable로도 구현할 수 있지만, 소비자가 다른 소비자만 깨우거나 생산자가 다른 생산자만 깨우는 불필요한 wakeup이 늘 수 있다. OSTEP의 bounded-buffer 분석처럼 서로 다른 predicate 집합을 분리하면 의도가 명확하다.

### 11.3 왜 `close()`는 둘 다 `notify_all`하는가

종료는 빈 큐를 기다리는 모든 소비자와 가득 찬 큐를 기다리는 모든 생산자의 predicate를 바꾼다. 모두 깨어나 `closed_`를 확인해야 한다.

### 11.4 왜 느린 작업은 lock 밖에서 하는가

`pop()`은 항목을 지역 변수로 이동하고 mutex를 푼 뒤 실제 처리를 맡긴다. I/O나 큰 계산을 임계 영역 안에서 하면 다른 생산자와 소비자가 모두 막힌다.

예제는 항목 이동 중 예외가 나서 queue 앞 원소가 부분적으로 변경되는 상황을 피하도록 `T`의 이동 생성자가 `noexcept`일 것을 요구한다. 범용 라이브러리라면 복사 가능성, allocator, 예외 보장까지 타입 정책으로 설계해야 한다.

## 12. Bounded Queue 사용 예

```cpp
#include <atomic>
#include <cassert>
#include <thread>
#include <vector>

int main() {
    BoundedQueue<int> queue{8};
    std::atomic<long long> sum{0};

    std::thread producer{[&] {
        for (int value = 1; value <= 1'000; ++value) {
            bool accepted = queue.push(value);
            assert(accepted);
        }
        queue.close();
    }};

    std::vector<std::thread> consumers;
    for (int i = 0; i < 4; ++i) {
        consumers.emplace_back([&] {
            while (auto value = queue.pop()) {
                sum.fetch_add(*value, std::memory_order_relaxed);
            }
        });
    }

    producer.join();
    for (auto& consumer : consumers) {
        consumer.join();
    }

    assert(sum.load() == 500'500);
}
```

queue의 내부 정확성은 mutex와 condition variable이 담당한다. 합계는 여러 소비자가 동시에 갱신하는 단일 값이므로 atomic을 사용했다. 복합 불변식과 대기 조건은 mutex가, 단순 누적 연산은 atomic이 담당하는 예다.

## 13. 시간 제한 대기

### 13.1 Predicate가 있는 `wait_for`

```cpp
using namespace std::chrono_literals;

std::unique_lock lock{mutex};
if (!condition.wait_for(lock, 500ms, [&] { return ready; })) {
    // 500ms 안에 ready가 참이 되지 않음
    return Timeout{};
}
```

predicate overload는 spurious wakeup이 있어도 남은 시간을 관리하며 조건을 재검사한다.

### 13.2 직접 반복한다면 absolute deadline

상대 시간 `wait_for(500ms)`를 루프마다 처음부터 다시 적용하면 spurious wakeup마다 전체 대기 시간이 늘어날 수 있다. 복잡한 반복 제어가 필요하면 한 번 계산한 deadline과 `wait_until`을 사용한다.

```cpp
auto deadline = std::chrono::steady_clock::now() + 500ms;
while (!ready) {
    if (condition.wait_until(lock, deadline) == std::cv_status::timeout) {
        if (!ready) {
            return Timeout{};
        }
    }
}
```

경과 시간 제한에는 시스템 시각 조정의 영향을 피하기 위해 `steady_clock`을 우선한다.

## 14. Memory Ordering과 가시성

다음 패턴에서 consumer가 `ready == true`를 보고도 오래된 `data`를 읽는지 걱정할 수 있다.

```cpp
// producer
{
    std::lock_guard lock{mutex};
    data = make_data();
    ready = true;
}
condition.notify_one();

// consumer
std::unique_lock lock{mutex};
condition.wait(lock, [&] { return ready; });
use(data);
```

동일한 mutex의 unlock과 뒤이은 lock이 synchronization을 형성하므로 producer의 임계 영역 쓰기는 consumer에게 보인다. notification 자체가 데이터를 publish하는 것이 아니라 **공유 mutex 프로토콜**이 가시성을 제공한다.

predicate가 atomic 변수여도 condition variable과 함께 사용할 상태라면 일반적으로 같은 mutex 아래에서 변경해 wait와의 프로토콜을 명확하게 만드는 편이 안전하다. C++20의 `atomic::wait/notify`처럼 atomic 전용 대기 모델을 선택한다면 처음부터 그 계약으로 설계한다.

## 15. Deadlock

두 스레드가 서로 가진 자원을 기다리며 영원히 진행하지 못하는 상태다.

```text
Thread A: lock M1 ── wait M2
Thread B: lock M2 ── wait M1
```

### 15.1 Coffman의 네 조건

1. mutual exclusion
2. hold and wait
3. no preemption
4. circular wait

모두 성립하면 deadlock 가능성이 생긴다. 최소 하나를 구조적으로 제거한다.

### 15.2 예방 규칙

- 한 번에 하나의 mutex만 소유하도록 설계를 단순화한다.
- 여러 mutex가 필요하면 `scoped_lock`으로 함께 획득한다.
- 시스템 전체에 일관된 lock ordering을 둔다.
- lock을 가진 채 외부 callback이나 알 수 없는 사용자 코드를 호출하지 않는다.
- lock을 가진 채 장시간 I/O, `join`, 다른 condition 대기를 하지 않는다.
- 임계 영역에서 다시 자신을 호출하는 구조를 피한다.

`recursive_mutex`는 같은 스레드의 재귀 획득을 허용하지만 lock 구조와 불변식을 숨기기 쉽다. 재진입이 정말 타입의 계약인지 검토하고 일반 mutex와 함수 분리를 우선한다.

---

## 16. Deadlock 이외의 진행 문제

| 문제 | 의미 |
|---|---|
| starvation | 특정 스레드가 계속 선택되지 않아 진행하지 못함 |
| livelock | 스레드들이 상태를 계속 바꾸지만 유용한 진행이 없음 |
| lock convoy | lock 소유권 전달과 scheduling 때문에 스레드 무리가 직렬 지연 |
| priority inversion | 낮은 우선순위 스레드가 가진 lock 때문에 높은 우선순위 스레드가 대기 |
| thundering herd | notify_all 뒤 많은 waiter가 깨어나 한 자원을 두고 경쟁 |

`std::mutex`나 condition variable이 강한 fairness를 보장한다고 가정하지 않는다. 실시간 요구가 있다면 운영체제의 priority inheritance와 실시간 동기화 primitive까지 검토해야 한다.

## 17. 흔한 잘못된 패턴

### 17.1 `if`로 wait

```cpp
if (queue.empty()) {
    condition.wait(lock);
}
```

Mesa semantics, 다른 consumer의 선점, spurious wakeup 때문에 틀릴 수 있다. predicate 기반 wait를 쓴다.

### 17.2 공유 상태 없이 notification만 사용

notification은 저장되지 않는다. 완료 여부나 queue 상태를 별도 predicate로 둔다.

### 17.3 predicate를 mutex 밖에서 읽음

```cpp
while (!stopped) { // stopped가 같은 mutex나 atomic으로 보호되지 않으면 data race
    std::unique_lock lock{mutex};
    condition.wait(lock);
}
```

predicate 읽기와 쓰기를 같은 mutex 계약에 넣는다.

### 17.4 서로 다른 mutex로 같은 상태 보호

producer는 M1, consumer는 M2로 같은 queue를 보호하면 상호 배제가 성립하지 않는다. 상태마다 담당 mutex를 문서화한다.

### 17.5 lock을 가진 채 느린 작업

네트워크, 파일 I/O, 큰 계산, logging callback을 임계 영역 밖으로 옮긴다. 필요한 값을 지역 객체로 복사/이동한 뒤 unlock한다.

### 17.6 수동 unlock 누락

RAII wrapper를 사용한다. `unique_lock::unlock()`이 필요해도 객체 소멸 시 남은 소유권은 안전하게 해제된다.

### 17.7 `notify_all`로 논리 버그 숨기기

`notify_one`에서는 멈추고 `notify_all`에서만 동작한다면 waiter 종류와 predicate 설계를 다시 본다. 여러 조건을 하나의 CV에 섞었는지, 상태 변경이 누락됐는지 확인한다.

### 17.8 객체를 파괴하는 동안 waiter가 남아 있음

mutex와 condition variable은 사용하는 모든 스레드보다 오래 살아야 한다. 소유 객체를 파괴하기 전에 종료 상태 설정, `notify_all`, 스레드 join을 완료한다. 자세한 객체 수명 원칙은 [[00.메모리·객체 수명·RAII]]를 참고한다.

## 18. 어떤 동기화 도구를 선택할까

| 요구 | 우선 검토 |
|---|---|
| 복합 공유 상태와 불변식 보호 | `mutex` |
| mutex 상태가 바뀔 때까지 대기 | `condition_variable` |
| 단일 값의 독립 원자 연산 | `atomic<T>` |
| 누적 permit/토큰 | `counting_semaphore` |
| 한 번의 결과 전달 | `promise/future` |
| 여러 스레드의 일회성 합류 | `latch` |
| 반복 단계의 집결 | `barrier` |
| 읽기 다수, 쓰기 독점 | `shared_mutex`를 측정 후 검토 |

condition variable을 이벤트, 메시지 큐, 세마포어처럼 억지로 쓰지 않는다. 실제 원하는 상태 기계를 먼저 정의한다.

## 19. 성능 설계

### 19.1 임계 영역을 짧게

다음은 lock 안에 남겨야 한다.

- predicate 확인
- 공유 컨테이너의 최소 변경
- 불변식 갱신

다음은 보통 밖으로 옮긴다.

- I/O
- formatting과 logging
- 사용자 callback
- 큰 계산
- 반환할 데이터의 후처리

### 19.2 Lock granularity

큰 lock 하나는 설계가 단순하지만 병렬성이 줄 수 있다. 작은 lock 여러 개는 병렬성을 늘릴 수 있지만 deadlock, 메모리 비용, 복잡성이 커진다. 먼저 정확한 coarse-grained lock으로 구현하고 경합을 측정한 뒤 분할한다.

### 19.3 False sharing

서로 다른 mutex나 카운터라도 같은 cache line에 있으면 코어 사이 invalidation이 반복될 수 있다. 이것은 논리적 lock 경합과 다른 cache line 경합이다. 자세한 내용은 [[02.동시성과 병렬성]]을 참고한다.

## 20. 디버깅과 검증

### 20.1 높은 경고와 sanitizer

```bash
c++ -std=c++20 -Wall -Wextra -Wpedantic -g \
  -fsanitize=thread example.cpp
```

ThreadSanitizer는 data race와 일부 lock 오용을 찾는 데 유용하다. AddressSanitizer와 보통 별도 구성으로 실행한다. MSVC 환경에서는 플랫폼이 제공하는 concurrency debugger, Application Verifier, ETW 계열 도구도 검토할 수 있다.

### 20.2 스트레스 테스트

- 스레드 수를 코어 수보다 크게/작게 바꾼다.
- queue capacity를 1로 줄여 경합을 높인다.
- producer/consumer에 무작위 지연을 넣는다.
- 시작 직후 close, 가득 찬 상태에서 close, 빈 상태에서 close를 시험한다.
- notification 직전/직후에 yield하도록 변형한다.
- 수천 번 반복하고 timeout으로 hang을 감지한다.

### 20.3 로그의 한계

로그 추가는 scheduling을 바꿔 버그를 숨길 수 있다. timestamp만 보지 말고 thread id, lock 대상, 상태 전이, queue size를 구조화해서 기록한다. 로그 호출 자체를 공유 mutex 안에서 오래 수행하지 않는다.

## 22. 자주 나오는 질문

### Q1. mutex가 있으면 condition variable은 왜 필요한가?

mutex는 현재 접근할 권리를 조정하지만 “조건이 나중에 참이 될 때까지 CPU를 양보하며 기다리기”를 직접 표현하지 않는다. condition variable은 mutex로 보호된 상태 변화를 효율적으로 기다리게 한다.

### Q2. `notify_one()`을 먼저 호출하고 나중에 wait해도 되는가?

notification 자체는 보관되지 않는다. 하지만 상태를 먼저 변경했다면 나중 waiter가 predicate를 확인하고 기다리지 않으므로 문제없다. 그래서 상태가 기억을 담당한다.

### Q3. 깨운 스레드는 즉시 실행되는가?

아니다. ready 상태가 될 뿐이며 scheduler와 mutex 경쟁을 거쳐 나중에 실행될 수 있다. 그 사이 predicate가 바뀔 수 있어 재검사가 필요하다.

### Q4. notify할 때 mutex를 꼭 잡아야 하는가?

공유 상태 변경은 mutex 아래에서 해야 한다. notify 자체는 올바른 프로토콜에서는 unlock 뒤에 할 수 있다. 단순 규칙보다 상태·수명·predicate의 전체 계약이 중요하다.

### Q5. `volatile`로 ready를 선언하면 되는가?

아니다. C++의 `volatile`은 스레드 간 원자성이나 happens-before를 제공하지 않는다. mutex 또는 적절한 atomic을 사용한다.

### Q6. `recursive_mutex`가 deadlock을 해결하는가?

같은 스레드의 자기 재획득만 허용할 뿐 스레드 사이 lock cycle은 해결하지 않는다. 오히려 불분명한 재진입 구조를 숨길 수 있다.

### Q7. condition variable이 FIFO로 깨우는가?

표준적으로 그런 공정성을 기대할 수 없다. 특정 순서가 정확성 요구라면 별도의 queue와 sequence 상태를 설계한다.

### Q8. atomic이면 mutex보다 항상 빠른가?

아니다. atomic도 cache line 경쟁을 만들며 복합 불변식을 표현하기 어렵다. 올바른 추상화를 선택하고 실제 workload로 측정한다.

## 23. 최종 압축 정리

1. mutex는 공유 상태와 불변식에 대한 상호 배제와 메모리 가시성을 제공한다.
2. C++의 data race는 단순히 결과가 틀리는 문제가 아니라 undefined behavior다.
3. mutex 소유권은 `lock_guard`, `unique_lock`, `scoped_lock`으로 RAII화한다.
4. condition variable은 조건을 저장하지 않으며 waiter를 재검사 시점까지 재운다.
5. 실제 기억은 mutex로 보호되는 predicate 상태가 담당한다.
6. wait는 대기 등록과 mutex unlock을 원자적으로 연결하고, 반환 전에 mutex를 재획득한다.
7. Mesa semantics와 spurious wakeup 때문에 predicate는 항상 반복해서 검사한다.
8. `wait(lock, predicate)`를 기본 패턴으로 사용한다.
9. notification은 축적되지 않으므로 상태 없는 notify는 lost wakeup을 만들 수 있다.
10. 항목 하나에는 보통 `notify_one`, 종료처럼 전체 predicate가 바뀌면 `notify_all`을 쓴다.
11. bounded queue는 `not_empty`, `not_full`, `closed` 상태로 설계하면 종료까지 명확해진다.
12. lock을 가진 채 느린 작업이나 알 수 없는 callback을 실행하지 않는다.
13. 여러 mutex는 `scoped_lock` 또는 일관된 순서로 획득한다.
14. 정확성을 먼저 확보하고 경합, hold time, wakeup 수를 측정해 최적화한다.

> [!tip] 실전 기본형
> **공유 상태를 mutex 아래에서 바꾸고, `condition.wait(lock, predicate)`로 기다리며, 상태 변경 후 필요한 범위만 `notify_one/all`한다. 알림이 아니라 predicate가 진실의 원천이다.**
