## 1. 전체 그림: 기능보다 경계를 먼저 본다

카메라 검사 프로그램을 예로 들면 다음 요소가 섞이기 쉽다.

- 카메라 SDK 호출
- 이미지 버퍼 소유권
- 검사 알고리즘
- 작업 큐와 스레드
- 결과 저장 또는 네트워크 전송
- 오류 기록
- 프로그램 종료

하나의 클래스가 이 모든 일을 하면 실제 장비와 스레드가 없이는 테스트하기 어렵고, 종료 순서와 예외 처리도 얽힌다. 역할을 다음처럼 나누는 편이 명확하다.

```text
Camera SDK adapter ──> FrameSource interface
                              │
                              v
                      InspectionService
                       │      │       │
                       v      v       v
                   Inspector Executor ResultSink
                   업무 규칙   실행 정책  외부 출력
```

OS 관점에서는 thread, file, socket, device handle이 구체적인 실행 자원이다. C++ 설계에서는 이 자원을 RAII adapter 안에 가두고, 업무 규칙은 작은 인터페이스만 보게 한다.

## 2. 객체지향과 인터페이스

### 2.1 객체지향의 목적

객체는 단순히 데이터와 함수를 한 클래스에 넣은 것이 아니다. 좋은 객체는 다음을 함께 가진다.

- 책임: 이 객체가 해야 하는 일
- 상태: 책임을 수행하는 데 필요한 데이터
- 불변식: public 함수 전후에 항상 만족해야 하는 조건
- 소유권: 어떤 자원의 수명을 책임지는가

예를 들어 bounded queue의 불변식은 다음처럼 표현할 수 있다.

```text
0 <= queue.size() <= capacity
closed 이후에는 새로운 작업을 받지 않음
queue가 비고 closed이면 consumer가 종료됨
```

클래스의 public API는 이 불변식을 깨뜨릴 수 있는 내부 상태를 직접 노출하지 않아야 한다.

### 2.2 상속은 is-a, 구성은 has-a

C++ PDF는 상속을 is-a 관계, 멤버 포함을 has-a 관계로 설명한다.

- `Manager is an Employee`: 대체 가능성이 성립하면 public 상속 후보
- `Car has an Engine`: 기능을 소유하거나 사용한다면 구성 후보

코드 재사용만을 위해 상속하면 기반 클래스의 내부 변화와 파생 클래스가 강하게 결합된다. 실행기, 카메라, 저장소 같은 협력 객체는 대개 has-a 구성과 의존성 주입이 적합하다.

### 2.3 인터페이스는 교체 가능한 계약이다

```cpp
#include <cstdint>
#include <vector>

struct Frame {
    std::uint64_t id{};
    std::vector<unsigned char> pixels;
};

struct InspectionResult {
    std::uint64_t frame_id{};
    bool passed{};
};

class IInspector {
public:
    virtual ~IInspector() = default;
    virtual InspectionResult inspect(const Frame& frame) = 0;
};
```

이 인터페이스가 약속하는 것은 “프레임을 받아 결과를 만든다”는 행위다. 카메라 SDK, 파일 시스템, mutex 같은 구현 세부는 포함하지 않는다.

### 2.4 다형성에서 지켜야 할 C++ 규칙

- 기반 클래스 포인터로 파생 객체를 삭제할 수 있다면 destructor를 `virtual`로 만든다.
- 재정의 함수에는 `override`를 붙여 signature 실수를 컴파일 시간에 잡는다.
- 인터페이스에는 필요한 최소 행위만 둔다.
- 객체를 기반 클래스 값으로 복사하면 slicing이 발생하므로 보통 reference나 pointer로 다룬다.
- 소유하지 않는 의존성은 reference 또는 명시적인 observer pointer로 표현한다.
- 소유하는 다형 객체는 보통 `std::unique_ptr<Base>`로 표현한다.

```cpp
class IFrameSource {
public:
    virtual ~IFrameSource() = default;
    virtual Frame next() = 0;
};

class CameraFrameSource final : public IFrameSource {
public:
    Frame next() override;
};
```

`final`은 이 구현을 다시 상속해 동작을 바꾸는 것이 설계 의도가 아님을 나타낸다.

### 2.5 좋은 인터페이스의 조건

| 조건 | 질문 |
|---|---|
| 작음 | 사용하는 쪽에 필요하지 않은 함수까지 강요하는가? |
| 의미 중심 | OS 함수 이름을 그대로 복사했는가, 업무 의미를 표현하는가? |
| 소유권 명확 | 인수와 반환값 중 누가 무엇을 소유하는가? |
| 오류 계약 명확 | 실패를 예외, 값, 상태 코드 중 무엇으로 표현하는가? |
| thread 계약 명확 | 동시에 호출해도 되는가? callback thread는 누구 것인가? |
| 종료 계약 명확 | `stop()`은 요청만 하는가, 완료까지 기다리는가? |

## 3. 예외 처리

### 3.1 예외는 정상 결과와 다른 실패 경로다

C++ PDF는 `throw` 뒤 가장 가까운 호환 `catch`까지 제어가 이동하고, 그 사이 stack 객체의 destructor가 호출되는 stack unwinding을 설명한다.

예외는 다음 상황에 잘 맞는다.

- 현재 함수가 정상 결과를 만들 수 없음
- 호출자가 더 높은 수준에서 복구 정책을 결정해야 함
- 생성자가 유효한 객체를 만들 수 없음

다음은 예외보다 명시적 결과가 더 적합할 수 있다.

- 파일 끝, 검색 결과 없음처럼 예상되는 분기
- 매우 빈번하게 발생하는 정상적인 재시도 상태
- ABI나 언어 경계를 넘는 C callback
- 실시간 경로에서 예외 사용이 프로젝트 정책상 금지된 경우

### 3.2 예외와 오류 코드를 섞지 않는다

한 추상화 계층 안에서는 실패 표현을 일관되게 정한다.

```cpp
Frame read_frame();                       // 실패 시 예외
std::optional<Frame> try_read_frame();    // 없음이 정상 상태
std::expected<Frame, ReadError> read();   // C++23: 오류를 값으로 표현
```

함수 이름과 반환형만 보고도 계약을 이해할 수 있어야 한다.

### 3.3 RAII가 예외 안전성의 기반이다

```cpp
void process() {
    std::vector<std::byte> buffer(4096);
    std::lock_guard lock(mutex);
    update(buffer); // 예외가 나도 lock과 buffer가 정리됨
}
```

수동 `lock()`/`unlock()`, `new`/`delete`, `open`/`close` 쌍은 중간 `throw`나 조기 반환이 생길 때 쉽게 깨진다. 자원 획득 직후 소유 RAII 객체에 넣으면 모든 탈출 경로가 같은 정리를 사용한다.

### 3.4 예외 안전성 보장 수준

| 수준 | 의미 | 구현 전략 |
|---|---|---|
| no-throw | 연산이 예외를 외부로 내보내지 않음 | destructor, `swap`, cleanup |
| strong guarantee | 실패하면 관찰 가능한 상태가 호출 전과 같음 | 임시 객체에 완성한 뒤 commit/swap |
| basic guarantee | 실패해도 불변식과 자원 안전은 유지 | RAII, 부분 상태의 유효성 유지 |
| no guarantee | 실패 뒤 상태를 신뢰할 수 없음 | 피해야 함 |

```cpp
void Config::replace(std::vector<Item> next) {
    validate(next);       // 실패하면 기존 items_는 그대로
    items_.swap(next);    // 검증 완료 뒤 commit
}
```

### 3.5 destructor와 예외

destructor는 원칙적으로 예외를 밖으로 내보내지 않아야 한다. stack unwinding 도중 destructor가 다시 예외를 던지면 프로그램이 종료될 수 있다.

```cpp
class FileLog {
public:
    ~FileLog() noexcept {
        try {
            flush_if_needed();
        } catch (...) {
            // destructor에서는 기록 가능한 최소 수단을 사용하고 삼킨다.
        }
    }
};
```

중요한 저장 실패를 destructor에서 처음 발견하도록 설계하지 말고, 호출자가 결과를 확인할 수 있는 명시적 `flush()`/`close()`를 제공한다.

### 3.6 생성자에서 예외가 발생할 때

생성자가 끝나기 전에 예외가 발생하면 아직 완성되지 않은 객체 자신의 destructor는 호출되지 않는다. 다만 이미 완전히 생성된 base와 member 객체는 역순으로 파괴된다. 따라서 생성자 본문에서 raw 자원을 먼저 획득하고 나중에 RAII 객체에 넣지 말고, 자원 자체를 RAII member로 즉시 구성한다.

```cpp
class Session {
public:
    explicit Session(const Path& path)
        : file_(open_file(path)), buffer_(4096) {
        validate_header(file_); // 실패해도 file_과 buffer_는 정리됨
    }

private:
    UniqueFile file_;
    std::vector<std::byte> buffer_;
};
```

### 3.7 비동기 경계의 예외

스레드 함수 밖으로 예외가 빠져나가면 `std::terminate`로 이어질 수 있다. 비동기 작업은 다음 중 하나로 예외를 전달해야 한다.

- `promise.set_exception()`과 `future.get()`
- 작업 결과의 error field
- worker 최상단의 `catch`에서 오류 sink로 변환

```cpp
auto future = std::async(std::launch::async, [] {
    return risky_work();
});

try {
    auto value = future.get(); // 저장된 예외가 여기서 다시 던져짐
} catch (const std::exception& error) {
    report(error.what());
}
```

## 4. 메모리·리소스 관리

### 4.1 메모리보다 리소스가 더 넓다

RAII가 관리하는 대상은 heap 메모리에 한정되지 않는다.

- 파일과 socket handle
- mutex lock
- thread
- 카메라·stream handle
- SDK frame lease
- memory mapping
- transaction

OS는 프로세스가 끝나면 여러 커널 자원을 회수하지만, 정상 실행 중의 파일 flush, frame 반납, lock 해제, thread 종료 순서까지 대신 설계해 주지는 않는다.

### 4.2 소유권 타입 선택

| 관계 | 기본 표현 | 의미 |
|---|---|---|
| 값 자체 소유 | 값 멤버, `std::vector`, `std::string` | 객체와 함께 생성·소멸 |
| 단독 동적 소유 | `std::unique_ptr<T>` | 복사 금지, 이동으로 소유권 이전 |
| 공동 수명 | `std::shared_ptr<T>` | 마지막 소유자가 파괴 |
| 공동 소유 관찰 | `std::weak_ptr<T>` | 참조 수를 늘리지 않음 |
| 비소유 참조 | `T&`, `T*`, `std::span<T>` | 대상의 수명을 연장하지 않음 |
| OS/SDK handle | 전용 RAII wrapper | 정확한 close/release 함수 호출 |

기본 선택은 값 또는 `unique_ptr`다. `shared_ptr`는 정말 공동 수명이 필요할 때만 사용한다. `shared_ptr`는 thread safety 전체를 보장하지 않고 제어 블록의 수명 관리만 제공한다.

### 4.3 Rule of Zero

멤버가 스스로 자원을 관리하면 사용자 정의 destructor·복사·이동 연산을 작성하지 않아도 된다.

```cpp
class FrameBatch {
public:
    std::vector<Frame> frames;
    std::string source_name;
}; // compiler가 안전한 복사·이동·소멸을 구성
```

raw handle을 직접 소유해야 한다면 작은 RAII wrapper 하나에만 그 책임을 모으고, 상위 클래스는 그 wrapper를 값으로 보유한다.

### 4.4 인터페이스와 소유권을 함께 설계한다

```cpp
class InspectionService {
public:
    InspectionService(IInspector& inspector, IResultSink& sink);

private:
    IInspector& inspector_; // 소유하지 않음: service보다 오래 살아야 함
    IResultSink& sink_;     // 소유하지 않음
};
```

reference 주입은 null이 아니며 소유하지 않는다는 뜻이 분명하지만, 외부 객체가 service보다 오래 살아야 한다. service가 의존성을 소유해야 한다면 `std::unique_ptr<IInspector>`로 받아 이동한다.

```cpp
class InspectionService {
public:
    explicit InspectionService(std::unique_ptr<IInspector> inspector)
        : inspector_(std::move(inspector)) {}

private:
    std::unique_ptr<IInspector> inspector_;
};
```

## 5. 비동기 처리

### 5.1 비동기는 실행 정책이다

비동기는 호출한 작업의 완료를 지금 기다리지 않고 나중에 관찰하는 구조다. 반드시 병렬 실행을 의미하지는 않는다.

| 개념 | 핵심 질문 |
|---|---|
| 동기 | 호출이 반환될 때 작업이 끝났는가? |
| 비동기 | 완료를 나중에 callback/event/future로 받는가? |
| 동시성 | 여러 작업의 진행 기간이 겹치는가? |
| 병렬성 | 여러 작업이 같은 순간에 실제 실행되는가? |

`std::async`도 launch policy에 따라 새 실행 주체에서 실행되거나 `future.get()` 시점까지 deferred될 수 있다. 실행 시점을 중요하게 다룬다면 policy를 명시한다.

### 5.2 비동기 API가 추가하는 상태

동기 함수는 호출 stack이 진행 상태를 보관한다. 이벤트·callback 방식에서는 프로그램이 상태를 별도로 보관해야 한다.

- 요청 식별자
- input buffer와 output buffer
- 현재 단계
- 완료·오류·취소 상태
- callback 대상의 수명
- timeout 또는 deadline

OSTEP의 AIO 예처럼 요청 구조체가 buffer 주소와 길이를 가리킨다면 완료 또는 취소 완료까지 그 메모리가 유효해야 한다.

### 5.3 callback capture 수명

```cpp
class Session {
public:
    void start() {
        executor_.post([this] { use_members(); });
    }
};
```

작업 실행 전에 `Session`이 파괴되면 `this`는 dangling pointer가 된다. 해결 방법은 계약에 따라 다르다.

- 소유 객체의 destructor가 executor를 stop/join하여 작업보다 오래 살아 있게 함
- 값으로 필요한 데이터만 capture
- 공동 비동기 수명이 필요하면 `shared_ptr`/`weak_ptr`를 신중히 사용
- callback 등록 해제와 in-flight callback 종료 대기 제공

```cpp
std::weak_ptr<Session> weak = shared_from_this();
executor.post([weak] {
    if (auto self = weak.lock()) {
        self->use_members();
    }
});
```

이 코드는 use-after-free는 피하지만 작업이 조용히 취소되는 의미가 적합한지도 별도로 판단해야 한다.

### 5.4 취소는 하나의 프로토콜이다

`cancel()` 호출과 작업이 실제로 멈춘 시점은 다를 수 있다.

```text
CancelRequested
  -> 작업이 요청을 관찰
  -> OS/SDK 작업 취소 또는 정상 종료
  -> Completion/Cancelled 통지
  -> buffer와 요청 객체 해제 가능
```

취소는 성공·실패와 함께 비동기 연산의 정상적인 종결 상태로 모델링한다.

## 6. 멀티스레딩

### 6.1 OS 관점의 핵심

같은 프로세스의 스레드는 주소 공간과 heap을 공유하지만 register, program counter, stack은 따로 가진다. 공유 메모리는 통신을 쉽게 하지만 동시에 race condition의 원인이 된다.

```text
Process address space
├─ code                  shared
├─ globals/static        shared
├─ heap                  shared
├─ Thread A stack        private
└─ Thread B stack        private
```

동일한 메모리에 둘 이상의 스레드가 접근하고, 그중 하나 이상이 쓰며, 동기화가 없다면 data race가 될 수 있다. C++의 data race는 undefined behavior다.

### 6.2 mutex는 데이터가 아니라 불변식을 보호한다

```cpp
class Counter {
public:
    void increment() {
        std::lock_guard lock(mutex_);
        ++value_;
    }

    int value() const {
        std::lock_guard lock(mutex_);
        return value_;
    }

private:
    mutable std::mutex mutex_;
    int value_ = 0;
};
```

“`value_`에 mutex를 붙였다”보다 “Counter의 모든 public 연산이 `value_`의 일관성을 유지한다”고 이해하는 것이 좋다. 여러 필드가 하나의 불변식을 구성한다면 같은 lock 아래에서 함께 갱신한다.

### 6.3 condition variable은 predicate와 한 쌍이다

```cpp
std::unique_lock lock(mutex_);
condition_.wait(lock, [this] {
    return closed_ || !queue_.empty();
});
```

- 상태는 mutex 아래에서 검사·변경한다.
- wakeup 자체가 조건의 참을 보장하지 않으므로 predicate를 다시 검사한다.
- 종료 상태도 predicate에 포함한다.
- queue에서 꺼낸 작업은 가능하면 lock을 해제한 뒤 실행한다.

### 6.4 thread도 소유 자원이다

thread를 시작한 객체는 다음을 책임져야 한다.

- 새 작업 접수를 언제 막는가?
- 대기 중인 worker를 어떻게 깨우는가?
- queue를 drain할지 discard할지?
- 누가 `join()`하는가?
- worker가 사용하는 의존성은 언제 파괴되는가?

```text
accepting = false
  -> wait 중인 worker notify
  -> queue drain/discard
  -> worker loop 종료
  -> join
  -> worker가 참조하던 의존성 파괴
```

### 6.5 lock의 범위를 외부 코드까지 넓히지 않는다

interface의 가상 함수나 사용자 callback을 mutex를 잡은 채 호출하면 다음 위험이 있다.

- 상대 코드가 다시 나를 호출해 deadlock
- 느린 I/O로 critical section 장기 점유
- 예상하지 못한 예외가 lock 범위와 상태 전이를 복잡하게 함

공유 상태에서 필요한 값을 복사·이동해 꺼내고 lock을 해제한 뒤 외부 코드를 호출한다.

## 7. 의존성 분리

### 7.1 의존성 역전의 실제 의미

상위 업무 정책이 하위 SDK의 구체 타입과 함수 이름을 직접 알지 않게 만든다.

```text
나쁜 방향
InspectionService -> VendorCamera -> VendorBuffer -> VendorThread

분리한 방향
InspectionService -> IFrameSource / IExecutor / IResultSink
                          ^              ^             ^
                          |              |             |
                   CameraAdapter   ThreadExecutor   FileResultSink
```

상위 정책과 adapter 모두 상위에서 정의한 작은 계약에 의존한다.

### 7.2 무엇을 분리해야 하는가?

- 외부 장치·SDK
- 파일·socket·database
- system clock와 timeout
- random 값
- thread/executor
- 환경 변수와 설정 파일
- logger와 결과 출력

순수 계산까지 모두 virtual interface로 만들 필요는 없다. 바뀌는 속도와 테스트 경계를 기준으로 분리한다.

### 7.3 런타임 다형성과 compile-time 주입

| 방식 | 예 | 장점 | 비용/제약 |
|---|---|---|---|
| virtual interface | `IInspector&` | ABI 경계, 런타임 교체, 이해하기 쉬운 fake | 간접 호출, 수명 계약 필요 |
| template | `template<class Executor>` | inlining, 정적 검증, zero-overhead 가능 | 구현 노출, compile time 증가 |
| callable | `std::function`, lambda | 작은 전략 주입에 간단 | type erasure 비용, 소유 capture 주의 |

장치 adapter처럼 구현을 런타임에 바꿀 필요가 있으면 virtual interface가 자연스럽다. 작은 clock 함수나 정책은 template/lambda가 더 간단할 수 있다.

### 7.4 생성자가 유효한 상태를 완성한다

필수 의존성은 setter로 나중에 넣기보다 생성자에서 받는다.

```cpp
InspectionService(
    IInspector& inspector,
    IExecutor& executor,
    IResultSink& sink)
    : inspector_(inspector), executor_(executor), sink_(sink) {}
```

이렇게 하면 null 여부, 초기화 순서, 테스트 대체 구현이 명확해진다.

## 8. 단위 테스트

### 8.1 단위 테스트의 목적

단위 테스트는 함수 호출 횟수를 많이 확인하는 것이 목적이 아니다. 외부 환경과 독립적으로 중요한 규칙과 상태 전이를 빠르고 반복 가능하게 확인하는 것이 목적이다.

좋은 테스트는 다음 성질을 가진다.

- 결정적: scheduler 운에 따라 성공·실패하지 않음
- 격리됨: 실제 카메라, 네트워크, wall clock이 없어도 실행
- 빠름: sleep과 큰 timeout에 의존하지 않음
- 행위 중심: 구현 세부보다 결과와 불변식을 검증
- 실패 원인이 분명함

### 8.2 fake, stub, mock의 역할

| 대역 | 목적 | 예 |
|---|---|---|
| stub | 준비된 값을 반환 | 항상 같은 frame을 주는 source |
| fake | 단순하지만 실제로 동작하는 구현 | memory sink, inline executor |
| spy | 호출 내용을 기록 | publish된 result 목록 |
| mock | 기대한 상호작용을 검증 | 특정 순서의 release 호출 |

프레임 결과 자체가 중요하다면 spy에 저장된 결과를 검증한다. 구현 내부 함수의 정확한 호출 순서를 과도하게 고정하면 refactoring이 어려워진다.

### 8.3 thread를 제거해 업무 규칙을 테스트한다

실서비스에서는 thread pool을 쓰더라도 테스트에서는 즉시 실행하는 executor를 주입할 수 있다.

```cpp
class InlineExecutor final : public IExecutor {
public:
    void post(std::function<void()> task) override {
        task();
    }
    void stop() noexcept override {}
};
```

이렇게 하면 검사 제출과 결과 수집이 한 thread에서 끝나므로 sleep이나 polling 없이 assert할 수 있다. 이것이 의존성 분리가 테스트 가능성을 만드는 대표적인 예다.

### 8.4 멀티스레드 구현 자체는 별도로 테스트한다

업무 규칙 테스트에서 thread를 제거했다고 thread 안전성 검증이 끝나는 것은 아니다. executor, queue, shutdown 구현에는 별도의 component test가 필요하다.

- 동시에 여러 producer가 제출해도 작업이 유실·중복되지 않는가?
- `stop()`과 `post()`가 경쟁할 때 계약대로 동작하는가?
- queue가 빈 상태에서 stop하면 worker가 깨어나는가?
- 작업이 예외를 던져도 worker가 정한 정책대로 계속 동작하는가?
- 모든 작업이 끝난 뒤 thread가 join되는가?
- ThreadSanitizer 같은 도구에서 data race가 보고되지 않는가?

### 8.5 시간 기반 테스트에서 sleep을 피한다

```cpp
class IClock {
public:
    virtual ~IClock() = default;
    virtual TimePoint now() const = 0;
};
```

fake clock을 주입해 시간을 직접 전진시키면 “100 ms를 실제로 기다린 뒤 확인”하는 느리고 불안정한 테스트를 피할 수 있다.

## 9. 통합 C++20 예제

다음 예제는 업무 규칙, 실행 정책, 결과 출력을 분리한다. 실제 환경은 `ThreadExecutor`, 단위 테스트는 `InlineExecutor`를 사용한다.

```cpp
#include <cassert>
#include <condition_variable>
#include <cstdint>
#include <deque>
#include <functional>
#include <mutex>
#include <stdexcept>
#include <string>
#include <thread>
#include <utility>
#include <vector>

struct Frame {
    std::uint64_t id{};
    std::vector<unsigned char> pixels;
};

struct InspectionResult {
    std::uint64_t frame_id{};
    bool passed{};
    std::string error;
};

class IInspector {
public:
    virtual ~IInspector() = default;
    virtual InspectionResult inspect(const Frame& frame) = 0;
};

class IResultSink {
public:
    virtual ~IResultSink() = default;
    virtual void publish(InspectionResult result) = 0;
};

class IExecutor {
public:
    virtual ~IExecutor() = default;
    virtual void post(std::function<void()> task) = 0;
    virtual void stop() noexcept = 0;
};

class InspectionService {
public:
    InspectionService(
        IInspector& inspector,
        IExecutor& executor,
        IResultSink& sink)
        : inspector_(inspector), executor_(executor), sink_(sink) {}

    ~InspectionService() {
        stop();
    }

    InspectionService(const InspectionService&) = delete;
    InspectionService& operator=(const InspectionService&) = delete;

    void submit(Frame frame) {
        {
            std::lock_guard lock(state_mutex_);
            if (!accepting_) {
                throw std::runtime_error("service is stopped");
            }
        }

        executor_.post([this, frame = std::move(frame)]() mutable {
            InspectionResult result;
            try {
                result = inspector_.inspect(frame);
            } catch (const std::exception& error) {
                result = InspectionResult{frame.id, false, error.what()};
            } catch (...) {
                result = InspectionResult{frame.id, false, "unknown error"};
            }
            sink_.publish(std::move(result));
        });
    }

    void stop() noexcept {
        {
            std::lock_guard lock(state_mutex_);
            if (!accepting_) {
                return;
            }
            accepting_ = false;
        }
        executor_.stop(); // 이 계약에서는 queue drain과 join까지 완료한다.
    }

private:
    IInspector& inspector_;
    IExecutor& executor_;
    IResultSink& sink_;
    std::mutex state_mutex_;
    bool accepting_ = true;
};

class ThreadExecutor final : public IExecutor {
public:
    ThreadExecutor() : worker_([this] { run(); }) {}

    ~ThreadExecutor() override {
        stop();
    }

    void post(std::function<void()> task) override {
        {
            std::lock_guard lock(mutex_);
            if (!accepting_) {
                throw std::runtime_error("executor is stopped");
            }
            tasks_.push_back(std::move(task));
        }
        ready_.notify_one();
    }

    void stop() noexcept override {
        {
            std::lock_guard lock(mutex_);
            accepting_ = false;
        }
        ready_.notify_all();
        if (worker_.joinable()) {
            worker_.join();
        }
    }

private:
    void run() noexcept {
        for (;;) {
            std::function<void()> task;
            {
                std::unique_lock lock(mutex_);
                ready_.wait(lock, [this] {
                    return !accepting_ || !tasks_.empty();
                });

                if (tasks_.empty()) {
                    return;
                }

                task = std::move(tasks_.front());
                tasks_.pop_front();
            }

            try {
                task();
            } catch (...) {
                // worker 경계 정책: task 예외가 thread 밖으로 나가지 않게 한다.
            }
        }
    }

    std::mutex mutex_;
    std::condition_variable ready_;
    std::deque<std::function<void()>> tasks_;
    bool accepting_ = true;
    std::thread worker_;
};

class InlineExecutor final : public IExecutor {
public:
    void post(std::function<void()> task) override {
        if (stopped_) {
            throw std::runtime_error("executor is stopped");
        }
        task();
    }

    void stop() noexcept override {
        stopped_ = true;
    }

private:
    bool stopped_ = false;
};

class ThresholdInspector final : public IInspector {
public:
    explicit ThresholdInspector(unsigned char minimum) : minimum_(minimum) {}

    InspectionResult inspect(const Frame& frame) override {
        if (frame.pixels.empty()) {
            throw std::invalid_argument("empty frame");
        }

        const bool passed = frame.pixels.front() >= minimum_;
        return InspectionResult{frame.id, passed, {}};
    }

private:
    unsigned char minimum_{};
};

class CollectingSink final : public IResultSink {
public:
    void publish(InspectionResult result) override {
        std::lock_guard lock(mutex_);
        results_.push_back(std::move(result));
    }

    std::vector<InspectionResult> snapshot() const {
        std::lock_guard lock(mutex_);
        return results_;
    }

private:
    mutable std::mutex mutex_;
    std::vector<InspectionResult> results_;
};

void unit_test_success_without_thread() {
    ThresholdInspector inspector{100};
    InlineExecutor executor;
    CollectingSink sink;
    InspectionService service{inspector, executor, sink};

    service.submit(Frame{7, {120}});

    const auto results = sink.snapshot();
    assert(results.size() == 1);
    assert(results[0].frame_id == 7);
    assert(results[0].passed);
    assert(results[0].error.empty());
}

void unit_test_exception_becomes_result() {
    ThresholdInspector inspector{100};
    InlineExecutor executor;
    CollectingSink sink;
    InspectionService service{inspector, executor, sink};

    service.submit(Frame{8, {}});

    const auto results = sink.snapshot();
    assert(results.size() == 1);
    assert(results[0].frame_id == 8);
    assert(!results[0].passed);
    assert(results[0].error == "empty frame");
}

void component_test_real_worker() {
    ThresholdInspector inspector{100};
    ThreadExecutor executor;
    CollectingSink sink;
    InspectionService service{inspector, executor, sink};

    service.submit(Frame{9, {130}});
    service.stop(); // queue drain과 join 뒤 반환

    const auto results = sink.snapshot();
    assert(results.size() == 1);
    assert(results[0].passed);
}

int main() {
    unit_test_success_without_thread();
    unit_test_exception_becomes_result();
    component_test_real_worker();
}
```

### 9.1 예제의 소유권과 수명

- `Frame`은 pixel buffer를 값으로 소유하며 task lambda로 이동된다.
- service는 세 의존성을 소유하지 않으므로 의존성이 service보다 오래 살아야 한다.
- 예제의 지역 변수 선언 순서상 service가 먼저 파괴되고 sink, executor, inspector가 나중에 파괴된다.
- service의 `stop()`은 executor의 queue drain과 worker join까지 완료한다.
- worker가 join된 뒤에만 service와 의존성을 파괴하므로 lambda의 `this`가 dangling되지 않는다.
- `CollectingSink`는 실제 worker test에서도 안전하도록 자체 mutex를 가진다.

### 9.2 예제에서 예외를 두 번 막는 이유

`InspectionService`는 검사 알고리즘 예외를 업무 결과로 바꾼다. `ThreadExecutor`의 최상위 `catch`는 그 밖의 예외가 thread 함수 밖으로 탈출하지 못하게 하는 마지막 방어선이다.

실제 시스템에서는 마지막 방어선에서 오류를 무시하기보다 다음을 기록해야 한다.

- task 식별자
- exception message
- 실패 시간과 thread 정보
- queue를 계속 처리할지 중지할지 정책

## 10. 설계 선택과 trade-off

### 10.1 interface가 많을수록 좋은가?

아니다. 다음 경우에 경계를 만든다.

- 외부 시스템에 접근한다.
- 테스트에서 대체해야 한다.
- 구현이 둘 이상 존재한다.
- 실행 정책과 업무 정책을 독립적으로 바꾸고 싶다.
- 수명·threading·오류 계약을 한곳에 캡슐화해야 한다.

단순한 값 객체나 내부 계산 함수까지 모두 interface로 만들면 탐색 비용과 간접 계층만 늘어난다.

### 10.2 예외와 `expected` 중 무엇을 쓰는가?

- 실패가 드물고 여러 호출 계층을 건너 정책 지점까지 전달되어야 하면 예외가 편리하다.
- 실패가 정상적인 분기이고 호출자가 즉시 처리해야 하면 `expected`/오류 값이 명시적이다.
- C callback·SDK 경계를 넘기 전에는 예외를 catch해 상태 코드로 변환한다.
- 어느 방식을 택하든 RAII로 자원 안전을 유지한다.

### 10.3 virtual interface의 성능이 걱정될 때

먼저 실제 측정으로 병목인지 확인한다. 이미지 처리처럼 큰 연산을 한 번 호출하는 경계에서는 가상 호출 한 번보다 buffer 복사·cache miss·알고리즘 비용이 훨씬 클 수 있다. 작은 함수가 매우 빈번한 hot loop라면 template 정책이나 값 타입을 검토한다.

## 11. 흔한 실패 패턴

### 11.1 God object

한 클래스가 SDK 연결, frame 수신, 검사, 파일 저장, thread 종료를 모두 담당한다. 작은 변경이 전체 상태 머신에 영향을 주고 실제 장비 없이는 테스트하기 어렵다.

### 11.2 interface가 raw pointer 소유권을 숨김

```cpp
virtual Frame* next() = 0; // 누가 delete하는가? SDK buffer인가?
```

값 반환, `unique_ptr`, non-owning view와 명시적 lease 중 하나로 계약을 분명히 한다.

### 11.3 constructor에서 thread를 시작한 뒤 파생 virtual 함수 호출

완전히 생성되지 않은 객체를 다른 thread가 관찰할 수 있다. construction과 `start()`를 분리하거나, 모든 불변식이 완성된 factory에서 시작한다.

### 11.4 destructor에서 join 없는 `std::thread`

joinable thread의 destructor는 프로그램 종료를 일으킬 수 있다. thread 소유 객체는 stop/join 정책을 가져야 한다.

### 11.5 sleep으로 동시성 테스트

```cpp
service.submit(frame);
std::this_thread::sleep_for(100ms);
assert(done);
```

느린 CI나 scheduler 상황에 따라 실패한다. inline executor, latch, future, condition variable처럼 완료를 의미하는 동기화 수단을 사용한다.

### 11.6 mutex를 잡고 callback 호출

callback 구현을 알 수 없으므로 재진입 deadlock과 장시간 lock 점유가 생긴다. 내부 상태를 확정한 뒤 lock을 풀고 callback을 호출한다.

### 11.7 `shared_ptr`로 모든 수명 문제를 덮음

소유자가 불명확해지고 순환 참조와 예측하기 어려운 파괴 thread가 생긴다. 기본은 단일 소유이며 observer에는 reference나 `weak_ptr`를 사용한다.

## 13. 핵심 결론

1. 객체지향의 핵심은 클래스 수가 아니라 책임·불변식·소유권의 경계다.
2. interface는 구현 교체보다 먼저 계약과 의존 방향을 명확하게 만든다.
3. 예외 안전성은 `catch`의 개수가 아니라 stack unwinding 중에도 자원이 정리되는 RAII에서 시작한다.
4. 메모리뿐 아니라 thread, file, socket, SDK frame도 소유 자원이다.
5. 비동기 코드는 요청 상태, callback 수명, 취소 완료, 오류 전달을 명시해야 한다.
6. 멀티스레드의 핵심은 thread 생성이 아니라 공유 상태와 종료 protocol이다.
7. executor와 외부 adapter를 분리하면 업무 규칙을 thread·장비 없이 테스트할 수 있다.
8. 단위 테스트와 실제 thread component test는 목적이 다르므로 분리한다.
